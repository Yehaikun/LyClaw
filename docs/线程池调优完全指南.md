# 第一部分：理论基础与公式

## 一、线程池调优的核心地位

### 1.1 为什么线程池大小如此重要

线程池大小的配置是Java并发编程中**最重要、也最常被忽视**的性能决策之一。美团技术团队曾明确指出，因其线程池参数配置不合理，触发了多起生产事故，这直接推动了其线程池动态化方案的诞生。

**配置过小的后果：**
- CPU资源闲置，吞吐量上不去
- 任务排队时间过长，响应延迟飙升

**配置过大的后果：**
- 上下文切换开销激增，CPU被调度消耗而非业务计算
- 内存占用膨胀（每个平台线程约占用1MB栈空间）
- 资源争抢加剧（锁竞争、缓存失效）
- 下游服务被带宽打满，引发级联故障

**核心挑战**：线程池最优大小并非固定常数，它依赖于CPU核心数、任务类型（CPU密集 vs IO密集）、IO等待时长、目标CPU利用率、任务到达率等多个动态变化的变量。

### 1.2 线程池在程序设计中的定位

```
                        请求流量
                           │
                           ▼
              ┌────────────────────────┐
              │    线程池（流量控制阀）   │  ← 系统第一道防线
              └────────┬───────────────┘
                       │
           ┌───────────┼───────────┐
           ▼           ▼           ▼
      ┌────────┐ ┌────────┐ ┌────────┐
      │ 数据库  │ │ 缓存   │ │ 下游   │  ← 受保护资源
      │ 连接池  │ │        │ │ 服务   │
      └────────┘ └────────┘ └────────┘
```

线程池本质上是一个**流量整形器**（Traffic Shaper），它在请求入口与后端资源之间充当缓冲与限流角色。配置不当的线程池不仅无法保护后端，自身还会成为故障源。

## 二、经典CPU密集型公式 N+1

### 2.1 公式描述

对于CPU密集型任务（几乎不存在IO等待），最广泛接受的公式是：

```
线程数 = CPU核心数 + 1
```

即 `N_cpu + 1`。

### 2.2 推导原理

CPU密集型任务中，线程几乎始终处于 `RUNNABLE` 状态：
- 线程数 = CPU核心数 → CPU利用率理论上可达100%
- 线程数 < CPU核心数 → 部分核心闲置
- 线程数 > CPU核心数 → 上下文切换开销

多出1个线程的意义：即使某个线程因偶尔的缺页中断（page fault）暂停，也能有线程立刻填补CPU空闲。

### 2.3 局限性

`N+1` 公式仅在纯CPU密集型任务中适用。现代服务端应用中，绝大多数任务都涉及数据库查询、RPC调用、文件读写等IO操作，此时 `N+1` 会严重低估所需线程数。

## 三、Brian Goetz IO密集型公式

### 3.1 公式来源

Brian Goetz 在经典著作 **《Java Concurrency in Practice》** 第8.2节中提出了线程池大小计算公式：

```
线程数 = N_cpu × (1 + W/C)
```

其中：
- **N_cpu**：CPU核心数
- **W (Wait Time)**：线程等待时间（IO等待、网络等待、锁等待等）
- **C (Compute Time)**：线程实际占用CPU进行计算的时间

### 3.2 推导逻辑

一个典型IO密集型任务的执行周期：

```
|---- 计算 C ----|-------- 等待IO W --------|---- 计算 C ----|-- 等待IO W --|
```

在等待IO的 `W` 时间段内，线程不占用CPU。通过让更多线程交替使用CPU——当线程A在等待IO时，线程B占用CPU计算——理论上 `1 + W/C` 个线程可以让一个CPU核心始终保持忙碌。扩展到N个核心：`N × (1 + W/C)`。

### 3.3 场景化简化表

| 场景 | W/C 比值 | 简化公式 | 典型推荐值 |
|------|----------|----------|-----------|
| 纯CPU密集 | W/C ≈ 0 | `N_cpu × 1` | `N_cpu` 或 `N_cpu + 1` |
| 轻度IO | W/C ≈ 1 | `N_cpu × 2` | `2 × N_cpu` |
| 中度IO | W/C ≈ 4 | `N_cpu × 5` | `4~8 × N_cpu` |
| 重度IO | W/C ≥ 9 | `N_cpu × 10+` | `8~16 × N_cpu` |

### 3.4 阻塞系数等价变形

```
线程数 = N_cpu / (1 - 阻塞系数)

其中 阻塞系数 = W / (W + C)
```

例如4核服务器，阻塞系数为0.9（90%时间在等待IO）：

```
线程数 = 4 / (1 - 0.9) = 4 / 0.1 = 40
```

## 四、带目标CPU利用率的完整公式

### 4.1 完整公式

```
线程数 = N_cpu × U_cpu × (1 + W/C)
```

- **U_cpu**：目标CPU利用率，取值范围 (0, 1]

### 4.2 为什么需要 U_cpu

将CPU跑到100%在生产环境中不可取：
1. GC停顿放大：高CPU利用率意味着GC线程与业务线程争抢激烈
2. 响应延迟尾部分布恶化：CPU接近饱和时，任何微小波动都会导致排队延迟急剧增加
3. 无缓冲余量：系统无法应对突发流量

### 4.3 推荐取值

| 场景 | 推荐 U_cpu | 说明 |
|------|-----------|------|
| 批处理/离线任务 | 0.9 ~ 1.0 | 可以吃满CPU |
| 在线Web服务 | 0.7 ~ 0.85 | 保留突发余量 |
| 延迟敏感服务 | 0.5 ~ 0.7 | 严格控制尾部延迟 |
| 容器化/云原生 | 0.6 ~ 0.8 | 配合HPA弹性伸缩 |

### 4.4 完整计算代码

```java
public class ThreadPoolSizeCalculator {

    /**
     * @param cpuCores         CPU核心数
     * @param targetUtilization 目标CPU利用率 (0~1)
     * @param waitTime         平均IO等待时间 (毫秒)
     * @param computeTime      平均CPU计算时间 (毫秒)
     * @return 推荐线程数
     */
    public static int calculate(int cpuCores, double targetUtilization,
                                 long waitTime, long computeTime) {
        double wcRatio = (double) waitTime / computeTime;
        double threads = cpuCores * targetUtilization * (1 + wcRatio);
        return (int) Math.ceil(threads);
    }

    public static void main(String[] args) {
        int cores = Runtime.getRuntime().availableProcessors();
        // W=90ms, C=10ms, U=0.8
        int recommended = calculate(cores, 0.8, 90, 10);
        System.out.println("推荐线程数: " + recommended);
        // 4核 → 输出: 推荐线程数: 32
    }
}
```

## 五、阿姆达尔定律与线程池的理论极限

### 5.1 阿姆达尔定律回顾

```
加速比 = 1 / [(1 - P) + (P / N)]
```

- **P**：程序中可并行化的部分所占比例
- **N**：并行处理器（核心）数量
- **(1 - P)**：必须串行执行的部分

当 N → ∞ 时，加速比趋近于 `1 / (1 - P)`，即串行部分成为瓶颈。

### 5.2 与线程池大小的关联

Brian Goetz公式本质上是阿姆达尔定律在线程池场景下的应用：

```
任务总时间 T_total = W + C

单个CPU核心的有效利用率 = C / (W + C)

为了让一个核心始终忙碌，需要 (W + C) / C = 1 + W/C 个任务轮流使用

扩展到N个核心：N × (1 + W/C) 个任务 → 即线程数
```

### 5.3 阿姆达尔定律揭示的极限

即使配置再多线程，系统的最大吞吐量仍受限于**串行瓶颈**：
- 数据库连接池大小
- 下游API的限流阈值
- 锁竞争的热点代码
- GC停顿时间比例

**关键推论**：当增加线程数不再提升吞吐量时，瓶颈可能不在计算层面，而在某个串行资源上。此时应优化串行瓶颈（如扩大数据库连接池、优化锁粒度），而非继续增加线程。

## 六、利特尔法则用于队列大小设计

### 6.1 利特尔法则（Little's Law）

```
L = λ × W
```

- **L**：系统中平均任务数（队列长度 + 正在执行的任务数）
- **λ**：任务到达率（tasks/second）
- **W**：任务平均响应时间（seconds）

### 6.2 在线程池队列设计中的应用

```
队列容量 = λ × W - 线程数

其中：
  λ = 峰值 QPS
  W = P99 响应时间（秒）
  线程数 = corePoolSize ~ maxPoolSize
```

**示例**：峰值QPS=1000，P99响应时间=0.2秒，线程池core=50：

```
队列容量 = 1000 × 0.2 - 50 = 200 - 50 = 150
```

### 6.3 三种队列策略的容量公式

| 队列策略 | 适用场景 | 容量公式 |
|----------|---------|---------|
| SynchronousQueue（零缓冲） | 强背压、弹性伸缩 | 0（不需要计算） |
| 有界队列 | 削峰填谷 | λ × W - 线程数 |
| 带超时的有界队列 | 防止无限等待 | 同上，配合DiscardOldestPolicy |

## 七、如何测量等待时间与计算时间（W/C）

### 7.1 五种实践方法

**方法一：代码埋点**

```java
public class TaskTimer {
    public static void execute(Runnable task) {
        long cpuBefore = ManagementFactory.getThreadMXBean()
            .getCurrentThreadCpuTime();  // 纳秒
        long wallBefore = System.nanoTime();

        task.run();

        long wallAfter = System.nanoTime();
        long cpuAfter = ManagementFactory.getThreadMXBean()
            .getCurrentThreadCpuTime();

        long wallTime = wallAfter - wallBefore;        // W + C
        long cpuTime = cpuAfter - cpuBefore;            // C
        long waitTime = wallTime - cpuTime;             // W

        double wcRatio = (double) waitTime / cpuTime;
        System.out.printf("W/C = %.2f (W=%dms, C=%dms)%n",
            wcRatio, waitTime / 1_000_000, cpuTime / 1_000_000);
    }
}
```

**方法二：ThreadMXBean 统计信息**

```java
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
bean.setThreadCpuTimeEnabled(true);

// 定期采样
long[] threadIds = bean.getAllThreadIds();
for (long id : threadIds) {
    long cpuTime = bean.getThreadCpuTime(id);   // 纳秒
    long userTime = bean.getThreadUserTime(id);  // 用户态
    // userTime / cpuTime 越小说明IO等待越多
}
```

**方法三：async-profiler**

```bash
# CPU 采样模式，找出热点
./profiler.sh -e cpu -d 60 -f cpu.html <pid>

# Wall-clock 采样模式，包含等待时间
./profiler.sh -e wall -d 60 -f wall.html <pid>

# 对比两次结果，wall中但不在cpu中的方法就是IO等待
```

**方法四：JDK Flight Recorder (JFR)**

```bash
# 启动JFR录制
jcmd <pid> JFR.start duration=120s filename=thread.jfr \
  settings=profile

# 分析Java Monitor Enter、Socket Read、File Read事件
# JMC中查看"Threads" → "Latencies" → 各等待事件的占比
```

**方法五：线程Dump统计分析**

```bash
# 连续采集N次线程Dump
for i in $(seq 1 10); do
  jstack <pid> > dump_$i.txt
  sleep 2
done

# 统计各线程状态出现次数
grep "java.lang.Thread.State" dump_*.txt | sort | uniq -c | sort -rn
```

### 7.2 测量方法的精度对比

| 方法 | 精度 | 侵入性 | 生产可用 | 适用阶段 |
|------|------|--------|---------|---------|
| 代码埋点（ThreadMXBean） | 纳秒级 | 需改代码 | 可（采样） | 开发/测试 |
| JFR | 微秒级 | 极低（<1%开销） | **强烈推荐** | 测试/生产 |
| async-profiler | 纳秒级 | 低（3-5%开销） | 谨慎（CPU密集场景） | 测试 |
| 线程Dump | 毫秒级 | 瞬时暂停 | **推荐** | 生产排查 |
| APM（Arthas/Dynamic-TP） | 统计级 | 低 | **推荐** | 生产监控 |

## 八、ThreadPoolExecutor 任务调度全流程

### 8.1 核心调度逻辑

```
任务提交 (execute)
    │
    ├─→ 1. 当前线程数 < corePoolSize？
    │       ├─ 是 → 创建核心线程，直接执行任务
    │       └─ 否 → 进入步骤 2
    │
    ├─→ 2. 工作队列未满？
    │       ├─ 是 → 任务入队等待
    │       └─ 否 → 进入步骤 3
    │
    ├─→ 3. 当前线程数 < maximumPoolSize？
    │       ├─ 是 → 创建非核心线程，直接执行任务
    │       └─ 否 → 进入步骤 4
    │
    └─→ 4. 触发 RejectedExecutionHandler 拒绝策略
```

**关键事实**：队列在步骤2被检查，非核心线程在步骤3才创建。因此：
- 使用**无界队列** → 步骤2永远不会返回"队列已满" → `maximumPoolSize` 形同虚设
- 使用**零容量队列（SynchronousQueue）** → 步骤2必然失败 → 直接跳到步骤3创建线程

## 九、七种工作队列深度对比

### 9.1 队列总览矩阵

| 队列 | 容量 | 数据结构 | 锁机制 | 排序 | 典型场景 |
|------|------|---------|--------|------|---------|
| SynchronousQueue | 0 | 栈/队列 | CAS无锁 | 无 | 弹性伸缩、强背压 |
| LinkedBlockingQueue | 有界/无界 | 单向链表 | 双锁(put+take) | FIFO | 稳定吞吐 |
| ArrayBlockingQueue | 有界(必须) | 环形数组 | 单锁(ReentrantLock) | FIFO | 内存敏感 |
| PriorityBlockingQueue | 无界 | 二叉堆(数组) | 单锁 | 按优先级 | VIP优先 |
| DelayQueue | 无界 | 二叉堆(数组) | 单锁 | 按到期时间 | 定时超时 |
| LinkedTransferQueue | 无界 | CAS链表 | CAS无锁 | FIFO/直传 | 高性能事件 |

### 9.2 SynchronousQueue：零容量直传

**核心语义**：没有内部存储空间，每个 `put()` 必须阻塞等待对应的 `take()`，实现"手递手"交接。

**内部实现**：两种模式

| 实现类 | 构造方式 | 公平性 | 数据结构 |
|--------|---------|--------|---------|
| TransferStack | `new SynchronousQueue()` (默认) | 非公平（LIFO） | CAS 栈 |
| TransferQueue | `new SynchronousQueue(true)` | 公平（FIFO） | CAS 队列 |

**CachedThreadPool的致命陷阱**：

```java
// newCachedThreadPool 内部实现
new ThreadPoolExecutor(
    0, Integer.MAX_VALUE,              // 最大线程无上限！
    60L, TimeUnit.SECONDS,
    new SynchronousQueue<Runnable>()   // 零容量直传
);
```

`maximumPoolSize = Integer.MAX_VALUE`，如果任务提交速率超过执行速率，线程数爆炸式增长。

**生产安全用法**：

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    4, 50,                            // 核心4，最大50，可控
    60L, TimeUnit.SECONDS,
    new SynchronousQueue<>(),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

### 9.3 LinkedBlockingQueue：无界风险与有界改造

**双锁设计**：入队和出队各用一把锁，生产者和消费者可以真正并行，吞吐量通常比单锁的 `ArrayBlockingQueue` 高2-5倍。

**危险链条**：

```
Executors.newFixedThreadPool(n)
    → new LinkedBlockingQueue<>()  无界
        → 队列永不满
            → maximumPoolSize 形同虚设
                → 任务无限堆积
                    → JVM堆内存耗尽 → OOM
```

**正确用法**：始终指定容量。

```java
// 有界改造
new LinkedBlockingQueue<>(2000)  // 必须指定容量！
```

### 9.4 ArrayBlockingQueue：有界队列的公平模式

**单锁设计**：入队和出队共享一把 `ReentrantLock`，在高并发下可能成为瓶颈。

**公平模式对比**：

| 模式 | 构造 | 吞吐量 | 延迟分布 | 适用场景 |
|------|------|--------|---------|---------|
| 非公平（默认） | `new ArrayBlockingQueue<>(1000)` | 高 | 有偏差 | 通用，追求吞吐 |
| 公平 | `new ArrayBlockingQueue<>(1000, true)` | 降低15-30% | 均匀 | 要求严格公平 |

**适用场景判定**：对内存敏感需要严格控制、任务执行时间较短、需要FIFO严格顺序。

### 9.5 PriorityBlockingQueue：任务优先级调度

基于二叉堆实现，任务必须实现 `Comparable` 或提供 `Comparator`。

**场景：**
- VIP用户请求优先处理
- 秒杀/抢购场景关键链路优先
- AI推理请求按优先级分级

**反直觉陷阱**：`PriorityBlockingQueue` 是无界的！配合 `DiscardOldestPolicy` 使用时，被丢弃的可能是优先级最高的任务（因为队头按优先级排序，不是按入队时间）。

### 9.6 DelayQueue：延迟/定时任务模式

元素必须实现 `Delayed` 接口，只有到期元素才能被取出。

```java
// 订单超时取消示例
class OrderTimeoutTask implements Delayed {
    private final long executeTime; // 到期时间戳（纳秒）
    private final String orderId;

    @Override
    public long getDelay(TimeUnit unit) {
        return unit.convert(executeTime - System.nanoTime(), TimeUnit.NANOSECONDS);
    }

    @Override
    public int compareTo(Delayed o) {
        return Long.compare(this.executeTime,
            ((OrderTimeoutTask) o).executeTime);
    }
}
```

### 9.7 LinkedTransferQueue：高性能直传

`LinkedTransferQueue` 是 `SynchronousQueue` + `LinkedBlockingQueue` 的超集：

- `transfer(E e)`：必须等待消费者接收才返回（SynchronousQueue语义）
- `tryTransfer(E e)`：立即尝试，无消费者则返回false
- `put(E e)`：无界队列语义（永不阻塞生产者）

## 十、拒绝策略深度解析与自定义实战

### 10.1 四种内置策略对比

| 策略 | 行为 | 数据安全性 | 适用场景 | 致命缺陷 |
|------|------|-----------|---------|---------|
| **AbortPolicy**（默认） | 抛出RejectedExecutionException | 安全（任务被拒绝通知提交方） | 需要快速失败的高可靠场景 | 未捕获异常会导致任务丢失 |
| **CallerRunsPolicy** | 由提交线程直接执行 | 安全（任务始终被执行） | **生产首选**，提供自然背压 | 可能阻塞关键线程 |
| **DiscardPolicy** | 静默丢弃 | **不安全（任务丢失无感知）** | 非关键日志/统计 | 配合submit()异常被吞 |
| **DiscardOldestPolicy** | 丢弃队头最旧任务 | 中等 | 更关心新数据 | PriorityBlockingQueue中优先丢弃高优先级任务 |

### 10.2 AbortPolicy 的致命缺陷

```java
// AbortPolicy 默认实现
public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
    throw new RejectedExecutionException("Task " + r.toString() +
        " rejected from " + e.toString());
}
```

如果使用 `executor.submit(task)`（而非 `execute`），**异常被封装在 `FutureTask` 内部**。只有调用 `Future.get()` 才会重新抛出，而不调用 `get()` 的话异常被静默吞掉。

### 10.3 自定义 RejectedExecutionHandler 生产级实现

```java
public class ProductionRejectedHandler implements RejectedExecutionHandler {

    private static final Logger log =
        LoggerFactory.getLogger(ProductionRejectedHandler.class);

    private final MeterRegistry meterRegistry;
    private final String poolName;
    private final Counter rejectedCounter;

    // 限频告警（每秒最多告警一次）
    private volatile long lastAlertTime = 0;
    private static final long ALERT_INTERVAL_MS = 60_000;

    public ProductionRejectedHandler(MeterRegistry registry, String name) {
        this.meterRegistry = registry;
        this.poolName = name;
        this.rejectedCounter = Counter.builder("threadpool.rejected")
            .tag("pool", poolName)
            .register(registry);
    }

    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        // 1. 记录指标（无条件）
        rejectedCounter.increment();

        // 2. 限频告警（一分钟最多一次）
        long now = System.currentTimeMillis();
        if (now - lastAlertTime > ALERT_INTERVAL_MS) {
            lastAlertTime = now;
            log.error("[线程池拒绝] pool={} activeCount={} poolSize={} "
                     + "queueSize={} completedTaskCount={}",
                     poolName,
                     executor.getActiveCount(),
                     executor.getPoolSize(),
                     executor.getQueue().size(),
                     executor.getCompletedTaskCount());
            // 接入告警通道：钉钉/企微/飞书/PagerDuty
        }

        // 3. 指数退避重试（最多3次）
        int maxRetries = 3;
        long baseDelayMs = 100;
        for (int i = 0; i < maxRetries; i++) {
            try {
                Thread.sleep(baseDelayMs * (1L << i)); // 100, 200, 400ms
                executor.getQueue().offer(r, 500, TimeUnit.MILLISECONDS);
                log.info("[线程池拒绝恢复] pool={} 第{}次重试成功", poolName, i + 1);
                return;
            } catch (InterruptedException ie) {
                Thread.currentThread().interrupt();
                break;
            }
        }

        // 4. 兜底降级：写入补偿表或MQ，异步补偿
        if (r instanceof FutureTask<?> ft) {
            log.error("[线程池拒绝兜底] pool={} 写入补偿队列", poolName);
            // compensationQueue.offer(taskInfo);
        }
    }
}
```

## 十一、内置监控指标与速率推导

### 11.1 核心API及其含义

| API 方法 | 含义 | 变化趋势解读 |
|----------|------|-------------|
| `getActiveCount()` | 当前正在执行任务的线程数(近似值) | 上升=负载增加 |
| `getPoolSize()` | 当前池中线程总数 | 观察扩/缩容行为 |
| `getLargestPoolSize()` | 池曾达到的最大线程数 | 历史上是否逼近过瓶颈 |
| `getQueue().size()` | 当前队列中排队等待的任务数 | **雪崩前最明显的先行信号** |
| `getCompletedTaskCount()` | 已完成任务总数（累计） | 须计算速率才有意义 |
| `getTaskCount()` | 已提交的总任务数（累计） | 配合完成数判断"进多出少" |

### 11.2 速率推导代码

```java
public class ThreadPoolMetrics {
    private long lastCompletedTaskCount = 0;
    private long lastTimestamp = System.currentTimeMillis();

    /** 任务完成率（tasks/second） */
    public double getCompletionRate(ThreadPoolExecutor executor) {
        long current = executor.getCompletedTaskCount();
        long now = System.currentTimeMillis();
        double rate = (current - lastCompletedTaskCount) * 1000.0
                      / Math.max(1, now - lastTimestamp);
        lastCompletedTaskCount = current;
        lastTimestamp = now;
        return rate;
    }

    /** 线程饱和度 = 活跃线程 / 最大线程 */
    public double getSaturation(ThreadPoolExecutor executor) {
        int max = executor.getMaximumPoolSize();
        return max > 0 ? (double) executor.getActiveCount() / max : 0.0;
    }

    /** 队列水位 = 队列当前任务数 / 队列容量 */
    public double getQueueWatermark(ThreadPoolExecutor executor) {
        int capacity = executor.getQueue().remainingCapacity()
                       + executor.getQueue().size();
        return capacity > 0
               ? (double) executor.getQueue().size() / capacity
               : 0.0;
    }
}
```

### 11.3 "慢性死亡"的五种危险信号

1. **`activeCount` 长期等于 `maxPoolSize`** — 线程不够用或任务执行太慢
2. **`queue.size()` 持续增长** — 消费速度跟不上生产速度，即将雪崩
3. **`completedTaskCount` 增速变缓** — 单个任务耗时变长
4. **拒绝策略频繁触发** — 用户已感知故障
5. **`poolSize` 始终达不到 `max`** — 典型无界队列坑（`LinkedBlockingQueue` 未设容量）

### 12.1 钩子方法总览

| 方法 | 调用时机 | 调用线程 | 用途 |
|------|---------|---------|------|
| `beforeExecute(Thread t, Runnable r)` | 任务执行前 | 工作线程 | 记录开始时间、设置MDC |

| `terminated()` | 线程池完全终止后 | 最后一个退出的线程 | 清理资源、发送关闭通知 |

### 12.2 完整监控线程池实现

```java
public class MonitoredThreadPoolExecutor extends ThreadPoolExecutor {

    private final MeterRegistry meterRegistry;
    private final String poolName;
    private final Timer taskExecutionTimer;
    private final Counter rejectedCounter;
    private final ThreadLocal<Long> startTime = new ThreadLocal<>();

    public MonitoredThreadPoolExecutor(
            int corePoolSize, int maximumPoolSize,
            long keepAliveTime, TimeUnit unit,
            BlockingQueue<Runnable> workQueue,
            ThreadFactory threadFactory,
            RejectedExecutionHandler handler,
            MeterRegistry meterRegistry, String poolName) {
        super(corePoolSize, maximumPoolSize, keepAliveTime, unit,
              workQueue, threadFactory, handler);
        this.meterRegistry = meterRegistry;
        this.poolName = poolName;

        this.taskExecutionTimer = Timer.builder("threadpool.task.execution")
            .tag("pool", poolName)
            .publishPercentiles(0.5, 0.95, 0.99)
            .publishPercentileHistogram()
            .register(meterRegistry);

        this.rejectedCounter = Counter.builder("threadpool.task.rejected")
            .tag("pool", poolName)
            .register(meterRegistry);
    }

    @Override
    protected void beforeExecute(Thread t, Runnable r) {
        startTime.set(System.nanoTime());
        super.beforeExecute(t, r);
    }

    @Override
    protected void afterExecute(Runnable r, Throwable t) {
        super.afterExecute(r, t);
        long elapsed = System.nanoTime() - startTime.get();
        startTime.remove();
        taskExecutionTimer.record(elapsed, TimeUnit.NANOSECONDS);

        // 关键：FutureTask 会吞掉异常，须主动探测
        if (t == null && r instanceof Future<?> future) {
            try {
                future.get();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } catch (ExecutionException e) {
                log.error("Task threw exception in pool {}",
                          poolName, e.getCause());
            }
        }
    }

    @Override
    protected void terminated() {
        log.info("Thread pool {} terminated. Completed: {}, Largest: {}",
                 poolName, getCompletedTaskCount(), getLargestPoolSize());
        super.terminated();
    }
}
```

# 第四部分：调优实战与反模式

## 十六、八大常见反模式

### 16.1 使用 Executors.newCachedThreadPool()

`maximumPoolSize` = `Integer.MAX_VALUE`，流量洪峰时可能瞬间创建数万线程，导致CPU上下文切换风暴。

**修复**：自定义 `ThreadPoolExecutor`，显式设置上限。

### 16.2 使用 Executors.newFixedThreadPool() + 无界队列

`newFixedThreadPool(n)` 内部使用无界 `LinkedBlockingQueue`，队列永不满，`maxPoolSize` 形同虚设，最终OOM。

**修复**：始终指定有界队列容量。

### 16.3 线程池中使用 ThreadLocal 未清理

线程池中的线程长期存活，每次任务遗留的 `key=null` 的脏Entry不断积累，老年代被填满后 OOM。

**修复三规则**：

```java
// 规则1：始终在 finally 中 remove()
try {
    threadLocal.set(value);
} finally {
    threadLocal.remove();
}

// 规则2：AutoCloseable 封装
public class ThreadLocalContext implements AutoCloseable {
    private static final ThreadLocal<String> CTX = new ThreadLocal<>();
    public static ThreadLocalContext put(String val) {
        CTX.set(val);
        return new ThreadLocalContext();
    }
    public static String get() { return CTX.get(); }
    @Override public void close() { CTX.remove(); }
}

// 使用 try-with-resources
try (var ctx = ThreadLocalContext.put(traceId)) {
    processRequest();
}

// 规则3：父子线程传递使用 TransmittableThreadLocal
TransmittableThreadLocal<String> context = new TransmittableThreadLocal<>();
ExecutorService ttlPool = TtlExecutors.getTtlExecutorService(pool);
```

### 16.4 在 ForkJoinPool.commonPool() 中执行阻塞IO

并行流、`CompletableFuture` 默认回调等都运行在 `ForkJoinPool.commonPool()` 上，其线程数默认=CPU核心数-1。阻塞IO会导致整个JVM中所有依赖commonPool的代码受影响，最坏情况下全部阻塞形成死锁。

**修复**：使用自定义 `ForkJoinPool` 或 `Executors.newVirtualThreadPerTaskExecutor()`。

### 16.5 混合CPU密集和IO密集任务在同一线程池

不同类型任务对线程数的需求完全不同。混在同一个池中导致饥饿效应：CPU任务长时间占用线程，IO任务被迫排队。

**修复**：为不同类型任务建立独立线程池。

### 16.6 缺乏超时和监控

线程池是"黑盒"——上线后无人问津，直到故障发生。

**必须监控的指标**：活跃线程数、队列深度、拒绝次数、任务平均执行时间、任务最大执行时间。

### 16.7 调用 shutdown() 后提交新任务

`shutdown()` 之后线程池拒绝接收新任务。在复杂业务流程中（如定时任务关闭的同时有新任务触发）容易发生。

**修复**：使用状态标志位，关闭前设置标志，提交前检查。

### 16.8 忽略 RejectedExecutionException

使用 `submit()` 提交任务时，如果触发拒绝策略，异常被封装在 `FutureTask` 中，不调用 `get()` 就会静默丢失。

## 十七、系统化调优方法论

### 17.1 五步迭代流程

```
第一步：建立基线 → 第二步：识别瓶颈 → 第三步：应用公式 → 第四步：验证测量 → 第五步：迭代优化
                                                                          ↑                    │
                                                                          └────────────────────┘
```

### 17.2 第一步：建立基线

| 基线指标 | 获取方式 |
|----------|----------|
| 吞吐量（TPS/QPS） | 压测工具（JMeter、wrk）+ APM |
| 平均响应时间（RT） | APM / Micrometer Timer |
| P50、P95、P99延迟 | Prometheus Histogram |
| 错误率 | 日志分析 / APM |
| CPU使用率 | top、vmstat、node_exporter |
| 线程池活跃线程数 | JMX / getActiveCount() |
| 队列深度 | JMX / 日志输出 |

### 17.3 第二步：识别瓶颈

**CPU瓶颈特征**：
- `top` 中CPU使用率持续 > 80%
- load average > CPU核心数
- 线程dump中大量线程处于 `RUNNABLE`

**IO瓶颈特征**：
- CPU使用率不高（< 50%），但TPS上不去
- 线程dump中大量线程处于 `WAITING` / `TIMED_WAITING`
- 网络IO等待高

**锁竞争瓶颈特征**：
- `jstack` 中大量线程在 `BLOCKED` 状态
- 特定方法的执行时间随并发增加呈非线性增长

**线程池瓶颈特征**：
- 队列持续增长
- activeCount 长期 = maxPoolSize
- 拒绝策略频繁触发

### 17.4 第三步到第五步：调优→验证→迭代

1. 根据瓶颈类型选择公式（CPU密集=N+1, IO密集=N×(1+W/C), 混合=分别建池）
2. 选择队列类型和大小（利特尔法则计算）
3. 选择拒绝策略（生产首选 CallerRunsPolicy）
4. 压测验证 → 观察指标 → 微调参数 → 再次压测 → 稳定后上线

### 18.1 ThreadPoolExecutor 原生API

// 动态调整核心线程数

## 十九、线程池隔离策略（舱壁模式）

### 19.1 为什么需要隔离

```
无隔离（单一线程池）:
  慢任务 ──→ 占满所有线程 ──→ 快任务排队等待 ──→ 整体延迟飙升

有隔离（多线程池）:
  慢任务 ──→ 慢任务专用池（线程少、队列深）
  快任务 ──→ 快任务专用池（线程多、队列短） ──→ 保持低延迟
```

### 19.2 隔离粒度对比

| 隔离粒度 | 线程池数量 | 管理复杂度 | 资源利用率 | 适用场景 |
|----------|-----------|-----------|-----------|---------|
| 接口级 | 多（几十个） | 高 | 低 | 核心接口的极限优化 |
| 服务级 | 中（几个） | 中 | 中 | **生产推荐** |
| 业务域级 | 少（2-3个） | 低 | 高 | 小型系统 |
| 全局 | 1个 | 极低 | 最高 | 极简场景（不推荐） |

### 19.3 Hystrix 线程池隔离

Netflix Hystrix 为每个依赖服务分配独立线程池，单个服务变慢不会拖垮全局。Netflix 实测：10亿次调用中，线程池隔离带来的额外延迟中位数3ms，99百分位9ms。

### 19.4 Sentinel 隔离模式

阿里巴巴 Sentinel 支持两种隔离：
- **信号量隔离**：轻量，不创建额外线程，但不能处理超时
- **线程池隔离**：功能完整，有一定开销，适用于高延迟场景

## 二十、优雅关闭模式

### 20.1 shutdown vs shutdownNow

| 方法 | 行为 | 队列中任务 | 执行中任务 |
|------|------|-----------|-----------|
| `shutdown()` | 有序关闭 | 等待执行完毕 | 不中断，等完成 |
| `shutdownNow()` | 立即关闭 | 返回未执行任务列表 | 调用interrupt()中断 |

### 20.2 两阶段关闭（推荐）

```java
public void gracefulShutdown(ThreadPoolExecutor executor) {
    // 第一阶段：阻止新任务，等待现有任务完成
    executor.shutdown();
    try {
        if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
            // 第二阶段：超时后强制中断
            List<Runnable> abandoned = executor.shutdownNow();
            log.warn("强制关闭线程池，丢弃了 {} 个未执行任务", abandoned.size());

            if (!executor.awaitTermination(10, TimeUnit.SECONDS)) {
                log.error("线程池无法终止！");
            }
        }
    } catch (InterruptedException e) {
        executor.shutdownNow();
        Thread.currentThread().interrupt();
    }
}
```

### 20.3 Spring Boot 集成

```java
@Configuration
public class ThreadPoolShutdownConfig implements DisposableBean {

    private final ThreadPoolTaskExecutor executor;

    @Override
    public void destroy() {
        executor.setWaitForTasksToCompleteOnShutdown(true);
        executor.setAwaitTerminationSeconds(30);
        executor.shutdown();
    }
}
```

## 二十一、Tomcat/Netty 线程池调优

### 21.1 Tomcat 线程池

Tomcat 的线程池扩展自 `ThreadPoolExecutor`，额外增加了三个特性：

```yaml
server:
  tomcat:
    threads:
      max: 200          # 最大工作线程数（默认200）
      min-spare: 10     # 最小空闲线程数（默认10）
    accept-count: 100   # 等待队列最大长度
    connection-timeout: 20000  # 连接超时（ms）
    max-connections: 10000     # 最大连接数
```

**Tomcat 线程数调优公式**：

```
maxThreads = (QPS × 平均响应时间(秒)) × 预留系数(1.5 ~ 2.0)

示例：QPS=500, 平均响应=200ms
maxThreads = 500 × 0.2 × 1.5 = 150
```

### 21.2 Netty 线程模型

```
Boss EventLoopGroup (1线程, 默认2×CPU)
  │  └─ 处理OP_ACCEPT，接受新连接
  │
  ▼ 将新连接的Channel注册到Worker
Worker EventLoopGroup (CPU×2线程, 默认2×CPU)
  │  └─ 处理OP_READ/OP_WRITE，读写数据
  │
  ▼ 业务处理
业务线程池（自定义、隔离）
  └─ 执行DB查询、RPC调用等阻塞操作
```

**Netty调优规则**：
- Boss线程数：1就够了（NIO模式下），除非端口数>1
- Worker线程数：`Runtime.availableProcessors() × 2`，默认即为最佳值
- **绝对不要在EventLoop中执行阻塞操作**——否则所有同EventLoop的连接都会卡死

## 二十四、数据库连接池与线程池的协同

### 24.1 HikariCP 经典公式

```
connections = (core_count × 2) + effective_spindle_count
```

其中 `effective_spindle_count` 对于SSD约为1，对于HDD是硬盘数量。

### 24.2 利特尔法则精确计算

```
连接数 = 峰值QPS × 平均DB查询耗时(秒)

示例：QPS=2000, DB查询平均耗时=10ms
连接数 = 2000 × 0.01 = 20
```

### 24.3 线程池与连接池的协同约束

```
线程数 ≤ 连接数

原因：如果线程多于连接，多出的线程永远在等待连接
      → 不仅浪费资源，还增加延迟
```

**集群单实例分配**：

```
单实例连接数 = 总连接数 / 实例数 × 0.8（预留余量）

示例：3实例集群，总连接数=30
单实例连接数 = 30 / 3 × 0.8 = 8
```

### 24.4 关键监控信号对照

| 线程池信号 | 连接池信号 | 诊断 |
|-----------|-----------|------|
| activeCount高 + queue堆积 | activeConnections高 + pendingConnections多 | 连接池不足 |
| activeCount高 + queue堆积 | activeConnections低 | 线程池不足 |
| activeCount低 + queue低 | activeConnections高 | DB慢查询 |

## 二十七、ForkJoinPool 深度调优

### 27.1 设计哲学

`ForkJoinPool` 为**分治并行计算**而设计。核心哲学：为每个工作线程分配独立的双端队列（Deque），通过工作窃取实现自动负载均衡。与 `ThreadPoolExecutor` 的中央共享队列不同，消除了单队列的竞争瓶颈。

### 27.2 工作窃取算法核心

```
拥有者线程操作队头（LIFO push/pop）— 无锁
窃取者线程操作队尾（FIFO poll）— CAS

   top (LIFO pop)
    ↓
 ┌───┬───┬───┬───┬───┐
 │ T4│ T3│ T2│ T1│   │  ← 环形数组
 └───┴───┴───┴───┴───┘
                    ↑
                 base (FIFO steal, CAS)
```

**设计精妙之处**：拥有者使用LIFO（缓存热数据），窃取者使用FIFO（窃取最老的大粒度任务），两者只在队列仅剩一个任务时才发生竞争。

### 27.3 常见陷阱与规避

**陷阱一：commonPool() 中阻塞**

```java
// 危险！阻塞IO在commonPool
list.parallelStream().forEach(id -> {
    httpClient.get("https://api.example.com/" + id);
});

// 正确：自定义ForkJoinPool
ForkJoinPool customPool = new ForkJoinPool(20);
customPool.submit(() ->
    list.parallelStream().forEach(id -> {
        httpClient.get("https://api.example.com/" + id);
    })
).get();
```

**陷阱二：并行流隐藏使用commonPool**

所有 `parallelStream()` 默认使用 `ForkJoinPool.commonPool()`。解决方案：

```java
// 方案A：自定义ForkJoinPool封装
ForkJoinPool pool = new ForkJoinPool(parallelism);
pool.submit(() -> list.parallelStream().forEach(...));

// 方案B：Java 21+ 使用虚拟线程替代
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    list.stream().forEach(id ->
        executor.submit(() -> process(id))
    );
}
```

### 27.4 ManagedBlocker：在FJP中正确处理阻塞

```java
ForkJoinPool pool = new ForkJoinPool(8);
pool.submit(() -> {
    // 阻塞操作必须通过ManagedBlocker
    ForkJoinPool.managedBlock(new ForkJoinPool.ManagedBlocker() {
        private boolean done = false;

        @Override
        public boolean block() throws InterruptedException {
            // 执行阻塞操作
            String result = httpClient.get("https://api.example.com");
            done = true;
            return true;  // 返回true表示阻塞完成
        }

        @Override
        public boolean isReleasable() {
            return done;
        }
    });
    return null;
}).get();
```

`ManagedBlocker` 会通知ForkJoinPool当前线程即将阻塞，池可以创建补偿线程来维持并行度。

### 27.5 ForkJoinPool vs ThreadPoolExecutor 选型决策

```
任务数量是否已知且巨大（数万+）？
  ├── 是 → 任务是纯计算还是有IO？
  │         ├── 纯计算 → ForkJoinPool（工作窃取高效）
  │         └── 有IO   → 先考虑虚拟线程，不行再用ThreadPoolExecutor
  └── 否 → 任务是否可递归分解？
            ├── 是 → ForkJoinPool
            └── 否 → ThreadPoolExecutor
```

## 二十八、虚拟线程：线程池的范式革命

### 28.1 工作原理

虚拟线程（JEP 444, Java 21）是JDK管理的轻量级线程：

| 特性 | 平台线程（Platform Thread） | 虚拟线程（Virtual Thread） |
|------|---------------------------|--------------------------|
| 栈内存 | ~1MB（固定） | 按需分配（存储在堆中） |
| 创建时间 | ~1ms | ~1μs（快1000倍） |
| 上下文切换 | OS内核态（昂贵） | Java用户态（Continuation） |
| 数量上限 | ~10000（受限于OS） | 数百万 |
| 调度器 | OS调度器 | JDK内置ForkJoinPool |

**核心机制**：当虚拟线程遇到阻塞IO操作时，JDK自动将其从载波线程（Carrier Thread）卸载，载波线程立即去执行其他虚拟线程。IO完成后，虚拟线程重新挂载到载波线程上继续执行。

### 28.2 何时虚拟线程可以取代线程池

- **IO密集型任务**：数据库查询、HTTP调用、文件读写
- **高并发短任务**：API网关代理、微服务调用
- **任务数量波动大**：无法事先确定合适的线程池大小
- **编程模型简化**：不需要为不同类型任务管理多个线程池

**替代模式**：

```java
// 旧模式：线程池 + 限流
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    10, 50, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000));

// 新模式：虚拟线程 + Semaphore限流
ExecutorService vThreads = Executors.newVirtualThreadPerTaskExecutor();
Semaphore rateLimiter = new Semaphore(500); // 并发限流

for (Request req : requests) {
    rateLimiter.acquire();
    vThreads.submit(() -> {
        try {
            handleRequest(req);
        } finally {
            rateLimiter.release();
        }
    });
}
```

### 28.3 何时仍需要线程池

- **CPU密集型任务**：加解密、编解码、科学计算（线程数=核心数最优）
- **需要强背压控制**：通过有界队列实现流量整形
- **线程亲和性**：需要绑定到特定CPU核心
- **需要线程局部复用**：ThreadLocal缓存昂贵对象，虚拟线程会过多创建
- **第三方库依赖**：使用了synchronized且在JDK 21-23上运行

### 28.4 钉住（Pinning）问题

**JDK 21-23**：当虚拟线程进入 `synchronized` 块/方法时，它被"钉住"到载波线程上，阻塞IO期间载波线程无法处理其他虚拟线程，可能导致载波线程池耗尽。

**JDK 24+**：synchronized钉住问题已修复（重新设计 `ObjectMonitor` 实现），不再钉住载波线程。但以下情况仍会钉住：
- 调用 `native` 方法
- 调用 `Foreign Function & Memory API` 的外部函数
- `Object.wait()`（不带超时）

**JFR检测钉住**：

```bash
java -XX:StartFlightRecording:filename=pin.jfr \
     -Djdk.tracePinnedThreads=full \
     -jar app.jar
```

JFR事件 `jdk.VirtualThreadPinned` 会记录每次钉住的持续时间和调用栈。

## 二十九、结构化并发与 Scoped Values

### 29.1 结构化并发（JEP 453, Java 21）

`StructuredTaskScope` 将一组并发任务视为一个工作单元：

```java
// ShutdownOnFailure：任一子任务失败则取消所有
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Future<String> user = scope.fork(() -> fetchUser(id));
    Future<Order> order = scope.fork(() -> fetchOrder(id));

    scope.join();            // 等待所有子任务
    scope.throwIfFailed();   // 有失败则抛异常

    return new Response(user.resultNow(), order.resultNow());
}

// ShutdownOnSuccess：取第一个成功的子任务
try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
    scope.fork(() -> fetchFromCache(key));
    scope.fork(() -> fetchFromDb(key));

    scope.join();
    return scope.result();   // 返回第一个成功的
}
```

### 29.2 Scoped Values（JEP 446, Java 21）

`ScopedValue` 是 `ThreadLocal` 的不可变替代品，专为虚拟线程设计：

```java
// 定义
private static final ScopedValue<String> TRACE_ID = ScopedValue.newInstance();

// 使用
ScopedValue.where(TRACE_ID, "trace-123")
    .run(() -> {
        String id = TRACE_ID.get();  // "trace-123"
        process();
    });

// 嵌套scope，子虚拟线程自动继承
ScopedValue.where(TRACE_ID, "parent")
    .run(() -> {
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            executor.submit(() -> {
                String id = TRACE_ID.get();  // "parent" — 自动继承
            });
        }
    });
```

`ThreadLocal` vs `ScopedValue` 对比：

| 特性 | ThreadLocal | ScopedValue |
|------|-----------|-------------|
| 可变性 | 可变（set） | 不可变（创建后不变） |
| 子线程继承 | InheritableThreadLocal | 自动支持 |
| 虚拟线程友好 | 需要清理，易泄漏 | 自动清理 |
| 性能 | 较高 | 更高（不可变→无写入开销） |

## 三十、从线程池迁移到虚拟线程

### 30.1 五步迁移路径

```
1. 识别IO密集型任务
    ↓
2. 替换为虚拟线程
    ↓
3. 添加并发限流（Semaphore）
    ↓
4. 压测对比（吞吐量、内存、P99延迟）
    ↓
5. 灰度上线（先5%流量，观察→扩大→全量）
```

### 30.2 合并多个线程池

迁移前（典型微服务架构可能有几十个线程池）：

```
业务池(50线程) + 通知池(10线程) + 日志池(5线程) + 定时池(3线程) + ...
```

迁移后：

```java
// 一个虚拟线程执行器 + 语义化限流
ExecutorService vt = Executors.newVirtualThreadPerTaskExecutor();

// 业务操作：限制500并发
Semaphore bizLimit = new Semaphore(500);

// 通知操作：不需要限流
// 日志操作：不需要限流
```

### 30.3 常见迁移陷阱

1. **ThreadLocal泄漏**：虚拟线程数量巨大，ThreadLocal未清理的代价被放大
   - 解决：迁移到ScopedValue，或确保finally中remove()
2. **synchronized钉住（JDK < 24）**：升级到JDK 24+或替换为ReentrantLock
3. **对象池复用假设**：原来10个线程复用的对象池，现在可能有10000个虚拟线程
   - 解决：按需分配，或添加Semaphore限流
4. **线程名假设**：代码中依赖Thread.getName()做业务逻辑的
   - 解决：使用ScopedValue或显式传参

## 三十一、业界真实案例

### 31.1 美团：动态化线程池实践

- 全公司统一线程池动态化平台
- 运行时热更新参数（无需重启）
- 实时监控+自动告警
- 支持逐步调整和灰度生效

**效果**：线程池相关故障减少80%+，参数调整周期从"小时级"变为"秒级"。

### 31.2 阿里巴巴：Sentinel 双十一大规模验证

Sentinel 的线程池隔离模式在双十一中保护了核心交易链路，将故障隔离在单个服务内，防止级联雪崩。流量控制规则可以实时下发，无需重启应用。

### 31.3 Netflix：Hystrix 舱壁模式

Netflix API网关在10亿次调用中验证：为每个下游依赖服务分配独立线程池的舱壁模式，额外延迟中位数仅3ms，99百分位9ms。单个下游服务超时不会耗尽全局线程资源。

### 31.4 字节跳动：Netty 线程池故障修复

### 31.5 Netflix：虚拟线程迁移

| 峰值QPS | 1200 | 3600（3倍） |

## 附录A：Brian Goetz公式完整推导

```
令：
  N = CPU核心数
  C = 每个任务的平均CPU计算时间（毫秒）
  W = 每个任务的平均IO等待时间（毫秒）

单个任务总时间：
  T_total = W + C

CPU利用率（单核心）：
  U_single = C / (W + C)

为了让一个核心保持100%利用率，需要的任务数：
  Tasks_per_core = T_total / C = (W + C) / C = 1 + W/C

扩展到N个核心（假设理想线性扩展）：
  Total_tasks = N × (1 + W/C)

引入目标CPU利用率 U_cpu （0 < U_cpu ≤ 1）：
  Total_tasks = N × U_cpu × (1 + W/C)

这就是最终的完整公式。
```

## 附录B：利特尔法则队列容量推导

```
由 L = λ × W 出发

L = 系统中平均任务数
  = 正在执行的任务数 + 队列中等待的任务数
  = TPS × 响应时间

队列容量 = 峰值L - 线程数
         = λ_peak × W_p99 - 线程数

示例：
  λ_peak = 800 QPS（峰值到达率）
  W_p99  = 0.25秒（P99响应时间）
  线程数  = 50

  L = 800 × 0.25 = 200
  队列容量 = 200 - 50 = 150
```
