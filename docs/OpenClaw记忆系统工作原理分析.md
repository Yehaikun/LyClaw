# OpenClaw 记忆系统工作原理分析

## 从一个用户问题说起

假设你在飞书上给 OpenClaw Agent 发了一条消息：

> "上次我们聊的台积电 CoWoS 封装产能的问题，结论是什么来着？"

接下来，整个记忆系统会经历一条完整的调用链路——从"收到消息"到"检索记忆"到"生成回答"。下面逐步拆解。

---

## 第一阶段：会话恢复（消息到达后立即发生）

### 1.1 加载会话运行记录

你发来消息的瞬间，OpenClaw 的运行时会做第一件事：**打开并读取你的会话记录文件**。

路径：`~/.openclaw/agents/main/sessions/<sessionId>.jsonl`

这个文件是 JSONL 格式（每行一个 JSON 对象），记录了从会话开始到现在的每一条消息、每次工具调用、每次模型切换。运行时不需要调用任何 LLM 工具，而是直接通过内部的会话管理接口读取：

```
{"type":"session","id":"0cc52c2b-0bb3-46a7-902a-83ebf15a118b","timestamp":"2026-05-19T09:15:35.152Z"}
{"type":"message","role":"user","content":"台积电CoWoS封装产能情况怎么样..."}     ← 你的历史消息
{"type":"message","role":"assistant","content":"台积电的CoWoS封装目前面临产能瓶颈..."}  ← Agent 的历史回复
```

读出来的历史消息会被构建为当前对话的上下文（ChatMemory），和你的新消息一起准备发送给 LLM。

### 1.2 加载 Bootstrap 文件

与此同时，运行时按照 `AGENTS.md` 中定义的工作流，从工作区读取以下文件注入 LLM 上下文：

| 文件 | 作用 | 每次都加载？ |
|------|------|------------|
| `SOUL.md` | Agent 的性格、伦理边界、语气风格 | 每会话都加载 |
| `USER.md` | 你的偏好、时区、项目上下文 | 每会话都加载 |
| `IDENTITY.md` | Agent 的名字、emoji、自我介绍 | 每会话都加载 |
| `MEMORY.md` | 长期记忆（重大决策、持久偏好） | **仅 main 私聊**加载 |
| `memory/2026-05-19.md` | 今天的日常记录 | 每会话都加载 |
| `memory/2026-05-18.md` | 昨天的日常记录 | 每会话都加载 |

**关键区别**：
- `MEMORY.md` 只在私聊（direct）中加载，群聊绝不加载——安全考虑。
- 日常记忆文件只加载"今天 + 昨天"两天的，再早的不自动注入——节省 Token。
- 这些 bootstrap 文件按预算截断（Token 上限），不是无限塞入。

到此为止，LLM 上下文中已经有了：
1. 你的人设和偏好（`SOUL.md` + `USER.md`）
2. Agent 的行为准则（`AGENTS.md`）
3. 长期关键事实（`MEMORY.md`）
4. 最近两天的活动记录（`memory/05-19.md` + `memory/05-18.md`）
5. 本会话的历史消息（`sessions/<id>.jsonl`）

---

## 第二阶段：记忆检索触发（Agent 决定"我需要去查"）

### 2.1 Agent 如何决定调用 memory_search？

你的问题是"上次聊的台积电 CoWoS 封装产能的结论"，这个问题有两个特征：
1. 涉及**特定话题**（台积电 CoWoS），不是泛泛的闲聊
2. 问题**有时效性**（"上次聊的"），说明答案不在当前会话的上下文中

Agent 收到这个问题后，经过 LLM 推理，会判断：
- bootstrap 注入的 `MEMORY.md` 和最近两天的 `memory/*.md` 里有没有相关答案？
- 如果没有（或信息不完整），就需要调用 `memory_search` 去**索引库**里检索。

这个判断不是硬编码的规则，而是 LLM 根据 `AGENTS.md` 中的操作指南自主做出的工具调用决策。

### 2.2 memory_search 调用链

Agent 决定调用 `memory_search("台积电 CoWoS 封装产能")` 后，触发以下完整调用链：

```
Agent 调用 memory_search(query)
       │
       ▼
┌──────────────────────────────────────────────┐
│  MemoryIndexManager.search(query, opts)       │
│                                              │
│  1. 检查是否需要等待正在进行的 sync()         │
│  2. 检查索引是否为"脏"（文件变化了但还没同步） │
│     → 如果是脏的，触发一次后台 sync()          │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│  候选召回阶段（Hybrid Search 并行两路）        │
│                                              │
│  ┌─────────────┐    ┌──────────────────────┐ │
│  │ BM25 全文检索 │    │ 向量语义检索          │ │
│  │              │    │                      │ │
│  │ 查 FTS 表     │    │ 1. query → embedding │ │
│  │ 关键词:       │    │ 2. 在 vec0 虚表中     │ │
│  │ "台积电"      │    │    做 ANN 最近邻搜索   │ │
│  │ "CoWoS"      │    │ 3. 返回语义最相近     │ │
│  │ "封装"       │    │    的 chunk           │ │
│  │ "产能"       │    │                      │ │
│  └──────┬──────┘    └──────────┬───────────┘ │
│         │                      │             │
│         └──────────┬───────────┘             │
│                    ▼                         │
│         mergeHybridResults()                 │
│         加权合并 + 去重 + 排序                │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│  返回结果（片段 + 路径 + 行号范围）            │
│                                              │
│  [                                           │
│    { path: "memory/2026-05-15.md",           │
│      startLine: 42, endLine: 58,             │
│      score: 0.94,                            │
│      snippet: "台积电CoWoS封装产能在2026Q3..." },│
│    { path: "MEMORY.md",                      │
│      startLine: 30, endLine: 35,             │
│      score: 0.81,                            │
│      snippet: "台积电先进封装仍是瓶颈..." },     │
│    ...                                       │
│  ]                                           │
└──────────────────────────────────────────────┘
```

### 2.3 如果 Embedding 不可用怎么办？

如果你没有配置 Embedding API，系统会进入 **FTS-only 模式**。此时：
- 向量检索路径被关闭（不会报错）
- `mergeHybridResults()` 退化为只使用 BM25 结果
- 检索仍然可用，只是缺少了语义理解能力（搜"代工"找不到只写"foundry"的文档）

### 2.4 如果是 QMD 后端呢？

如果你配置了 `memory.backend = "qmd"`，上面的调用链会被替换为 QMD 路径。之前的问题中已经详细解析过 QMD 的三阶段流程（`qmd update` → `qmd embed` → `qmd search/vsearch/deep_search`），这里不再重复。核心区别是 QMD 作为独立进程运行，使用自己的索引文件和嵌入模型，不依赖 OpenClaw 的 sqlite-vec。

## 第三阶段：渐进式披露（Progressive Disclosure）

### 3.1 为什么 memory_search 返回的是片段而不是全文？

这是 OpenClaw 记忆系统最重要的设计思想：**渐进式披露**（Progressive Disclosure）。

```
第一层（memory_search 返回的内容）：
  ├── 片段文本（snippet，默认最多 700 字符/条）
  ├── 文件路径（精确到哪个 .md 文件）
  ├── 行号范围（第几行到第几行）
  ├── 相关性得分（score）
  └── 来源类型（memory 还是 sessions）

第二层（memory_get 按需获取）：
  ├── 完整段落（指定文件 + 行号范围）
  └── 原始 Markdown 全文

第三层（需要时才深潜）：
  └── 读取完整的原始 .md 文件
```

**为什么这样做？**

类比人类阅读习惯：你在找资料时，先看搜索结果列表（标题+摘要），找到感兴趣的再点进去看全文，而不是一开始就把所有结果的全文都下载下来。

在 LLM 场景下，这对应：
- 记忆文件可能有几百 MB，全部塞进上下文是不可能的
- `memory_search` 返回的是"摘要 + 定位信息"（每条约 700 字符 × 默认 6 条 = 约 4000 字符）
- LLM 根据摘要判断哪些真正相关
- 再通过 `memory_get` 按路径 + 行号精确读取原文
- 两步操作的 Token 消耗远小于"把所有可能相关的文件全读进来"

### 3.2 memory_get 的调用

回到你的问题。`memory_search` 返回了 6 条结果，Agent 发现第一条得分最高（0.94），是 `memory/2026-05-15.md` 的第 42-58 行。但片段只有 700 字符，可能不足以完整回答你的问题。于是 Agent 再次调用：

```
memory_get(
  path: "memory/2026-05-15.md",
  from: 40,      // 从片段前面几行开始，获取更多上下文
  lines: 30      // 读取 30 行
)
```

这次读取返回了完整的原文内容，Agent 终于获得了足够的信息来回答你的问题。

### 3.3 渐进式披露的收益

假设你的记忆库有 100 个 .md 文件，总计 5MB 文本。如果每次查询都全文加载，需要约 1.25M Token（按 4 字符/Token 估算），这远超任何模型的上下文窗口。

而渐进式披露的方式：
- `memory_search` 返回 6 条片段 × 700 字符 = 约 4200 字符 ≈ **1050 Token**
- `memory_get` 回读 2 条 × 30 行 ≈ 3000 字符 ≈ **750 Token**
- 总计约 **1800 Token**，仅为全量加载的 0.14%

## 第四阶段：记忆写入（对话过程中的"记笔记"）

你的问题被回答了，但故事还没完。在对话过程中，记忆系统还在**持续写入**。

### 4.1 会话运行记录（实时写入，无需 Agent 干预）

每一条消息、每一次工具调用、每一次 LLM 推理，都由运行时**自动追加**到：

```
~/.openclaw/agents/main/sessions/<sessionId>.jsonl
```

这不是 Agent 调用工具写入的，而是运行时内部通过会话管理接口直接落盘。写入频率最高——基本跟随对话过程持续发生。

### 4.2 日常记忆的写入时机

**时机1：Agent 主动记录**

在对话任何阶段，当 Agent 判断当前信息需要暂存（临时决定、待办事项、重要上下文线索），会主动调用 `write` 或 `edit` 工具将内容追加到 `memory/2026-05-19.md`。

比如你说"这个台积电的结论很重要，下周要跟老板汇报"，Agent 可能会在今天的日志里记录一条：

```markdown
## 待办事项
- 整理台积电 CoWoS 封装产能分析结论，下周向老板汇报
- 关键数据：2026Q3 产能约 50K wpm，仍低于需求 80K wpm
```

**时机2：Pre-compaction Memory Flush（压缩前抢救）**

这是最关键的触发点。当会话上下文接近 LLM 的窗口限制时（比如你聊了 200 轮），系统会触发 Pre-compaction Memory Flush：

1. OpenClaw 发起一个**静默的 Agentic 轮次**（用户看不到这个过程）
2. 提示模型："会话即将压缩，请将持久化的笔记写入 `memory/YYYY-MM-DD.md`"
3. Agent 把当前会话中的重要信息提取出来，调用 `write` 工具写入今天的日志
4. 然后会话压缩才开始——旧消息被摘要替代，但重要细节已经被"抢救"到磁盘上了

这个机制确保了：即使上下文被压缩，重要的决策、事实、承诺不会丢失。

### 4.3 长期记忆的写入时机

`MEMORY.md` 的更新频率最低，写入条件更严格：

**触发条件1：用户明确要求**
- "记住，我以后回复邮件都要用广东话风格"
- "把我每次的偏好评测标准记下来"

**触发条件2：Agent 主动提炼**
- 已经积累了大量 `memory/*.md` 日志
- Agent（或心跳任务）主动总结提炼，写入 `MEMORY.md`
- 例如从 30 天的日常日志中提取出"用户偏好使用 PyTorch 而非 TensorFlow"这条长期事实

**长期记忆 vs 日常记忆的区别**：

| | MEMORY.md | memory/YYYY-MM-DD.md |
|---|----------|---------------------|
| 内容性质 | 提炼后的精华（决策、偏好、承诺） | 原始过程记录（当天事项、临时上下文） |
| 加载方式 | 每次私聊会话启动时注入 | 仅加载今天+昨天的 |
| 更新频率 | 低（几天/几周一次） | 高（每次会话都可能追加） |
| 更新方式 | 覆盖/编辑（edit 工具） | 追加（write/append 工具） |
| 安全性 | 绝不在群聊中加载 | 群聊中也不加载 |

## 第五阶段：索引同步（文件变化后如何更新检索库）

### 5.1 写入文件 ≠ 立即可检索

你在对话中让 Agent 记了一条笔记到 `memory/2026-05-19.md`，但这并不意味着下次 `memory_search` 立刻就能搜到它。因为记忆文件和向量索引是**解耦的**：

```
原始文件（Source of Truth）          向量索引（可重建的派生数据）
memory/2026-05-19.md                ~/.openclaw/memory/main.sqlite
       │                                        │
       │     sync() 触发后才同步                  │
       └────────────────────────────────────────┘
```

### 5.2 sync() 的五种触发时机

**1. 会话开始时**：异步尝试同步一次，保证检索时的索引新鲜度。

**2. memory_search 调用前**：如果系统检测到记忆文件在上次同步后被修改过，索引被标记为"脏"。在检索开始前，系统会安排一次后台同步，让索引尽快追上文件内容。

**3. 文件变更监听**：系统持续监听工作区中的记忆文件（`MEMORY.md` + `memory/*.md`）。当检测到新增、修改、删除时：
- 不立刻同步（防止文件正在写入时被读取）
- 而是先把索引标记为"脏"
- 启动一个短时间的**防抖等待**（debounce），合并短时间内的一批变更
- 等待结束后才执行实际索引更新

**4. 定时同步**：兜底机制，按配置的时间间隔周期性触发检查。

**5. 手动触发**：用户通过 CLI 执行 `memory index` 等命令。

### 5.3 sync() 内部做了什么

```
sync()
  → runSync()
    → syncMemoryFiles()
      → 扫描 MEMORY.md + memory/**/*.md
      → 检测哪些文件是新增/修改/删除
      → indexFile(新增/修改的文件)
        → 将文件内容切分为 chunk
        → 对每个 chunk 调用 embedding API 生成向量
        → 写入 sqlite-vec 的 vec0 虚表（向量存储）
        → 写入 FTS 表（全文检索索引）
        → 记录路径、行号范围、哈希、更新时间
      → removeDeletedFiles(已删除文件的索引)
```

**存储的具体内容**：
- 内容本身：chunk 级文本（原始片段，不是摘要）
- 定位信息：文件路径、起止行号、来源类型（memory 或 sessions）
- 向量：embedding 浮点数组
- 辅助信息：哈希、更新时间、provider/model

这就是为什么 `memory_search` 能直接返回"片段 + 路径 + 行号范围"——索引本身保存了可定位的 chunk 文本，不需要检索时临时生成摘要。

## 总结：记忆系统的五大设计原则

1. **Markdown 即事实来源**：所有记忆以 .md 文件存在磁盘上，人类可读、可编辑、可版本控制。向量索引只是可重建的派生数据。

2. **渐进式披露**：memory_search 返回片段 + 定位信息（省 Token），memory_get 按需回读全文（保精度）。不把所有文件全文塞进上下文。

3. **自动写入 + 主动写入双轨**：会话记录由运行时自动追加（无需 Agent 干预），长期记忆和日常记忆由 Agent 通过文件工具主动写入。

4. **压缩前抢救**：上下文接近窗口限制时，强制 Agent 把重要信息写入磁盘后再压缩——保证压缩不丢信息。

5. **文件变更与索引解耦**：写入文件不立即触发索引同步，通过防抖 + 脏标记 + 定时任务多机制保障新鲜度与性能平衡。
