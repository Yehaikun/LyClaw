# 第一部分：计算机是怎么同时做很多件事的

## 一、程序和进程：一个餐厅的比喻

### 1.1 硬盘里的程序 vs 运行中的程序

想象你的电脑是一栋大楼。

**程序（Program）**是放在硬盘里的文件——就像一份菜谱放在书架上。它只是一些文字和图片，什么也不做，只是存在那里。

**进程（Process）**是当你双击打开程序后，操作系统在内存里为它创建的一个"活"的实体——就像你拿着菜谱走进厨房，灶台点上火，菜开始做了。同一个程序可以启动多次，产生多个进程（比如你同时打开三个Word文档窗口，就是三个进程），它们虽然用的是同一份菜谱，但各自在做各自的菜。

进程是操作系统分配资源的基本单位。每个进程有自己独立的内存空间——A进程不能随便访问B进程的内存，就像两个餐厅的厨房之间有一堵墙。这堵墙是操作系统刻意设立的，目的是保护各进程之间互不干扰。

### 1.2 进程里有什么

操作系统给每个进程分配的资源包括：

| 资源 | 比喻 | 说明 |
|------|------|------|
| **内存空间** | 厨房的面积 | 堆（Heap）放食材、栈（Stack）放临时笔记 |
| **文件句柄** | 厨房登记的水电账户 | 打开的文件、网络连接等 |
| **线程** | 厨房里的厨师 | 真正动手干活的人 |
| **PID** | 厨房的门牌号 | 操作系统中唯一的进程ID |

一个刚启动的进程至少包含一个线程（主线程）。这个线程就是进程的"主厨"，从程序的入口（比如 `main` 方法）开始一行行执行指令。

## 二、CPU核心：厨房里有几个厨师

### 2.1 CPU核心是什么

CPU（中央处理器）是电脑的大脑，负责执行所有计算指令。一个CPU核心就是**一个能够独立执行指令的物理单元**。

- **单核CPU**：只有一个物理执行单元，任何时刻只能做一件事
- **多核CPU**：有多个独立的执行单元，可以同时做多件事

现代CPU通常有多个核心（4核、8核、16核……）。服务器的CPU核心数可能高达64核、128核。

### 2.2 超线程：一个核心装两个人

英特尔（Intel）有一种叫"超线程"（Hyper-Threading）的技术，让一个物理核心对外表现为两个逻辑核心。原理是这样的：

一个CPU核心内部有多个功能单元（加法器、乘法器、内存读写单元等），大多数时候不会全部同时使用。超线程技术让小本核心交替处理两条指令流——当指令A在等待内存数据时，指令B用另一个功能单元做计算。

超线程不是真正的双倍性能，一般能提升15%~30%的吞吐量。

### 2.3 怎么看自己电脑的CPU核心数

```
物理CPU个数：几个CPU芯片插在主板上
每个CPU的物理核心数：这个芯片里有几个真正的计算核心
逻辑核心数 = 物理核心数 × 超线程倍数（通常为2）

Java 中 Runtime.getRuntime().availableProcessors() 返回的是逻辑核心数
```

举个例子：一台双路服务器（2个CPU芯片），每个芯片8核且支持超线程：
- 物理核心数：16（2 × 8）
- 逻辑核心数：32（2 × 8 × 2）
- Java 看到的 `availableProcessors`：32

## 三、线程：厨师同时炒几道菜

### 3.1 线程是什么

线程是**进程中真正执行代码的单元**。一个进程可以包含多个线程，这些线程共享进程的内存空间，但各自独立执行。

继续用餐厅比喻：
- **进程 = 厨房**（一个独立的做菜空间，有自己的食材和灶台）
- **线程 = 厨师**（在厨房里干活的人，同一时刻一个厨师只能做一件事）

多线程就是让厨房里不止一个厨师。主厨负责切菜，二厨负责炒菜，三厨负责摆盘——各司其职，但共享同一个厨房（同一块内存空间）。

### 3.2 线程之间共享什么，不共享什么

**共享的**（同一厨房/同一进程）：
- 堆内存：所有线程都能访问进程堆中的对象（new 出来的东西都在堆上）
- 静态变量：类的 static 字段
- 打开的文件：进程打开的文件所有线程都能读写

**不共享的**（每个厨师自备的）：
- 栈内存：每个线程有自己独立的栈，存放局部变量和方法调用链
- 程序计数器（PC寄存器）：记录每个线程当前执行到哪一行指令

这个"共享堆、独立栈"的设计非常关键。它意味着：
- 多个线程可以操作同一个对象（共享堆）——这带来了并发安全问题
- 每个线程的方法内局部变量互不干扰（独立栈）——这是安全的

### 3.3 为什么需要多线程

单线程程序的问题是"一心不能二用"。举个例子：

你写了一个Web服务器，单线程处理请求：
```
请求1到达 → 查询数据库（等待50ms）→ 处理结果 → 返回
请求2到达 → 查询数据库（等待50ms）→ 处理结果 → 返回
请求3到达 → 查询数据库（等待50ms）→ 处理结果 → 返回
```

每个请求处理过程中，50ms在等待数据库返回数据——这段时间CPU在**空等**，什么也不做。如果有100个请求，总共等待时间5000ms，实际CPU干活时间可能只有500ms。

多线程的Web服务器：
```
请求1到达 → 线程1：查询数据库（等待50ms，此时CPU空闲）
                                    ↓
                              线程1等待时，CPU切换到线程2
                                    ↓
请求2到达 → 线程2：查询数据库（等待50ms，CPU继续空等？不！切换到线程3）
                                    ↓
                          ... 线程3、线程4、线程5 ...
```

关键洞察：**IO等待时间远大于CPU计算时间**。多线程的核心价值在于——当一个线程等待IO时，另一线程占用CPU做计算，让CPU不闲着。

### 3.4 多线程的代价

多线程不是免费午餐。额外代价包括：

1. **上下文切换开销**：CPU从一个线程切换到另一个线程，需要保存当前线程的状态、加载新线程的状态。这就像厨师放下正在炒的锅，洗手，拿起另一个锅——这个"切换"本身消耗时间。

2. **内存开销**：每个线程默认分配约1MB的栈内存空间。1000个线程就是约1GB内存，还没算线程本身的数据结构。

3. **同步开销**：多个线程访问共享数据时需要加锁，锁竞争会导致线程等待、降低并发度。

4. **编程复杂度**：线程安全问题（数据竞争、死锁、活锁）是编程中最难排查的bug类别之一。

## 四、上下文切换：厨师换锅的代价

### 4.1 什么是上下文切换

上下文切换（Context Switch）是操作系统的核心调度机制：CPU从一个线程切换到另一个线程的过程。

切换时操作系统需要做的事：

```
步骤1：保存当前线程A的状态
  - 程序计数器（PC）：A执行到哪一行了
  - 寄存器内容：A正在用哪些CPU寄存器
  - 栈指针：A的栈顶在哪里

步骤2：加载新线程B的状态
  - 读取B上次保存的PC、寄存器、栈指针

步骤3：CPU开始执行线程B的指令
```

这个过程耗时通常在几微秒到几十微秒之间。听起来很快，但如果每秒发生成千上万次上下文切换，累积开销就相当可观了。

### 4.2 上下文切换的触发条件

| 触发条件 | 说明 | 比喻 |
|----------|------|------|
| **时间片耗尽** | 线程的CPU时间配额用完了，操作系统强制切换 | 每个厨师只能用灶台5分钟，时间到换人 |
| **主动让出CPU** | 线程调用了sleep、wait、或等待IO | 菜谱上说"等汤汁收干"，厨师暂时离开灶台 |
| **被更高优先级的线程抢占** | 紧急任务插入 | 老板说VIP客人的菜优先做 |
| **等待锁** | 尝试获取被其他线程持有的锁 | 等别人用完菜刀 |

### 4.3 上下文切换为什么是性能杀手

假设一台服务器：
- CPU时间片：10ms（线程每次最多连续执行10ms就被强制切换）
- 上下文切换开销：5μs（微秒）
- 有100个线程在竞争CPU

在最坏情况下，100个线程每轮都跑满时间片：
- 一轮总执行时间：100 × 10ms = 1000ms（1秒）
- 切换开销：100 × 5μs = 500μs（几乎可忽略）

但如果这些线程大部分时间在做IO（比如处理HTTP请求），实际情况是：
- 每个线程刚拿到CPU，处理几微秒，发现要等数据库返回，让出CPU
- 100个线程不断进入等待→被唤醒→短暂执行→再次等待
- 上下文切换次数暴增：每秒可能数万次甚至数十万次

上下文切换风暴时，CPU可能花30%~50%的时间在切换线程而非执行业务代码。这就是线程数过多反而吞吐量下降的根本原因。

## 五、并发与并行：看起来同时 vs 真正同时

### 5.1 定义区分

**并发（Concurrency）**：多个任务在**同一时间段内**都在推进，但未必在**同一时刻**都在执行。就像一个人同时煮饭和炒菜——他实际是在两个任务之间快速切换。

**并行（Parallelism）**：多个任务在**同一时刻**真正同时执行。就像两个人分别煮饭和炒菜——物理上同时在发生。

```
并发（单核CPU，时间片轮转）：
时间 →
线程A: ████░░░░░░░░████░░░░░░░░████
线程B: ░░░░████░░░░░░░░████████░░░░
线程C: ░░░░░░░░████████░░░░░░░░████

并行（多核CPU）：
时间 →
核心1 线程A: ████████████████████████
核心2 线程B: ████████████████████████
核心3 线程C: ████████████████████████
```

### 5.2 这个区分为何重要

因为线程池大小的公式依赖于任务类型：

- **CPU密集型任务**需要并行（在多个核心上真正同时计算），线程数应该约等于核心数
- **IO密集型任务**可以通过并发获得收益（一个线程等IO时其他线程继续用CPU），线程数可以远超核心数

如果你的任务是纯计算的（比如视频编码、加密解密），线程再多也没用——CPU核心就那么几个。但如果是Web服务器（大量数据库查询、RPC调用），线程数就值得远超核心数。

# 第二部分：为什么需要线程池

## 六、不用线程池的生活方式

### 6.1 每次新建线程

不使用线程池时，最直观的做法是：每次有任务来，`new Thread().start()`。

这条操作在操作系统层面发生了什么：

1. **分配线程栈**：操作系统在内存中为线程预留一块连续空间（默认约1MB），作为线程的调用栈。如果你在64位JVM上，最小也有约1MB（受 `-Xss` 参数控制）。

2. **创建内核线程**：操作系统在内核空间创建一个线程控制块（TCB，Thread Control Block），记录线程ID、状态、优先级、寄存器快照等元数据。

3. **初始化用户态结构**：JVM在Java堆中创建 `java.lang.Thread` 对象，包含线程名、ThreadGroup、ContextClassLoader等。

4. **注册到调度器**：将新线程注册到操作系统的线程调度器中，等待被分配CPU时间。

一个线程从创建到可以执行，消耗时间约0.5ms~2ms，消耗内存约1MB~2MB。看起来不多，但乘上数量就触目惊心。

### 6.2 用完就扔的问题

线程执行完任务后被销毁（线程的 `run()` 方法结束）：

1. **回收栈内存**：1MB的栈空间还给操作系统
2. **销毁内核数据结构**：内核中的线程控制块被释放
3. **销毁JVM对象**：Java堆中的 `Thread` 对象等待GC回收

创建和销毁都是有开销的。如果每个HTTP请求都经历"创建线程→处理→销毁线程"，在高并发下这些开销会显著影响响应时间。

### 6.3 没有上限控制的问题

不用线程池最大的问题不是开销，而是**无法控制并发上限**。

假设你的服务收到10000个并发请求：
- 创建10000个线程
- 每个线程栈1MB → 10GB栈内存
- 10000个线程争抢CPU → 上下文切换风暴
- 数据库连接池只有50个连接 → 9950个线程在排队等连接
- 最终：内存耗尽 + CPU满载 + 响应超时 → 系统崩溃

这就是所谓的"线程爆炸"。一个没有并发控制的系统，在流量洪峰面前不堪一击。

## 七、线程池的核心思想：复用而非新建

### 7.1 线程池的直觉理解

线程池本质上就是一个**线程的缓存**。

想象一个维修队：
- **无线程池**：每次有人报修，就招一个临时工，修完就辞退。招人办手续（创建线程）耗时，辞退办手续（销毁线程）耗时。报修人多的时候，到处都是临时工，管理混乱。
- **有线程池**：维修队长期雇佣10个师傅。报修单来了，师傅去修，修完回来接下一个单。忙不过来时，报修单排队等候。实在太多时，临时加人（扩容到最大线程数）。都不行就拒单（拒绝策略）。

核心思路：**提前创建好一定数量的线程，反复使用，而不是临时创建、用完就扔**。

### 7.2 线程池解决的三个问题

**问题一：减少创建/销毁开销**。线程创建一次后反复使用，消除重复创建和销毁的CPU和内存开销。

**问题二：控制并发上限**。限制最大线程数和工作队列容量，防止流量洪峰时系统崩溃。这是流量整形能力——把尖刺状的请求流量削平为平稳的处理速率。

**问题三：统一管理和监控**。有一个统一的地方查看：当前有多少线程在工作、有多少任务在排队、完成了多少任务、是否有任务被拒绝——而不是散落各处的"野线程"。

### 7.3 线程池不是什么

线程池不是让任务变快的魔法。它只是：
- 让线程的获取更高效（复用而非创建）
- 让并发规模更可控（上限保护）
- 让运行状态更可见（统一监控）

如果一个任务的执行时间就是需要100ms，无论你用不用线程池，它都是100ms。线程池优化的是线程的创建和调度开销，不是任务的执行效率。

## 八、线程池在系统中的位置

### 8.1 作为流量整形器

```
                        请求流量（尖刺/洪峰）
                              │
                              ▼
                 ┌────────────────────────┐
                 │      线程池（流量整形）  │
                 │  ┌──────┐  ┌─────────┐ │
                 │  │ 线程1 │  │ 排队队列 │ │
                 │  │ 线程2 │  │ [等][等] │ │
                 │  │ 线程3 │  │ [等][等] │ │
                 │  └──────┘  └─────────┘ │
                 └─────────┬──────────────┘
                           │ 平稳的并发执行
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌────────┐  ┌────────┐  ┌────────┐
         │ 数据库  │  │ 缓存   │  │ 下游   │
         │ 连接池  │  │ Redis  │  │ 微服务 │
         └────────┘  └────────┘  └────────┘
```

线程池在请求入口和后端资源之间起缓冲作用。它把不可控的请求流量转化为可控的后端并发压力。

### 8.2 作为资源保护屏障

线程池保护的不只是自身，更是下游资源：

- **数据库连接池**：线程池限制并发线程数，间接限制了同时访问数据库的线程数，防止连接池被耗尽
- **下游微服务**：限制并发调用量，防止把下游打垮（类似于客户端限流）
- **JVM内存**：限制线程数，间接限制了线程栈内存的占用

一个100线程的线程池同时最多有100个线程在执行。如果这100个线程都去访问数据库，而数据库连接池只有30个连接，那么只有30个线程在做有效工作，另外70个在等待。这告诉你一个信息：要么扩大数据库连接池，要么减小线程池——它们在数量上需要匹配。

# 第三部分：线程池的内部结构

## 九、线程池的四个组成部分

### 9.1 四个组件的直觉模型

Java的线程池（`ThreadPoolExecutor`）由四个组件构成：

```
                    ┌──────────────────────┐
   任务提交 ──────→ │     线程池            │
                    │                      │
                    │  ┌────────────────┐  │
                    │  │   工作线程集合   │  │  核心线程 + 临时线程
                    │  │  Thread-1      │  │
                    │  │  Thread-2      │  │
                    │  │  Thread-3      │  │
                    │  └───────┬────────┘  │
                    │          │           │
                    │  ┌───────▼────────┐  │
                    │  │   工作队列      │  │  等待执行的任务排队处
                    │  │ [任务4][任务5] │  │
                    │  └───────┬────────┘  │
                    │          │           │
                    │  ┌───────▼────────┐  │
                    │  │   线程工厂      │  │  负责创建新线程
                    │  └───────┬────────┘  │
                    │          │           │
                    │  ┌───────▼────────┐  │
                    │  │   拒绝策略      │  │  忙不过来时怎么办
                    │  └────────────────┘  │
                    └──────────────────────┘
```

**四个角色的职责：**

| 组件 | 职责 | 比喻 |
|------|------|------|
| 工作线程集合 | 真正执行任务的线程 | 修理工师傅们 |
| 工作队列 | 暂存等待执行的任务 | 待处理的工单夹 |
| 线程工厂 | 创建新线程的工厂方法 | 招人流程 |
| 拒绝策略 | 线程和队列都满了怎么办 | 客满拒客的规则 |

### 9.2 线程池构造函数——参数的直觉含义

当你在代码中写 `new ThreadPoolExecutor(...)` 时传入的每个参数，都有一个直观的含义：

```
核心线程数（corePoolSize）  → 生意淡季时日常维持的厨师数量
最大线程数（maximumPoolSize）→ 生意旺季时最多能拉来多少人
存活时间（keepAliveTime）   → 临时厨师最多空闲多久就让他下班
工作队列（workQueue）       → 客人点了菜但厨师还没开始做时，菜单放在哪里
线程工厂（threadFactory）   → 怎么招人（名字叫什么、属于哪个组）
拒绝策略（handler）         → 满座时怎么告诉新来的客人
```

## 十、核心线程：餐厅的固定厨师

### 10.1 什么是核心线程

核心线程（core threads）是线程池**长期维持**的工作线程。只要线程池没有关闭，哪怕这些线程什么事都不做，它们也保持存活（除非配置了 `allowCoreThreadTimeOut`）。

和生活中的"编制"类似：事业单位有固定编制人员，除非机构撤销，否则不会裁员。核心线程就是线程池的编制。

### 10.2 核心线程数量的含义

```
corePoolSize = 5

表示：正常情况下，维持5个线程待命。
     - 任务少（≤5个并发任务）：5个线程可以直接处理，任务不需要排队
     - 每个线程处理完当前任务后，会去队列取下一个任务
     - 没有任务时，这5个线程进入等待状态（WAITING），不消耗CPU
```

### 10.3 核心线程和prestart（预创建）

线程池的核心线程默认是**懒加载**的：只有当任务提交时才会创建线程，而不是线程池一初始化就创建好全部核心线程。

为什么设计成懒加载？因为有时候创建了线程池但可能根本没任务提交，提前创建就是浪费。

如果你希望线程池一启动就准备好全部核心线程（比如你知道很快就有大量任务来），可以调用 `prestartAllCoreThreads()` 方法。这相当于提前通知所有固定厨师准时到岗。

---

## 十一、最大线程数：高峰期能动员的上限

### 11.1 核心线程 vs 最大线程

```
核心线程数 = 5    （平日固定人员）
最大线程数 = 20   （高峰能召集的人员上限）
临时线程数 = 20 - 5 = 15（最多额外拉来的人）
```

最大线程数是线程池的**安全阀**。它代表系统能承受的极限——"不管压力多大，我最多就让这么多人同时干活"。

### 11.2 什么时候创建临时线程

临时线程（超出核心线程数的线程）只在**核心线程全部在工作 + 工作队列已满**时才会创建。

流程：
```
任务到达
  → 所有核心线程都在干活？→ 是
    → 队列有位置？→ 是 → 入队等待（不创建新线程）
    → 队列满了？→ 是
      → 还有余量到最大线程数？→ 是 → 创建临时线程执行
      → 已经达到最大线程数？→ 是 → 拒绝
```

关键理解：**先排队，后扩容**。不是说有任务就马上加人，而是队列实在装不下了才加人。这个设计是因为创建线程成本高，操作系统希望在现有资源内尽量消化任务。

### 11.3 最大线程数不是越大越好

最大线程数设得太大（比如10000），问题来了：
- 如果真的来了10000个任务同时执行，CPU根本忙不过来，大量时间花在上下文切换
- 1万个线程 × 1MB栈 = 10GB栈内存，JVM没这么多内存就OOM
- 下游数据库连接池可能只有50个，9950个线程在等连接——纯浪费

所以最大线程数是一个**根据系统资源精心计算的值**，不是拍脑袋的数字。

---

## 十二、工作队列：厨房里的等菜台

### 12.1 工作队列的角色

工作队列（Work Queue）是存放**已提交但还没轮到执行**的任务的地方。

这个队列的存在非常关键：它让线程池可以"削峰填谷"。当任务提交速度超过处理速度时，不是直接拒绝，而是先排队。等线程处理完手头任务，再逐个从队列取任务。

### 12.2 队列的三种策略

**策略一：无缓冲（容量为0的队列）**

相当于没有等菜台——厨师做完了直接端走，没位置排队。新客人来了，如果厨师都在忙，要么加新厨师（创建临时线程），要么到了上限就拒客。

这种策略的好处是响应快、没有任务在排队中"过期"。代价是需要足够多的线程来吸收流量波动。

**策略二：有界缓冲（容量有限制，比如200）**

相当于一个固定大小的等菜台。来了新的菜单，先放台上；满了再加人；人加满了就拒客。

这是生产环境最推荐的做法——兼顾了削峰和保护。

**策略三：无界缓冲（容量无限）**

相当于一个无限大的等菜台。不管多少菜单都能放下，好像永远不会拒客。但问题是：如果来菜速度持续大于做菜速度，菜单（内存中的任务对象）会无限增长，直到内存耗尽、系统崩溃。

这就是无界队列是"定时炸弹"的原因——它不会直接拒绝任务，而是让你的系统在毫无征兆的情况下慢慢走向OOM。

### 12.3 队列的类型选择

不同的队列实现有不同的特性：

| 队列类型 | 比喻 | 适用场景 |
|----------|------|---------|
| **有界链表队列** | 一个排队的走廊，先进先出 | **生产首选**，通用性强 |
| **数组队列** | 固定大小的格子，内存紧凑 | 内存敏感的嵌入式场景 |
| **零容量直传队列** | 没有缓冲区，必须手递手交接 | 强背压、弹性伸缩 |
| **优先级队列** | VIP客人插队到前面 | 优先级调度的场景 |
| **延迟队列** | 定时炸弹，到时间才生效 | 定时超时处理 |

关于每种队列的详细对比和选择方法，请参考配套文档《线程池调优完全指南》的第9章。

## 十三、拒绝策略：忙不过来了怎么办

### 13.1 什么时候触发

拒绝策略（RejectedExecutionHandler）在以下条件同时满足时触发：
1. 所有核心线程都在执行任务
2. 工作队列已满
3. 线程总数已达到最大线程数

就像餐厅：所有厨师都在炒菜，等菜台堆满了，临时工也全召来了——再来客人就不得不拒之门外。

### 13.2 四种内置拒绝策略的直觉理解

**策略一：直接拒绝（AbortPolicy，默认）**

"不好意思，我们实在做不了了"，然后直接告诉客人。干净利落，但客人（调用方）需要自己处理这个拒绝——如果他没处理，这个任务就丢失了。

**策略二：调用者自己执行（CallerRunsPolicy）**

"我们是做不了了，要不你自己进厨房做吧？"——拒绝在调用方的线程中直接执行这个任务。这是一种自然的反向压力（背压）：如果调用方线程被占用来执行任务，它就无法再提交新任务，从而减慢任务到达速度。

这是生产环境最推荐的做法——不丢任务，自然限流。

**策略三：直接丢弃（DiscardPolicy）**

任务被默默丢弃，不通知任何人。就像客人来了没人理，自己走了。适合允许丢失的非关键任务（如日志、统计），但必须配合监控使用——至少要知道丢了东西。

**策略四：丢弃最旧的（DiscardOldestPolicy）**

把队列头（最早入队的任务）丢掉，把新任务插入队尾。适用于"新数据比旧数据更重要"的场景，比如实时行情数据。

### 13.3 选择拒绝策略的思考框架

问自己三个问题，按顺序回答：

1. **这个任务能丢吗？** 不能 → 选 CallerRunsPolicy
2. **丢了需要有感知吗？** 需要 → 不能用 DiscardPolicy
3. **新数据比旧数据重要吗？** 是 → 选 DiscardOldestPolicy

大多数业务场景下，CallerRunsPolicy 是最安全的选择。

## 十四、keepAlive：临时厨师什么时候下班

### 14.1 存活时间的含义

`keepAliveTime` 控制**临时线程**（超出核心线程数的线程）在空闲多久后被回收。

```
keepAliveTime = 60秒

意思是：一个临时线程处理完手头任务后，如果没有新任务可做，
        等待60秒，如果这60秒内还是没任务，这个线程就终止了。
```

### 14.2 为什么需要这个机制

没有 keepAliveTime，超出核心线程数的线程就会永久存活——导致线程数在高流量过后不会降回来，资源浪费。

keepAliveTime 让线程池具有"弹性"：高峰期扩容，低峰期缩容。

### 14.3 allowCoreThreadTimeOut

通过配置 `allowCoreThreadTimeOut(true)`，可以让核心线程超时空闲时也被回收。这时线程池可缩容到0线程。

这在流量极不平均的场景有用：比如凌晨2点流量极低，维持5个空闲线程纯属浪费。

# 第四部分：任务的完整旅程

## 十五、一个任务从提交到执行完毕经历了什么

### 15.1 完整流程图

这是 `ThreadPoolExecutor.execute(task)` 的完整决策流程：

```
            ┌─────────────────┐
            │  新任务提交       │
            └────────┬────────┘
                     │
                     ▼
         ┌───────────────────────┐
         │ 当前线程数 < 核心线程数？│
         └───────────┬───────────┘
                     │
            ┌────────┴────────┐
            ▼ 是              ▼ 否
    ┌──────────────┐  ┌───────────────────┐
    │ 创建核心线程   │  │ 工作队列未满？     │
    │ 直接执行任务   │  └────────┬──────────┘
    └──────────────┘           │
                      ┌────────┴────────┐
                      ▼ 是              ▼ 否
              ┌──────────────┐  ┌───────────────────────┐
              │ 任务入队等待   │  │ 当前线程数 < 最大线程数？│
              └──────────────┘  └───────────┬───────────┘
                                            │
                                   ┌────────┴────────┐
                                   ▼ 是              ▼ 否
                           ┌──────────────┐  ┌──────────────┐
                           │ 创建临时线程   │  │ 触发拒绝策略   │
                           │ 直接执行任务   │  └──────────────┘
                           └──────────────┘
```

### 15.2 关键判断顺序的记忆口诀

"**核 → 队 → 最 → 拒**"：
1. **核**心线程够吗？够就创建核心线程执行
2. 不行就**队**列有位置吗？有就排队
3. 不行就**最**大线程还有余量吗？有就创建临时线程
4. 都不行就**拒**绝

---

## 十六、为什么这个顺序如此重要

### 16.1 排队优先于扩容的设计哲学

为什么设计成"先排队，后扩线程"而非"先扩线程，后排队"？

因为操作系统希望最小化线程数量。每个线程都有开销（内存、调度），能不创建就不创建。短暂的任务堆积（比如几百毫秒的微突发）用队列缓冲即可，不值得为此创建和销毁线程。

这种设计在突发流量下有显著效果：微突发被队列吸收，只有持续超载才会触达扩容。

### 16.2 这个顺序的反直觉后果

如果你创建了一个 `newFixedThreadPool(10)`，它的内部是：

```
corePoolSize = 10
maximumPoolSize = 10
workQueue = new LinkedBlockingQueue<>()  // 无界队列

执行流程：
任务1~10  → 创建核心线程，直接执行
任务11+   → 所有核心线程忙 → 队列未满（无界！）→ 入队
                → 永远不会创建第11个线程
                → 如果入队速度 > 出队速度，队列无限增长
                → OOM
```

这里 `maximumPoolSize` 根本没机会用上！因为无界队列永远不会"满"，流程永远到不了步骤3（检查最大线程数）。这就是为什么 `newFixedThreadPool` 是生产环境反模式——不是你直觉以为的"固定10个线程"，而是"10个线程 + 无限大的队列"。

---

## 十七、无界队列为什么是定时炸弹

### 17.1 危险链条

```
流量突增
  → 提交速度 > 处理速度
    → 队列长度持续增长
      → 每个任务对象在JVM堆上占用内存（请求参数、上下文等）
        → 队列中积压了几十万个任务对象
          → 堆内存耗尽
            → Full GC频繁触发（STW，Stop-The-World）
              → GC overhead limit exceeded 或 OOM
                → 应用崩溃
```

**关键：这个过程没有任何报错**。系统看起来还在运行，队列默默增长，GC越来越频繁，直到最终崩溃。等你从监控或用户投诉中发现时，往往已经在崩溃边缘。

### 17.2 如何避免

三条铁律：

1. **永远给队列设置容量上限**：不要用无参构造的 `LinkedBlockingQueue`，始终传容量参数
2. **监控队列深度**：队列中任务数 > 容量的80% → 告警
3. **设置合理的拒绝策略**：不要用可能吞掉异常的默认 `AbortPolicy` + `submit()` 组合

# 第五部分：线程池的类型与选择

## 十八、固定大小线程池：稳定的餐厅

### 18.1 内部结构

```
corePoolSize = N
maximumPoolSize = N
keepAliveTime = 0（非核心线程不存在，此参数无意义）
workQueue = 无界 LinkedBlockingQueue
```

始终维持N个线程。所有线程都是核心线程，一个不多一个不少。任务超出N个时排队。

### 18.2 优点

- 架构简单，行为可预测
- 不会因为创建/销毁线程而产生额外的CPU开销
- 资源占用稳定

### 18.3 缺点

- **无界队列是致命缺陷**：流量持续超载时队列无限增长，最终OOM
- 无法应对突发流量：再多任务也只能排队等待
- 固定N意味着低峰期也有N个线程闲置

### 18.4 什么场景适合

- 流量非常稳定的后台任务
- 已知并发上限且可控的场景
- **前提：一定要给队列设置容量**

---

## 十九、缓存线程池：弹性伸缩的排檔

### 19.1 内部结构

```
corePoolSize = 0
maximumPoolSize = Integer.MAX_VALUE（约21亿，不设上限）
keepAliveTime = 60秒
workQueue = SynchronousQueue（容量为0）
```

没有核心线程。每个任务到达：
- 有空闲线程 → 直接交给空闲线程执行
- 没有空闲线程 → 创建新线程

空闲超过60秒的线程自动回收。

### 19.2 优点

- 完全弹性，理论上可以应对任意大的并发
- 没有核心线程，低峰期0资源占用

### 19.3 缺点

- **最大线程数无上限**：突发流量时会创建数万线程，系统直接崩溃
- 每个新任务提交时可能需要创建线程（耗时）
- 60秒 keepAlive 可能对长连接场景不友好

### 19.4 什么场景适合

- 大量短生命周期的异步任务
- 任务执行时间极短（毫秒级）
- **前提：必须在外部限制最大并发数**

---

## 二十、单线程池：只有一个厨师的店

### 20.1 内部结构

```
corePoolSize = 1
maximumPoolSize = 1
workQueue = 无界 LinkedBlockingQueue
```

整个线程池只有1个线程。所有任务严格按顺序执行。

### 20.2 为什么需要单线程池

在并发编程中，单线程池解决了"我不想处理锁，但我需要顺序"的需求。

比如：
- 写日志文件：多个生产者写同一个文件，用单线程池保证不交叉写乱
- 处理链表操作：非线程安全的链表，单线程操作不出错
- 顺序消息处理：消息必须按到达顺序依次处理

单线程池本质上是用"串行化"来避免"并发控制"。代价是失去了并发带来的吞吐量提升。

---

## 二十一、定时调度线程池：按时间表做事

### 21.1 内部结构

和固定大小线程池类似，但队列使用 `DelayedWorkQueue`（一种按到期时间排序的优先级队列）。

### 21.2 能做什么

- `schedule(task, delay, timeUnit)`：delay秒后执行一次任务
- `scheduleAtFixedRate(task, initialDelay, period, timeUnit)`：固定速率执行（上一个任务开始后period毫秒触发下一次）
- `scheduleWithFixedDelay(task, initialDelay, delay, timeUnit)`：固定间隔执行（上一个任务完成后delay毫秒开始下一个）

### 21.3 和定时任务框架的区别

定时调度线程池本身不支持cron表达式（如"每天凌晨2点"），它是**基于时间间隔**的调度，不是**基于日历时刻**的调度。如果需要cron表达式，通常配合Spring的 `@Scheduled` 注解使用，它底层用的也是 `ScheduledThreadPoolExecutor`。

## 二十二、工作窃取线程池：互相帮忙的厨师团队

### 22.1 传统线程池的问题

传统线程池（ThreadPoolExecutor）中，所有线程共享一个中央队列。任务在线程之间"推"：

```
        中央队列 [任务7][任务6][任务5][任务4]
         ↙        ↓        ↓        ↘
     线程1    线程2    线程3    线程4
```

当线程数很多、任务执行时间不均时，中央队列成为瓶颈——所有线程的出队/入队都要竞争同一把锁。

### 22.2 工作窃取的设计

工作窃取线程池（ForkJoinPool）为每个线程分配自己的双端队列：

```
  线程1队列 [任务A][任务B]    线程2队列 [任务C]    线程3队列 [ 空 ]
       ↑ 自己的任务                ↑ 自己的任务          ↑ 自己的队列空了
                                                         │
                                                     偷看别人的 ──→ 从线程1队列尾偷一个走
```

当线程3完成了自己的所有任务后，它不会闲着，而会去"偷"其他线程队列中的任务。为了减少竞争：
- 线程自己操作队列的头部（你用LIFO：最近的任务最容易偷）
- 窃取线程从队列的尾部偷（FIFO：偷最老的任务，减少竞争）

### 22.3 为什么叫"工作窃取"

这个名字来自一个精妙的观察：一个线程偷另一个线程的工作，表面上"不道德"，实际上让整个系统更高效——CPU核心不会闲着，总吞吐量更高。本质是自动负载均衡。

### 22.4 什么场景适合

- 递归分治算法（如归并排序、快速排序的并行版本）
- 任务可以被分解为大量小任务
- 每个子任务的执行时间差异大（需要窃取来均衡）

Java的并行流（`parallelStream()`）和 `CompletableFuture` 默认就在工作窃取线程池上运行。

# 第六部分：线程池与操作系统

## 二十三、线程在操作系统层面是什么

### 23.1 进程和线程的内存视角

先从内存视角看进程和线程的区别：

```
进程A的内存空间（4GB虚拟地址空间）
├── 代码段（.text）    ← 程序的机器指令
├── 数据段（.data）    ← 全局变量、静态变量
├── 堆（Heap）         ← new出来的对象都在这里，动态增长
├── 栈区
│   ├── 线程1的栈（1MB）
│   ├── 线程2的栈（1MB）
│   └── 线程3的栈（1MB）
└── 共享库映射区
```

所有线程共享代码段、数据段和堆（堆上的对象对所有人可见），但每个线程有自己的栈（存放局部变量和方法调用链）和程序计数器（存放当前执行到哪条指令）。

### 23.2 操作系统看到的线程

在Linux中，线程和进程在内核层面用的是同一种数据结构（`task_struct`）。创建线程的系统调用是 `clone()`，比创建进程的 `fork()` 更轻量，因为线程之间可以共享内存地址空间、文件描述符表等。

```
fork()：复制一份完整的地址空间 → 进程，开销大
clone(CLONE_VM | CLONE_FS | CLONE_FILES | ...)：共享大部分资源 → 线程，开销相对小
```

但即使是相对小的开销，每次创建线程仍然要走系统调用、分配内核数据结构、分配栈空间——这就是线程池要"复用"的根本原因——省掉的就是这些操作系统层面的开销。

## 二十四、用户线程与内核线程的关系

### 24.1 线程实现的三种模型

**模型一：一对一（1:1，内核线程模型）**

Java在Linux上的默认实现。每个Java线程直接对应一个操作系统内核线程。

```
Java线程1  ←→  内核线程1  ←→  CPU核心
Java线程2  ←→  内核线程2  ←→  CPU核心
Java线程3  ←→  内核线程3  ←→  CPU核心
```

- 优点：真正并行（多核同时执行），一个线程阻塞不影响其他线程
- 缺点：创建/销毁/切换都需要系统调用，开销较大，线程数受限于操作系统（通常上限几千到几万）

Java 21之前的平台线程就是这种模型。

**模型二：多对一（N:1，用户线程模型）**

多个用户态线程映射到一个内核线程。

```
用户线程1 ┐
用户线程2 ├→ 内核线程1  ←→  CPU核心
用户线程3 ┘
```

- 优点：轻量，用户态切换极快
- 缺点：一个线程阻塞（比如IO等待），所有用户线程都被阻塞，没法利用多核

老的"绿色线程"（Green Threads）是这种模型，Java早期版本用过，后来废弃了。

**模型三：多对多（M:N，混合线程模型）**

Java 21的虚拟线程就是这种模型：

```
虚拟线程1 ┐
虚拟线程2 ├→ 载波线程1（平台线程）
虚拟线程3 ┘
虚拟线程4 ┐
虚拟线程5 ├→ 载波线程2（平台线程）
虚拟线程6 ┘
       ...	        ←→ 操作系统内核线程 → CPU核心
虚拟线程N ──→ 载波线程M
```

M个虚拟线程被调度到N个平台线程（载波线程）上执行，N远小于M。虚拟线程的阻塞和唤醒在Java用户态完成，不涉及操作系统。

## 二十五、线程的状态转换图

### 25.1 Java线程的六种状态

```
                    ┌─────────┐
         创建线程 → │  NEW    │
                    └────┬────┘
                         │ start()
                         ▼
                    ┌─────────┐
         ┌─────────│RUNNABLE │←─────────┐
         │         └─┬──┬──┬─┘          │
         │     等待  │  │  │  阻塞      │
         │      锁  │  │  │  获取锁    │
         │         ▼  │  ▼            │
         │  ┌─────────┐│┌─────────┐   │
         │  │BLOCKED  │││WAITING  │   │
         │  └────┬────┘│└────┬────┘   │
         │       │      │     │       │
         │   获取到锁    │  notify/   │
         │       │      │  unpark    │
         │       ▼      │     │       │
         │  回到RUNNABLE←┘     │       │
         │                     ▼       │
         │              ┌─────────────┐│
         │              │TIMED_WAITING││
         │              └──────┬──────┘│
         │                 超时/通知    │
         │                     │       │
         │                     ▼       │
         │              回到RUNNABLE────┘
         │
         │  run()结束
         ▼
    ┌──────────┐
    │TERMINATED│
    └──────────┘
```

### 25.2 每种状态的直觉解释

| 状态 | 线程在干什么 | 是否消耗CPU | 线程池中的含义 |
|------|-------------|-----------|--------------|
| **NEW** | 刚创建，还没start() | 否 | 刚通过线程工厂创建 |
| **RUNNABLE** | 正在执行或在等待操作系统分配CPU | **是**（执行时）/ 否（等待调度时） | 正在处理任务 |
| **BLOCKED** | 在等待进入synchronized代码块 | 否 | 线程在竞争共享资源的锁 |
| **WAITING** | 无限期等待另一个线程的通知 | 否 | 空闲线程在队列上等待任务 |
| **TIMED_WAITING** | 限时等待（sleep/wait(timeout)） | 否 | keepAlive超时等待 |
| **TERMINATED** | 线程执行完毕，已终止 | 否 | 临时线程被回收后 |

### 25.3 线程池中线程的正常状态

在线程池中，空闲的核心线程通常会处于 **WAITING** 状态——它们调用了工作队列的 `take()` 方法，这是一个无限期阻塞操作，直到有任务入队时才被唤醒。

```
线程池繁忙时：
  Thread-1: RUNNABLE（正在执行业务代码）
  Thread-2: RUNNABLE（正在执行业务代码）
  Thread-3: RUNNABLE（正在执行业务代码）
  Thread-4: WAITING（空闲，在队列take()上等待）
  Thread-5: WAITING（空闲，在队列take()上等待）

线程池空闲时：
  Thread-1: WAITING
  Thread-2: WAITING
  Thread-3: WAITING
  Thread-4: WAITING
  Thread-5: WAITING
  （都在队列上等待任务，完全不消耗CPU）
```

## 二十六、什么是阻塞和非阻塞

### 26.1 阻塞的含义

在计算机中，"阻塞"（Blocking）指线程在等待某个条件满足时，**被操作系统挂起**，不再被调度到CPU上执行，直到那个条件满足后才被唤醒。

关键在于：**阻塞期间线程不消耗CPU**。这是好事也是坏事——好事是不浪费CPU，坏事是你不知道要等多久。

### 26.2 三种常见的阻塞原因

**IO阻塞**：最常见。读文件、发HTTP请求、查数据库——线程发出IO请求后，操作系统告诉它"数据还没准备好"，线程进入等待状态。数据到达后，硬件中断通知操作系统，操作系统再唤醒等待的线程。

```
应用线程：读取文件 → 发起read()系统调用
            ↓
操作系统：磁盘寻道...（线程进入WAITING状态，不占CPU）
            ↓ (几毫秒后)
操作系统：数据就绪，唤醒线程
            ↓
应用线程：拿到数据，继续执行
```

**锁阻塞**：当线程尝试获取一个被其他线程持有的锁（比如进入synchronized代码块），它必须等待锁被释放。线程进入BLOCKED状态。

**等待通知**：线程调用 `wait()` 或 `LockSupport.park()`，主动放弃CPU，等待另一个线程的 `notify()` 或 `unpark()` 来唤醒它。线程进入WAITING状态。

### 26.3 非阻塞的含义

"非阻塞"（Non-Blocking）指线程发起一个操作后，如果条件不满足（比如数据还没准备好、锁被其他人持有），**不等待，立即返回**。

比如：
- 非阻塞IO：读socket时如果没有数据可读，不阻塞等数据，而是立即返回0（表示没数据），线程可以去做别的事
- `tryLock()`：尝试获取锁，如果拿不到不等待，立即返回false

非阻塞的好处是线程永远不会被迫等待，可以持续做有用的事。代价是编程模型更复杂——你需要不断轮询"有数据了吗？锁能拿了吗？"

## 二十七、内存模型与线程安全的关系

### 27.1 为什么多线程会有数据问题

回到前面的概念：线程共享堆内存。这意味者线程A和线程B可能同时操作同一个对象。

一个经典的例子——计数器：

```
线程A：读取 count = 0
线程B：读取 count = 0
线程A：count = 0 + 1 → 写回 count = 1
线程B：count = 0 + 1 → 写回 count = 1（应该是2！）
```

这不是线程池特有的问题，而是所有多线程程序的共有问题。但线程池加剧了它——因为线程池中的线程反复复用，它们修改共享数据的概率更高。

### 27.2 什么是线程安全

"线程安全"（Thread-Safe）指：多个线程同时访问某个类或对象时，不管运行时环境如何调度这些线程，这个类始终能表现出正确的行为。

实现线程安全的三种基本策略：

1. **互斥（Mutual Exclusion）**：同一时刻只允许一个线程访问临界区，用锁（synchronized、ReentrantLock）实现
2. **不可变（Immutability）**：对象创建后状态永不改变，多线程随便读，没有任何写入冲突
3. **原子操作（Atomic）**：用CPU提供的原子指令（CAS，Compare-And-Swap）实现无锁并发，如 `AtomicInteger`

### 27.3 线程池特有的线程安全考虑

线程池复用线程会放大某些问题：

- **ThreadLocal残留**：线程A上次任务在ThreadLocal中设置了用户信息，任务结束忘记清除。线程A被复用来执行下一个任务时，下一个任务的代码可能读到上一个任务的用户信息。这既是内存泄漏也是数据错乱。
- **对象池的复用假设**：如果代码假设"每个线程有自己的某对象"（如DateFormat），可能会在线程数少时工作正常，线程池扩容后出现奇怪的并发问题。

# 第七部分：虚拟线程与未来

## 二十八、为什么传统线程"重"

### 28.1 传统线程的三个重量级来源

**重量来源一：栈内存（约1MB/线程）**

每个平台线程在创建时，操作系统为它分配一块栈内存（Linux默认约1MB）。1000个线程就是约1GB栈内存。这块内存在线程整个生命周期中一直占用，即使线程大部分时间在等待IO、栈几乎是空的。

**重量来源二：操作系统调度**

平台线程的调度由操作系统内核完成。每次上下文切换需要从用户态切换到内核态，再切回来——这个过程本身消耗CPU周期。而且操作系统调度器不知道Java应用的特点（比如哪些线程在等待数据库、哪些在做计算），只能"一刀切"地按时间片轮转。

**重量来源三：创建和销毁的系统调用开销**

创建一个平台线程需要操作系统分配内核数据结构、分配栈、注册到调度器——全部是系统调用。销毁时需要回收这些资源。高频创建/销毁的累积开销可观。

### 28.2 传统线程数为什么被限制在几千到几万

操作系统的线程实现决定了每个线程在内核中都有一个 `task_struct` 数据结构。Linux系统中，线程数受限于：
- `pid_max`：默认32768，即系统最多约32000个进程+线程
- 内存：每个线程1MB栈 × N个线程
- 调度器性能：调度器维护的运行队列随线程数增加而变慢

实际生产环境中，一个JVM实例通常不建议超过几千个平台线程。

## 二十九、虚拟线程的直觉理解

### 29.1 不用操作系统管理线程了

虚拟线程（Virtual Thread，Java 21引入）的核心思想是：**线程的调度不再由操作系统负责，而是由JVM自己管理**。

```
传统平台线程：
  Java代码 → 平台线程 → 操作系统内核线程 → CPU

虚拟线程：
  Java代码 → 虚拟线程 → JVM调度器 → 载波线程（少量平台线程）→ 操作系统内核线程 → CPU
```

虚拟线程的"挂载"和"卸载"完全在JVM内部完成（用户态），不涉及操作系统。当虚拟线程遇到阻塞操作时，JVM将它从载波线程上卸下来，载波线程立刻去执行另一个虚拟线程。等阻塞完成，JVM再把虚拟线程挂回某个载波线程继续执行。

这意味着：**你可以创建大量虚拟线程（数万、数十万甚至百万级），它们共享少量载波线程。线程切换的代价从"操作系统上下文切换"降低为"Java对象引用的交换"**。

### 29.2 为什么虚拟线程更轻

| 特性 | 平台线程 | 虚拟线程 |
|------|---------|---------|
| 栈内存 | 预先分配~1MB | 按需分配，存在堆中（可GC回收） |
| 创建时间 | ~1ms | ~1μs（快约1000倍） |
| 调度者 | 操作系统内核 | JVM（用户态） |
| 数量上限 | 几千~几万 | 数百万 |
| 阻塞行为 | 阻塞时占用整个平台线程 | 阻塞时释放载波线程给其他虚拟线程用 |

### 29.3 虚拟线程的本质：让IO等待不再成为瓶颈

回到前面的例子——Web服务器处理请求：

```
传统模式（1000个并发请求，100个平台线程）：
  请求1~100：各占一个线程，大部分时间在线程里等数据库
  请求101~1000：在队列里排队

虚拟线程模式（1000个并发请求）：
  1000个虚拟线程同时处理1000个请求
  底层可能只有8个载波线程
  当某个虚拟线程等数据库时，它被卸载，载波线程立即去执行另一个虚拟线程
  等数据库返回时，JVM再把它挂回某个空闲的载波线程
```

关键洞察：虚拟线程不提升单个任务的速度（数据库查询该多久还是多久），但它让系统**在大量并发IO操作时保持高吞吐量**——因为没有一个线程是"占着茅坑不拉屎"的。

## 三十、虚拟线程如何改变线程池的设计

### 30.1 线程池不再必要（对IO密集型任务）

虚拟线程最大的意义在于：**对于IO密集型任务，你不再需要线程池**。

传统做法：
```
定义一个线程池，精心计算corePoolSize和maxPoolSize
    ↓
任务太多 → 排队 → 队列满了 → 创建临时线程 → 都满了 → 拒绝
    ↓
需要监控、调优、防止OOM、防止拒绝风暴...
```

虚拟线程做法：
```java
// 直接为每个任务创建一个虚拟线程，不需要池！
var executor = Executors.newVirtualThreadPerTaskExecutor();

for (Request req : requests) {
    executor.submit(() -> handleRequest(req));
}
```

每个任务获得一个虚拟线程，任务结束虚拟线程自动销毁。不需要队列、不需要核心线程数、不需要拒绝策略——这些概念对虚拟线程没有意义，因为虚拟线程的创建几乎无成本。

### 30.2 仍需要控制并发上限

虽然不需要限制线程数了，但你仍然需要限制**对外部资源的并发访问量**。

虚拟线程让你可以创建100万个线程，但如果它们都去访问同一个数据库（连接池只有50个），那绝大多数线程还是在等。解决办法是用信号量（Semaphore）限制并发数：

```
Semaphore(500) → 限制最多500个虚拟线程同时访问数据库
```

这种模式从"池化线程"变成了"池化资源访问权限"——概念上更简洁，目的更明确。

### 30.3 什么场景仍需要传统线程池

即使在虚拟线程时代，传统线程池仍有价值：

- **CPU密集型任务**：计算量大的任务用虚拟线程没有优势，因为瓶颈在CPU核心数而非IO等待
- **需要线程局部性的场景**：有些优化依赖平台线程的ThreadLocal缓存
- **原生代码（JNI）**：调用C/C++代码时虚拟线程会被钉住（pinned），不能从载波线程卸载
- **JDK版本限制**：Java 17及以下不能用虚拟线程

### 30.4 未来的趋势

Java并发编程的范式正在从"池化稀缺资源（线程）"转向"以任务为中心"。

- **过去**：线程是稀缺资源 → 需要池化 → 需要精细配置 → 程序员负担重
- **现在**：虚拟线程几乎免费 → 每个任务一个线程 → 不需要池 → 程序员关注业务逻辑即可

就像垃圾回收（GC）从手动内存管理解放了程序员一样，虚拟线程正在从手动线程管理解放并发编程。线程池不会完全消失，但它的角色将从"一切并发问题的默认答案"退变为"特定场景的专用工具"。

| 概念 | 一句话解释 |
|------|-----------|
| 进程 | 操作系统分配资源的单位，一个运行中的程序 |
| 线程 | 进程中真正执行代码的单元，共享进程的内存空间 |
| CPU核心 | 能独立执行指令的物理单元 |
| 并发 | 同一时间段内多任务轮流推进 |
| 并行 | 同一时刻多任务真正同时执行 |
| 上下文切换 | CPU从一个线程切换到另一个线程时的状态保存和恢复过程 |
| 阻塞 | 线程等待某个条件，被操作系统挂起，不消耗CPU |
| 非阻塞 | 线程发现条件不满足时立即返回，不等待 |
| 线程池 | 预先创建一组线程反复使用，避免频繁创建销毁 |
| 核心线程 | 线程池维持的固定线程，长期存活 |
| 最大线程 | 线程池能创建的最大线程数量上限 |
| 工作队列 | 存放等待执行的任务的缓冲区 |
| 拒绝策略 | 线程池满载时处理新任务的方式 |
| 工作窃取 | 空闲线程从其他线程的队列中"偷"任务来执行 |
| 虚拟线程 | JVM管理的轻量线程，不需要操作系统调度 |
| 线程安全 | 多线程同时访问时仍能保持正确行为 |
