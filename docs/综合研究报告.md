## 二、方向一：Java 线程池调优体系

### 2.1 研究范围

全面覆盖 Java 并发编程中最核心的线程池技术栈，从基础原理到生产实战共 8 份深度文档：

| 序号 | 文档名称 | 核心内容 |
|:---:|:---------|:---------|
| 1 | 线程池原理与概念详解 | 线程池核心参数（corePoolSize、maxPoolSize、workQueue、RejectedExecutionHandler），ThreadPoolExecutor 源码级执行流程 |
| 2 | threadpool-ecosystem-research | Spring Boot 配置、动态线程池框架（Dynamic TP/Hippo4J）、微服务/消息中间件/响应式编程场景下的配置实践 |
| 3 | threadpool-fjp-virtual-research | ForkJoinPool 工作窃取算法深度剖析、Java 21+ Virtual Threads 迁移策略、Structured Concurrency |
| 4 | threadpool-monitoring-research | Micrometer/Prometheus 指标暴露、Spring Actuator 集成、动态调整、告警体系设计 |
| 5 | threadpool-queue-rejection-research | 5 种阻塞队列对比、4 种内置拒绝策略分析、自定义拒绝策略、优雅关闭最佳实践 |
| 6 | threadpool-sizing-research | CPU密集型 N+1、IO密集型 Brian Goetz 公式、带目标利用率公式、利特尔法则 |
| 7 | threadpool-tuning-practice-research | 全链路压测方法论、JProfiler/Async Profiler 工具链、真实案例调优 |
| 8 | 线程池调优完全指南 | 从理论公式到生产实战的完整知识体系，含 async-profiler/Arthas/ZGC 调优 |

### 2.2 关键结论

- **公式体系**：从 N+1 → Brian Goetz W/C 比值法 → 带目标 CPU 利用率的完整公式，层层递进适用于不同场景
- **FJP vs VT**：Java 21+ 虚拟线程在大规模 IO 密集型场景下可替代传统线程池，但 CPU 密集型仍需 ForkJoinPool
- **监控是前提**：没有监控的线程池就是生产环境的定时炸弹，Micrometer + Prometheus + Grafana 是标准方案
- **动态调优**：Hippo4J/Dynamic TP 等框架实现运行时参数调整，是解决"调优参数难以一次确定"的有效方案

## 三、方向二：LangChain4j Agent 编排设计模式

### 3.1 研究范围

对 LangChain4j（Java 生态最具影响力的 Agent 框架）进行系统性逆向分析，覆盖 7 个核心维度：

| 序号 | 文档名称 | 核心内容 |
|:---:|:---------|:---------|
| 1 | langchain-tool-system-analysis | BaseTool 继承链、Tool/StructuredTool 包装模式、Toolkit 聚合机制 |
| 2 | langchain-message-prompt-analysis | BaseMessage 体系、ChatPromptTemplate 组合、MessagePlaceholder 动态渲染 |
| 3 | langchain-runnable-engine-analysis | Runnable 接口设计、Pipe 操作符链式组合、Stream/Event 驱动机制 |
| 4 | langchain-v1-agent-middleware-analysis | V1 Agent 的 AgentExecutor 循环逻辑、中间件链、LLM 调用编排 |
| 5 | langchain-classic-agent-patterns-analysis | OpenAI Function Calling、ReAct、Plan-and-Execute、Multi-Agent 模式 |
| 6 | LangChain4j-Agent编排设计模式分析 | 四层分层架构（AiServices → Agentic → Core → SPI），JDK 动态代理机制 |
| 7 | langchain-agent-orchestration-master-report | 上述 6 篇的总报告，含 Agent 框架能力全景矩阵对比 |

### 3.2 关键结论

- **架构分层**：AiServices 声明式层（注解驱动）→ Agentic 编排层（Planner/Workflow）→ Core 核心原语层（Model/Tool/Memory）→ SPI 模型层
- **核心机制**：JDK 动态代理是 LangChain4j 与 Python LangChain 最根本的区别，编译器可静态验证类型安全
- **工具系统**：每个工具本身就是一个 Runnable，可通过 Pipe 操作符链式组合，ToolCall 标准化 LLM 交互
- **编排模式**：从简单 ReAct 到 Plan-and-Execute，再到 Multi-Agent 协作，复杂度逐步递增，需根据场景选择

## 四、方向三：Agent 封装与规划模式设计

### 4.1 研究范围

基于方向一、二的成果，完成 LyClaw 自身 Agent 框架的封装设计和规划模式创新：

| 序号 | 文档名称 | 核心内容 |
|:---:|:---------|:---------|
| 1 | agent封装思路计划 | Stage 管线（8 个阶段 13 个 SPI）、行业 Agent 框架能力全景对标、差异化创新（沙箱隔离、工具审批、双层拦截） |
| 2 | agent-planning-mode-design | 三种规划模式（ON/OFF/AUTO）、LLM 驱动的 DAG 规划引擎、前端实时进度展示 |
| 3 | proxy-agent-capability-integration | 代理模式（@Agent 注解）与编排管线的能力集成方案，沙箱/审批/安全审核的差异处理 |

### 4.2 关键结论

**Stage 管线架构**：
```
Request → ParseStage → SecurityCheckStage → PlanExecutionStage
→ ToolExecutionStage → ReflectionStage → RespondStage
```

**三种规划模式**：
| 模式 | 行为 | LLM 调用次数 | 适用场景 |
|:---:|:-----|:-----------:|:--------|
| **ON** | 永远先规划再 DAG 执行 | 2 次（规划+回复） | 复杂任务，多步推理 |
| **OFF** | 跳过规划直接 ReAct | 1 次（直接回复） | 简单对话、闲聊 |
| **AUTO** | 智能判断复杂度，动态切换 | 1~2 次 | 通用场景 |

**差异化创新**：
- 🛡️ **沙箱隔离**：工具执行在独立 Sandbox 中运行，与主进程资源隔离
- ✅ **工具审批**：支持人工审批流程，关键工具需批准后执行
- 🔄 **双层拦截**：Stage 级别全局拦截 + Hook 级别步骤级拦截
- 🧠 **DAG 规划**：LLM 动态生成 DAG，引擎按拓扑顺序并发执行节点

## 五、三大方向交叉分析

### 5.1 关联关系

```
方向一：线程池调优体系
    |
    +---> 为方向三 Agent 规划模式中的 DAG 并发执行提供线程池基础设施
    +---> 为方向二的 Runnable 引擎链式调用提供任务调度基础
    |
方向二：LangChain4j 编排设计模式
    |
    +---> 为方向三的 Stage 管线架构提供设计参考（AiServices -> Agentic 层映射）
    +---> 工具系统设计直接指导 LyClaw 的 ToolRegistry 实现
    |
方向三：Agent 封装与规划模式设计
    |
    +---> 落地实现：将方向一（线程池）和方向二（编排模式）整合为可运行的 Agent 框架
```

### 5.2 技术选型建议

| 能力维度 | 推荐方案 | 来源方向 |
|:---------|:---------|:--------:|
| 线程池管理 | Dynamic TP + Virtual Threads | 方向一 |
| Agent 声明式接口 | JDK 动态代理（参考 LangChain4j） | 方向二 |
| 任务规划 | DAG 拓扑排序 + 三种模式（ON/OFF/AUTO） | 方向三 |
| 工具执行 | ToolRegistry + Sandbox 隔离 | 方向三 |
| 监控告警 | Micrometer + Prometheus + Grafana | 方向一 |
