## 1. 当前记忆架构诊断

### 1.1 现状总览

当前 LyClaw 的记忆系统由以下组件构成：

```
TieredMemorySystem (唯一实现)
  ├── 4个 ConcurrentHashMap 存储器
  │     ├── perceptionStore   (SENSORY层)
  │     ├── shortTermStore    (SHORT_TERM层)
  │     ├── longTermStore     (LONG_TERM层)
  │     └── entityStore       (ENTITY层)
  │
  ├── HybridMemoryRetriever (检索器)
  │     ├── InMemoryVectorStore (暴力余弦相似度)
  │     ├── BM25 关键词评分 (Okapi BM25)
  │     └── 时间衰减 + 重要性评分
  │
  ├── SimpleEmbeddingModel (SHA-256伪随机, 768维)
  ├── DefaultMemoryConsolidator (Jaccard去重 + Union-Find合并)
  ├── DefaultMemoryJanitor (去重+冲突解决+过期清理, 有已知Bug)
  └── LLMMemoryExtractor (纯正则, 7种模式)
```

### 1.2 十大问题清单

#### 问题1：全内存存储，无持久化

四个 `ConcurrentHashMap` 存储全部记忆数据。服务重启后所有记忆丢失。
短期记忆丢失可以接受，但长期记忆和实体记忆是本应持久化的知识资产。
虽然有 `MemoryPersistence` 和 `MemoryWriteState` 接口定义了"写前评估"模式，
但 `TieredMemorySystem` 完全没有调用它们。持久化链路是断的。

#### 问题2：嵌入模型无语义

`SimpleEmbeddingModel` 用 SHA-256 哈希作为随机种子生成 768 维伪随机向量。
同一个文本每次产生相同向量（确定性），但不同文本之间的向量距离是随机的——
"猫"和"狗"的余弦相似度与"猫"和"汽车"一样，完全不具备语义表征能力。
这导致向量检索退化成了随机排序，BM25 关键词匹配成了唯一有效的检索路径。

#### 问题3：无真实向量数据库

`InMemoryVectorStore` 用 `ConcurrentHashMap` + 暴力遍历 + 优先队列做 top-K。
对 1000 条记忆做一次检索需要遍历全部 1000 × 768 = 76.8 万次浮点乘法。
当记忆增长到 10 万条时，每次检索将计算 7680 万次乘法，延迟不可接受。

#### 问题4：无知识库概念

没有文档上传、解析、分块（chunking）能力。用户无法将自己的
PDF、Markdown、代码文件导入为可检索的知识库。没有文档级别的管理
（按知识库分类、按文档查询、按分块溯源）。

#### 问题5：无知识图谱

`@GraphStore` 注解、`GraphQueryLanguage` 枚举、`StorageCapability.GRAPH`
都存在，但零实现。`EntityMemory` 模型虽然设计了 `EntityRelation` 内嵌类，
但在 `TieredMemorySystem` 中仅做平面 key-value 存储，没有图遍历、
多跳推理、关系权重计算。

#### 问题6：检索能力弱

`ContextBuildStage` 在管道中仅用 `queryText` + `topK=10` 调检索，
不使用 `MemoryQuery` 的 `layerFilter`、`categoryFilter`、`tagFilter`、
`metadataFilter` 等丰富的过滤能力。嵌入为空时退化到按创建时间排序。
没有重排序（reranking）步骤。

#### 问题7：MemoryStrategy 无实现

`MemoryStrategy` 接口定义了 `formatForContext`、`shouldIncludeInContext`、
`getPriority` 三个方法，但整个代码库中零实现。记忆如何注入 LLM 上下文
完全依赖 `ContextBuilder` 的临时逻辑，没有可插拔的策略体系。

#### 问题8：FusionRanker 无独立实现

`FusionRanker` 接口存在，但其逻辑直接硬编码在 `HybridMemoryRetriever.retrieve()`
中。无法替换为 Reciprocal Rank Fusion (RRF) 或其他融合算法。

#### 问题9：Consolidation 绕过接口

`TieredMemorySystem.consolidate()` 直接遍历 STM Map、按阈值筛选、调用
`commitLongTerm()`。完全不使用 `MemoryConsolidator` 接口。
`DefaultMemoryConsolidator` 通过独立的 Union-Find 流程工作，
两套逻辑并存但不互通。

#### 问题10：无异步事件驱动

`MemoryConsolidatedEvent` 已定义，但 consolidation 是同步 REST 调用触发。
没有定时自动 consolidatioon、没有事件驱动的级联更新（例如新事实
加入知识图谱）、没有异步的 janitor 清理。

### 1.3 可保留的设计资产

尽管有以上问题，现有架构中以下设计是正确且应保留的：

- **四层记忆模型** (SENSORY → SHORT_TERM → LONG_TERM → ENTITY)：
  层次分明，符合认知科学中的人类记忆模型
- **MemorySystem 接口**：完整的生命周期定义，方法签名合理
- **MemoryQuery 参数体系**：包含向量、文本、过滤、权重等全部检索要素
- **注解驱动的存储后端注册**：`@StorageBackend` + `@VectorStore` + `@GraphStore`
  的 BeanPostProcessor 自动发现机制设计优雅
- **StorageFacade 抽象层**：统一的 `put/get/query/searchSimilar` 接口
- **DeferredRegistrar 三阶段收集模式**：collect → filter → register
- **HybridMemoryRetriever 的多路评分框架**：向量 + BM25 + 时间 + 重要性
  的线性加权思路正确，只是缺乏真实嵌入和高效向量存储

## 2. 架构 2.0 全景

### 2.1 设计原则

1. **接口兼容优先**：不改 `MemorySystem` 接口签名，新增实现类
2. **渐进式增强**：每个组件都有轻量级默认实现（不依赖外部服务）和
   生产级实现（连接真实向量数据库/图数据库/嵌入服务）
3. **管道可组合**：每个处理阶段（解析→分块→嵌入→索引→检索→重排序→注入）
   都是可独立替换的组件
4. **存储分层**：热数据（向量）进专用向量库，温数据（元数据）进 MySQL，
   冷数据（原始文档）进对象存储，超热数据（频繁访问的嵌入）进 Redis 缓存
5. **异步优先**：所有写操作（ingest、index、consolidate）异步化，
   读操作（retrieve）保持同步以满足聊天 pipeline 的低延迟要求

## 3. 核心组件设计

### 3.1 PersistentMemorySystem（新主实现）

这是架构 2.0 的核心——替代 `TieredMemorySystem` 的持久化四层记忆系统。
它实现完全相同的 `MemorySystem` 接口，但底层委托给持久化存储。

```
PersistentMemorySystem implements MemorySystem
│
├── 委托: StorageFacade
│     ├── SENSORY   → Redis (TTL=1h)     // 感知记忆：超短生命周期，高频写入
│     ├── SHORT_TERM→ Redis (TTL=24h)    // 短期记忆：会话级，过期自动清理
│     ├── LONG_TERM → MySQL + 向量库      // 长期记忆：持久化 + 向量索引
│     └── ENTITY    → 图数据库 + MySQL    // 实体记忆：关系存储 + 元数据
│
├── 索引: VectorStore
│     └── LONG_TERM 和 ENTITY 层自动同步到向量库
│
├── 事件: ApplicationEventPublisher
│     ├── MemoryIngestedEvent   → 触发异步嵌入计算
│     ├── MemoryConsolidatedEvent → 触发知识图谱更新
│     └── MemoryExpiredEvent    → 触发级联清理
│
└── 缓存: Redis
      ├── embedding_cache:{hash}  → 缓存高频嵌入向量 (TTL=1h)
      └── ltm_index:{userId}      → 长期记忆索引缓存 (TTL=5min, 写入时失效)
```

**关键方法实现策略：**

- `ingestPerception(sessionId, data)`:
  写入 Redis SENSORY 层（TTL=1h），发布 `MemoryIngestedEvent`，
  异步触发 LLMMemoryExtractor 或 LLMDrivenExtractor 从对话中提取结构化记忆

- `storeShortTerm(sessionId, entry)`:
  写入 Redis SHORT_TERM 层（TTL=24h），关联 sessionId，

- `commitLongTerm(entry)`:
  1. 计算嵌入（EmbeddingModel）
  2. 写入 MySQL `lyclaw_memory_entries` 表（元数据）
  3. 写入 VectorStore（向量索引）
  4. 更新 Redis 索引缓存（写入时失效）
  5. 如果 `entry.category == RELATION` 或 `entityType != null`，
     异步更新知识图谱

- `retrieve(query)`:
  委托给 HybridRetrievalEngine，详见第9章

- `consolidate(userId, policy)`:
  委托给 MemoryConsolidator 实现，详见第10章

## 4. 嵌入服务层

### 4.1 设计目标

- 统一接口（复用现有 `EmbeddingModel` 接口）
- 支持多种嵌入源：本地 ONNX、OpenAI API、HuggingFace、自定义服务
- 内置缓存层（Redis）减少重复计算
- 支持批量嵌入提升吞吐
- 自动检测维度并校验与向量存储的一致性

### 4.2 嵌入源实现矩阵

```
EmbeddingModel (现有接口，不变)
│
├── SimpleEmbeddingModel (保留, @DevelopmentOnly)
│     └── 维度: 768, 用途: 开发/测试，不影响任何生产行为
│
├── OpenAiEmbeddingModel (新增)
│     ├── 模型: text-embedding-3-small (1536维) / text-embedding-3-large (3072维)
│     ├── 调用: OpenAI REST API
│     ├── 批量: 支持 batch embedding (最多2048条/批次)
│     └── 重试: 指数退避, 最多3次
│
├── LocalOnnxEmbeddingModel (新增, 推荐默认)
│     ├── 模型: BGE-M3 (1024维) / BGE-Large-ZH (1024维) / all-MiniLM-L6-v2 (384维)
│     ├── 推理: ONNX Runtime, 本地CPU/GPU
│     ├── 优点: 零网络延迟, 无API费用, 数据不出域
│     └── 预热: 启动时加载模型到内存 (JNI or Process调用)
│
├── HuggingFaceEmbeddingModel (新增)
│     ├── 模型: 任意 sentence-transformers 兼容模型
│     ├── 调用: HuggingFace Inference API 或自建 TEI (Text Embeddings Inference)
│     └── 优点: 模型选择丰富，社区活跃
│
└── CachedEmbeddingModel (新增, 装饰器模式)
      └── 包装任意 EmbeddingModel，添加 Redis 缓存层
          键: embed:{model}:{sha256(text)}
          值: float[] 序列化后的Base64
          TTL: 1h (高频文本自动续期)
```

### 4.3 嵌入缓存设计

```
请求流:
  ① embed("今天天气真好")
  ② SHA-256 → "a1b2c3..."
  ③ 查 Redis: embed:bge-m3:a1b2c3...
  ④ 命中 → 返回 Base64解码 → float[]
  ⑤ 未命中 → 调真实EmbeddingModel → 写Redis → 返回

缓存策略:
  - TTL=1h, 每次命中的key TTL刷新为1h (LRU近似)
  - 批量嵌入: pipeline批量查Redis → 仅未命中的调真实模型 → 批量写回
  - 预热: 启动时可选加载常用查询的嵌入(从MySQL warmup表)
```

### 4.4 嵌入质量保障

```yaml
# 嵌入质量度量
- 向量归一化: 所有嵌入统一L2归一化
- 维度校验: EmbeddingModel.getDimension() 必须匹配 VectorStore 期望维度
- 空文本处理: 空字符串返回零向量(记录警告日志)
- 超长文本: 超过模型max_token的文本自动截断(记录截断日志)
- 延迟监控: Micrometer Timer 记录每次嵌入耗时
```

## 5. 向量存储层

### 5.1 设计目标

- 复用现有 `VectorStore` 接口（`store/search/delete`）
- 支持多种向量数据库后端，通过 `@VectorStore` 注解自动注册
- 支持元数据过滤（metadata filter）在向量搜索时缩小范围
- 支持混合搜索（向量 + 标量过滤 + 全文）
- 内置连接池管理和健康检查

### 5.2 向量数据库选型矩阵

```
                     Milvus      Qdrant      pgvector     RedisSearch   InMemory
                     (分布式)     (单机/集群)  (PostgreSQL) (Redis模块)   (开发)
──────────────────────────────────────────────────────────────────────────────
部署复杂度             高           低          低(已有PG)    中           零
搜索性能(百万级)       ★★★★★       ★★★★        ★★★          ★★★         ★(不可用)
元数据过滤             完善         完善         SQL WHERE     有限         手动遍历
混合搜索               原生支持     原生支持     需手动拼SQL   有限支持     手动实现
磁盘索引               IVF/HNSW    HNSW         IVFFlat/HNSW  HNSW        无

```

**推荐路径：**

- **开发/测试**：InMemoryVectorStore（保留，只用于单元测试和快速原型）
- **中小规模（<100万向量）**：pgvector（复用 lyclaw-storage-jdbc 的 PostgreSQL 连接，零额外部署）
- **大规模（>100万向量）**：Milvus 或 Qdrant 独立部署
- **超大规模（>1000万向量）**：Milvus 分布式集群

### 5.3 统一向量存储抽象

虽然 `VectorStore` 接口已存在，但需要扩展以支持生产级向量数据库的
高级特性。这里采用**适配器模式**——在现有接口基础上，通过内部扩展接口
提供高级能力，下游实现按需支持：

```
VectorStore (现有SPI接口，不改)
  ├── store(id, vector, metadata)
  ├── search(queryVector, topK)
  ├── delete(id)
  └── getCollectionName()

VectorStoreAdvanced (内部扩展接口，各后端按需实现)
  ├── search(QuerySpec)              → 带元数据过滤的搜索
  ├── searchHybrid(QuerySpec)        → 向量+全文混合搜索
  ├── batchStore(List<VectorEntry>)  → 批量写入
  ├── batchDelete(List<String> ids)  → 批量删除
  ├── createIndex(IndexConfig)       → 创建向量索引
  ├── getStats()                     → 获取存储统计
  └── healthCheck()                  → 健康检查

各后端实现：
  MilvusVectorStore      implements VectorStore, VectorStoreAdvanced
  QdrantVectorStore      implements VectorStore, VectorStoreAdvanced
  PgVectorStore          implements VectorStore, VectorStoreAdvanced
  RedisVectorStore       implements VectorStore, VectorStoreAdvanced
  InMemoryVectorStore    implements VectorStore  (仅基础功能)
```

### 5.4 PgVectorStore 设计（推荐首选）

pgvector 是 PostgreSQL 的向量扩展，在本项目中可复用 `lyclaw-storage-jdbc`
模块的数据库连接（未来切换到 MySQL 时用 Milvus/Qdrant）。

```sql
-- 启用 pgvector 扩展
CREATE EXTENSION IF NOT EXISTS vector;

-- 向量存储表（通用，不限于记忆）
CREATE TABLE vector_embeddings (
    id            VARCHAR(64)   PRIMARY KEY,
    collection    VARCHAR(128)  NOT NULL   COMMENT '集合名如 memory_ltm, kb_docs',
    vector        VECTOR(1024)  NOT NULL   COMMENT 'BGE-M3默认1024维',
    content_hash  VARCHAR(64)   NOT NULL   COMMENT '原文本SHA-256(去重用)',
    metadata      JSONB         DEFAULT '{}',
    created_at    TIMESTAMPTZ   DEFAULT NOW(),
    updated_at    TIMESTAMPTZ   DEFAULT NOW()
);

-- HNSW索引 (高召回 + 高性能)
-- m=16 连接数, ef_construction=200 构建时的搜索深度
CREATE INDEX idx_vector_ltm ON vector_embeddings
    USING hnsw (vector vector_cosine_ops)
    WITH (m = 16, ef_construction = 200)
    WHERE collection = 'memory_ltm';

-- 元数据过滤索引
CREATE INDEX idx_vector_collection ON vector_embeddings (collection);
CREATE INDEX idx_vector_metadata ON vector_embeddings USING GIN (metadata);
```

**PgVectorStore 搜索实现：**

```sql
-- 向量搜索 + 元数据过滤
SELECT id, metadata,
       1 - (vector <=> :queryVector::vector) AS similarity
FROM vector_embeddings
WHERE collection = 'memory_ltm'
  AND metadata->>'userId' = :userId
  AND (metadata->>'category' IS NULL OR metadata->>'category' = :category)
ORDER BY vector <=> :queryVector::vector
LIMIT :topK;
```

### 5.5 向量索引策略

```
集合命名规范:
  memory_ltm:{userId}       → 用户的长期记忆 (按userId分区)
  memory_entity              → 实体记忆 (全局)
  kb:{kbId}                  → 知识库文档分块
  graph_entity:{entityType}  → 图谱实体嵌入

索引构建策略:
  - 初始: 无索引，暴力搜索 (适合 <1万 向量)
  - 1万~10万: 自动构建 IVFFlat 索引
  - >10万: 自动构建 HNSW 索引
  - 触发: 每次 INSERT 后检查行数，超过阈值自动创建索引

索引参数调优 (HNSW):
  - m=16: 每个节点的最大连接数 (精度 vs 构建速度)
  - ef_construction=200: 构建时的搜索深度 (精度 vs 构建时间)
  - ef_search=100: 查询时的搜索深度 (精度 vs 查询延迟)
```

## 6. 文档处理管道 (RAG)

### 6.1 RAG 管道总览

这是记忆架构 2.0 的核心新增能力——将任意文档转化为可检索的知识。

```
                         RAG 文档处理管道
                         ═══════════════

  用户上传文档
      │
      ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Stage 0: DocumentParser (文档解析)                               │
  │                                                                  │
  │  PDF → Apache PDFBox         → 提取文本 + 表格 + 图片描述         │
  │  DOCX → Apache POI           → 提取文本 + 样式                   │
  │  Markdown → CommonMark       → 提取文本 + 保留代码块              │
  │  HTML → Jsoup                → 提取纯文本 + 保留链接文本          │
  │  TXT → 直接读取              → 编码检测 + 分行                    │
  │  Code → TreeSitter           → AST解析 + 保留函数签名             │
  │                                                                  │
  │  输出: ParsedDocument { rawText, metadata, sections[], images[] }│
  └───────────────────────────────┬─────────────────────────────────┘
                                  │
                                  ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Stage 1: ChunkingStrategy (分块策略)                              │
  │                                                                  │
  │  ① FixedSizeChunking:      固定大小 (默认512 tokens, 重叠64)     │
  │  ② SentenceChunking:       按句子边界分割 (NLP分句)              │
  │  ③ SemanticChunking:       按语义相似度断点分割                   │
  │  ④ RecursiveChunking:      按\n\n→\n→。→. 递归尝试               │
  │  ⑤ MarkdownAwareChunking:  按H1/H2/H3标题层级分割                │
  │  ⑥ CodeAwareChunking:      按函数/类边界分割                     │
  │                                                                  │
  │  Chunk元数据:                                                     │
  │    - chunkIndex: 在原文档中的序号                                  │
  │    - startOffset/endOffset: 在原文档中的字符偏移                   │
  │    - sectionTitle: 所属章节标题 (Markdown)                         │
  │    - prevChunkId/nextChunkId: 相邻分块引用 (上下文扩展用)          │
  │    - tokenCount: Token数量估算                                     │
  └───────────────────────────────┬─────────────────────────────────┘
                                  │
                                  ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Stage 2: EmbeddingPipeline (嵌入计算)                             │
  │                                                                  │
  │  ① 计算每个分块的向量嵌入                                         │
  │  ② 计算标题的嵌入 (用于章节级检索)                                 │
  │  ③ 可选: 计算文档级摘要嵌入 (ColBERT风格的后期交互可替代)         │
  │                                                                  │
  │  批量处理: 每批次最多100个分块, 调 batchEmbed()                   │
  │  并发控制: 限制并发嵌入请求数 (默认4并发)                          │
  └───────────────────────────────┬─────────────────────────────────┘
                                  │
                                  ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Stage 3: IndexingPipeline (索引写入)                              │
  │                                                                  │
  │  ① VectorStore.batchStore()     → 向量索引 (HNSW/IVF)            │
  │  ② MySQL INSERT (分块元数据)     → lyclaw_document_chunks         │
  │  ③ MySQL INSERT (文档元数据)     → lyclaw_documents               │
  │  ④ 可选: BM25索引更新            → lyclaw_kb_bm25_index           │
  │                                                                  │
  │  事务保证:                                                        │
  │    向量写入和MySQL写入不在同一事务(不同系统)，策略:                │
  │    - 先写MySQL (元数据), 成功后再写VectorStore                       │
  │    - 向量写入失败 → 标记chunk状态为 INDEX_FAILED → 定时重试          │
  │    - 查询时过滤掉 INDEX_FAILED 状态的chunk                         │
  └───────────────────────────────┬─────────────────────────────────┘
                                  │
                                  ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ Stage 4: PostProcessHook (后处理钩子)                             │
  │                                                                  │
  │  ① 实体提取: 从文档内容中提取实体 → 自动录入知识图谱                │
  │  ② 摘要生成: LLM生成文档摘要 → 存入 lyclaw_documents.summary       │
  │  ③ 关键词提取: 提取文档关键词 → 存入 tags 字段                     │
  │  ④ 关系发现: 新文档实体与已有实体的关系 → 自动创建图关系            │
  └─────────────────────────────────────────────────────────────────┘
```

### 6.2 分块策略详解

分块是 RAG 质量的最关键环节。分块太大→检索精度下降（噪音多），
分块太小→上下文不完整（语义断裂）。

```
策略选择逻辑:

  IF 文档类型 == code AND 语言已支持:
    → CodeAwareChunking (按AST边界)
  ELSE IF 文档类型 == markdown AND 有标题:
    → MarkdownAwareChunking (按标题层级)
  ELSE IF 文档语言 == 中文:
    → SentenceChunking (按中文标点分句)
  ELSE IF 文档语言 == 英文:
    → RecursiveChunking (按\n\n → \n → . →  )
  ELSE:
    → FixedSizeChunking (512 tokens, 64 overlap)

RecursiveChunking 工作流程:
  目标大小: 512 tokens (~1500中文字符 / ~2000英文字符)
  
  ① 尝试按 "\n\n" 分割
  ② 如果某段 > 512 tokens → 按 "\n" 再分割
  ③ 如果某段 > 512 tokens → 按 "。" 或 "." 分割
  ④ 如果某段 > 512 tokens → 按 " " (空格) 分割
  ⑤ 最终手段: 强制按字符截断 (保证不超过 1024 tokens)

  相邻分块保留 64 tokens 重叠 → 防止关键信息落在边界

CodeAwareChunking 工作流程:
  ① TreeSitter 解析为 AST
  ② 定位 function_definition / class_definition 节点
  ③ 每个函数/类的源码作为一个分块
  ④ 如果单个函数超过 1024 tokens → 拆分为多个分块 (标记为函数片段)
  ⑤ 分块元数据包含: 函数名、类名、文件路径、行号范围
```

### 6.3 检索时的小窗口→大窗口策略

RAG 检索的一个常见问题是：向量检索返回的是独立的分块，
但用户的问题可能需要查看分块前后的上下文。解决方案：

```
检索增强流程 (小窗口 → 大窗口):

① 粗排: 向量检索获取 topK=20 个分块
   (小窗口: 每个分块 512 tokens)

② 上下文扩展: 对每个候选分块，拉取其前后各 1 个分块
   (chunk.prevChunkId, chunk.nextChunkId 已在分块时写入)
   
③ 合并重叠分块: 相邻分块合并为更大的文本块
   (大窗口: 合并后约 1500 tokens)

④ 精排: 用 Cross-Encoder 对大窗口文本重排序

⑤ 注入: 将 Top-3 大窗口文本 + 用户问题 送入 LLM
```

## 7. 知识库系统

### 7.1 知识库模型

```
知识库 (KnowledgeBase)
  ├── kbId:          "kb_" + ULID
  ├── name:          "技术文档库"
  ├── description:   "公司内部技术文档"
  ├── ownerId:       所属用户(或个人)
  ├── visibility:    PRIVATE / SHARED / PUBLIC
  ├── documentCount:  文档数量(反范式)
  ├── totalChunks:   总分块数
  ├── embeddingModel: 使用的嵌入模型
  ├── chunkStrategy: 默认分块策略
  └── tags:          分类标签

文档 (KnowledgeDocument)
  ├── docId:         "doc_" + ULID
  ├── kbId:          所属知识库
  ├── fileName:      原始文件名
  ├── fileType:      PDF/DOCX/MD/TXT/CODE
  ├── fileSize:      文件大小(bytes)
  ├── fileHash:      SHA-256 (去重检测)
  ├── status:        PROCESSING / INDEXED / INDEX_FAILED / DELETED
  ├── summary:       LLM生成的摘要
  ├── metadata:      自定义元数据JSON
  ├── chunkCount:    分块数
  └── createdAt/updatedAt

分块 (DocumentChunk)
  ├── chunkId:       "chk_" + ULID
  ├── docId:         所属文档
  ├── kbId:          所属知识库(反范式，加速过滤)
  ├── chunkIndex:    序号
  ├── content:       分块文本
  ├── embedding:     向量 (同时存在于VectorStore)
  ├── prevChunkId / nextChunkId:  上下文链接
  ├── sectionTitle:  章节标题
  ├── tokenCount:    Token数估算
  ├── startOffset/endOffset: 字符偏移
  └── metadata:      自定义元数据
```

### 7.2 知识库操作

```
创建知识库:
  ① POST /api/knowledge-bases
     请求: { name, description, embeddingModel?, chunkStrategy?, visibility }
  ② 创建知识库记录 → MySQL
  ③ 在 VectorStore 中创建集合 kb:{kbId}
  ④ 返回 KnowledgeBase 对象

上传文档:
  ① POST /api/knowledge-bases/{kbId}/documents
     请求: multipart/form-data (文件)
  ② 计算文件SHA-256，检查去重(同知识库内)
  ③ 创建 Document 记录 (status=PROCESSING)
  ④ 异步提交 RAG处理任务 (EventBus)
  ⑤ 返回 Document 对象 (status=PROCESSING)
  
  异步处理:
    ⑥ DocumentParser 解析 → ChunkingStrategy 分块
    ⑦ EmbeddingModel 计算嵌入 → VectorStore 写入
    ⑧ MySQL 写入分块元数据
    ⑨ 更新 Document.status = INDEXED
    ⑩ 发布 KnowledgeBaseUpdatedEvent

检索知识库:
  ① POST /api/knowledge-bases/{kbId}/search
     请求: { query, topK=5, rerankEnabled=true }
  ② 计算查询嵌入
  ③ VectorStore.search(embedding, topK * 2, filter: {kbId})
  ④ 小窗口→大窗口上下文扩展
  ⑤ Cross-Encoder 重排序 (topK * 2 → topK)
  ⑥ 返回 List<SearchResult> (含content + score + 源文档信息)

删除文档:
  ① DELETE /api/knowledge-bases/{kbId}/documents/{docId}
  ② 标记 Document.status = DELETED
  ③ 异步: VectorStore.batchDelete(chunkIds)
  ④ 异步: MySQL DELETE chunks
  ⑤ 更新 KnowledgeBase.documentCount/chunkCount
```

### 7.3 知识库与对话记忆的融合检索

在聊天 pipeline 中，用户的问题应同时从"对话记忆"和"知识库"两个来源检索：

```
ContextBuildStage (改造后):

  ① 接收用户最后一条消息
  ② 同时发起两个异步检索:
     a. MemoryFeignClient.retrieve(query)   → 查对话记忆
     b. KnowledgeBaseFeignClient.searchAllUserKBs(query, topK=5) → 查知识库
  ③ 合并结果:
     - 对话记忆: 标记 sourceType=MEMORY, 优先级=0.8
     - 知识库文档: 标记 sourceType=KB_DOC, 优先级=1.0 (权威性更高)
     - 知识图谱: 标记 sourceType=GRAPH_ENTITY, 优先级=0.9
  ④ 按 (relevanceScore * sourcePriority) 综合排序
  ⑤ 取 topK=10 注入 ChatContext.memory
  ⑥ 格式化: MemoryStrategy.formatForContext() → 注入LLM system prompt
```

### 8.3 图模型设计

实体在图中以节点表示，关系以有向边表示：

节点类型 (EntityNode):

  User          (用户)
    属性: userId, username, displayName

  Person        (人物 - 从对话/文档中提取)
    属性: entityId, name, aliases[], description, properties{}

  Organization  (组织)
    属性: entityId, name, industry, description

  Location      (地点)
    属性: entityId, name, type(city/country/building/...), coordinates

  Concept       (概念 - 抽象知识)
    属性: entityId, name, definition, category

  Document      (文档 - 知识库文档)
    属性: docId, title, summary, fileType

  Event         (事件)
    属性: entityId, name, date, description

  Task          (任务)
    属性: entityId, name, status, priority, deadline


关系类型 (EntityRelation):

  KNOWS(person→person)          权重: 0.8  属性: context, since
  WORKS_AT(person→org)          权重: 1.0  属性: role, since
  LOCATED_IN(entity→location)   权重: 1.0  属性: since
  RELATED_TO(concept→concept)   权重: 0.6  属性: relationType
  MENTIONED_IN(entity→doc)      权重: 0.5  属性: count, firstAt
  PARTICIPATED_IN(person→event) 权重: 0.9  属性: role
  DEPENDS_ON(task→task)         权重: 1.0  属性: critical
  PARENT_OF(concept→concept)    权重: 1.0  属性: level
  CREATED_BY(entity→user)       权重: 1.0  属性: timestamp
  EXTRACTED_FROM(entity→conversation) 权重: 0.7  属性: sessionId
```

### 8.4 图检索器 (GraphRetriever)

```
GraphRetriever implements MemoryRetriever

检索策略:

① 实体链接 (Entity Linking):
   从用户查询中提取实体提及 (基于精确匹配 + 嵌入相似度)
   → 定位到图中的实体节点

② 一跳检索:
   找到实体节点 → 返回所有直接关联的邻居节点
   示例: "张三" → 返回 ["腾讯"(WORKS_AT), "北京"(LOCATED_IN), "李四"(KNOWS)]

③ 多跳检索 (graphTraversalDepth >= 2):
   从起始实体开始，BFS遍历指定深度
   每个路径计算累积权重 = Π(各边权重)
   返回累积权重 > 阈值的路径

④ 子图摘要:
   对检索到的子图，用LLM生成自然语言摘要
   示例: "张三在腾讯工作(角色:工程师)，居住在北京，认识李四..."

⑤ 注入LLM上下文:
   子图摘要 + 关键实体属性 → 格式化 → 注入system prompt
```

### 8.5 实体自动提取与更新

```
触发时机:
  - 新长期记忆形成 (consolidation 后)
  - 新文档索引完成 (RAG管道 Stage 4)
  - 用户手动创建实体

实体提取流程 (LLMDrivenExtractor):

  ① 输入: 文本内容 (对话摘要 / 文档内容)
  ② LLM Prompt:
     "从以下文本中提取实体和关系，以JSON格式输出:
      {
        entities: [{type, name, description, properties}],
        relations: [{source, relationType, target, weight, context}]
      }
      已知实体列表: [...], 优先关联已知实体"
  ③ 解析LLM输出的JSON
  ④ 去重: 新实体与已知实体做嵌入相似度匹配 (>0.85 → 合并)
  ⑤ 写入图数据库 (MERGE 操作，避免重复创建)
  ⑥ 更新实体嵌入向量 (实体name + description的嵌入)
```

## 9. 混合检索引擎

### 9.1 总览

`HybridRetrievalEngine` 是架构 2.0 的检索核心，替代当前的
`HybridMemoryRetriever`。它协调多路检索器、融合排名、和重排序。

### 9.2 多路检索器

```
检索请求: MemoryQuery
│
├── 路径1: VectorRetriever
│     来源: VectorStore (Milvus/Qdrant/pgvector)
│     算法: 余弦相似度 / 内积
│     特点: 语义匹配，模糊查询
│     返回: topK=query.topK * 2 (给融合留余量)
│
├── 路径2: BM25Retriever / FullTextRetriever
│     来源: MySQL (全文索引) 或 Elasticsearch
│     算法: BM25 / TF-IDF / Inverted Index
│     特点: 关键词精确匹配，中文分词
│     返回: topK=query.topK * 2
│
├── 路径3: GraphRetriever
│     来源: GraphStore (Neo4j/NebulaGraph)
│     算法: BFS图遍历 + PageRank/Personalized PageRank
│     特点: 精确关系查询，多跳推理
│     返回: 关联实体 + 子图摘要
│
└── 路径4: MetadataRetriever
      来源: MySQL
      算法: SQL WHERE + 排序
      特点: 按tags/时间/类别精确过滤
      返回: 符合过滤条件的记忆
```

### 9.3 融合排名器 (FusionRanker)

现有的 `FusionRanker` 接口没有独立实现。架构 2.0 提供 3 种融合算法：

```
FusionRanker (现有接口，保留)

① WeightedSumFusion (加权求和 - 当前HybridMemoryRetriever的逻辑)
   score = α*vs + β*bs + γ*ts + δ*is + ε*gs
   
   其中:
     vs = 向量相似度 (归一化到 [0,1])
     bs = BM25分数 (归一化到 [0,1])
     ts = 时间衰减分数 TemporalProps.computeDecay()
     is = 重要性 MemoryEntry.importance
     gs = 图相关性分数 (GraphRetriever计算)
     
     权重可通过 MemoryQuery.{alpha,beta,gamma,delta,epsilon} 调整
     各分数归一化方法: Min-Max 归一化

② ReciprocalRankFusion (RRF - 推荐用于多路检索)
   score = Σ 1 / (k + rank_i)
   
   其中:
     k = 60 (常数，防止低排名条目分数过低)
     rank_i = 该条目在第i路检索中的排名
     
   优点: 不需要分数归一化，对异常值不敏感
   缺点: 丢失了分数的量级信息
   
   实现细节:
     - 各路检索结果先按各自分数排序，得到排名
     - 只在某路出现(其他路未返回)的条目 → 该路rank=topK+1 (最低)
     - 最终按RRF分数排序取topK

③ LearnToRankFusion (学习排序 - 高级，可选)
   使用 LightGBM/XGBoost 等模型学习融合权重
   特征: {vs, bs, ts, is, gs, chunkLength, entityType, category, ...}
   训练数据: 用户点击/采纳反馈 (需额外埋点)
   适用场景: 有大量用户反馈数据后启用
```

### 9.4 重排序器 (Reranker)

融合后的结果仍然可能有语义上不相关的排在前面。
重排序使用更强但更慢的模型对融合后的 topK 个候选做精排。

```
Reranker (新接口)

① CrossEncoderReranker (推荐)
   模型: BGE-Reranker-v2-m3 / Cohere Rerank API
   
   流程:
     ① 对融合后的 topK*2=20 个候选
     ② 每个候选与查询组成一对: [query, candidate.content]
     ③ 送入 Cross-Encoder 模型 → 输出相关性分数
     ④ 按分数降序排列 → 取 topK=10
   
   延迟: 20个候选 × ~10ms = 200ms (本地ONNX) / ~500ms (API)
   优化: 缓存相似查询的重排序结果

② LLMReranker (最准确但最慢)
   使用 LLM 对候选列表打分:
   Prompt: "请对以下检索结果按与查询的相关性排序，输出排序后的ID列表。
            查询: {query}
            候选: [{id, content}, ...]
            只输出ID列表，格式: [id1, id2, ...]"
   
   延迟: ~2-5秒 (取决于LLM)
   适用: 对响应时间不敏感的批量检索 / 知识库管理后台

③ NoOpReranker
   直接返回融合后的排序结果 (开发/测试环境)
```

```

### 10.1 四层记忆状态机

```

     ════════════════           ════════════════════
                                                                  
  原始对话流入                    从SENSORY中提取
  │                              │
  ▼                              ▼

  └──────────────┐               │ │ 与LTM去重 → 合并

            短期记忆 ─────────────┘
                                     │
                                     ▼
     长期记忆 (LONG_TERM)           实体记忆 (ENTITY)

  [MySQL + 向量库]                [图数据库 + MySQL]
  │                              │
  │ MemoryJanitor                │ KnowledgeGraphEngine

  │ 过期清理                      │ 知识推理 (规则 + LLM)
  │                              │
  │ 实际是持久化的                │ 是"企业知识"的存储
  └──────────────────────────────┘

MemoryConsolidator (现有接口，保留)

### 10.3 Janitor (记忆清理)

修复 `DefaultMemoryJanitor` 的已知 Bug（instanceof 检查导致非 TieredMemorySystem
实现无法删除条目），并增强功能。

```
MemoryJanitor (现有接口，保留)

  删除 instanceof TieredMemorySystem 检查
  改为通过 MemorySystem 接口方法删除 (removeLongTermEntry)

新增: ScheduledJanitorJob
  定时任务: 每天凌晨3点执行
  操作:
    ① 去重: LTM中Jaccard > 0.85的条目合并

### 11.2 内置策略

```
① ChronologicalStrategy (时间顺序, 优先级=100)

     "## 相关历史记忆 (按时间顺序)

② FactualStrategy (事实陈述, 优先级=90)
   适用: 知识库检索到的文档、用户偏好、已知事实
   格式:
     "## 相关知识
      
      - 用户偏好使用DeepSeek模型进行代码生成任务

      - 数据库已选择MySQL 8.0 + Redis 7.x作为存储方案

③ GraphStrategy (图谱关系, 优先级=80)
   适用: 知识图谱检索到的实体和关系
   格式:
     "## 相关知识图谱
      
      实体: 张三 (工程师)
        - 工作于: 腾讯 (角色: 高级工程师)
        - 居住于: 北京
        - 认识: 李四 (同事), 王五 (前同事)
        - 参与项目: LyClaw (角色: 架构师)"

④ ContextualStrategy (上下文感知, 优先级=70)
   适用: 根据当前对话动态组织
   格式: 将最高相关的3-5条记忆放在最前面，附带相关性解释
     "## 与当前问题最相关的信息
      
      1. [相关性: 0.92] 用户之前讨论过JWT Token的设计...
      2. [相关性: 0.87] 用户项目使用WebFlux，不能用阻塞式JDBC...
      3. [相关性: 0.81] 用户偏好详细的技术设计文档..."

⑤ MinimalStrategy (最小化注入, 优先级=50)
   适用: Token预算紧张时 (接近模型上下文限制)
   格式: 每条记忆压缩为一行
     "相关: JWT+Redis; MySQL已选; DeepSeek偏好; WebFlux非阻塞; Nacos发现"

⑥ CompositeStrategy (组合策略, 优先级=0 - 内部使用)
   不直接使用，由 MemoryStrategyRegistry 根据 ChatContext 自动选择:
   
   选择逻辑:
     ① 如果 context.toolDefinitions.size() > 10:
        工具密集型任务 → ContextualStrategy (精排，少量记忆)
     ② 如果 context.request.messages 总token > 3000:
        上下文空间紧张 → MinimalStrategy
     ③ 如果 context.memory 中有 GRAPH_ENTITY 类型的条目:
        混合: FactualStrategy(文档) + GraphStrategy(实体)
     ④ 默认:
        ChronologicalStrategy(对话历史) + FactualStrategy(知识库)
```

### 11.3 格式化器管道

```
MemoryFormatter (新增)

格式化流程:
  ① 接收 List<MemoryContent> (混合来源: MEMORY + KB_DOC + GRAPH_ENTITY)
  ② 按 sourceType + MemoryStrategy 分组
  ③ 每组内按 relevanceScore 降序排列
  ④ 应用 Token 预算:
     总预算 = 模型上下文限制 - 当前消息token - 预留回复token
     记忆预算 = 总预算 * 0.3  (记忆最多占用30%上下文)
     各策略按 priority 分配预算:
       高优先级策略 (Chronological/Factual) 分配 60% 预算
       中优先级策略 (Graph/Contextual) 分配 30% 预算
       低优先级策略 (Minimal) 分配 10% 预算
     超出预算的条目被截断 (truncate) 而不是丢弃全部
  ⑤ 各策略独立格式化
  ⑥ 拼接所有格式化后的文本
  ⑦ 返回最终注入文本
```

## 12. 数据流与管道集成

### 12.1 聊天管道中的记忆集成

ContextBuildStage 是管道中与记忆系统交互的唯一阶段。架构 2.0 的改造：

```
改造后的 ContextBuildStage (阶段0):

 ① 提取查询
    从 ChatContext.request.messages 中取最后一条用户消息
    提取关键实体 (Entity Linking)

 ② 并行检索 (异步组合)
    Mono.zip(
      MemoryFeignClient.retrieve(query),         
      // → 查对话记忆 (LONG_TERM + 相关SHORT_TERM)
      
      KnowledgeBaseFeignClient.searchAllUserKBs(query, topK=5, rerankEnabled=true),
      // → 查用户所有知识库
      
      KnowledgeGraphFeignClient.searchEntities(query, traversalDepth=1),
      // → 查知识图谱
    )
    .timeout(Duration.ofSeconds(5))  // 总超时5秒
    .onErrorResume(emptyResults)      // 任一路失败 → 空结果，不阻塞管道

 ③ 结果合并
    - 去重 (同一事实的多个来源 → 保留最高分)
    - 归一化分数
    - 按综合优先级排序

 ④ 记忆注入
    - 调用 MemoryStrategyRegistry.select(context) 选择策略
    - 调用 strategy.formatForContext(memoryContent) 格式化
    - 将格式化文本注入 system prompt (追加在用户定义的system prompt之后)
    - 或将记忆直接注入 ChatContext.memory 供后续Stage使用

 ⑤ SSE事件发送
    - 发送 context_build_start (含检索统计)
    - 发送 context_build_complete (含注入的记忆条目数)
    - 发送 memory_context (含格式化后的记忆预览，前端可展示)
```

### 12.2 异步事件流

```
事件驱动架构:

  ConversationEnded (对话结束)
    │
    ├──▶ MemoryIngestedEvent
    │      → LLMMemoryExtractor 提取结构化记忆
    │      → 写入 Redis SHORT_TERM
    │
    ├──▶ MemoryConsolidatableEvent (延迟5分钟, 给extractor时间)
    │      → IncrementalConsolidator 增量合并该session的STM
    │      → 高重要性条目提升到 LTM → MySQL + VectorStore
    │
    ├──▶ EntityExtractionEvent (提升到LTM后)
    │      → LLMDrivenExtractor 从新LTM中提取实体
    │      → KnowledgeGraphEngine.upsertEntity()
    │
    └──▶ KnowledgeBaseIndexedEvent (文档索引完成后)
           → PostProcessHook 提取实体 → 图谱
           → 文档与已有实体关联

  ScheduledConsolidation (定时, 每小时)
    → LLMDrivenConsolidator 批量处理所有用户
    → 跨session合并 + 冲突解决

  ScheduledJanitor (定时, 每天凌晨)
    → Janitor 全量清理
    → 冷数据归档
```

## 13. 存储架构

### 13.1 存储分层

五层存储各司其职：

```
存储分层设计:

  Layer 0: Redis (超热数据, 读延迟 <1ms)
    ├── SENSORY 感知记忆 (TTL=1h)
    ├── SHORT_TERM 短期记忆 (TTL=24h)
    ├── 嵌入缓存 embedding_cache:* (TTL=1h)
    ├── 检索缓存 retrieval:{query_hash} (TTL=5min)
    ├── 限流与计数器
    └── 会话临时状态

  Layer 1: VectorStore (热数据, 读延迟 <10ms)
    ├── 长期记忆向量 memory_ltm:{userId}
    ├── 实体记忆向量 memory_entity
    ├── 知识库文档向量 kb:{kbId}
    └── 图谱实体嵌入 graph_entity:{entityType}

  Layer 2: MySQL (温数据, 读延迟 <10ms)
    ├── lyclaw_memory_entries    (长期记忆元数据)
    ├── lyclaw_documents         (知识库文档)
    ├── lyclaw_document_chunks   (文档分块)
    ├── lyclaw_knowledge_bases   (知识库)
    ├── lyclaw_entity_memories   (实体元数据)
    └── lyclaw_memory_stats      (记忆统计)

  Layer 3: GraphStore (温数据, 读延迟 <20ms)
    ├── 实体节点 + 属性
    ├── 关系边 + 权重
    └── 图索引 (实体类型, 属性)

  Layer 4: ObjectStorage (冷数据, 读延迟 <100ms)
    ├── 原始文档文件 (PDF/DOCX/MD...)
    ├── 归档记忆 (>90天未访问)
    └── 记忆导出备份
```

### 13.2 缓存策略

```
多级缓存:

  L1: 本地Caffeine缓存 (JVM内, <0.01ms)
     - 当前会话的短期记忆 (会话级别，天然跟随请求)
     - 高频实体的嵌入 (LRU, 最大1000条)
     - 热门知识库的检索结果 (TTL=30s)

  L2: Redis缓存 (分布式, <1ms)
     - 嵌入向量缓存 (TTL=1h)
     - 检索结果缓存 (TTL=5min, key=sha256(query+参数))
     - 实体关系缓存 (TTL=10min, 写入时失效)

  L3: 持久存储 (MySQL + VectorStore + GraphStore)
     - 所有数据的最终持久化副本

缓存一致性问题:
  记忆更新时的缓存失效链:
    ① 更新 MySQL lyclaw_memory_entries
    ② 更新 VectorStore 向量
    ③ 删除 Redis retrieval:{query_hash}*  (通配符删除)
    ④ 删除 Redis embedding_cache:{hash}  (如果内容变了)
    ⑤ Caffeine缓存由TTL自然过期
```

### C.1 LocalOnnxEmbeddingModel 详细设计

这是生产推荐的嵌入方案——使用 ONNX Runtime 在本地运行 BGE-M3 模型。

```
LocalOnnxEmbeddingModel implements EmbeddingModel

启动流程:
  ① 创建 Bean 时，检查模型文件是否存在
     路径: ${lyclaw.memory.embedding.model-path} (默认 ~/.lyclaw/models/bge-m3.onnx)
     如果不存在 → 自动下载 (从 HuggingFace 或配置的镜像URL)
  
  ② 创建 ONNX Runtime Session
     OrtEnvironment env = OrtEnvironment.getEnvironment()
     OrtSession session = env.createSession(modelPath, new OrtSession.SessionOptions())
     
     可选: 使用 GPU 加速 (需 onnxruntime_gpu)
     sessionOptions.addCUDA(0)  // 使用第一块GPU
  
  ③ 加载 Tokenizer
     BGE-M3 使用 XLM-Roberta Tokenizer
     从 HuggingFace 下载 tokenizer.json → 构建词汇表
     最大输入长度: 8192 tokens (BGE-M3 支持长文本)
  
  ④ 预热
     对 10 个常见中文句子做嵌入 (预热JIT编译 + GPU显存分配)
     记录预热耗时，超过 30s 则警告

嵌入计算流程:
  ① 文本预处理
     - 去除控制字符
     - 规范化 Unicode (NFKC)
     - BGE指令前缀: "为这个句子生成表示以用于检索相关文章：" + text
  
  ② Tokenize
     tokenizer.encode(text, maxLength=8192)
     → inputIds, attentionMask, tokenTypeIds
     如果超过 8192 → 截断 (取前 8092 + 后 100)
  
  ③ ONNX 推理
     Map<String, OnnxTensor> inputs = Map.of(
       "input_ids", OnnxTensor.createTensor(env, inputIds),
       "attention_mask", OnnxTensor.createTensor(env, attentionMask)
     )
     OrtSession.Result result = session.run(inputs)
  
  ④ 提取向量
     float[][] hiddenStates = (float[][]) result.get(0).getValue()
     取最后一层 [CLS] token → 或对所有token做平均池化 (BGE-M3用CLS)
     float[] embedding = hiddenStates[0]  // 第0个位置是CLS
  
  ⑤ L2归一化
     float norm = sqrt(sum(e_i^2))
     for i in range(dim): embedding[i] /= norm

性能指标预估:
  单次嵌入延迟: 20-50ms (CPU), 2-5ms (GPU)
  吞吐: 50次/秒 (CPU 4核), 200+次/秒 (GPU)
  内存占用: ~2GB (模型加载后)
  嵌入维度: 1024 (BGE-M3)

线程安全:
  单个 OrtSession 线程安全 (ONNX Runtime 1.16+)
  Tokenizer 需要加锁或每线程一个实例
  实现: 每线程一个 Tokenizer 实例 (ThreadLocal)
```

## 附录D: 分块策略算法详解

### D.1 RecursiveChunking 完整算法

```
输入:
  text: 原始文档文本
  targetTokens: 512  (目标分块大小，单位tokens)
  overlapTokens: 64  (相邻分块重叠大小)
  maxTokens: 1024    (单个分块最大大小)

输出:
  List<Chunk> (每个chunk含content + metadata)

算法:

function recursiveChunk(text, targetTokens, overlapTokens, maxTokens):
    separators = ["\n\n", "\n", "。", ".", "！", "!", "？", "?", "；", ";", " "]
    
    return splitBySeparator(text, separators, 0, targetTokens, overlapTokens, maxTokens)

function splitBySeparator(text, separators, sepIdx, targetTokens, overlapTokens, maxTokens):
    // 终止条件
    if estimateTokens(text) <= maxTokens:
        return [new Chunk(text)]
    
    if sepIdx >= separators.length:
        // 最终手段: 强制按字符截断
        return forceSplit(text, targetTokens, overlapTokens, maxTokens)
    
    sep = separators[sepIdx]
    
    // 按分隔符分割
    fragments = split(text, sep)
    
    if fragments.length == 1:
        // 此分隔符无法分割，试下一个
        return splitBySeparator(text, separators, sepIdx + 1, 
                                targetTokens, overlapTokens, maxTokens)
    
    // 贪心合并
    chunks = []
    current = ""
    
    for frag in fragments:
        tentative = current + sep + frag  (如果current非空)
        否则 tentative = frag
        
        if estimateTokens(tentative) <= targetTokens:
            current = tentative
        else if estimateTokens(frag) > targetTokens:
            // 单个片段超过目标大小 → 递归处理
            if current is not empty:
                chunks.add(new Chunk(current))
            subChunks = splitBySeparator(frag, separators, sepIdx + 1,
                                         targetTokens, overlapTokens, maxTokens)
            chunks.addAll(subChunks)
            current = ""
        else:
            // 添加到当前chunk会超出，开始新chunk
            if current is not empty:
                chunks.add(new Chunk(current))
            current = frag
    
    if current is not empty:
        chunks.add(new Chunk(current))
    
    // 添加重叠
    return addOverlap(chunks, overlapTokens)

function addOverlap(chunks, overlapTokens):
    for i from 0 to chunks.length - 2:
        currentEnd = getLastTokens(chunks[i].content, overlapTokens)
        chunks[i + 1].content = currentEnd + chunks[i + 1].content
    return chunks

function forceSplit(text, targetTokens, maxTokens):
    // 按字符数估算tokens (中文: 1字符≈0.5tokens, 英文: 1词≈1.3tokens)
    charsPerChunk = targetTokens * 2  // 粗略估算
    overlapChars = charsPerChunk / 8  // 10%重叠
    
    chunks = []
    for i from 0 to text.length step (charsPerChunk - overlapChars):
        end = min(i + charsPerChunk, text.length)
        chunks.add(new Chunk(text.substring(i, end)))
    return chunks
```

### D.2 SemanticChunking 详解

语义分块是最智能但最慢的分块方式——通过计算相邻句子的嵌入相似度，
在"语义断点"处分割。

```
SemanticChunking:

  ① 分句 (使用 LingPipe / HanLP / spaCy)
     sentences = sentenceSplitter.split(text)
     
  ② 计算逐句嵌入
     embeddings = [embeddingModel.embed(s) for s in sentences]
     
  ③ 计算相邻句子对的余弦相似度
     similarities = []
     for i from 0 to len(sentences) - 2:
         sim = cosine(embeddings[i], embeddings[i + 1])
         similarities.add(sim)
     
  ④ 识别语义断点
     将相似度序列视为"信号"，找到局部极小值
     
     方法: 比较每个相似度与前后相似度
     断点条件: sim[i] < sim[i-1] * 0.85 AND sim[i] < sim[i+1] * 0.85
     
     或者更简单的方法:
     断点条件: sim[i] < percentile(similarities, 25)  // 低于25分位数

  ⑤ 在断点处分割
     chunks = []
     start = 0
     for i in sentences.indices:
         if isBreakPoint(i):
             chunks.add(sentences[start..i])
             start = i + 1
     chunks.add(sentences[start..])
     
  ⑥ 大chunk二次分割
     如果某个chunk超过 maxTokens → 对其递归用 RecursiveChunking

  适用场景:
    - 高质量文档 (学术论文、技术文档、书籍)
    - 自然段落结构不明显
    - 可以接受额外的嵌入计算成本 (~100ms/页面)

  不适用场景:
    - 代码文件 (语义分句对代码无效)
    - 纯列表/表格文档
    - 实时处理要求高 (每个文档额外做 N次嵌入)
```

### D.3 中文特化处理

中文分词和分句的特殊处理：

```
中文分句 (ChineseSentenceSplitter):

  分句标点 (终止符):
    。！？!? … \n  (主分隔)
    
  分句标点 (非终止符，需上下文判断):
    ，、；：  (在非括号内时)

  特殊情况:
    - 省略号 "……" → 不在此分句
    - 引号内的标点 → 不在此分句 (需配对检测)
    - 英文句号在数字中间 "3.14" → 不分句
    - 中英混排 "这是PyTorch。这是框架。" → 正常分句

  实现:
    ① 正则扫描识别终止标点
    ② 向前向后看 +- 2字符，排除数字/缩写等
    ③ 引用深度跟踪: 遇到 " 深度+1，遇到 " 深度-1
    ④ 深度=0时遇到终止标点 → 分句

中文Token估算:
  中文: 1字符 ≈ 0.5 tokens (BGE tokenizer)
  英文: 1词 ≈ 1.3 tokens
  数字: 1数字 ≈ 0.3 tokens
  标点: 忽略或极低

  混合文本Token估算:
    chineseChars * 0.5 + englishWords * 1.3 + digits * 0.3 + codeTokens * 0.8
```

## 附录E: 知识图谱遍历算法

### E.1 Personalized PageRank 用于图检索

当用户查询"张三"时，从"张三"实体节点出发，
用 Personalized PageRank 算法找出最相关的邻居实体。

```
PersonalizedPageRank:

输入:
  seedEntityId: "张三"的节点ID
  graph: 完整图 (Node[], Edge[])
  alpha: 阻尼系数 (default=0.85, 推荐 0.75 用于知识图谱)
  maxIter: 最大迭代次数 (default=50)
  tolerance: 收敛容差 (default=1e-6)

输出:
  Map<EntityId, Double>  (每个实体的PPR分数)

算法:
  ① 初始化
     for each node in graph:
         ppr[node] = 0.0
     ppr[seedEntity] = 1.0  (从种子开始)
     
  ② 迭代传播 (Power Iteration)
     for iter in 1..maxIter:
         newPpr = {}
         totalDiff = 0.0
         
         for each node in graph:
             if node == seedEntity:
                 // 种子节点: alpha概率跳回
                 newPpr[node] = (1 - alpha) * (sum over incoming edges of ppr[src]/outDegree[src]) + alpha
             else:
                 // 非种子: 0概率跳回
                 newPpr[node] = (1 - alpha) * (sum over incoming edges of ppr[src]/outDegree[src])
             
             totalDiff += abs(newPpr[node] - ppr[node])
         
         ppr = newPpr
         
         if totalDiff / graph.size() < tolerance:
             break
     
  ③ 排序返回
     按 ppr 降序排列
     排除种子节点自身
     返回Top-K

在图检索中的应用:
  查询 → 实体链接 → 定位种子实体
  → PersonalizedPageRank(seed, alpha=0.75)
  → 返回PPR分数最高的20个邻居实体
  → 提取这些实体的属性 + 与种子的关系 → 格式化 → 注入LLM上下文
```

### E.2 多跳推理

```
多跳推理 (Multi-Hop Reasoning):

场景: 用户问"张三的同事李四所在公司的CEO是谁？"

推理链:
  ① 张三 -(KNOWS)→ 李四
  ② 李四 -(WORKS_AT)→ 腾讯
  ③ 腾讯 -(HAS_CEO)→ 马化腾
  
  答案: 马化腾

实现 (BFS路径探索):

function multiHopQuery(startEntityId, queryEmbedding, maxDepth, topK):
    // 结果收集
    paths = []  // List<Path>
    queue = [(startEntityId, depth=0, path=[startEntityId], weight=1.0)]
    visited = {}
    
    while queue is not empty:
        (currentId, depth, path, weight) = queue.pop()
        
        if weight < 0.1:  // 剪枝: 累积权重太低
            continue
        
        if currentId in visited and visited[currentId] >= weight:
            continue
        visited[currentId] = weight
        
        if depth >= 1:  // 一跳及以上
            paths.add(Path(path, weight))
        
        if depth >= maxDepth:
            continue
        
        // 扩展邻居
        for edge in graph.getOutEdges(currentId):
            newWeight = weight * edge.weight
            newPath = path + [edge.targetId]
            queue.add((edge.targetId, depth + 1, newPath, newWeight))
        
        // 反向边 (知识图谱的边是有向的，但推理时可以逆向)
        for edge in graph.getInEdges(currentId):
            newWeight = weight * edge.weight * 0.7  // 逆向边权重打折
            newPath = path + [edge.sourceId]
            queue.add((edge.sourceId, depth + 1, newPath, newWeight))
    
    // 排序 + 去重
    ranked = rankPathsByRelevance(paths, queryEmbedding)
    return ranked.topK(topK)
```

### E.3 图嵌入

将图结构信息编码为向量，使向量检索能感知图拓扑：

```
图嵌入方法 (简化Node2Vec风格):

对图中有嵌入的实体节点:
  ① 为每个实体计算结构特征向量:
     - 入度 / 出度 (归一化)
     - PageRank分数 (全局重要性)
     - 局部聚类系数 (邻居之间的连接紧密程度)
     - 平均邻居PageRank
     
  ② 拼接为结构向量 (4维)
  
  ③ 将结构向量拼接到实体文本嵌入的尾部:
     enhancedEmbedding = concat(textEmbedding[0:1020], structureVector[0:4])
     → 1024维增强嵌入 (文本语义 + 图结构)
     
  ④ 归一化

在图检索时:
  查询嵌入与增强嵌入做余弦相似度
  → 同时匹配语义相关性和图结构重要性
```

## 附录J: 安全设计

### J.1 数据隔离

记忆架构 2.0 中的数据隔离确保用户不能访问其他用户的记忆：

```
隔离层级:

  ① API层: userId 从 JWT 提取，所有Controller方法强制注入
     示例: @RequestAttribute("userId") String userId
  
  ② 服务层: 所有查询方法必须传 userId 参数
     MemorySystem.retrieve(query) → query 中必须设置 userId (在Filter层填充)
     KnowledgeBaseManager.search(kbId, query) → kbId → ownerId校验
  
  ③ 存储层: 向量检索时 metadata.userId 过滤
     PgVectorStore.search(embedding, filter: {userId: "u_xyz"})
  
  ④ 图存储层: Cypher查询强制带 userId
     MATCH (n:Entity {userId: $userId}) WHERE ...
  
  ⑤ 缓存层: 缓存键包含 userId
     retrieval:{sha256(query)}:{userId}

预防水平越权:
  - 知识库: 加载前校验 kb.ownerId == userId
  - 文档: 先查 kb.ownerId 再操作
  - 实体: 先查 entity.createdBy == userId 再修改
  - 所有校验失败 → 返回 PERMISSION_DENIED (不暴露实体是否存在)

共享知识库:
  - visibility=SHARED: 指定用户ID可读
    实现: lyclaw_kb_permissions (kb_id, user_id, permission_level: READ/WRITE/ADMIN)
    所有权限直接绑定到具体用户ID，无角色中间层
  - visibility=PUBLIC: 所有用户可读
  - 共享知识库的检索: 向量搜索时允许多个 userId (IN子句)
```

### J.2 知识库访问控制

```
权限模型 (Owner-based，基于所有者直接授权):

  核心原则: 
    - 没有角色层级，所有权限直接授予具体用户ID
    - 知识库只有一个 owner，owner 拥有全部权限
    - owner 可以将读写权限直接授权给其他 userId
    - 简单透明，适合目前以用户为中心的架构

  知识库操作              创建者   协作者(WRITE)  协作者(READ)  其他用户
  ───────────────────────────────────────────────────────────────
  查看KB信息                ✅       ✅             ✅           ❌(PRIVATE)
  修改KB设置                ✅       ✅             ❌           ❌
  上传文档                  ✅       ✅             ❌           ❌
  删除文档                  ✅       ✅             ❌           ❌
  搜索KB内容                ✅       ✅             ✅           ❌(PRIVATE)
  删除KB                    ✅       ❌             ❌           ❌

  权限存储: lyclaw_kb_permissions (kb_id, user_id, permission_level)
    无角色字段，user_id 直接关联 lyclaw_users.id

  注意: PUBLIC 知识库对所有用户可读可搜索
