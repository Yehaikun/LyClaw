# 反思系统架构设计

## 一、概述

### 1.1 设计目标

将 LyClaw 的反思能力从当前硬编码、单一拓扑、纯规则评估的现状，重构为**可组合的反思组件系统**。开发者可以像搭乐高一样自由选择和组装反思原语，构建任意的反思拓扑（Reflexion、Self-Refine、CRITIC、LATS、Voyager、AutoGen Debate 等），甚至可以由 AI 在运行时根据任务特征动态生成反思架构。

### 1.2 核心思想

- **反思组件 = 七个可组合的原语接口**（Strategy 模式），每种原语有多种内置实现
- **反思架构 = 一个有向图数据对象**（节点是原语，边带条件路由，拓扑与执行引擎分离），支持 Fork/Join 并发、嵌套拓扑（Composite）、动态拓扑生成
- **反思 Stage = 管线的固定一环**，所有 Agent 共享同一个 `ReflectionTopologyStage`，差异仅在于绑定的拓扑数据不同
- **"无反思"是拓扑的特例**（`Actor → STOP`），不需要换 Stage，只需换拓扑配置

### 1.3 设计覆盖的反思模式

经过对 13 种经典及前沿反思模式的逐一检验，本设计的覆盖度如下：

| 覆盖状态 | 模式 | 说明 |
|---------|------|------|
| 可直接表达 | Reflexion、Self-Refine、CRITIC、Generative Agents | 现有6原语+条件边即可 |
| 需Fork/Join | AutoGen Debate、LATS、ChatDev、混合自适应 | 需扩展边的并发语义 |
| 需嵌套拓扑 | ChatDev、Self-Discover | 拓扑作为另一个拓扑的节点 |
| 需扩展原语 | Self-RAG（RetrievalGate）、Voyager（Memory多类型） | 需新增第7原语/扩展接口 |
| 结构上不支持 | DSPy 编译时优化 | 完全不同的执行范式，走第三层自定义Stage |
| **动态生成** | **全动态模式**：LLM按任务特征生成拓扑 + 动态创建Agent | 需 `PrimitiveCatalog`（零件发现）+ `AgentRegistry`（运行时注册）+ `DynamicTopologyBuilder` |

## 二、架构定位

### 2.1 在 LyClaw 管线中的位置

```
当前管线（硬编码协调，实际未生效）:
  ContextBuild → SecurityCheck → Respond → Reflection → Metrics
                                    ↑           ↑
                              纯ReAct调用    纯规则评估
                              AgentInvocationHandler 在两者之间硬编码重试闭环

改造后管线（拓扑驱动）:
  ContextBuild → SecurityCheck → ReflectionTopology → Metrics
                                    ↑
                              单一Stage，内部执行拓扑图
                              AgentInvocationHandler 只做线性串联
                              "反思"概念对管线层完全透明
```

### 2.2 与现有架构的关系

- **替代 `RespondStage`**：ReAct 执行能力作为 `ReActActor`（Actor 原语的一种实现）存在于拓扑内部
- **替代 `ReflectionStage`**：质量评估能力作为 `LLMJudgeEvaluator`（Evaluator 原语的一种实现）存在于拓扑内部
- **简化 `AgentInvocationHandler`**：删除 `executeStages()` 中按名称查找 PlanExecution/Reflection 的硬编码重试逻辑（当前第 386-452 行），退化为纯线性 Stage 串联
- **废弃现有的纯规则评估组件**：`DefaultQualityEvaluator`、`DefaultErrorDetector`、`DefaultStrategyAdjuster` 不再作为核心路径，但保留作为 `HeuristicEvaluator` 策略的一种实现选项

## 三、核心概念

### 3.1 原语（Primitive）

反思流程中的最小可复用处理单元。每个原语是单一职责的接口，通过不同实现（Strategy 模式）适配不同场景。七种原语类型：

| 原语 | 职责 | 类比 |
|------|------|------|
| Actor | 执行任务，生成输出 | "做事的工人" |
| Evaluator | 评估输出质量，给出评分和问题列表 | "质检员" |
| Reflector | 根据评估结果生成改进建议（文字反思） | "事后诸葛" |
| Router | 根据评估结果决定下一步流向 | "调度员" |
| Memory | 持久化/检索历史反思记录 | "记事本" |
| Synthesizer | 合并多轮输出为最终结果 | "编辑" |
| RetrievalGate | 在Action前决策是否需要检索/验证等前置操作 | "门卫"（可选原语） |

### 3.2 拓扑（Topology）

一张有向图，描述原语之间的连接关系与流转条件。拓扑是纯数据对象，不包含执行逻辑，可以被序列化为 JSON/YAML、存储在配置文件中、或由 AI 在运行时动态生成。

**拓扑不一定是严格的有向无环图（DAG）**——反思循环天然需要回路（如 Router→Reflector→Actor 的回边）。终止条件由 `maxIterations` + Router 的 STOP 决策共同保证，而非图论的无环约束。

```
拓扑示例（Reflexion）:
                    ┌──────────────────────────┐
                    │     ReflectionMemory      │
                    │   (store & retrieve)     │
                    └──────────┬───────────────┘
                               │
  ┌──────────┐    ┌───────────▼────────┐    ┌──────────┐    ┌──────────┐
  │  Actor   │───▶│    Evaluator       │───▶│  Router  │───▶│  STOP    │
  │(执行任务) │    │  (评估输出质量)     │    │(决策流向) │    │(退出节点) │
  └──────────┘    └───────────────────┘    └────┬─────┘    └──────────┘
       ▲                                        │
       │              ┌──────────┐              │ ON_RETRY
       └──────────────│Reflector │◀─────────────┘
                      │(生成反思) │
                      └──────────┘
```

### 3.3 拓扑执行器（TopologyExecutor）

解释器模式的具体实现。拿拓扑数据对象，从入口节点开始遍历图：

1. 调用当前节点的原语，传入 `ReflectionContext`
2. 读取原语返回的结果（含状态标记）
3. 根据当前节点发出的边条件，选择匹配的出边
4. 对于 Fork 出边：并发启动所有目标节点
5. 对于 Join 入边：等待所有上游分支完成后才触发该节点
6. 将游标移动到目标节点，重复直到到达出口节点或超过最大迭代次数

引擎不关心节点具体是什么类型，只调用统一的 `ReflectionPrimitive.execute(ctx)` 方法。

## 四、七大原语接口

### 4.1 接口体系

```
ReflectionPrimitive (标记接口，所有原语的父类型)
  ├── Actor           — 执行任务
  ├── Evaluator       — 评估质量
  ├── Reflector       — 生成反思
  ├── Router          — 决策流向
  ├── Memory          — 持久化记忆
  ├── Synthesizer     — 合并输出
  └── RetrievalGate   — 事前决策门控（可选）
```

每个原语接口有独立的方法签名。除 Memory 外均用 `@FunctionalInterface` 标注。

### 4.2 Actor

**职责**：执行一轮任务，生成文本输出。通常封装一次 LLM 调用 + 工具执行，是反思循环的"劳动"环节。

**方法签名**：接收 `ReflectionContext`，返回 `ActorResult`。

**`ActorResult` 属性**：
- `output: String` — 本轮生成的文本输出
- `toolCalls: List<ToolCallRecord>` — 本轮使用的工具调用记录
- `successCount: int` — 成功的工具调用次数
- `failCount: int` — 失败的工具调用次数
- `taskSummary: String` — 当前任务的简要描述（Actor 执行后更新，供 Memory 语义检索使用）
- `metadata: Map<String, Object>` — 扩展元数据

**内置实现**：
- `ReActActor`：封装 `ReActEngine`，标准的 ReAct（思考→工具调用→观察）循环。读取 `ReflectionContext` 中的 `currentReflection` 或 `currentIssues` 注入到系统提示词中
- `SimpleChatActor`：单次 LLM 调用，无工具，用于简单问答场景

**Actor 读取反馈的路径**（设计要点）：
Actor 在下一轮执行时，可以从 `ReflectionContext` 中读取三种形式的反馈，按优先级：
1. `currentReflection`（由 Reflector 生成的结构化反思文本）→ 注入到 system prompt
2. `currentIssues`（由 Evaluator 生成的 Issue 列表）→ 追加到 prompt："请改进以下问题：{issues}"
3. `lastToolOutput`（由 ToolVerifierEvaluator 生成的工具失败输出）→ 追加到 prompt："上次执行报错：{output}"

### 4.3 Evaluator

**职责**：评估 Actor 的输出质量，给出结构化的评分和问题诊断。

**方法签名**：接收 `ReflectionContext`，返回 `Evaluation`。

**`Evaluation` 属性**：
- `score: double` — 综合评分（0.0 ~ 1.0），用于 Router 的阈值判断
- `reasoning: String` — 评估推理过程（LLM生成的自然语言解释）
- `issues: List<Issue>` — 检测到的问题列表
- `dimensions: Map<String, Double>` — 各维度的分项评分（如正确性、完整性、格式等）
- `needsRetry: boolean` — 是否建议重试
- `isSuccess: boolean` — 任务是否成功（二元判定，用于 Voyager 模式的技能/经验分流）
- `isConsistent: boolean` — 输出是否内部一致（用于 CoVe 模式的一致性检验）
- `inconsistencies: List<Inconsistency>` — 不一致项列表（CoVe 模式专用）
- `importanceScore: double` — 事件重要性评分（Generative Agents 模式，非质量分）

**`Issue` 属性**：
- `severity: Severity` — 严重程度（枚举：CRITICAL / MAJOR / MINOR / INFO）
- `category: String` — 问题类别（如 "逻辑错误"、"信息缺失"、"格式问题"）
- `description: String` — 问题描述

**`Inconsistency` 属性**（CoVe 模式专用）：
- `claim1: String` / `claim2: String` — 两个不一致的断言
- `reason: String` — 为什么它们冲突
- `resolution: String` — 建议如何调和

**`Severity` 枚举**：`CRITICAL`, `MAJOR`, `MINOR`, `INFO`

**内置实现**：
- `LLMJudgeEvaluator`：**默认实现**。调用 LLM 根据可配置的评估维度（正确性、完整性、可用性等）对输出进行打分。评估 prompt 模板可通过 Builder 自定义
- `HeuristicEvaluator`：纯规则评估（继承自现有 `DefaultQualityEvaluator`）。用于低成本、低延迟场景
- `ToolVerifierEvaluator`：通过运行外部命令（编译、测试套件、输出比对等）验证输出。**不根据退出码单一判定** `isSuccess`，而是根据可配置的验证策略（见下方验证模式）
- `ImportanceEvaluator`：评估事件重要性而非质量。用于 Generative Agents 模式（输出 `importanceScore`）
- `ConsistencyEvaluator`：做交叉一致性检验（CoVe 模式）。输入是基线回答+验证回答，输出 `isConsistent` + `inconsistencies`
- `CrossExaminerEvaluator`：多输出交叉评估（AutoGen Debate 模式）。接收多个 Actor 的输出，评估观点一致性、优劣对比、争议点
- `CompositeEvaluator`：组合多个 Evaluator，按权重加权汇总评分

#### 4.3.1 ToolVerifierEvaluator 验证模式

`ToolVerifierEvaluator` 不是简单地 `isSuccess = (exitCode == 0)`。代码可能正常退出但产生错误结果（语义正确性），也可能非零退出但部分正确。因此 `isSuccess` 的判定取决于**验证策略**（`config.verificationType`），而非单一退出码。

**`VerificationType` 枚举**：

| 模式 | `isSuccess` 判定逻辑 | 适用场景 |
|------|---------------------|---------|
| `EXIT_CODE` | `exitCode == 0` | 编译检查、语法校验、lint |
| `TEST_SUITE` | 解析测试框架的结构化报告（JUnit XML / pytest JSON / Mocha JSON），所有用例通过 | 有测试套件的代码生成任务 |
| `OUTPUT_DIFF` | stdout 与预期输出文件逐行比对（支持正则和误差容忍），无差异 | 算法题、脚本输出验证、CLI 工具 |
| `CUSTOM_SCRIPT` | 运行用户提供的校验脚本，解析其 JSON 输出 `{success, score, issues}` | 复杂验证逻辑（如 API 响应校验、数据库状态检查） |

**模式详解**：

**EXIT_CODE 模式**（最简单，适用面窄）：
```
eval.isSuccess = (exitCode == 0)
// 局限性：代码可能 exit 0 但输出错误；可能 exit 1 但只因一个非关键 warning
// 仅适用于：编译检查（javac）、lint（shellcheck）、语法校验
```

**TEST_SUITE 模式**（推荐用于代码生成任务）：
```
// 不依赖退出码，解析测试框架的结构化输出
// 支持格式：JUnit XML、pytest JSON、Mocha JSON、Go test -json
testReport = parseTestReport(config.testOutputFormat, stdout, stderr)
eval.isSuccess = testReport.allPassed()
eval.issues = testReport.failures.map(f -> Issue{
    category: "TEST_FAILURE",
    description: f.testName + " failed. expected=" + f.expected + " actual=" + f.actual
})
eval.score = testReport.passRate  // 0.0 ~ 1.0

// 关键：即使 exitCode == 0，如果测试报告显示有用例失败，isSuccess 仍为 false
// 这解决了"代码正常运行但结果错误"的场景
```

**OUTPUT_DIFF 模式**（无测试框架时的替代方案）：
```
expectedOutput = Files.readString(config.expectedOutputFile)
actualOutput   = stdout

diffs = diffLines(expectedOutput, actualOutput, config.toleranceMode)
// toleranceMode: EXACT（逐字符） / IGNORE_WHITESPACE / REGEX（每行正则匹配）

eval.isSuccess = diffs.isEmpty()
eval.issues = diffs.map(d -> Issue{
    category: "OUTPUT_MISMATCH",
    description: "Line " + d.lineNum + ": expected=" + d.expected + " actual=" + d.actual
})

// 适用场景：算法题（输入固定，输出可预期）、CLI 工具（命令输出与 golden file 比对）
// 局限：只适合确定性输出，不适合 LLM 自由文本生成
```

**CUSTOM_SCRIPT 模式**（最灵活）：
```
// 运行用户提供的校验脚本，脚本输出 JSON 到 stdout
validationJson = runScript(config.validationScript)  // 如 "python validate.py"
result = parseJson(validationJson)
// 期望的 JSON 格式: {"success": bool, "score": 0.0-1.0, "issues": [{"category":"...", "description":"..."}]}

eval.isSuccess = result.success
eval.score = result.score
eval.issues = result.issues

// 适用场景：复杂验证（调 API 检查响应、查数据库、多步骤端到端验证）
```

**配置示例**（拓扑中的 Evaluator 节点配置）：
```java
// EXIT_CODE 模式 — 只检查编译
Map.of("verificationType", "EXIT_CODE",
       "command", "javac Solution.java")

// TEST_SUITE 模式 — 完整测试套件
Map.of("verificationType", "TEST_SUITE",
       "command", "cd /tmp/solution && javac Solution.java && java -ea SolutionTest",
       "testOutputFormat", "junit_xml",
       "testOutputPath", "/tmp/solution/test-results.xml")

// OUTPUT_DIFF 模式 — 比对输出
Map.of("verificationType", "OUTPUT_DIFF",
       "command", "python solution.py < input.txt",
       "expectedOutputFile", "/tmp/expected_output.txt",
       "toleranceMode", "IGNORE_WHITESPACE")

// CUSTOM_SCRIPT 模式 — 自定义校验
Map.of("verificationType", "CUSTOM_SCRIPT",
       "validationScript", "python validate_solution.py --code /tmp/solution.py --test-cases /tmp/cases.json")
```

**设计原则**：无论哪种模式，Evaluator 始终是**纯机械解析**（正则、JSON解析、字符串比对），不调用 LLM。所有需要 LLM 判断的（如"这个回答是否语义正确"、"代码逻辑是否合理"）走 `LLMJudgeEvaluator`，不属于 `ToolVerifierEvaluator` 的职责范围。

### 4.4 Reflector

**职责**：根据 Evaluator 的评估结果生成"文字反思"——一段自然语言文本，说明上一轮哪里做得不好、下一轮应该如何改进。这段文本写入 `ReflectionContext.currentReflection`，下一轮 Actor 自动读取。

**方法签名**：接收 `ReflectionContext` 和 `Evaluation`，返回 `String`（反思文本）。

**内置实现**：
- `VerbalReflector`：调用 LLM 生成反思文本。prompt 模板："上一轮输出存在以下问题：[issues]。请生成简短建议，指导下一轮如何改进。"
- `TopologyPlanner`（特殊 Reflector）：不生成自然语言反思，而是生成 JSON 拓扑定义。用于 Self-Discover 模式的动态拓扑生成
- `NoOpReflector`：返回空字符串。适用于不需要文字反馈、仅靠 Router 直接重试的场景（如自我修正模式）

### 4.5 Router

**职责**：根据当前评估结果、迭代次数和上下文状态，决定拓扑执行的下一步走向。

**方法签名**：接收 `Evaluation`、当前迭代次数、最大迭代次数，返回 `RouteDecision`。

**`RouteDecision` 枚举值**：
- `CONTINUE` — 继续走默认出边（通常是回到 Actor 进行下一轮）
- `RETRY` — 触发重新执行（先经过 Reflector 生成反思，再回到 Actor）
- `STOP` — 停止迭代，进入出口节点（通常触发 Synthesizer 合并输出）
- `FALLBACK` — 降级处理，使用备选方案（如返回简单回答、请求人工介入）
- `BRANCH(targetNodeId)` — 跳转到指定的分支节点（用于多分支探索）
- `FORK(List<String> targetNodeIds)` — 同时启动多个目标节点并发执行（用于 LATS、AutoGen Debate）

**内置实现**：
- `ThresholdRouter`：基于评分阈值的简单路由。`score >= threshold → STOP`，`score < threshold && iteration < max → RETRY`，`iteration >= max → STOP`
- `FixedIterRouter`：固定迭代次数路由，忽略评分，跑满 N 轮后停止
- `LLMRouter`：调用 LLM 自主决策是否继续、走哪个分支。适用于复杂任务场景，LLM 综合评估当前进展后决定下一步
- `MCTSRouter`：基于 UCT（Upper Confidence Bound for Trees）公式选择最佳子节点继续探索。用于 LATS 树搜索模式。维护每个候选节点的访问次数和累计价值统计

### 4.6 Memory

**职责**：持久化记忆记录，并在后续检索相关的历史记忆，为 Actor 提供跨轮次、跨会话的学习能力。

**方法签名**：
- `store(ctx, record)` — 存储单条记忆记录
- `storeSkill(ctx, skill)` — 存储技能（成功执行的任务，Voyager 模式）
- `storeExperience(ctx, experience)` — 存储经验（失败的任务，Voyager 模式）
- `retrieve(ctx, query, limit)` — 按查询条件检索记忆
- `retrieveSkills(ctx, taskDescription, limit)` — 按任务语义检索相似技能
- `retrieveExperiences(ctx, taskDescription, limit)` — 检索相似经验

**`MemoryRecord` 属性**（统一记忆模型）：
- `recordId: String` — 唯一标识
- `type: MemoryType` — 记忆类型（枚举：SKILL / EXPERIENCE / REFLECTION / INSIGHT / DECISION）
- `userId: String` — 用户维度分区键
- `projectId: String` — 项目维度分区键
- `sessionId: String` — 会话维度
- `agentId: String` — Agent 维度
- `taskType: String` — 任务类型标签（如 "code_generation"、"bug_fix"、"refactoring"）
- `summary: String` — 简短摘要（用于检索匹配）
- `content: String` — 完整内容（反思文本/技能代码/经验描述）
- `embedding: List<Double>` — 向量嵌入（用于语义相似度检索）
- `importanceScore: double` — 重要性评分（Generative Agents 模式）
- `accessCount: int` — 访问次数
- `successReferCount: int` — 被引用后成功的次数（用于 Voyager 技能评分）
- `createdAt: long` / `updatedAt: long` / `expiresAt: Long` — 时间戳

**`MemoryType` 枚举**：`SKILL`, `EXPERIENCE`, `REFECTION`, `INSIGHT`, `DECISION`

**内置实现**：
- `InMemoryReflectionStore`：基于 `ConcurrentHashMap` 的内存存储。开发/测试环境默认
- `RedisReflectionStore`：基于 Redis 的持久化存储，支持向量相似度检索、TTL 过期、跨会话共享

### 4.7 Synthesizer

**职责**：当拓扑执行多轮迭代或多分支并发后，将各输出合并为最终的单一响应。

**方法签名**：接收 `List<String>`（各轮/各分支的输出）和 `List<Evaluation>`（对应的评估），返回 `String`（最终输出）。

**内置实现**：
- `LastOutputSynthesizer`：直接返回最后一轮的输出
- `BestScoreSynthesizer`：返回评估分最高的那轮输出
- `LLMSynthesizer`：调用 LLM 综合各轮/各分支输出，生成一份融合了各方优点的最终输出
- `WeightedVotingSynthesizer`：多分支按评估分加权投票，合并共识观点（AutoGen Debate 模式）
- `ChainMergeSynthesizer`：将多阶段输出按顺序拼接（ChatDev 模式）

### 4.8 RetrievalGate（可选原语）

**职责**：在 Actor 执行前，判断是否需要检索外部知识、验证前置条件或加载上下文。与 Router（事后决策）不同，RetrievalGate 是**事前决策**——在行动之前判断需要什么准备工作。

**适用场景**：Self-RAG 模式的"是否需要RAG检索"判断、Voyager 模式的"是否加载相关技能"判断。

**方法签名**：接收 `ReflectionContext`，返回 `RetrievalDecision`。

**`RetrievalDecision` 枚举值**：
- `RETRIEVE` — 需要检索，触发 RAG/Memory 检索流程
- `NO_RETRIEVE` — 不需要检索，直接进入 Actor
- `LOAD_SKILLS` — 加载相似技能（Voyager 模式）
- `LOAD_EXPERIENCES` — 加载历史经验（Voyager 模式）
- `VERIFY_PREREQUISITES` — 验证前置条件

**内置实现**：
- `LLMRetrievalGate`：调用 LLM 判断当前任务是否需要检索外部知识（Self-RAG 风格，生成 `[Retrieve]` / `[NoRetrieve]` token）
- `AlwaysRetrieveGate`：总是检索
- `NeverRetrieveGate`：从不检索（等同于无此原语）

**注意**：RetrievalGate 是可选的。大多数拓扑不需要它，框架默认拓扑中也不包含。它主要面向 Self-RAG 和 Voyager 这类需要在执行前做检索决策的模式。

## 五、拓扑数据模型

### 5.1 ReflectionTopology

纯数据对象，描述反思架构的图结构。可被序列化为 JSON/YAML，可存储、传输、运行时生成。

**核心属性**：
- `topologyId: String` — 拓扑的唯一标识
- `name: String` — 拓扑的可读名称，如 "reflexion"、"self-refine"、"critic"
- `nodes: Map<String, NodeDef>` — 节点定义集合，key 为节点 ID
- `edges: List<Edge>` — 边定义列表
- `entryNodeId: String` — 入口节点 ID
- `exitNodeIds: Set<String>` — 出口节点 ID 集合（到达任一出口则拓扑结束）
- `maxIterations: int` — 全局最大迭代次数（防止死循环）
- `maxRecursionDepth: int` — 嵌套拓扑的最大递归深度（默认 3）
- `defaultTimeoutMs: long` — 节点默认超时时间
- `maxTokensPerTopology: long` — 拓扑级 Token 消耗上限（可选，成本控制）
- `metadata: Map<String, String>` — 扩展元数据（版本、作者、描述等）

### 5.2 NodeDef

描述拓扑中的一个节点——即一个原语实例的引用。

**属性**：
- `nodeId: String` — 节点在图中的唯一 ID（如 "actor1"、"main_evaluator"）
- `primitiveType: PrimitiveType` — 原语类型（枚举：ACTOR / EVALUATOR / REFLECTOR / ROUTER / MEMORY / SYNTHESIZER / RETRIEVAL_GATE / COMPOSITE）
- `implementationName: String` — 具体实现的 Bean 名称（如 "llmJudgeEvaluator"、"thresholdRouter"）
- `config: Map<String, Object>` — 该节点的配置参数（如 Evaluator 的评估 prompt 模板、Router 的阈值等）
- `subTopology: ReflectionTopology` — 嵌套子拓扑（仅当 `primitiveType == COMPOSITE` 时非空，用于 ChatDev 的阶段嵌套）
- `timeoutMs: long` — 该节点的超时时间（覆盖拓扑级默认值）

### 5.3 Edge

描述节点之间的有向连接及其流转条件。

**属性**：
- `edgeId: String` — 边的唯一标识
- `edgeType: EdgeType` — 边的类型（枚举：SEQUENTIAL / FORK / JOIN）
- `from: List<String>` — 源节点 ID 列表（SEQUENTIAL和FORK通常为单个，JOIN为多个上游）
- `to: List<String>` — 目标节点 ID 列表（SEQUENTIAL和JOIN通常为单个，FORK为多个下游）
- `condition: EdgeCondition` — 流转条件类型（枚举）
- `conditionValue: String` — 条件的参数值（如阈值分数）

**`EdgeType` 枚举**：
- `SEQUENTIAL` — 顺序边。from 完成后，按 condition 决定是否走向 to（默认类型）
- `FORK` — 分叉边。from 完成后，同时触发所有 to 目标节点并发执行
- `JOIN` — 汇合边。所有 from 上游节点完成后，才触发 to 目标节点

**`EdgeCondition` 枚举**（扩展后）：
- `ALWAYS` — 无条件流转
- `ON_RETRY` — Router 返回 RETRY 时
- `ON_STOP` — Router 返回 STOP 时
- `ON_FALLBACK` — Router 返回 FALLBACK 时
- `ON_CONTINUE` — Router 返回 CONTINUE 时
- `ON_SUCCESS` — Evaluation.isSuccess == true（Voyager 模式：成功→存技能）
- `ON_FAIL` — Evaluation.isSuccess == false（Voyager 模式：失败→存经验）
- `ON_SCORE_ABOVE(threshold)` — Evaluation.score >= 阈值
- `ON_SCORE_BELOW(threshold)` — Evaluation.score < 阈值
- `ON_IMPORTANCE_ABOVE(threshold)` — Evaluation.importanceScore >= 阈值（Generative Agents 模式）
- `ON_IMPORTANCE_BELOW(threshold)` — Evaluation.importanceScore < 阈值
- `ON_CONSISTENT` — Evaluation.isConsistent == true（CoVe 模式）
- `ON_INCONSISTENT` — Evaluation.isConsistent == false（CoVe 模式）
- `ON_BRANCH(branchName)` — 匹配特定分支名（LLMRouter 或 MCTSRouter 返回的 BRANCH 决策）
- `ON_RETRIEVE` / `ON_NO_RETRIEVE` — RetrievalGate 返回的检索决策（Self-RAG 模式）

### 5.4 PrimitiveType 枚举

```java
enum PrimitiveType {
    ACTOR, EVALUATOR, REFLECTOR, ROUTER, MEMORY, SYNTHESIZER, RETRIEVAL_GATE,
    COMPOSITE  // 嵌套子拓扑，通过 subTopology 字段指向另一个 ReflectionTopology
}
```

### 5.5 嵌套拓扑（Composite）

一个 `ReflectionTopology` 可以作为另一个拓扑中的一个节点（`primitiveType = COMPOSITE`）。被嵌套的拓扑有独立的入口、出口、迭代计数，但共享外层拓扑的 `ReflectionContext`（数据总线透传）。

**嵌套时的上下文传递**：
- 外层 `ReflectionContext` 的 `outputs`、`evaluations`、`reflections` 列表透传到内层拓扑
- 内层拓扑的迭代计数器独立（内层 `maxIterations` 可以小于外层）
- 内层拓扑到达出口后，控制权返回外层拓扑的外层节点，继续沿出边流转
- 嵌套深度受 `maxRecursionDepth` 限制，超限则记录警告并跳过嵌套执行

**典型用例**：ChatDev 模式。每个阶段（需求分析、设计、编码、测试）是一个独立的子拓扑，内部有自己的 Actor→Evaluator→Router→Retry 闭环。外层拓扑将这些阶段串行连接。

### 5.6 拓扑校验规则

拓扑在构建（`build()`）或动态加载（`DynamicTopologyBuilder`）时需要校验以下规则：
- 入口节点必须存在于 `nodes` 中
- 所有出口节点（`exitNodeIds`）必须存在于 `nodes` 中
- 每条边的 `from` 和 `to` 引用的节点必须存在
- Fork 边必须有 ≥2 个 `to`，Join 边必须有 ≥2 个 `from`
- 节点不能有矛盾的条件边（如同时有 `ON_SUCCESS` 和 `ON_FAIL` 边都指向不同目标）
- 存在回路时必须有 Router 节点和 STOP 出口（确保可终止）
- 嵌套拓扑（`primitiveType == COMPOSITE`）必须有非空的 `subTopology`
- `TopologyValidator` 作为独立组件，供 Builder 和动态加载时复用

## 六、拓扑执行引擎

### 6.1 TopologyExecutor

解释器模式的实现，是反思系统的核心运行时组件。它不包含业务逻辑——所有决策委托给原语，它只负责图遍历和并发协调。

**职责**：
1. 从 `entryNodeId` 开始遍历
2. 每个节点：通过 `PrimitiveFactory` 解析原语实例 → 调用 `execute(ctx)` → 收集返回值到 `ReflectionContext`
3. 遇到 `COMPOSITE` 节点时，递归创建子执行器进入嵌套拓扑
4. Fork 边：使用 `Flux.merge()` 或线程池并发启动所有目标节点
5. Join 边：使用 `CountDownLatch` 或 `Flux.zip()` 等待所有上游分支完成后再触发目标节点
6. Router 节点的返回值优先匹配边的条件（`ON_RETRY` → 走 retry 边，`ON_STOP` → 走 stop 边）
7. RetrievalGate 节点的返回值匹配 `ON_RETRIEVE` / `ON_NO_RETRIEVE` 等条件
8. 到达 `exitNodeIds` 中任一节点时终止
9. 超过 `maxIterations` 或 `maxRecursionDepth` 时强制终止并降级
10. 跨节点调用 `MemoryHook` 回调（见第十三章）
11. 异常处理：单个节点失败时，如果拓扑定义了 `ON_FALLBACK` 边则走降级路径，否则终止并抛出

**核心方法**：
- `execute(topology, ctx)` → `Flux<TopologyEvent>`：流式执行拓扑，每经过一个节点发射 `TopologyEvent`
- `executeBlocking(topology, ctx)` → `ExecutionResult`：阻塞执行，返回最终输出文本

**ExecutionResult 属性**：
- `finalOutput: String` — 最终输出文本
- `totalIterations: int` — 总迭代次数（含嵌套）
- `scores: List<Double>` — 各轮评分序列（可绘制趋势图）
- `totalDurationMs: long` — 总耗时
- `nodeDurations: Map<String, Long>` — 各节点耗时分布

### 6.2 TopologyEvent

执行器在遍历过程中发出的事件，供上层（Stage）消费并转换为 SSE。

**类型**（枚举）：
- `NODE_START` — 开始执行某个节点（含 `nodeId`、`primitiveType`、`iteration`）
- `NODE_END` — 节点执行完毕（含执行耗时、原语返回结果摘要）
- `NODE_ERROR` — 节点执行出错（含异常信息）
- `FORK_START` — 开始并发分叉（含分支数和分支节点 ID 列表）
- `JOIN_COMPLETE` — 所有并发分支完成，准备汇合
- `ITERATION_START` — 新一轮迭代开始（含迭代序号）
- `MESSAGE` — 流式输出文本块（来自 Actor 的流式输出）
- `REFLECTION` — 反思文本已生成
- `EVALUATION` — 评估结果（含评分和问题列表）
- `MEMORY_STORE` — 记忆已写入
- `MEMORY_RETRIEVE` — 记忆已检索
- `RETRIEVAL_DECISION` — 检索决策已做出（RetrievalGate 输出）
- `NESTED_TOPOLOGY_START` — 开始执行嵌套子拓扑
- `NESTED_TOPOLOGY_END` — 嵌套子拓扑执行完毕
- `TOPOLOGY_END` — 拓扑执行完毕（含最终输出、总迭代次数、总耗时、评分序列）

## 七、数据总线

### 7.1 ReflectionContext

贯穿整个拓扑执行过程的上下文对象，是所有原语之间传递数据的唯一载体。

**管线级透传**（从 AgentContext 1:1 映射）：
- `agentContext: AgentContext` — LyClaw 管线级上下文（sessionId、traceId、sandboxLevel、toolRegistry）

**迭代状态**：
- `iteration: int` — 当前迭代序号（从 0 开始，Fork 分支共享同一序号）
- `phaseName: String` — 当前阶段名（嵌套拓扑时标识所在阶段，如 "requirements"、"design"）

**Actor 产物**：
- `outputs: List<String>` — 各轮/各分支 Actor 的输出文本（按时间顺序追加）
- `currentOutput: String` — 最近一轮 Actor 的输出（快捷引用）
- `toolResults: List<String>` — 工具执行结果列表

**Evaluator 产物**：
- `evaluations: List<Evaluation>` — 各轮 Evaluator 的评估结果（按时间顺序追加）
- `lastEvaluation: Evaluation` — 最近一次评估结果（快捷引用）
- `currentIssues: List<Issue>` — 最近一次评估的问题列表（Actor 读取此字段做 Self-Refine）

**Reflector 产物**：
- `reflections: List<String>` — 各轮 Reflector 生成的反思文本
- `currentReflection: String` — 当前轮次的反思文本（下一轮 Actor 读取并注入 prompt）

**Memory 产物**（由 Memory Hook 写入）：
- `activeMemories: List<MemoryRecord>` — 本轮检索到的相关记忆记录（替代简单类型，包含类型+内容+元数据）
- `retrievedSkills: List<SkillRecord>` — 检索到的相似技能（Voyager 模式）
- `retrievedExperiences: List<ExperienceRecord>` — 检索到的相似经验（Voyager 模式）
- `retrievedDocuments: List<String>` — 检索到的外部文档（Self-RAG 模式）

**检索与知识**（由 RetrievalGate 或 Memory Hook 写入）：
- `taskSummary: String` — 当前任务的简短摘要（Actor 执行后写入，Memory 检索用）
- `taskTags: List<String>` — 任务类型标签（如 "code_generation"、"bug_fix"）
- `retrievalNeeded: boolean` — 是否需要检索（RetrievalGate 输出）

**搜索树状态**（LATS 模式专用，由 MCTSRouter 维护）：
- `treeState: MCTSTreeState` — MCTS 搜索树状态对象（包含节点统计信息）
  - `MCTSTreeState` 内部维护 `Map<String, TreeNodeStats>`，每个节点有 `visits: int`、`totalValue: double`
  - UCT 计算公式：`UCT = meanValue + C * sqrt(ln(parent.visits) / node.visits)`
  - `C` 为探索常数（默认 sqrt(2) ≈ 1.414）
- `currentSearchNodeId: String` — 当前在搜索树中的节点 ID
- `searchPath: List<String>` — 从根节点到当前节点的路径（用于回溯）

**持久化与分区**（供 Memory Hook 使用）：
- `userId: String` — 用户标识（从 AgentContext 提取）
- `projectId: String` — 项目标识（从 AgentContext 或配置提取）
- `persistentSessionKey: String` — 跨 session 的持久化标识

**最终产物**：
- `finalOutput: String` — 拓扑执行完成后的最终输出

**通用扩展**：
- `attributes: Map<String, Object>` — 通用扩展属性，供自定义原语和 Hook 传递数据

## 八、Stage 集成

### 8.1 ReflectionTopologyStage

实现 `ReactivePipelineStage`，在管线中替代 `RespondStage`（当前 `getOrder()=3`）和 `ReflectionStage`（当前 `getOrder()=4`）。

**注解声明**：
```java
@PipelineStage(name = "ReflectionTopology", after = SecurityCheckStage.class, group = "CORE")
```

**职责**：
1. **拓扑查找**：从 `ReflectionTopologyRegistry` 按 `agentContext.getAgentId()` 查找拓扑。找不到则使用默认拓扑（`passthrough`：`Actor → STOP`）
2. **上下文构建**：从 `AgentContext` 创建 `ReflectionContext`，初始化所有列表和计数器，注入 `userId`、`projectId` 等分区键
3. **执行拓扑**：委托 `TopologyExecutor.execute(topology, reflectionCtx)` 执行，接收 `Flux<TopologyEvent>`
4. **SSE 转换**：将 `TopologyEvent` 映射为 `ServerSentEvent`
5. **降级兜底**：拓扑执行异常时，回退到 `SimpleChatActor` 单次调用，确保 Agent 总是能返回内容
6. **指标记录**：向 `MetricsCollector` 写入拓扑级指标
7. **反思评分回写**：将最终评分写入 `agentContext.getReflectScoreRef()`

**SSE 映射表**：

| TopologyEvent | SSE Event | SSE Data |
|--------------|-----------|----------|
| `MESSAGE` | `sseEvent("message", chunk)` | 文本块 |
| `EVALUATION` | `sseEvent("evaluation", data)` | `{score, reasoning, issues}` |
| `REFLECTION` | `sseEvent("reflection_feedback", text)` | 反思文本 |
| `RETRIEVAL_DECISION` | `sseEvent("retrieval", data)` | `{decision, query}` |
| `FORK_START` | `sseEvent("branch_start", data)` | `{branches, iteration}` |
| `TOPOLOGY_END` | `sseEvent("done", data)` | `{output, iterations, score}` |

## 九、动态代理简化

### 9.1 AgentInvocationHandler 改造

当前 `AgentInvocationHandler` 的 `executeStages()` 方法（第 386-452 行）包含约 70 行反思闭环逻辑。**改造后全部删除**。`executeStages()` 退化为纯线性串联：

```
for each stage (sorted by getOrder()):
    pipeline = pipeline.concatWith(stage.execute(ctx))
```

阻塞模式同理。AgentInvocationHandler 不再包含任何"反思"概念——它只是一个 Stage 调度器。

### 9.2 为什么动态代理本身不需要变

`@Agent` 注解 → `AgentProxyFactory.createProxy()` → `AgentInvocationHandler` 这条链保持不变。原因：

1. Agent 的定义方式不变：`@Agent` 接口 + `@SystemMessage` 方法
2. AgentInvocationHandler 的核心职责不变：解析注解、构建上下文、调度 Stage、触发 Hook
3. 变化仅在管线的 Stage 组成：`RespondStage + ReflectionStage` → `ReflectionTopologyStage`
4. Stage 组成由 Spring 自动发现（`@PipelineStage` 注解），不依赖代码硬编码

## 十、注册与查找

### 10.1 双层注册表

**第一层：拓扑注册表（ReflectionTopologyRegistry）**

管理 Agent 到拓扑的映射关系。

**职责**：
- `register(agentId, topology)` — 注册拓扑
- `resolve(agentId, taskHint?)` — 查找拓扑（可选的任务提示用于动态拓扑选择）
- `unregister(agentId)` — 移除拓扑
- `listTopologies()` — 列出所有已注册的拓扑
- `registerDynamic(agentId, topology)` — 运行时注册动态生成的拓扑

**解析优先级**（高到低）：
1. `@ReflectionConfig` 注解（编译时声明）
2. YAML/Properties 配置文件（部署时配置）
3. 运行时动态注册（AI生成 或 代码调用 `register()`）
4. 框架默认拓扑（`passthrough`：`Actor → STOP`）

**第二层：原语工厂（PrimitiveFactory）**

管理原语实现 Bean 的查找与实例化。

**职责**：
- `resolve(type: PrimitiveType, name: String)` → `ReflectionPrimitive`
- `register(type, name, instance)` — 注册自定义原语
- `listImplementations(type)` — 列出某类型的所有可用实现

`TopologyExecutor` 不直接依赖 Spring 容器，通过 `PrimitiveFactory` 间接获取原语实例。

### 10.2 启动时的拓扑构建流程

```
应用启动
  │
  ├── 1. Spring 扫描 @PipelineStage → 发现 ReflectionTopologyStage → 注册为 Bean
  │
  ├── 2. Spring 扫描 @Agent 接口
  │       │
  │       ├── 有 @ReflectionConfig → 解析注解 → 生成拓扑对象 → 注册到 Registry
  │       └── 无 @ReflectionConfig → 不注册（运行时使用默认拓扑）
  │
  ├── 3. 加载 YAML 配置文件（agent-config.yml）
  │       │
  │       └── 解析 topology 配置 → 注册/覆盖到 Registry
  │
  ├── 4. 扫描所有 MemoryHook Bean → 注册到 MemoryHookRegistry
  │
  └── 5. 构建管线
          │
          └── AgentInvocationHandler 注入 List<ReactivePipelineStage>
              （包含 ReflectionTopologyStage）
```

### 10.3 原语目录（PrimitiveCatalog）

当 AI 需要在运行时动态生成拓扑时，它必须知道**有哪些原语可用**——就像一个厨师需要知道厨房里有什么食材。`PrimitiveCatalog` 是原语实现的自描述注册表，暴露给 LLM 作为拓扑生成的"零件清单"。

**职责**：
- `listAll()` → `List<PrimitiveDescriptor>` — 列出所有已注册的原语实现
- `listByType(PrimitiveType)` → `List<PrimitiveDescriptor>` — 按类型筛选
- `resolve(type, name)` → `PrimitiveDescriptor` — 查找单个原语的描述信息
- `toPromptFragment()` → `String` — 生成可直接注入 LLM prompt 的文本描述
- `register(type, descriptor)` — 注册新原语（插件/扩展用）

**`PrimitiveDescriptor` 属性**：
- `primitiveType: PrimitiveType` — 原语类型
- `implementationName: String` — 实现 Bean 名（如 `"toolVerifierEvaluator"`）
- `displayName: String` — 人类可读名称（如 "工具验证评估器"）
- `description: String` — 功能描述（如 "运行外部命令或测试套件验证代码输出，支持多种验证模式"）
- `configSchema: Map<String, ConfigParam>` — 可配置参数清单（参数名 → 类型+默认值+说明）
- `applicableScenarios: List<String>` — 适用场景标签（如 `["code_generation", "bug_fix", "refactoring"]`）
- `requiresLLM: boolean` — 是否调用 LLM（帮助 AI 估算成本和延迟）
- `typicalLatencyMs: long` — 典型延迟（帮助 AI 做拓扑性能预估）

**`ConfigParam` 属性**：
- `type: String` — 参数类型（`"string"`, `"int"`, `"double"`, `"boolean"`, `"enum"`）
- `defaultValue: String` — 默认值
- `description: String` — 参数说明
- `required: boolean` — 是否必填
- `allowedValues: List<String>` — 枚举类型的可选值

**`toPromptFragment()` 输出示例**（供 LLM 做拓扑生成）：
```
可用原语清单：

## ACTOR
- reActActor: 执行ReAct循环（思考→工具调用→观察），可调用工具完成任务。参数: maxSteps(默认10), temperature(默认0.7)
- simpleChatActor: 单次LLM调用，无工具。参数: temperature(默认0.7)

## EVALUATOR
- toolVerifierEvaluator: 运行外部命令验证输出，支持EXIT_CODE/TEST_SUITE/OUTPUT_DIFF/CUSTOM_SCRIPT四种验证模式。参数: verificationType(默认TEST_SUITE), command(必填), testOutputFormat(默认junit_xml)
- llmJudgeEvaluator: 调用LLM对输出打分评估。参数: evalPrompt(必填), dimensions(默认["正确性","完整性"])
- heuristicEvaluator: 纯规则评估（正则匹配），低成本低延迟。参数: rules(正则规则列表)

## REFLECTOR
- verbalReflector: 调用LLM生成文字反思建议。参数: temperature(默认0.3)
- topologyPlanner: 特殊Reflector，生成JSON拓扑定义用于动态拓扑构建。参数: 无

## ROUTER
- thresholdRouter: 基于评分阈值做STOP/RETRY决策。参数: threshold(默认0.7), maxRetries(默认3)
- llmRouter: 调用LLM综合决策下一步流向。参数: temperature(默认0.1)

...（其他原语类型同理）
```

**PrimitiveCatalog 的注册时机**：
- Spring 启动时，每个原语 Bean 通过 `@PrimitiveDescriptor` 注解声明自身描述信息
- `PrimitiveCatalog` 扫描所有带该注解的 Bean，自动构建目录
- 开发者自定义原语只需添加注解即可自动注册

```java

    displayName = "工具验证评估器",
    description = "运行外部命令或测试套件验证代码输出，支持多种验证模式",
    applicableScenarios = {"code_generation", "bug_fix"},
    requiresLLM = false,
    typicalLatencyMs = 3000
)
public class ToolVerifierEvaluator implements Evaluator { ... }
```

## 十一、开发者使用方式

### 11.1 三层配置体系

| 层级 | 方式 | 适用场景 | 灵活性 |
|------|------|---------|--------|
| 第一层 | 注解声明 | 简单场景，快速上手 | 低（选模板 + 调参数） |
| 第二层 | 编程式 Builder | 需要自定义原语组合或参数 | 高（任意组合） |
| 第三层 | 完全自定义 Stage | 非图结构的反思架构（如 DSPy 编译时优化） | 最高（完全自由） |

### 11.2 第一层：注解声明

在 `@Agent` 接口上添加 `@ReflectionConfig` 注解。

**`@ReflectionConfig` 注解属性**：
- `topology: String` — 预置拓扑模板名，默认 "passthrough"。可选值见第十二章
- `maxRetries: int` — 最大重试次数，默认 3
- `threshold: double` — 质量阈值（0.0~1.0），默认 0.7
- `evaluator: String` — Evaluator 实现名，默认 "llmJudge"
- `memoryEnabled: boolean` — 是否启用跨会话记忆，默认 false
- `memoryType: String` — 记忆存储类型（"inMemory" / "redis"），默认 "inMemory"
- `customPrompt: String` — 自定义评估 prompt 模板

### 11.3 第二层：编程式 Builder

开发者通过 `ReflectionTopology.builder()` 流式 API 组装拓扑。

**Builder 核心方法**：
- `topologyId(String)` / `name(String)` — 标识
- `actor(String implName, Map config)` — 添加 Actor 节点
- `evaluator(String implName, Map config)` — 添加 Evaluator 节点
- `reflector(String implName)` — 添加 Reflector 节点（可选）
- `router(String implName, Map config)` — 添加 Router 节点
- `memory(String implName)` — 添加 Memory 节点（可选）
- `synthesizer(String implName)` — 添加 Synthesizer 节点（可选）
- `retrievalGate(String implName)` — 添加 RetrievalGate 节点（可选）
- `compositeNode(String nodeId, ReflectionTopology sub)` — 添加嵌套拓扑节点
- `edge(String from, String to, EdgeCondition cond)` — 添加顺序边
- `forkEdge(String from, List<String> to)` — 添加分叉边
- `joinEdge(List<String> from, String to)` — 添加汇合边
- `maxIterations(int)` / `maxRecursionDepth(int)` — 迭代与递归限制
- `exitNode(String nodeId)` — 标记出口节点
- `build()` — 构建并校验（内部调用 `TopologyValidator`）

**Builder 校验（build() 时自动执行）**：
- 入口节点存在、出口节点可达
- 无孤立节点（每个非出口节点至少有一条出边）
- Fork 边目标数 ≥ 2，Join 边来源数 ≥ 2
- 有回路时必须存在 Router 和 STOP 出口
- 嵌套拓扑节点必须有有效的 subTopology

### 11.4 第三层：完全自定义 Stage

开发者完全不使用框架的拓扑引擎，自己实现 `ReactivePipelineStage`。

适用场景：
- **DSPy 编译时优化**：完全不同的执行范式（训练集→多轮编译→指标收敛→编译产物）
- 需要与外部工作流引擎（Prefect、Temporal）深度集成
- 非图结构的自定义反思逻辑

## 十二、预置拓扑模板

框架内置多种拓扑模板，可在 `ReflectionTopologyRegistry` 中按名称查找。

### 12.1 passthrough（直通，框架默认）

```
Actor ──[ALWAYS]──▶ STOP
```

无反思，单轮 ReAct 执行后直接输出。等同于当前的无反思 RespondStage 行为，是所有 Agent 的默认拓扑。

### 12.2 reflexion（反思循环）

```
Actor ──[ALWAYS]──▶ Evaluator ──[ALWAYS]──▶ Memory.store
                                              │
  ┌───────────────────────────────────────────┘
  ▼
Router ──[ON_STOP]──▶ STOP
  │
  └──[ON_RETRY]──▶ Reflector ──[ALWAYS]──▶ Actor
```

- Actor：`ReActActor`（注入反思文本到 prompt）
- Evaluator：`LLMJudgeEvaluator`
- Reflector：`VerbalReflector`
- Router：`ThresholdRouter`
- Memory：`InMemoryReflectionStore`
- Synthesizer：`LastOutputSynthesizer`
- 对应：Shinn et al., NeurIPS 2023

### 12.3 self-refine（自我修正）

```
Actor ──[ALWAYS]──▶ Evaluator ──[ALWAYS]──▶ Router
                                               │
                    ┌──────────────────────────┘
                    │ ON_RETRY
                    ▼
                  Actor（读取 currentIssues，追加 "请改进以下问题：{issues}"）
                    │
                    └──[ALWAYS]──▶ Evaluator ──[ALWAYS]──▶ Router ──[ON_STOP]──▶ STOP
```

- 无独立 Reflector，Actor 直接读取 `currentIssues`
- 对应：Madaan et al., NeurIPS 2023

### 12.4 critic（工具验证）

```
Actor ──[ALWAYS]──▶ ToolVerifierEvaluator ──[ALWAYS]──▶ Router
                         │                                  │
                         │ ON_RETRY                         │ ON_STOP
                         ▼                                  ▼
                       Actor（注入工具失败输出）              STOP
```

- Evaluator：`ToolVerifierEvaluator`，执行外部命令根据退出码判断 `isSuccess`
- 无 Reflector，工具失败输出直接作为反馈
- 对应：Gou et al., ICLR 2024

### 12.5 auto-debate（多Agent辩论）

```
                    ┌──────────────────────────────┐
                    │        FORK (并发分支)         │
                    └──┬─────────┬──────────┬───────┘
                       ▼         ▼          ▼
                 ┌────────┐ ┌────────┐ ┌────────┐
                 │Actor A │ │Actor B │ │Actor C │  （不同角度/策略）
                 └───┬────┘ └───┬────┘ └───┬────┘
                     │          │          │
                     └──────────┼──────────┘
                                │ JOIN (同步栅栏)
                                ▼
                       ┌────────────────┐
                       │CrossExaminer   │  （统一交叉检验）
                       │Evaluator       │
                       └───────┬────────┘
                               │
                          ┌────┴────┐
                          │ Router  │
                          └────┬────┘
                               │
                     ┌─────────┼──────────┐
                     │ ON_RETRY            │ ON_STOP
                     ▼                     ▼
              回到 FORK（下一轮辩论）   WeightedVotingSynthesizer → STOP
```

- 使用 `EdgeType.FORK` + `EdgeType.JOIN`
- Evaluator：`CrossExaminerEvaluator`
- Synthesizer：`WeightedVotingSynthesizer`
- 对应：Wu et al., AutoGen 2024

### 12.6 chatdev（多阶段角色链）

```
  entry ┌──────────┐      ┌──────────┐      ┌──────────┐      ┌──────────┐
  ─────▶│ Phase 1  │─────▶│ Phase 2  │─────▶│ Phase 3  │─────▶│ Phase 4  │──▶ STOP
        │ 需求分析  │      │ 设计     │      │ 编码     │      │ 测试     │
        │ (子拓扑)  │      │ (子拓扑)  │      │ (子拓扑)  │      │ (子拓扑)  │
        └──────────┘      └──────────┘      └──────────┘      └──────────┘
```

- 每个 Phase 是一个嵌套的 `ReflectionTopology`（`primitiveType = COMPOSITE`）
- 每个子拓扑内有 `Actor→Evaluator→Router→RETRY环`，通过后进入下一阶段
- 对应：Qian et al., 2024

### 12.7 generative-agents（重要性触发反思）

```
Actor ──[ALWAYS]──▶ ImportanceEvaluator ──[ALWAYS]──▶ Router
                                                         │
                                      ┌──────────────────┼──────────────────┐
                                      │ ON_IMPORTANCE_ABOVE                 │ ON_IMPORTANCE_BELOW
                                      ▼                                     ▼
                                  Reflector ──▶ Memory.store(INSIGHT)     STOP（直接输出，跳过反思）
```

- Evaluator：`ImportanceEvaluator`，输出 `importanceScore`
- 边条件：`ON_IMPORTANCE_ABOVE(threshold)` / `ON_IMPORTANCE_BELOW(threshold)`
- 反思不是每轮都做，动态频率
- 对应：Park et al., 2023

### 12.8 voyager（技能库积累）

```
                         ┌──────────────────────────────────────┐
                         │        Memory                        │
                         │  ┌──────────┐  ┌──────────┐         │
                         │  │技能库     │  │经验库     │         │
                         │  │(成功→技能)│  │(失败→经验)│         │
                         │  └─────┬────┘  └─────┬────┘         │
                         └────────┼──────────────┼──────────────┘
                                  │              │
  entry ┌──────┐  ALWAYS  ┌──────┴──────┐  ┌────┴────────┐
  ─────▶│Actor │─────────▶│ Evaluator   │──▶│ Router      │
        │      │          │             │  │             │
        └──┬───┘          └─────────────┘  └──┬──┬───────┘
           │                                  │  │
           │  ON_FAIL（注入经验到prompt）       │  │ ON_SUCCESS
           └──────────────────────────────────┘  ▼
                                           Memory.storeSkill → STOP
```

- 边条件：`ON_SUCCESS` / `ON_FAIL` 分流
- 成功→Memory 写入技能库，失败→检索经验→注入 Actor→重试
- 对应：Wang et al., NeurIPS 2023

## 十三、记忆系统钩子

### 13.1 设计动机

记忆系统的读写需求因反思模式不同而差异显著。Reflexion 需要在 Reflector 后持久化反思，Voyager 需要在 Evaluator 后按成功/失败分流写入，Generative Agents 只有在重要性高时才写入。不能把记忆读写硬编码在 TopologyExecutor 中——必须通过钩子（Hook）机制让记忆系统独立演进。

### 13.2 MemoryHook 接口

定义一组生命周期回调，记忆系统按需实现。所有方法有默认空实现（不强制全部实现），写入操作异步执行不阻塞拓扑。

```java
public interface MemoryHook {

    /**
     * Hook #1: 拓扑启动时。
     * 时机: TopologyExecutor.execute() 入口。
     * 用途: 检索跨session的全局记忆。
     * 写入: ctx.activeMemories（覆盖）
     */
    default void onTopologyStart(ReflectionContext ctx, ReflectionTopology topology) {}

    /**
     * Hook #2: Actor 执行前。
     * 时机: 每个 Actor 节点执行前。
     * 用途: 检索与当前task最相关的记忆/技能/经验。
     *       注入到 ctx.activeMemories / retrievedSkills / retrievedExperiences。
     *       Actor 内部读取这些字段注入到 system prompt。
     */
    default void onBeforeActor(ReflectionContext ctx, NodeDef actorNode) {}

    /**
     * Hook #3: Evaluator 完成后。
     * 时机: 每个 Evaluator 节点执行后。
     * 用途: 条件化写入记忆。
     *       - Evaluation.isSuccess → 写入技能库（Voyager）
     *       - !Evaluation.isSuccess → 写入经验库（Voyager）
     *       - Evaluation.importanceScore >= threshold → 标记需要深度反思（Generative Agents）
     *       异步写入，不阻塞拓扑继续执行。
     */
    default void onAfterEvaluation(ReflectionContext ctx, Evaluation evaluation) {}

    /**
     * Hook #4: Reflector 完成后。
     * 时机: 每个 Reflector 节点执行后。
     * 用途: 持久化反思文本到长期记忆。
     */
    default void onAfterReflection(ReflectionContext ctx, String reflection) {}

    /**
     * Hook #5: 拓扑执行完毕。
     * 时机: 到达exitNode或超过maxIterations。
     * 用途: 将最终输出+整体summary写入记忆，触发consolidation。
     *       清理临时状态。
     */
    default void onTopologyEnd(ReflectionContext ctx, ExecutionResult result) {}

    /**
     * Hook #6: 重要性评估（可选，Generative Agents模式）。
     * 时机: 可在每次iteration后调用。
     * 用途: 计算当前事件的重要性，决定是否触发Reflection。
     * @return 重要性分数(0.0~1.0)，实现方可从ctx中读取任何字段来计算
     */
    default double evaluateImportance(ReflectionContext ctx) { return 1.0; }

    /**
     * Hook #7: 检索门控（可选，Self-RAG模式）。
     * 时机: Actor执行前。
     * 用途: 判断当前iteration是否需要RAG检索。
     * @return true表示需要检索
     */
    default boolean shouldRetrieve(ReflectionContext ctx) { return false; }
}
```

### 13.3 MemoryHookRegistry

管理 MemoryHook 的注册与调用。

**职责**：
- 扫描所有 `MemoryHook` Bean，按 `@Order` 排序
- `invokeAll(consumer)` — 遍历所有 Hook 异步执行回调（`CompletableFuture.runAsync`，不阻塞拓扑）
- TopologyExecutor 在每个生命周期节点调用 `hookRegistry.invokeAll(h -> h.onXxx(...))`

### 13.4 不同模式的钩子使用对照

| 模式 | onTopologyStart | onBeforeActor | onAfterEvaluation | onAfterReflection | onTopologyEnd |
|------|:---:|:---:|:---:|:---:|:---:|
| Reflexion | 检索历史reflection | 检索本轮reflection | — | 持久化reflection | 持久化summary |
| Voyager | 检索全部技能 | 检索相似技能 | **成功→写技能 / 失败→写经验** | — | 更新技能评分 |
| Generative Agents | — | — | 重要性高→标记 | 持久化insight | consolidation |
| Self-RAG | — | RAG检索判断 | — | — | — |
| 简单模式 | — | — | — | — | — |

## 十四、动态反思

### 14.1 概念

开发者可以不预先定义拓扑，而是让 AI 在运行时根据任务特征动态生成反思拓扑。这是"元拓扑"模式。

### 14.2 元拓扑结构

```
TaskAnalyzer(Actor) ──▶ TopologyPlanner(Reflector的特殊实现)
                              │
                              │ 输出: {"topologyId":"dynamic-001", "nodes":{...}, "edges":[...]}
                              ▼
                        DynamicTopologyBuilder 解析 JSON → 校验 → 构建 ReflectionTopology
                              │
                              ▼
                        TopologyExecutor 递归执行子拓扑
```

### 14.3 实现要点

- `TopologyPlanner` 是 Reflector 的特殊实现，prompt 导向生成 JSON 拓扑定义而非自然语言反思
- `DynamicTopologyBuilder` 将 LLM 输出的 JSON 反序列化为 `ReflectionTopology`，内部调用 `TopologyValidator` 做结构校验
- 校验失败时，返回错误给 LLM 让其修正（最多 2 次修正机会），或降级到默认拓扑
- 执行器递归执行：遇到动态生成的拓扑时，通过 `ReflectionTopologyRegistry.registerDynamic()` 注册，然后递归创建执行器
- 递归深度受 `maxRecursionDepth` 限制（默认 3 层）

### 14.4 适用场景

- "帮我修复这个 bug" → AI 分析：需要读代码→定位→生成修复→测试验证 → 自动生成 CRITIC 拓扑
- "写一篇技术博客" → AI 分析：需要大纲→初稿→自审→修改→润色 → 自动生成 Self-Refine 拓扑
- "帮我设计系统架构" → AI 分析：需要调研→方案A→方案B→对比评估 → 自动生成 auto-debate 拓扑
- "解决这个复杂的数学问题" → AI 分析：需要多分支探索+回溯 → 自动生成 LATS 拓扑

### 14.5 动态 Agent 生成

当 Agent 不再只是 `@Agent` 注解的编译时接口，而是由 AI 在运行时根据需求动态创建时，需要一套运行时 Agent 注册机制。

**触发场景**：
- 用户在对话中说"帮我创建一个专门审查 Python 代码的 Agent"
- AI 根据任务特征自动生成专用的临时 Agent（如一次性数据迁移 Agent）
- 多 Agent 协作场景，协调者 Agent 动态 spawn 子 Agent

**`DynamicAgentDefinition` 数据模型**：

```java
public class DynamicAgentDefinition {
    String agentId;              // 唯一标识（运行时生成）
    String displayName;          // 显示名称
    String systemPrompt;         // 系统提示词
    List<String> toolNames;      // 绑定的工具名列表（引用 ToolRegistry）
    String topologyId;           // 绑定的反思拓扑（引用 ReflectionTopologyRegistry）
    String modelName;            // 使用的模型（可选，默认继承）
    Map<String, Object> config;  // 扩展配置（temperature, maxTokens 等）
    Long ttlMs;                  // 存活时间（临时 Agent 到期自动注销，null=永久）
}
```

**`AgentRegistry` 接口**：

```java
public interface AgentRegistry {
    // 运行时注册动态 Agent
    AgentDefinition register(DynamicAgentDefinition def);

    // 注销动态 Agent
    void unregister(String agentId);

    // 查找 Agent 定义（先查注解 Agent，再查动态 Agent）
    Optional<AgentDefinition> resolve(String agentId);

    // 列出所有 Agent（含注解和动态）
    List<AgentDefinition> listAll();

    // 按拓扑 ID 查找使用该拓扑的所有 Agent
    List<AgentDefinition> findByTopology(String topologyId);
}
```

**`AgentDefinition` 统一模型**（注解 Agent 和动态 Agent 的统一表示）：
- `agentId: String`
- `source: AgentSource` — 枚举：`ANNOTATION`（编译时注解）/ `DYNAMIC`（运行时注册）
- `systemPrompt: String`
- `toolNames: List<String>`
- `topologyId: String`
- `modelName: String`
- `ttlMs: Long` — 仅 `DYNAMIC` 来源有效

**AgentInvocationHandler 的查找逻辑**：

```
AgentInvocationHandler.invoke(agentId, userMessage):
    // 查找优先级：动态 Agent > 注解 Agent
    agentDef = agentRegistry.resolve(agentId)
    if (agentDef == null):
        throw AgentNotFoundException(agentId)

    // 统一构建 AgentContext（无论 Agent 来源）
    topology = topologyRegistry.resolve(agentId, taskHint?)
    // 如果 agentId 在 topologyRegistry 中没有匹配，使用 agentDef.topologyId 查找

    ctx = AgentContext.builder()
        .agentId(agentId)
        .systemPrompt(agentDef.systemPrompt)
        .toolNames(agentDef.toolNames)
        .topologyId(agentDef.topologyId)
        // ...
        .build()

    // 后续流程与注解 Agent 完全相同
    return executePipeline(ctx)
```

**与现有 `@Agent` 注解的关系**：
- Spring 启动时扫描 `@Agent` → 自动转为 `AgentDefinition(source=ANNOTATION)` → 注册到 `AgentRegistry`
- 运行时 `register(DynamicAgentDefinition)` → 转为 `AgentDefinition(source=DYNAMIC)` → 注册到 `AgentRegistry`
- `resolve(agentId)` 统一查找，动态 Agent 优先级高于注解 Agent（允许运行时覆盖）

**完整的动态 Agent 生命周期**：

```
1. 用户请求 → "创建一个Python代码审查Agent"
2. LLM（TopologyPlanner 或 MetaAgent）分析需求
3. 输出 DynamicAgentDefinition JSON:
   {
     "agentId": "python-reviewer",
     "systemPrompt": "你是Python代码审查专家...",
     "toolNames": ["file_read", "shell_exec", "web_search"],
     "topologyId": "critic",     ← 使用预置 CRITIC 拓扑
     "ttlMs": 3600000            ← 1小时后自动清理
   }
4. 如果 topologyId 指向的拓扑不存在或需要定制
   → TopologyPlanner 同时生成自定义拓扑 JSON
   → DynamicTopologyBuilder 构建 → 注册到 ReflectionTopologyRegistry
5. AgentRegistry.register(agentDef)  → Agent 立即可用
6. 后续调用 "python-reviewer" 与普通注解 Agent 完全一致
7. TTL 到期 → 自动 unregister（清理 Agent + 关联的临时拓扑）
```

### 14.6 全动态模式：拓扑 + Agent 均由 AI 生成

结合 `PrimitiveCatalog`、`DynamicTopologyBuilder`、`AgentRegistry`，可以实现**零预配置**的全动态模式：

```
用户: "帮我审查这个项目的代码质量"

1. TaskAnalyzer(LLM) 分析任务:
   → 任务类型: code_review
   → 需要能力: 读文件、运行lint、分析代码模式
   → 建议拓扑: CRITIC 变体（ToolVerifierEvaluator + LLMJudgeEvaluator 组合）

2. TopologyPlanner(LLM) 生成拓扑 JSON:
   → 查询 PrimitiveCatalog.toPromptFragment() 获取零件清单
   → 生成拓扑: Actor(lint→修复) → ToolVerifierEvaluator(EXIT_CODE) → LLMJudgeEvaluator(代码质量评分) → ThresholdRouter → STOP
   → DynamicTopologyBuilder 校验+构建 → 注册为 "code-review-topology"

3. 如需专用 Agent:
   → 生成 DynamicAgentDefinition{agentId:"code-reviewer", topologyId:"code-review-topology", ...}
   → AgentRegistry.register()

4. 执行拓扑:
   → TopologyExecutor 加载 "code-review-topology" → 逐节点执行

整个过程没有一行 YAML 配置，没有一行 Java 注解，全部由 LLM 在运行时决策。
```

## 十五、设计模式总结

| 设计模式 | 应用位置 | 作用 |
|---------|---------|------|
| **Strategy** | 七个原语接口 | 每种原语多种实现，拓扑不关心具体实现类 |
| **Builder** | `ReflectionTopology.Builder` | 流式 API 构建图数据对象，`build()` 时自动校验 |
| **Composite** | `COMPOSITE` 节点类型 | 拓扑可作为另一个拓扑中的节点，嵌套执行 |
| **Template Method** | `ReflectionTopologyStage.execute()` | Stage 固定生命周期骨架，拓扑填充执行步骤 |
| **Registry** | `ReflectionTopologyRegistry` + `PrimitiveFactory` + `PrimitiveCatalog` + `AgentRegistry` + `MemoryHookRegistry` | Agent↔拓扑、原语名→实例、原语发现、动态Agent注册、Hook→回调 的五层解耦 |
| **Interpreter** | `TopologyExecutor` | 遍历图，调用节点原语，按条件选边，协调 Fork/Join |
| **Decorator** | `ReflectionTopologyStage` vs `RespondStage` | 对外接口相同（`ReactivePipelineStage`），内部能力增强 |
| **Observer** | `MemoryHook` 回调 | 记忆系统观察拓扑执行事件，异步响应，不侵入核心逻辑 |
| **Catalog** | `PrimitiveCatalog` | 自描述的原语实现注册表，供 AI 发现可用零件并生成拓扑 |
