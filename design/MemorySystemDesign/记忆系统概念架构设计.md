# LyClaw Agent 记忆系统 — 概念架构设计

> 状态：草案
> 基于：认知科学CoALA框架 + Generative Agents + MemGPT + Mem0 + 业界主流框架调研
> 前置依赖：无（记忆系统是基础设施层，零内部依赖）

---

## 一、记忆分类模型

借鉴认知科学（CoALA框架）和业界实践，Agent的记忆系统分为四类功能记忆加实体记忆。这种分类的核心思想是"功能分离"——不同类型的记忆有不同的时间常数、存储格式、检索方式和生命周期，不能混在一起当一种东西处理。

```
┌──────────────────────────────────────────────────────────────┐
│                     Agent 记忆系统                            │
│                                                              │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  │  工作记忆    │  │  情节记忆    │  │  语义记忆    │  │  程序记忆    │
│  │  Working    │  │  Episodic   │  │  Semantic   │  │ Procedural  │
│  ├─────────────┤  ├─────────────┤  ├─────────────┤  ├─────────────┤
│  │ 当前上下文窗口 │  │ 带时间戳的   │  │ 抽取的事实   │  │ 技能与规则   │
│  │ 系统提示词    │  │ 交互事件流   │  │ 知识条目     │  │ 行为指令     │
│  │ 活跃对话轮次  │  │ "发生了什么"  │  │ "知道什么"   │  │ "怎么做"    │
│  ├─────────────┤  ├─────────────┤  ├─────────────┤  ├─────────────┤
│  │ 存活：单次请求 │  │ 存活：天~周  │  │ 存活：周~永久 │  │ 存活：持久   │
│  │ 容量：Token窗 │  │ 容量：无限   │  │ 容量：无限   │  │ 容量：少量   │
│  │ 读写：极快    │  │ 读写：快     │  │ 读写：中等   │  │ 读写：低频   │
│  └─────────────┘  └─────────────┘  └─────────────┘  └─────────────┘
│                                                              │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │                    实体记忆 (Entity)                     │ │
│  │  跨类型的结构化画像：用户画像、文档画像、项目画像          │ │
│  │  动态更新、版本管理、冲突检测                             │ │
│  └─────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

### 1.1 工作记忆 (Working Memory)

**它是什么**：Agent 的"意识"。当前正在处理的所有信息——就像你此刻脑子里活跃的思考内容。在认知科学中，人类工作记忆容量约为 7±2 个信息块，只能维持约 20 秒。对 Agent 而言，工作记忆就是 LLM 的上下文窗口。

**在Agent中的具体形态**：
- 系统提示词（定义了Agent的角色、行为规则、输出格式）
- 当前会话的历史消息（本轮和过去几轮对话）
- 工具调用的输入和输出
- 刚才检索出来的相关记忆条目（从情节/语义记忆中检索到的）
- 引导文件内容（AGENTS.md、SOUL.md等）

**核心特性**：
- **容量有限**：受 LLM 上下文窗口的 token 上限约束。超出则触发压缩（Compaction）或截断
- **完全易失**：请求结束即释放。下次请求时从零开始重建
- **访问极快**：不需要任何检索算法，LLM 直接在注意力机制中"看到"所有内容
- **写入隐式**：程序员不需要显式"写工作记忆"，对话消息自动成为工作记忆的一部分

**与其它记忆的关系**：工作记忆是其它记忆的"消费端"。情节记忆和语义记忆中检索到的内容被加载到工作记忆，程序记忆中的规则在工作记忆中约束Agent的行为。工作记忆中的内容经过过滤后，被写入情节记忆。

**示例**：
```
当前工作记忆内容（一个Agent看到的东西）：
┌────────────────────────────────────────────┐
│ System: 你是代码审查助手。                │
│         规则：只审查Safety和Logic问题。    │   ← 来自程序记忆
│         背景：用户偏好PostgreSQL、Rust。   │   ← 来自语义记忆（检索注入）
│         上次审查：该用户不喜欢过度注释。    │   ← 来自情节记忆（检索注入）
├────────────────────────────────────────────┤
│ User: 帮我审查这个PR                       │
├────────────────────────────────────────────┤
│ Assistant: 好的，先读取变更文件。           │
│ Tool Call: grep("src/", "TODO")            │
│ Tool Result: [3处TODO]                     │
└────────────────────────────────────────────┘
```

### 1.2 情节记忆 (Episodic Memory)

**它是什么**：Agent 的"自传"。记录了 Agent 经历过什么——和谁、在什么时候、发生了什么、结果如何。在人类认知中，海马体负责将日常经历编码为情节记忆，带有明确的时间戳和空间上下文。对 Agent 而言，情节记忆就是带时间线的交互事件流。

**在Agent中的具体形态**：
- 每次对话的完整或摘要记录（"上周三和用户讨论了数据库迁移"）
- 每个任务执行的轨迹（"任务#123从分解到执行到完成"）
- 工具调用的历史记录（"上次对`src/main.rs`运行grep找到了什么"）
- 反思引擎的评估结果（"那次回复的准确率评分为0.65，低于阈值"）
- 错误和失败记录（"上次做代码审查时第3步超时了"）

**核心特性**：
- **带时间戳**：每条记录都有明确的发生时间。时间信息是检索的关键因子
- **按时间自然衰减**：越久远的情节记忆检索价值越低（但不一定被删除）
- **不可修改**（通常）：情节记忆是历史记录，不应事后修改。矛盾或错误通过新增更正条目来处理
- **容量极大**：理论上无限，实际上取决于存储能力
- **是语义记忆的原料**：情节记忆中的原始事件被提炼后形成语义记忆

**检索方式**：
- 时间检索："上次对话是什么时候？"
- 语义检索："找一下之前关于数据库迁移的讨论"
- 三因子加权：近因性 × 重要性 × 相关性

**示例**：
```
情节记忆中的一条记录：
┌────────────────────────────────────────────┐
│ id: epi-20260523-0042                      │
│ session_id: sess-abc123                     │
│ timestamp: 2026-05-23T14:22:30Z            │
│ event_type: TASK_EXECUTION                  │
│ summary: "代码审查任务#123：扫描src/main.rs， │
│          发现3处TODO和1处潜在空指针"          │
│ importance: 0.7                             │
│ related_entities: ["user:张三",              │
│    "project:payment-service"]                │
│ source: session sess-abc123, turns 3-7      │
│ reflection_score: 0.85                      │
│ recall_count: 2                             │
│ strength: 0.91                              │
└────────────────────────────────────────────┘
```

**关键区分**：情节记忆保存的是"事件"——在什么时间、什么情境下发生了什么。它不保存从事件中抽象出来的通用知识。例如，"我在5月23日帮张三审查了payment-service"是情节记忆；"payment-service使用Rust + Postgres"是语义记忆。

### 1.3 语义记忆 (Semantic Memory)

**它是什么**：Agent 的"知识库"。存储从情节记忆中抽取的通用事实、概念和关系——去掉了时间上下文，只保留知识本身。人类的语义记忆就是你无需回忆"什么时候学到"就能脱口而出的知识。对 Agent 而言，语义记忆就是可检索的长期知识存储。

**在Agent中的具体形态**：
- 用户偏好和画像（"张三偏好PostgreSQL、Rust、简洁注释风格"）
- 项目技术知识（"payment-service的技术栈是Rust+PostgreSQL 15"）
- 领域知识（"代码审查中`unsafe`代码块属于Safety类问题"）
- 从多次任务中总结的模式（"该用户的PR通常包含数据库迁移，最常出现的问题是缺少索引"）
- 决策记录（"2026年5月决定将日志系统从logback迁移到log4j2，原因是性能"）

**核心特性**：
- **去时间化**：语义记忆不携带"什么时候学到的"。它只是已知的事实
- **可合并更新**：新的事实与已有语义记忆通过相似度判断后合并（ADD/UPDATE/DELETE/NOOP）
- **有向量表示**：每条语义记忆都生成嵌入向量，支持语义相似度检索
- **强度不衰减**（或极慢衰减）：有用的知识不应该遗忘
- **可关联**：语义记忆条目之间有链接关系，形成知识网络

**检索方式**：
- 语义搜索："用户偏好什么数据库？"
- 关键词搜索："PostgreSQL"
- 实体关联："和payment-service相关的所有知识"

**示例**：
```
语义记忆中的一条记录：
┌────────────────────────────────────────────┐
│ id: sem-20260523-0107                      │
│ memory_type: USER_PREFERENCE                │
│ summary: "张三偏好PostgreSQL 15，倾向于使用  │
│          sqlx而非ORM，重视查询性能"           │
│ embedding: [0.12, -0.08, 0.34, ...]  (768维)│
│ importance: 0.9                             │
│ recall_count: 15                            │
│ source_episodes: [epi-...042, epi-...089]   │  ← 可追溯到原始情节记忆
│ related: [sem-...0106, sem-...0108]          │
│ created_at: 2026-05-23T14:22:30Z            │
│ updated_at: 2026-05-23T16:45:00Z            │
│ strength: 0.98                              │
└────────────────────────────────────────────┘
```

**从情节到语义的转换**：
```
情节记忆 (多条)                      语义记忆 (一条提炼的知识)
┌──────────────────┐               ┌──────────────────────────┐
│ 5/23: 张三问了DB  │               │                          │
│ 迁移，选了PG 15   │──────┐        │ "张三的项目使用           │
├──────────────────┤      │        │  PostgreSQL 15 + sqlx，   │
│ 5/25: 张三讨论   │      ├───→    │  偏好原生SQL，            │
│ ORM vs sqlx      │──────┘        │  查询性能是首要关注点"     │
├──────────────────┤               │                          │
│ 5/28: 张三的PR   │──→ ADD/UPDATE │ importance: 0.9           │
│ 包含查询优化      │               │ source: [epi-..]         │
└──────────────────┘               └──────────────────────────┘
```

### 1.4 程序记忆 (Procedural Memory)

**它是什么**：Agent 的"技能和习惯"。存储 Agent 应该怎么做的知识和规则。人类的程序记忆让你无需思考就能骑车、打字。对 Agent 而言，程序记忆就是行为约束、执行策略和可复用的工作流程。

**在Agent中的具体形态**：
- 系统提示词中定义的规则（"只审查Safety和Logic，不审查Style"）
- 引导文件中定义的角色行为（BOOTSTRAP.md 中的工作流程）
- 从过往成功或失败中学到的策略（"下次做代码审查时，先读Cargo.toml了解依赖"）
- Skill库：Agent可以调用的可复用工作流或技能配方
- 反思引擎的调整策略（"检测到幻觉时，强制增加验证步骤"）

**核心特性**：
- **容量小但稳定**：程序记忆条目通常很少（几十到几百条就足够）
- **几不衰减**：有用的技能和规则不应随时间遗忘
- **触发式检索**：不是靠语义搜索，而是靠条件匹配——"当遇到X情况，执行Y策略"
- **可版本管理**：技能随着反思迭代更新，需要保留旧版本以便回退
- **来源多样**：手动定义（引导文件） + 自动产生（反思调整）

**写入来源**：
- 手动：系统提示词、引导文件、管理员配置的规则
- 自动：反思引擎建议调整策略 → 经审批后写入程序记忆
- 自动：从多次成功任务中提取可复用的工作步骤

**示例**：
```
程序记忆中的一条记录：
┌────────────────────────────────────────────┐
│ id: proc-20260523-0003                      │
│ name: "Rust代码审查策略"                    │
│ trigger: task_type == "code_review"         │
│          AND language == "rust"             │
│ content:                                    │
│   1. 先读Cargo.toml了解依赖                │
│   2. 搜索unsafe代码块                       │
│   3. 搜索.unwrap()和.expect()               │
│   4. 检查输入验证                           │
│   5. 不要评论代码风格（除非是明显的错误）    │
│ learned_from: epi-...042 (成功审查)         │
│              epi-...089 (失败审查，步骤2遗漏)│
│ performance: 成功3次 / 失败1次              │
︎│ version: 3                                  │
│ updated_at: 2026-05-28T10:00:00Z            │
└────────────────────────────────────────────┘
```

**程序记忆的演化**：
- 初始：来自手动编写的系统提示词和引导文件
- 第1次任务后：Agent发现缺少关键步骤，反思引擎建议添加
- 第N次任务后：多条成功/失败经验被合并，形成成熟的策略条目
- 持续：低成功率的策略被高成功率的替代（进化）

### 1.5 实体记忆 (Entity Memory)

**它是什么**：跨记忆类型的结构化画像，是Agent与外部实体（用户、项目、文档、工具）长期交互形成的综合知识。它与语义记忆的区别在于——语义记忆是零散的"知识点"，实体记忆是围绕一个外部实体组织起来的"完整档案"。

**为什么需要它**：
- 语义记忆中有 20 条关于"张三"的知识，散落在不同条目中，需要聚合
- 每次检索都需要跨多条语义记忆拼接用户画像，效率低
- 实体画像需要版本管理和冲突检测（新旧信息矛盾时怎么办）

**在Agent中的具体形态**：
- 用户画像：姓名、角色、偏好、习惯、交互统计
- 项目画像：技术栈、代码规范、常见问题模式、关键决策记录
- 文档画像：重要文档的摘要、关键词、变更历史
- 工具画像：哪些工具最常用、哪些容易出错、使用心得

**核心特性**：
- **结构化 + 非结构化混合**：既有固定字段（姓名、角色），也有动态属性（偏好JSONB）
- **持久且高频更新**：每次交互都可能更新实体画像的某个字段
- **版本管理**：更新时保留旧版本，支持冲突检测和回退
- **有嵌入向量**：支持按实体名或实体属性语义检索
- **跨记忆类型**：一个实体的信息可能来自情节记忆（交互事件）、语义记忆（提取的知识）、程序记忆（与该实体相关的策略）

**示例**：
```
实体记忆中的一条记录 — 用户画像：
┌────────────────────────────────────────────┐
│ entity_id: user-zhangsan                    │
│ entity_type: USER                           │
│ base_attributes:                            │
│   name: "张三"                              │
│   role: "后端工程师"                        │
│   department: "支付组"                      │
│ dynamic_profile:                            │
│   tech_preferences:                         │
│     database: ["PostgreSQL 15", "sqlx"]     │
│     language: ["Rust", "Go"]                │
│     style: "简洁注释、重性能"               │
│   review_patterns:                          │
│     common_issues: ["缺少索引", "未处理错误"] │
│     avg_pr_size: "中型(200-500行)"           │
│ interaction_summary:                        │
│   total_sessions: 42                        │
│   total_tasks: 156                          │
│   avg_reflection_score: 0.78                │
│   last_active: 2026-05-28T16:00:00Z         │
│ embedding: [0.45, -0.12, 0.67, ...]        │
│ version: 23                                 │
│ updated_at: 2026-05-28T16:00:00Z            │
└────────────────────────────────────────────┘
```

### 五种记忆的关系总结

```
                    ┌────────────────────────────────────────┐
                    │         实体记忆 (Entity)               │
                    │  聚合、结构化、版本管理                   │
                    │  跨记忆类型的综合画像                    │
                    └──────────┬─────────────────────────────┘
                               │ 从下方三种记忆中抽取和聚合
            ┌──────────────────┼──────────────────┐
            │                  │                  │
   ┌────────▼──────┐  ┌───────▼───────┐  ┌───────▼──────┐
   │  情节记忆      │  │  语义记忆      │  │  程序记忆     │
   │  (Episodic)   │  │  (Semantic)   │  │ (Procedural) │
   │               │  │               │  │              │
   │  "发生了什么"   │  │  "知道什么"    │  │  "怎么做"     │
   │  带时间的事件   │──→ 从事件提取    │  │  行为策略     │
   │  检索:时间+语义 │  │  检索:语义     │  │  检索:条件匹配 │
   └───────┬───────┘  └───────┬───────┘  └───────┬──────┘
           │                  │                  │
           └──────────────────┼──────────────────┘
                              │ 检索到的内容注入
                    ┌─────────▼──────────┐
                    │   工作记忆 (Working) │
                    │   当前上下文窗口     │
                    │   容量受Token限制    │
                    │   单次请求生命周期   │
                    └────────────────────┘
```

**数据流**：
1. 工作记忆中的对话和工具调用结果 → 编码后写入**情节记忆**
2. 情节记忆中的原始事件 → 巩固提炼后形成**语义记忆**（知识）和**程序记忆**（策略）
3. 情节记忆 + 语义记忆 → 聚合为**实体记忆**（画像）
4. 新请求开始时 → 从情节/语义/程序/实体中检索相关内容 → 注入**工作记忆**
5. 闭环完成：工作记忆 → 情节 → 语义/程序/实体 → 回到工作记忆

## 二、记忆生命周期

一条信息从产生到消亡经历六个阶段：

```
  感知             编码              存储             检索             巩固              衰减/清理
┌────────┐      ┌────────┐      ┌────────┐      ┌────────┐      ┌────────┐      ┌────────┐
│ 原始输入 │ ──→ │ LLM提取 │ ──→ │ 写入对应│ ──→ │ 三因子  │ ──→ │ 定时合并│ ──→ │ 强度归零│
│ 对话消息 │      │ 关键事实 │      │ 记忆层级 │      │ 加权检索 │      │ 去重摘要 │      │ 归档删除 │
│ 工具结果 │      │ 实体关系 │      │         │      │ 注入上下文│      │ 情节→语义│      │         │
│ 反思评分 │      │ 重要性分 │      │         │      │         │      │         │      │         │
└────────┘      └────────┘      └────────┘      └────────┘      └────────┘      └────────┘
```

### 2.1 阶段一：感知 (Perception)

管线共6个阶段，但不是每个阶段都有值得记忆的产出。ContextBuild（加载引导文件）和SecurityCheck（安全校验）是准备性动作，产出没有记忆价值。实际记忆摄入发生在3个有意义的节点：

**摄入节点1 — RespondStage 之后（核心）**
- 触发时机：ReAct循环结束，LLM响应和工具调用完成
- 摄入内容：本轮用户消息、助手回复、工具调用及其结果、是否触发审批
- 价值：这是最核心的情节记忆原料，记录了"发生了什么"

**摄入节点2 — ReflectionStage 之后**
- 触发时机：反思引擎完成质量评估
- 摄入内容：质量评分（准确率/完整性/安全性）、检测到的错误类型、建议的调整策略
- 价值：高价值元记忆，"上次这样做失败了"的经验教训

**摄入节点3 — CompactionStage 之前（MemoryFlush）**
- 触发时机：上下文窗口接近token上限，即将执行压缩
- 摄入内容：将被压缩掉的对话历史中尚未提取的关键事实
- 价值：压缩等于永久丢弃上下文窗口中的内容，必须在丢弃前抢救未保存的知识

**暂存机制**：所有摄入的原始感知数据先进入感知缓冲区（perception buffer），不做处理，等待下一阶段的编码任务异步执行。

### 2.2 阶段二：编码 (Encoding)

借鉴 Mem0 的两阶段流水线设计：

**第一遍 — 提取**：
- 输入：最新对话 + 滚动摘要 + 最近 N 条消息
- LLM 提取：关键事实、实体提及、用户决策、偏好变化、任务结果
- 输出：候选记忆条目列表，每条带重要性预评分

**第二遍 — 决策**：
- 对每条候选记忆，在已有记忆中做语义相似检索（Top-K）
- LLM 判定四种操作之一：

| 操作 | 含义 | 触发条件 |
|------|------|---------|
| ADD | 全新信息，直接写入 | 无相似已有记忆 |
| UPDATE | 补充或更新已有信息 | 语义相似但内容更新 |
| DELETE | 新旧矛盾，标记旧记忆为过时 | 冲突检测触发 |
| NOOP | 信息已存在或无关，跳过 | 高度重复 |

### 2.3 阶段三：存储 (Storage)

根据编码阶段的操作结果，写入对应的记忆层级：

- **情节记忆**：完整的交互事件记录，带时间戳、session_id、事件类型标签
- **语义记忆**：从情节记忆中提取的事实和知识点，去除了时间上下文
- **程序记忆**：Agent 学到的行为规则和技能
- **实体记忆**：人物/文档/项目等实体的结构化画像

### 2.4 阶段四：检索 (Retrieval)

借鉴 Generative Agents (Park et al., 2023) 的三因子加权检索：

```
检索分数 = α × Recency(近因性) + β × Importance(重要性) + γ × Relevance(相关性)

Recency    = e^(-λ × Δt)              # 指数衰减，最近访问越近分越高
Importance = LLM评分或规则评分(0~1)     # 重要事件天然优先
Relevance  = cosine(Query向量, Memory向量)  # 语义匹配
```

- α、β、γ 可配置权重，默认各为 1/3
- 每次检索命中后，该记忆的 `recall_count` +1，`strength` 重新计算
- 这模仿人类记忆的"再巩固"（reconsolidation）机制：每次回忆都会刷新记忆强度

**多通道检索**（可选增强）：
1. 语义检索 — 向量嵌入相似度
2. 关键词检索 — BM25 精确匹配
3. 时间检索 — 时间范围筛选
4. 实体检索 — 关联实体图遍历

结果通过 RRF（Reciprocal Rank Fusion）融合：`RRFscore(d) = Σ( 1 / (k + rank_i(d)) )`，k 通常取 60。

### 2.5 阶段五：巩固 (Consolidation)

借鉴 SleepGate 的"睡眠周期"思想，在后台异步运行：

**第一阶段：突触降缩 (Synaptic Downscaling)**
- 所有记忆强度整体衰减（标准化衰减）
- 消除噪声，让弱信号归零

**第二阶段：选择性回放 (Selective Replay)**
- 高重要性、高访问频率的记忆被加强
- 类似人类慢波睡眠中的尖波涟漪（sharp-wave ripples）

**第三阶段：定向修剪 (Targeted Pruning)**
- 低强度、长期未访问的记忆标记为可归档
- 冗余记忆合并

**情节→语义转换**：
- 触发条件：短期记忆缓冲区达到阈值（如20条）或定时（如每小时）
- 合并算法：
  - LLM 对短期情节记忆做摘要压缩
  - 计算摘要向量 vs 已有语义记忆向量的余弦相似度
  - 相似度 > 0.85：合并到已有语义记忆（更新摘要和访问时间）
  - 相似度 0.6~0.85：作为关联条目存储（建立语义链接）
  - 相似度 < 0.6：新建语义记忆条目
- 保留 `source_chunks` 字段追溯原始情节记忆

### 2.6 阶段六：衰减与清理 (Decay & Eviction)

基于 Ebbinghaus 遗忘曲线：

```
基础公式：  R(t) = e^(-t / S)                    S = 记忆强度，初始值越高衰减越慢
增强公式：  strength = importance × e^(-λ_eff × days) × (1 + recall_count × 0.2)

其中 λ_eff = 0.16 × (1 - importance × 0.8)
```

关键参数：

| 参数 | 含义 | 典型值 |
|------|------|--------|
| importance | 重要性评分 (0~1) | LLM或规则评分 |
| recall_count | 被检索命中的次数 | 每次检索命中 +1 |
| strength | 当前记忆强度 | 实时计算，低于阈值触发清理 |
| eviction_threshold | 清理阈值 | strength < 0.01 时归档或删除 |

**清理策略**：
- 软删除：标记 `expired = true`，保留数据用于审计
- 硬删除：Janitor 定时任务扫描 `expired = true AND updated_at < now() - 30天`，物理删除
- 临时Agent的SESSION作用域记忆：会话结束时直接标记过期

## 三、记忆作用域模型

针对"每个Agent独立上下文，临时vs永久Agent"的需求，定义四级作用域：

```
┌──────────────────────────────────────────────┐
│              SESSION (会话级)                  │
│  agent_id + session_id                        │
│  会话结束即标记可清理                           │
│  临时Agent的所有记忆都在此作用域                 │
│  示例："本次调试会话中发现的临时问题"             │
├──────────────────────────────────────────────┤
│              PERSONAL (Agent私有)              │
│  agent_id                                     │
│  跨会话持久，仅该Agent可见                      │
│  永久Agent的核心记忆在此作用域                   │
│  示例："code-reviewer Agent对用户代码偏好的了解"│
├──────────────────────────────────────────────┤
│              TEAM (团队共享)                    │
│  team_id / project_id                         │
│  同项目多个Agent共享的知识                      │
│  白板记忆、任务决策、协作上下文                  │
│  示例："项目A的技术栈选型决策"                   │
├──────────────────────────────────────────────┤
│              GLOBAL (全局公共)                  │
│  所有Agent可见                                 │
│  组织级知识、通用规则                           │
│  示例："公司代码规范文档内容"                    │
└──────────────────────────────────────────────┘
```

### 临时Agent清理机制

1. 临时Agent创建时标记 `agent_type = TEMPORARY` + `ttl`（生存时间）
2. 会话结束时，该Agent在 SESSION 作用域的所有记忆标记为 `expired`
3. PERSONAL 作用域的记忆：检查是否仅此Agent持有引用，若是则也标记过期
4. TEAM/GLOBAL 作用域的记忆：不随临时Agent消亡而删除（属于共享知识）
5. 后台 Janitor 定时任务：扫描过期记忆 → 检查依赖 → 物理删除或归档

## 四、与管线的集成点

记忆系统与管线的交互分为两条路径：**读路径**（检索记忆用于增强上下文）和**写路径**（摄入新记忆）。两条路径只在有意义的节点触发，不是每个管线阶段都参与。

```
请求进入
   │
   ▼
ContextBuildStage  ←── 【读】检索记忆，注入System Prompt
   │                    在管线最开始，根据当前用户意图和对话上下文检索相关历史记忆
   │                    memorySystem.retrieve(query, agentId, topK=10)
   │                    检索范围：PERSONAL + TEAM + GLOBAL
   │                    检索算法：三因子加权 + 语义匹配
   │                    检索结果注入到Agent的系统提示词中，作为"背景知识"
   │
   ▼
SecurityCheckStage  （无记忆交互）
   │
   ▼
PlanExecutionStage  （可选）将检索到的记忆条目传入TaskPlanner
   │                    TaskPlanner 利用历史经验优化任务分解策略
   │                    "上次类似任务拆了5步，第3步失败过，这次调整"
   │
   ▼
RespondStage  ←── 【读】ReAct循环中，LLM通过memory_search工具自主检索
   │                    Agent可以主动调用记忆检索工具查找更多上下文
   │                    "用户提到了PostgreSQL，让我查查之前的偏好"
   │               【写】摄入点1 — RespondStage 之后
   │                    本轮对话内容和工具调用结果写入感知缓冲区
   │                    memorySystem.ingest(sessionId, PerceptionData.of(turn))
   │                    这是最核心的情节记忆原料
   │
   ▼
ReflectionStage  ←── 【写】摄入点2 — ReflectionStage 之后
   │                    反思引擎的质量评估结果写入感知缓冲区
   │                    memorySystem.ingest(sessionId, PerceptionData.of(reflection))
   │                    记录：评估结论、质量评分、检测到的错误、调整策略
   │                    这是高价值元记忆："上次这样做失败了"的经验教训
   │
   ▼
CompactionStage  ←── 【写】摄入点3 — 压缩前 MemoryFlush
   │                    上下文窗口即将超过token上限，必须压缩历史
   │                    memorySystem.flush(sessionId)
   │                    在压缩（丢弃）历史之前，抢救其中尚未提取的关键事实
   │                    压缩等于永久遗忘，这是遗忘前最后的记忆保存机会
   │
   ▼
MetricsStage     （无记忆交互）
                    管线执行摘要（耗时/任务数/成功率）可作为可选感知数据摄入
                    但通常是轻量级元数据，不一定是高价值记忆
```

**总结**：

| 管线阶段 | 读 | 写 | 说明 |
|----------|:--:|:--:|------|
| ContextBuildStage | ✅ | ❌ | 检索记忆增强上下文 |
| SecurityCheckStage | ❌ | ❌ | 无记忆交互 |
| PlanExecutionStage | 可选 | ❌ | 利用历史经验优化计划 |
| RespondStage | ✅ | ✅ | Agent自主检索 + 摄入对话内容 |
| ReflectionStage | ❌ | ✅ | 摄入反思结论 |
| CompactionStage | ❌ | ✅ | MemoryFlush抢救即将遗忘的内容 |
| MetricsStage | ❌ | ❌ | 无记忆交互 |

## 五、待讨论的设计决策

### 5.1 Agent是否可以自主编辑自己的记忆？

**Letta 的设计**：Agent 通过工具调用 `core_memory_replace("name", "new_value")` 自行修改记忆块。

**优势**：Agent 更自主，能自我纠正错误记忆
**风险**：Agent 可能"记错"或被提示注入篡改记忆

**选项**：
- A. 只允许系统在管线阶段自动写入，Agent 只能检索不能修改
- B. 允许 Agent 通过工具自主编辑 PERSONAL 作用域的记忆
- C. 允许 Agent 编辑所有作用域，但变更需要审计日志

### 5.2 重要性评分：LLM打分还是规则打分？

**LLM 打分**（Generative Agents 方案）：
- 每个感知事件调用 LLM 评分（1-10）
- 准确但成本高（每条记忆一次LLM调用）

**规则打分**：
- 出现专有名词 +0.3
- 用户明确说"记住这很重要" +0.5
- 反思评分高（>0.8）+0.2
- 涉及决策/偏好变化 +0.4
- 成本低但粗糙

**折中方案**：大部分事件用规则打分，触发巩固（consolidation）时才用LLM重新评估重要性。

### 5.3 情节记忆何时转成语义记忆？

**定时触发**：每天凌晨跑一次巩固任务
- 适合：延迟要求低的系统，批量处理效率高

**事件驱动**：短期记忆缓冲区满 N 条触发
- 适合：需要及时巩固的场景

**两者结合**（推荐）：
- 事件触发局部巩固（增量）：缓冲区满20条 → LLM摘要 → 与已有语义记忆对比合并
- 定时触发全量巩固（批量）：每天凌晨执行 SleepGate 三阶段（降缩→回放→修剪）

### 5.4 记忆共享的权限边界

核心问题：同项目的Agent A说"用户喜欢PostgreSQL"，Agent B做代码审查时能自动读到这条吗？

**选项**：
- A. 严格隔离：Agent A 写入的默认 PERSONAL，除非显式声明 `scope=TEAM`
- B. 自动共享：同项目内所有 Agent 的 PERSONAL 记忆互相可见
- C. 分层默认：用户偏好类 → TEAM 自动共享；技术细节类 → PERSONAL 私有

### 5.5 记忆系统自身的记忆（元记忆）

记忆系统是否应该记录自己的行为？
- "上次检索时Top-3的结果里第1条最有帮助" → 用于调优检索权重
- "该Agent的记忆中70%已经强度低于0.1" → 用于触发更激进的清理
- "最近的巩固任务平均耗时2.3秒" → 用于监控和调优
