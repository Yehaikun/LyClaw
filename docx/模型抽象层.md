## 一、模块定位与业务目标

### 1.1 一句话定位

> **模型抽象层是 LyClaw 的"翻译官"，负责将应用内部的统一对话请求翻译成各个大模型厂商能理解的格式，并将厂商的响应翻译回统一格式，让上层业务无需关心底层调用的是哪家厂商的模型。**

### 1.2 业务背景

LyClaw 是一个 AI 网关应用，用户配置自己的大模型 API Key 后，通过统一入口调用各种大模型。市面上有多个大模型厂商，每家都有自己的 API 格式：

| 厂商 | API 格式 | system 位置 | content 类型 | Token 字段 |
|------|----------|-------------|-------------|------------|
| MiniMax | Anthropic 兼容 | 顶层 `system` 字段 | 对象数组 `[{type, text}]` | `input_tokens` / `output_tokens` |
| DeepSeek | OpenAI 兼容 | `messages[0]` 中 `role=system` | 纯字符串 | `prompt_tokens` / `completion_tokens` |
| DeepSeek | Anthropic 兼容 | 顶层 `system` 字段 | 对象数组 `[{type, text}]` | `input_tokens` / `output_tokens` |

如果没有模型抽象层，上层业务（对话服务、Agent 调度等）需要为每个厂商写一套调用逻辑，导致代码臃肿、难以维护。

### 1.3 本层要完成的核心业务

| 业务目标 | 说明 |
|----------|------|
| **统一入口** | 上层只需调用 `adapter.chat(ChatRequest)`，不关心底层是哪个厂商 |
| **格式适配** | 自动将统一请求转为厂商格式，将厂商响应转为统一格式 |
| **动态路由** | 根据配置中的 `provider` 字段，自动选择对应的适配器 |
| **流式支持** | 支持同步对话和流式 SSE 对话两种模式 |
| **工具调用** | 自动适配各厂商的 function calling / tool use 格式 |
| **错误处理** | 统一将 HTTP 错误码、业务错误码转为 ModelException |
| **连接验证** | 提供 API Key 有效性验证（发送最小 token 请求） |

### 1.4 本层不负责的事情

| 不负责 | 由谁负责 |
|--------|----------|
| 存储配置 | lyclaw-storage（ConfigStorage） |
| 会话管理 | AI 引擎层（未来实现） |
| 工具执行 | 工具执行模块（未来实现） |
| 记忆管理 | 记忆管理模块（未来实现） |
| 定时任务 | 定时任务模块（未来实现） |

## 三、设计模式应用全景

本层共应用了 **6 种设计模式**，每种模式解决一个特定的设计问题：

### 3.1 策略模式 — ModelAdapter 接口

**解决的问题**：多种厂商的调用方式不同，但上层只需要一种统一的调用方式。

**实现方式**：定义 `ModelAdapter` 接口作为策略接口，每个厂商的适配器都是该接口的一种具体策略。

```
ModelAdapter (策略接口)
    ↑ 实现
    ├── MinimaxAdapter      — MiniMax 策略
    ├── DeepSeekOpenAIAdapter — DeepSeek OpenAI 策略
    └── (未来) XXXAdapter   — 其他厂商策略
```

**优势**：上层代码只依赖接口，不依赖具体实现。切换厂商只需替换适配器实例。

---

### 3.2 模板方法模式 — AbstractModelAdapter

**解决的问题**：所有厂商的调用流程（校验 → 构建请求 → 发送 → 解析响应 → 转换）是相同的，但每个步骤的具体实现不同。

**实现方式**：`AbstractModelAdapter` 定义了 `chat()` 方法的流程骨架，将可变的步骤（`buildRequest()`、`parseResponse()`、`toUnifiedResponse()`）定义为抽象方法由子类实现。

```
AbstractModelAdapter
│
├── 模板方法（固化流程）:
│   chat()
│   ├── ① beforeCall()        — 钩子（可选重写）
│   ├── ② buildRequest()      — 抽象（必须实现）
│   ├── ③ sendRequest()       — 抽象（必须实现）
│   ├── ④ parseResponse()     — 抽象（必须实现）
│   ├── ⑤ toUnifiedResponse()  — 抽象（必须实现）
│   └── ⑥ afterCall()         — 钩子（可选重写）
│
├── 公共方法（直接继承）:
│   countTokens() — Token 估算
│   validate()   — 连接验证
│
└── 钩子方法（可选重写）:
    beforeCall()  — 调用前预处理
    afterCall()   — 调用后日志记录
    handleError() — 错误处理
```

**优势**：新增厂商只需实现 3-5 个抽象方法，不需要重写整个调用流程。

---

### 3.3 工厂模式 + 注册表模式 — ModelAdapterFactory

**解决的问题**：如何动态选择对应的适配器？新增适配器如何自动被发现？

**实现方式**：`ModelAdapterFactory` 在启动时扫描所有带 `@Component` 的 `ModelAdapter` 实现，按 `getProvider()` 返回值注册到内部 Map。

```
应用启动
  │
  ▼
ModelAdapterFactory.init()
  │
  ├── 扫描所有 ModelAdapter 类型的 Spring Bean
  ├── 调用 getProvider() 获取厂商名（如 "minimax"）
  ├── 存入 Map: provider → adapter 实例
  └── 完成注册
```

**使用方式**：
```java
// 根据配置动态获取
ModelAdapter adapter = factory.getConfiguredAdapter(modelConfig);
ModelResponse response = adapter.chat(request);
```

**优势**：新增适配器只需加 `@Component` 注解，自动注册，无需修改工厂代码。

---

### 3.4 适配器模式 — 各厂商 Adapter

**解决的问题**：厂商 API 的接口与我们需要的接口不兼容。

**实现方式**：每个厂商适配器将厂商特定的 API 格式转换为我们定义的统一格式。

```
┌──────────────────────┐     ┌──────────────────────┐
│  MiniMax API         │     │  DeepSeek API         │
│                      │     │                       │
│  system: 顶层字段     │     │  system: messages[0]  │
│  content: 数组       │     │  content: 字符串      │
│  token: input/output │     │  token: prompt/comp   │
└──────────┬───────────┘     └──────────┬────────────┘
           │ 适配                       │ 适配
           ▼                            ▼
┌────────────────────────────────────────────────────┐
│              统一格式                              │
│                                                   │
│  ChatRequest → 厂商请求                           │
│  厂商响应 → ModelResponse                         │
└────────────────────────────────────────────────────┘
```

---

### 3.5 建造者模式 — ChatRequest

**解决的问题**：模型请求参数繁多（消息、温度、工具、思考模式等），且大部分是可选的。直接使用构造函数或大量 setter 会让代码难以阅读。

**实现方式**：`ChatRequest` 使用 Lombok `@Builder`，让上层可以链式构建请求。

```java
ChatRequest request = ChatRequest.builder()
    .messages(session.getMessages())
    .systemPrompt("你是编程助手")
    .temperature(0.7)
    .maxTokens(2048)
    .tools(toolRegistry.getAllTools())
    .thinkingEnabled(true)
    .build();
```

**优势**：
- 参数可选，不传则使用默认值
- 链式调用，代码可读性高
- 不变对象，线程安全

---

### 3.6 责任链模式 — ResponseParser

**解决的问题**：不同厂商的响应格式不同（Anthropic 格式 vs OpenAI 格式），需要一种可扩展的方式来判断和解析。

**实现方式**：定义 `ResponseParser` 接口，每个实现负责一种格式。通过 `canParse()` 判断是否能处理。

```
原始响应 JSON
  │
  ├──► AnthropicResponseParser.canParse()
  │    │ 检查是否包含 type: "message"
  │    │
  │    ├── 是 → 解析为 AnthropicResponse
  │    └── 否 → 传递给下一个
  │
  └──► OpenAIResponseParser.canParse()
       │ 检查是否包含 object: "chat.completion"
       │
       ├── 是 → 解析为 OpenAIResponse
       └── 否 → 抛出异常
```

**优势**：新增响应格式只需添加新的 Parser 实现，不影响现有解析器。

### 5.1 lyclaw-common 中的类

---

#### ChatRequest

- **模块**：`lyclaw-common`
- **包路径**：`lyjew.com.lyclaw.model`
- **文件路径**：`lyclaw-common/src/main/java/lyjew/com/lyclaw/model/ChatRequest.java`
- **设计模式**：建造者模式（Builder Pattern）
- **角色**：统一的模型对话请求体，屏蔽不同厂商请求格式的差异

**类职责**：
- 封装一次模型调用所需的全部参数
- 通过 Builder 模式让参数组合灵活且可读
- 提供便捷方法（`hasSystemPrompt()`、`hasTools()`、`getLastUserMessage()` 等）

**核心字段**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `messages` | `List<Message>` | ✅ | 对话历史，至少包含一条用户消息 |
| `model` | `String` | ❌ | 模型名，为空时使用适配器默认模型 |
| `systemPrompt` | `String` | ❌ | 系统提示词 |
| `maxTokens` | `Integer` | ❌ | 生成内容的最大 Token 数 |
| `temperature` | `Double` | ❌ | 温度系数，控制输出随机性 |
| `topP` | `Double` | ❌ | Top-P 采样策略 |
| `tools` | `List<ToolDefinition>` | ❌ | 可用工具列表 |
| `thinkingEnabled` | `boolean` | ❌ | 是否启用思考模式 |
| `thinkingBudget` | `Integer` | ❌ | 思考模式 Token 预算 |
| `toolChoice` | `String` | ❌ | 强制调用指定工具 |
| `stopSequences` | `List<String>` | ❌ | 停止序列 |
| `extras` | `Map<String,Object>` | ❌ | 厂商特有扩展参数 |

**核心方法**：

| 方法 | 返回类型 | 说明 |
|------|----------|------|
| `hasSystemPrompt()` | `boolean` | 是否设置了系统提示 |
| `hasTools()` | `boolean` | 是否有可用工具 |
| `getLastUserMessage()` | `String` | 获取最后一条用户消息 |
| `getMessageCount()` | `int` | 获取消息总数 |

#### ModelResponse

- **模块**：`lyclaw-common`
- **包路径**：`lyjew.com.lyclaw.model`
- **文件路径**：`lyclaw-common/src/main/java/lyjew/com/lyclaw/model/ModelResponse.java`
- **角色**：统一的模型响应体，所有厂商的返回值都转成这个

**类职责**：
- 统一封装模型的回复内容、工具调用、Token 用量
- 提供便捷判断方法

**核心字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `String` | 本次响应的唯一标识 |
| `content` | `String` | AI 回复的文本内容（finishReason="stop" 时有值） |
| `thinking` | `String` | 模型的思考过程（部分厂商支持） |
| `model` | `String` | 实际使用的模型名 |
| `toolCalls` | `List<ToolCallRequest>` | 工具调用请求列表（finishReason="tool_calls" 时有值） |
| `finishReason` | `String` | 停止原因：stop / tool_calls / length / content_filter |
| `usage` | `Usage` | Token 用量统计 |
| `metadata` | `Map<String,Object>` | 厂商特有字段 |

**核心方法**：

| 方法 | 返回类型 | 说明 |
|------|----------|------|
| `hasToolCalls()` | `boolean` | 是否需要调用工具 |
| `hasThinking()` | `boolean` | 是否有思考过程 |
| `isStopped()` | `boolean` | 是否正常结束 |
| `isTruncated()` | `boolean` | 是否因达到长度上限而截断 |

### 6.2 同步对话流程

```java
// 上层业务代码
ModelConfig config = configStorage.get("minimax"); // 从存储层获取配置
ModelAdapter adapter = factory.getConfiguredAdapter(config);

ChatRequest request = ChatRequest.builder()
    .messages(session.getMessages())
    .systemPrompt("你是编程助手")
    .temperature(0.7)
    .build();

ModelResponse response = adapter.chat(request);
// 使用 response.getContent() 获取回复文本
```

```
adapter.chat(request)
  │
  ▼
AbstractModelAdapter.chat(request)              ← 模板方法
  │
  ├── ① beforeCall(request)
  │   │  检查消息列表不为空
  │   │  log.debug 记录请求信息
  │   │
  ├── ② buildRequest(request)                  ← 子类实现
  │   │  MinimaxAdapter:
  │   │    ChatRequest → AnthropicRequest
  │   │    • model → MiniMax-M2.7
  │   │    • systemPrompt → system 顶层字段
  │   │    • messages → Anthropic 格式 messages（content 是数组）
  │   │    • tools → {name, description, input_schema}
  │   │
  │   │  DeepSeekOpenAIAdapter:
  │   │    ChatRequest → OpenAIRequest
  │   │    • model → deepseek-v4-flash
  │   │    • systemPrompt → messages[0] role="system"
  │   │    • messages → OpenAI 格式 messages（content 是字符串）
  │   │    • tools → {type:"function", function:{...}}
  │   │
  │   │  返回 厂商特定请求对象
  │   │
  ├── ③ sendRequest(apiRequest)                ← 子类实现
  │   │  MinimaxAdapter:
  │   │    objectMapper.writeValueAsString(apiRequest) → JSON
  │   │    httpClient.post(baseUrl + "/anthropic/v1/messages", headers, json)
  │   │    返回 原始 JSON 字符串
  │   │
  ├── ④ parseResponse(rawJson)                 ← 子类实现
  │   │  MinimaxAdapter:
  │   │    responseParser.parse(rawJson) → AnthropicResponse
  │   │
  │   │  DeepSeekOpenAIAdapter:
  │   │    responseParser.parse(rawJson) → OpenAIResponse
  │   │
  │   │  返回 厂商响应对象
  │   │
  ├── ⑤ toUnifiedResponse(apiResp)             ← 子类实现
  │   │  MinimaxAdapter:
  │   │    AnthropicResponse → ModelResponse
  │   │    • content[].type="text" 的 text → content
  │   │    • content[].type="thinking" 的 thinking → thinking
  │   │    • stop_reason → finishReason
  │   │    • input_tokens/output_tokens → Usage
  │   │
  │   │  DeepSeekOpenAIAdapter:
  │   │    OpenAIResponse → ModelResponse
  │   │    • choices[0].message.content → content
  │   │    • choices[0].finish_reason → finishReason
  │   │    • choices[0].message.tool_calls → toolCalls
  │   │    • prompt_tokens/completion_tokens → Usage
  │   │
  │   │  返回 ModelResponse
  │   │
  └── ⑥ afterCall(response)                    ← 钩子
      │  记录 Token 用量日志
      │
      ▼
  返回 ModelResponse 给上层
```

### 6.3 流式对话流程

```
adapter.chatStream(request)
  │
  ▼
AbstractModelAdapter.chatStream(request)
  │
  ├── buildStreamRequest(request) — 比普通请求多设 stream=true
  │
  ├── sendStreamRequest(apiRequest)
  │   │
  │   httpClient.postStream(url, headers, body)
  │   │
  │   ▼
  │   OkHttpModelApiClient.postStream()
  │   │
  │   Flux.create(sink -> {
  │       try (Response response = httpClient.newCall(request).execute()) {
  │           // 在 boundedElastic 线程中阻塞读取 SSE 流
  │           BufferedReader reader = ...;
  │           String line;
  │           while ((line = reader.readLine()) != null) {
  │               sink.next(line);  // 逐行推送给下游
  │           }
  │           sink.complete();
  │       }
  │   })
  │   .subscribeOn(Schedulers.boundedElastic())
  │   │
  │   ▼
  │   返回 Flux<String> — 每行是一个 SSE 事件
  │
  ▼
上层订阅这个 Flux，逐行处理 SSE 数据
例如 Controller 将每行直接写回给客户端的 SSE 连接
```

### 6.4 错误处理流程

```
HTTP 请求
  │
  ├── 成功（2xx）
  │   │
  │   ▼
  │   正常解析响应 → ModelResponse
  │
  ├── 401 Unauthorized
  │   │
  │   ▼
  │   ModelException(ErrorCode.MODEL_API_INVALID_KEY, "状态码=401")
  │
  ├── 403 Forbidden
  │   │
  │   ▼
  │   ModelException(ErrorCode.MODEL_API_FORBIDDEN, "状态码=403")
  │

  │   │
  │   ▼

  │

  │   │

  │   ModelException(ErrorCode.MODEL_API_ERROR, "服务器错误, 状态码=5xx")
  │
  └── 其他错误
      │
      ▼
      ModelException.withRawResponse(httpStatus, message, rawBody)
```

## 七、扩展性指南

### 7.1 新增一个厂商适配器

只需 **2 步**，**0 行已有代码改动**：

**步骤 1**：在 `lyclaw-adapter/adapter/` 下新建包，创建适配器类

```java
package lyjew.com.lyclaw.adapter.新厂商;

import lyjew.com.lyclaw.template.AbstractModelAdapter;
import org.springframework.stereotype.Component;

@Component
public class 新厂商Adapter extends AbstractModelAdapter {

    @Override
    public String getProvider() { return "新厂商名"; }

    @Override
    protected Object buildRequest(ChatRequest request) { /* 构建请求 */ }

    @Override
    protected Object parseResponse(String rawResponse) { /* 解析响应 */ }

    @Override
    protected ModelResponse toUnifiedResponse(Object apiResponse) { /* 转统一 */ }

    @Override
    protected String sendRequest(Object apiRequest) { /* 发送请求 */ }

    @Override
    protected Flux<String> sendStreamRequest(Object apiRequest) { /* 流式请求 */ }

    @Override
    protected String getDefaultBaseUrl() { return "https://api.xxx.com"; }

    @Override
    protected String getDefaultModel() { return "xxx-model"; }
}
```

**步骤 2**：如果响应格式是全新的，新建对应的 ResponseParser

```java
@Component
public class 新格式ResponseParser implements ResponseParser {
    @Override
    public boolean canParse(String rawJson) { /* 判断逻辑 */ }
    
    @Override
    public <T> T parse(String rawJson, Class<T> clazz) { /* 解析逻辑 */ }
    
    @Override
    public String getFormat() { return "新格式名"; }
}
```

**完成**！适配器会自动被 `ModelAdapterFactory` 扫描并注册。

### 7.2 新增请求参数

在 `ChatRequest` 中添加字段即可，已有的 Builder 调用不受影响（新字段有默认值）。

### 7.3 新增响应字段

在 `ModelResponse` 中添加字段即可，已有的 setter/getter 调用不受影响。

### 7.4 切换 HTTP 客户端实现

新建一个 `ModelApiClient` 的实现类（如 `WebClientModelApiClient`），加上 `@Component` 注解，或通过 `@ConditionalOnMissingBean` 覆盖默认实现。

## 九、设计原则总结

| 原则 | 体现 |
|------|------|
| **开闭原则** | 新增厂商适配器只需新增类，不修改已有代码 |
| **单一职责** | 每个类职责明确：Adapter 负责适配、Factory 负责管理、Client 负责通信、Parser 负责解析 |
| **依赖倒置** | 上层依赖 ModelAdapter 接口，不依赖具体实现 |
| **里氏替换** | 任何 ModelAdapter 子类都可以替换父类使用 |
| **接口隔离** | ModelAdapter 接口方法精简，不强制子类实现不需要的功能 |
| **迪米特法则** | 上层只和 Factory + Adapter 交互，不直接接触 HTTP 客户端和解析器 |
