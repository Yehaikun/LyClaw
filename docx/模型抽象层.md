## 第一章：整体架构概览

### 1.1 AI 引擎层的定位

AI 引擎层是 LyClaw 的核心业务逻辑层，位于模型抽象层之上、API 网关层之下。它在整个系统中的位置如下：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  lyclaw-web（API 网关层）                                                    │
│  Controller / WebSocket Handler / CLI TUI                                   │
│  职责：接收 HTTP 请求、参数校验、路由转发、SSE 流式写回                       │
└─────────────────────────────────────┬───────────────────────────────────────┘
                                      │ 调用
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  lyclaw-engine（AI 引擎层）← 本文档描述的对象                                │
│  Engine / Pipeline / ContextBuilder / Interceptor / Tool / Memory / Event   │
│  职责：协调对话流程、构建上下文、调度工具、管理记忆、发布事件                    │
└─────────────────────────────────────┬───────────────────────────────────────┘
                                      │ 调用
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  lyclaw-adapter（模型抽象层）← 已实现                                        │
│  ModelAdapter / ModelAdapterFactory / OkHttpModelApiClient                  │
│  职责：屏蔽不同厂商 API 差异，提供统一调用接口                                 │
└─────────────────────────────────────┬───────────────────────────────────────┘
                                      │ 调用
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  lyclaw-storage（存储层）← 已实现                                            │
│  SessionStorage / ConfigStorage / MemoryStorage / CronStorage               │
│  职责：JSON 文件存储，提供增删改查接口                                        │
└─────────────────────────────────────────────────────────────────────────────┘
```

引擎层负责的核心业务：

1. 接收用户的对话请求，选择合适的引擎处理
2. 构建模型输入上下文——拼接消息历史、注入 system prompt、加载长期记忆、注入可用工具列表
3. 经过拦截器链进行预处理——限流检查、日志记录、敏感信息脱敏、认证校验
4. 调用模型抽象层获取 AI 回复
5. 当模型返回工具调用请求时，通过工具注册表执行工具
6. 将工具结果注入上下文，再次调用模型，循环直到模型不再要求调用工具
7. 处理响应、发布事件、管理记忆、协调 Agent 生命周期
8. 持久化会话状态，保障数据最终一致性

### 1.2 为什么需要 AI 引擎层

在没有引擎层的情况下，上层业务（如 Controller）需要直接处理以下所有逻辑：

- 从存储层加载会话历史
- 从存储层加载长期记忆
- 拼接消息列表、注入 system prompt
- 调用模型适配器
- 判断模型返回是否包含工具调用请求
- 调用工具并获取结果
- 将工具结果注入上下文
- 再次调用模型（可能多轮循环）
- 处理各种错误和重试
- 更新会话、持久化数据
- 提取记忆、记录日志

这会导致 Controller 代码极其臃肿——可能超过 500 行，而且所有逻辑完全耦合在一个类中。更致命的是：**未来增加任何新功能（如缓存、限流、多 Agent 并行、WebSocket 支持）都需要修改 Controller 代码。**

引擎层将这些逻辑从 Controller 中剥离出来，形成独立的、可扩展的业务层。Controller 只需要做三件事：

1. 构建 `ChatRequest`
2. 调用 `EngineSelector.select(request).execute(request)`
3. 将返回的 `Flux<String>` 写回客户端

仅此而已。所有复杂的业务逻辑都在引擎层内部处理，Controller 完全不需要关心底层的实现细节。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              上层调用者                                       │
│                                                                              │
│  HTTP Controller / WebSocket Handler / CLI TUI / gRPC Service               │
│                                                                              │
│  所有入口都通过 EngineSelector 选择合适的 Engine 执行                         │
└─────────────────────────────────────┬───────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                          EngineSelector                                      │
│                                                                              │
│  职责：根据 ChatRequest 的特征自动选择合适的 Engine                           │
│                                                                              │
│  工作方式：                                                                   │
│  1. 启动时，Spring 自动注入所有 Engine 实现                                   │
│  2. 收到请求时，遍历所有 Engine，调用 supports(request)                       │
│  3. 返回第一个 supports() 返回 true 的 Engine                                │
│  4. 如果没有匹配的 Engine，抛出 NoEngineFoundException                       │
│                                                                              │
│  匹配示例：                                                                   │
│  - 普通对话请求 → DefaultEngine（supports() 始终返回 true，作为兜底）         │
│  - 推理任务请求 → ReasoningEngine（supports() 检查 request.flag）            │
│  - RAG 查询请求  → RagEngine（supports() 检查是否有检索需求）                │
│                                                                              │
│  新增 Engine 只需 @Component 自动注册，无需修改 EngineSelector 代码。         │
└─────────────────────────────────────┬───────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                          Engine（顶层接口）                                   │
│                                                                              │
│  接口定义：                                                                   │
│  ┌─────────────────────────────────────────────────────────────────────┐    │
│  │ public interface Engine {                                           │    │
│  │     String getName();          // 引擎名称，如 "default"、"reasoning"│    │
│  │     boolean supports(ChatRequest request);  // 是否支持该请求         │    │
│  │     Flux<String> execute(ChatRequest request);  // 执行对话，流式返回 │    │
│  │     EngineMetadata getMetadata();  // 引擎元信息                     │    │
│  │ }                                                                   │    │
│  └─────────────────────────────────────────────────────────────────────┘    │
│                                                                              │
│  每一个 Engine 实现都是一个独立的"引擎"，拥有完全不同的对话处理逻辑。          │
│  它们共享底层的 ToolRegistry、MemoryManager、EventBus 等组件，                │
│  但执行流程、阶段编排、策略选择都可以完全不同。                               │
│                                                                              │
│  第一版实现：DefaultEngine（标准对话引擎）                                    │
│  未来实现：ReasoningEngine、PlanningEngine、RagEngine、BatchEngine...        │
└─────────────────────────────────────┬───────────────────────────────────────┘
                                      │
        ┌─────────────────────────────┼─────────────────────────────┐
        │                             │                             │
        ▼                             ▼                             ▼
┌───────────────┐         ┌───────────────┐         ┌───────────────┐
│ DefaultEngine │         │ReasoningEngine│         │(未来任意引擎) │
│               │         │               │         │               │
│ 使用 Pipeline │         │ 独立的推理流程 │         │ 实现 Engine   │
│ Builder 编排  │         │ ChainOfThought│         │ 接口即可      │
│ 标准对话流程  │         │ → 模型调用    │         │               │
└───────────────┘         │ → 验证        │         └───────────────┘
        │                 │ → 输出        │
        │                 └───────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                    DefaultEngine 内部 — Pipeline 管道                        │
│                                                                              │
│  Pipeline = PipelineBuilder                                                  │
│      .addStage(ContextBuildStage)       ← 阶段1：构建上下文                  │
│      .addStage(InterceptorStage)        ← 阶段2：拦截器链预处理              │
│      .addStage(ToolCallLoopStage)       ← 阶段3：模型调用 + 工具循环         │
│      .addStage(MetricsStage)           ← 阶段4：指标采集                    │
│      .addStage(ResponseBuildStage)     ← 阶段5：响应构建                    │
│      .build();                                                               │
│                                                                              │
│  每个 PipelineStage 都是一个可插拔的处理阶段。                                │
│  新增阶段：新建类实现 PipelineStage，通过 addStage() 加入管道。               │
│  移除阶段：从 Builder 中删除对应的 addStage() 调用。                          │
│  调整顺序：改变 addStage() 的调用顺序。                                       │
│  条件执行：Stage 通过 supports(ChatContext) 自判断是否执行。                   │
└─────────────────────────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                        ToolCallLoopStage（独立循环组件）                       │
│                                                                              │
│  内部使用同步模式调用模型（第一版）：                                           │
│                                                                              │
│  int rounds = 0;                                                             │
│  while (rounds < toolCallPolicy.getMaxRounds()) {                           │
│      // 调用模型，阻塞等待完整响应                                             │
│      ModelResponse resp = modelAdapter.chat(context);                       │
│                                                                              │
│      // 如果模型不请求工具，退出循环                                           │
│      if (!resp.hasToolCalls()) {                                            │
│          将 resp.getContent() 通过 Flux.just() 返回给上层                     │
│          return;                                                            │
│      }                                                                      │
│                                                                              │
│      // 执行工具                                                             │
│      for (ToolCall tc : resp.getToolCalls()) {                              │
│          ToolResult result = toolRegistry.execute(tc);                      │
│          context.addToolResult(tc.getId(), result);                         │
│      }                                                                      │
│                                                                              │
│      // 判断是否继续                                                          │
│      if (!toolCallPolicy.shouldContinue(context, rounds)) {                 │
│          break;                                                             │
│      }                                                                      │
│      rounds++;                                                              │
│  }                                                                          │
│                                                                              │
│  循环终止条件（由 ToolCallPolicy 决定）：                                      │
│  1. 模型不再返回工具调用请求（finishReason = "stop"）                         │
│  2. ToolCallPolicy.shouldContinue() 返回 false                              │
│  3. 达到 ToolCallPolicy.getMaxRounds() 的最大轮次（默认 10 轮）               │
│  4. 发生不可恢复的错误                                                        │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 1.5 一次完整对话请求的流转

以下是一次用户对话请求经过引擎层的完整路径，每一步都标注了对应的设计模式和职责边界：

```
用户发送 "帮我查一下北京今天天气"
  │
  ▼
Controller 接收请求
  │  构建 ChatRequest：包含 sessionId、用户消息、模型名
  │
  ▼
EngineSelector.select(request) → 遍历所有 Engine
  │  DefaultEngine.supports(request) → true（兜底）
  │  返回 DefaultEngine 实例
  │
  ▼
DefaultEngine.execute(request)
  │
  ▼
Pipeline 开始执行（通过 PipelineBuilder 编排的 5 个阶段）：

  ├── Stage 1: ContextBuildStage（上下文构建阶段）
  │   │  
  │   │  1.1 从 SessionStorage 加载会话历史
  │   │      获取 Session 对象，包含 messages[] 列表
  │   │  
  │   │  1.2 从 MemoryManager.recall() 加载长期记忆
  │   │      读取所有 enabled=true 的记忆文件
  │   │  
  │   │  1.3 选择上下文策略（遍历所有 ContextBuilder 实现）
  │   │      ├── SlidingWindowContextBuilder.supports() → 消息数 > 50？否
  │   │      ├── SummaryContextBuilder.supports() → 消息数 > 100？否
  │   │      └── FullWindowContextBuilder.supports() → true（兜底，最后检查）
  │   │      选中 FullWindowContextBuilder
  │   │  
  │   │  1.4 构建模型输入消息列表
  │   │      ├── 注入 system prompt（从 ChatRequest 或默认值）
  │   │      ├── 注入长期记忆（放在消息列表最前面）
  │   │      └── 追加所有历史消息（按时间顺序）
  │   │  
  │   │  1.5 注入可用工具列表
  │   │      从 ToolRegistry.getAllDefinitions() 获取
  │   │      将工具定义添加到请求参数中
  │   │  
  │   │  输出：完整的 ChatContext（包含消息列表、工具列表、token 估算）
  │   │  数据传递：直接修改传入的 ChatContext 对象（可变对象），各 Stage 共享
  │
  ├── Stage 2: InterceptorStage（拦截器阶段）
  │   │  
  │   │  按 @Order 从小到大顺序执行所有拦截器的 preHandle()：
  │   │  
  │   │  RateLimitInterceptor（order=10）.preHandle()
  │   │  ├── 检查当前用户/IP 的请求频率
  │   │  ├── 如果超限 → 抛出 RateLimitExceededException，中断流程
  │   │  └── 如果未超限 → 计数器+1，继续
  │   │  
  │   │  SensitiveDataInterceptor（order=50）.preHandle()
  │   │  ├── 扫描用户输入中的敏感信息（手机号、邮箱、身份证号等）
  │   │  └── 替换为脱敏后的占位符
  │   │  
  │   │  LoggingInterceptor（order=100）.preHandle()
  │   │  └── 记录请求开始时间和基本信息（消息长度、模型名等）
  │   │  
  │   │  输出：经过拦截器处理的 ChatContext
  │
  ├── Stage 3: ToolCallLoopStage（工具调用循环阶段）
  │   │  
  │   │  第 1 轮：
  │   │  ├── 3.1 调用模型：modelAdapter.chat(context)
  │   │  │   阻塞等待完整响应（第一版使用同步模式）
  │   │  ├── 3.2 检查响应：resp.hasToolCalls() → true
  │   │  │   模型返回 tool_calls: [{name:"get_weather", arguments:{city:"北京"}}]
  │   │  ├── 3.3 执行工具：
  │   │  │   ToolRegistry.execute("get_weather", {city:"北京"})
  │   │  │   内部通过 CompletableFuture.orTimeout(30秒) 控制超时
  │   │  │   返回 ToolResult: {status:SUCCESS, content:"北京今日晴，18-28℃"}
  │   │  ├── 3.4 注入结果：context.addToolResult(callId, result)
  │   │  │   将工具调用结果添加到 ChatContext 的工具调用历史中
  │   │  └── 3.5 判断继续：toolCallPolicy.shouldContinue(context, 1) → true
  │   │  
  │   │  第 2 轮：
  │   │  ├── 3.1 再次调用模型：modelAdapter.chat(context)
  │   │  │   此时上下文中已包含第 1 轮的工具调用和结果
  │   │  ├── 3.2 检查响应：resp.hasToolCalls() → false
  │   │  │   模型返回纯文本回复："北京今天晴，18-28℃，适合出行"
  │   │  └── 3.3 退出循环，将回复内容通过 Flux.just() 返回
  │   │  
  │   │  输出：最终模型回复（文本内容）
  │
  ├── Stage 4: MetricsStage（指标采集阶段）
  │   │  
  │   │  4.1 累计 Token 用量（prompt + completion）
  │   │  4.2 计算请求总耗时（从收到请求到现在的毫秒数）
  │   │  4.3 发布 TokenConsumedEvent（通过 EventBus.publish()）
  │   │  4.4 发布 ToolCalledEvent（如果在本轮对话中调用过工具）
  │   │  
  │   │  输出：不变（ChatContext 中增加了指标数据）
  │
  ├── Stage 5: ResponseBuildStage（响应构建阶段）
  │   │  
  │   │  5.1 构建 ChatResult 对象
  │   │      包含：回复文本、Token 用量、执行耗时、完成原因等
  │   │  
  │   │  5.2 按逆序执行所有拦截器的 postHandle()：
  │   │      LoggingInterceptor.postHandle()：记录响应日志（耗时、Token量）
  │   │      SensitiveDataInterceptor.postHandle()：无操作（第一版不做响应脱敏）
  │   │      RateLimitInterceptor.postHandle()：无操作
  │   │  
  │   │  输出：ChatResult
  │
  ▼
Pipeline 执行完毕，DefaultEngine 拿到 ChatResult
  │
  ├── 更新会话
  │   ├── 将用户消息追加到 Session.messages[]
  │   ├── 将 AI 回复追加到 Session.messages[]
  │   └── 更新 Session.updatedAt
  │
  ├── 持久化会话
  │   └── SessionStorage.save(session)
  │
  ├── 提取记忆（可选）
  │   └── MemoryManager.remember(session, strategy)
  │       └── strategy.shouldExtract(session) → 判断是否需要提取
  │
  ├── 发布事件
  │   └── EventBus.publish(ConversationCompletedEvent)
  │
  └── 返回 ChatResult 给 Controller
  │
  ▼
Controller 将回复通过 SSE 流式写回给用户
```

### 1.6 核心设计理念

本架构的核心设计理念可以概括为三个"一切"：

**一切皆可替换**：架构中没有任何一个组件是"写死"的。引擎、管道阶段、上下文策略、工具、记忆管理器、事件总线——所有组件都通过接口定义，通过依赖注入绑定，可以随时替换。替换一个组件时，只需要新建实现类并切换注入，所有调用方代码零修改。

**一切皆可编排**：Pipeline 的阶段不是固定顺序的方法调用，而是通过 PipelineBuilder 动态编排的列表。新增阶段、移除阶段、调整顺序、条件执行——全部通过 Builder 配置，不修改核心流程代码。未来如果需要在"模型调用"之前增加"安全审核"阶段，只需要新建一个 Stage 类，然后在 Builder 中 add 即可。

**一切皆可扩展**：新增任何功能都遵循"新建一个类、实现一个接口、加一个 @Component 注解"的模式。已有代码零修改。这个原则覆盖了从新增工具、新增拦截器、新增上下文策略到新增整个引擎的所有扩展场景。无论是第一版的功能增强，还是第三版的完全不同的引擎逻辑，都遵循同一套扩展机制。

## 第二章：设计原则与哲学

### 2.1 六大设计原则

#### 原则一：单一职责原则

每一个类、每一个接口、每一个模块都只有一个引起它变化的原因。这个原则是本架构拆分粒度的核心指导思想。

具体体现：

- `ContextBuilder` 只负责构建上下文消息列表。它不负责调用模型、不负责管理记忆、不负责持久化。它的唯一变化原因是"上下文构建策略需要改变"——从全量窗口变为滑动窗口，或从滑动窗口变为摘要压缩。这些变化只会影响 ContextBuilder 的实现类，不会影响 Pipeline、Engine 或其他任何组件。

- `ToolRegistry` 只负责工具注册、发现和执行。它不负责判断是否需要调用工具（那是模型的事），不负责控制循环轮次（那是 ToolCallPolicy 的事）。它的唯一变化原因是"工具的管理方式需要改变"——从 HashMap 存储变为 Redis 存储，或增加工具版本管理。

- `MemoryManager` 只负责记忆的增删改查和格式化。它不负责构建对话上下文（那是 ContextBuilder 的事），不负责判断哪些信息值得记住（那是 MemoryStrategy 的事）。它的唯一变化原因是"记忆的存储方式需要改变"——从文件存储变为 Redis 或数据库存储。

- `EventBus` 只负责事件的发布和订阅。它不关心事件的内容（那是 Event 子类的事），不关心事件的处理逻辑（那是监听器的事）。它的唯一变化原因是"事件传递机制需要改变"——从内存传递变为 Kafka 或 RabbitMQ。

- `Interceptor` 只负责单一横切关注点。`RateLimitInterceptor` 只关心限流逻辑，`LoggingInterceptor` 只关心日志记录，`AuditInterceptor` 只关心审计。每个拦截器的唯一变化原因是"该关注点的处理逻辑需要改变"——限流算法从固定窗口变为滑动窗口，日志格式从文本变为 JSON。

- `PipelineStage` 只负责管道中的一个处理阶段。`ContextBuildStage` 只负责调度上下文构建，`InterceptorStage` 只负责调度拦截器，`ToolCallLoopStage` 只负责模型调用和工具循环。每个 Stage 的唯一变化原因是"该阶段的调度逻辑需要改变"。

当每个类只有一个职责时，修改任何一个功能都只会影响对应的类，不会产生连锁反应。新增任何功能都只需要新增类，不需要修改已有类。这就是"高内聚、低耦合"的具体体现。

#### 原则二：开闭原则

对扩展开放，对修改关闭。这是本架构最重要的设计目标——**所有未来扩展都不需要修改已有代码。**

具体体现：

- 新增工具：新建 `XxxTool` 类实现 `Tool` 接口，加 `@Component` 注解。`ToolRegistry` 通过 Spring 的依赖注入自动发现并注册这个新工具。已有的 `WebSearchTool`、`CalculatorTool` 等工具类和 `ToolRegistry` 本身不需要修改任何一行代码。

- 新增拦截器：新建 `XxxInterceptor` 类实现 `Interceptor` 接口，加 `@Component` 注解，设置合适的 `getOrder()` 返回值。`InterceptorChain` 自动发现并按 order 排序。已有的 `RateLimitInterceptor`、`LoggingInterceptor` 等拦截器代码完全不受影响。

- 新增上下文策略：新建 `XxxContextBuilder` 类实现 `ContextBuilder` 接口，加 `@Component` 注解。`ContextBuildStage` 遍历所有策略时自动包含新策略，通过 `supports()` 方法判断是否使用。已有的 `FullWindowContextBuilder`、`SlidingWindowContextBuilder` 代码完全不受影响。

- 新增 Pipeline 阶段：新建 `XxxStage` 类实现 `PipelineStage` 接口。在 `PipelineBuilder` 中通过 `.addStage()` 加入管道。已有的所有阶段代码不受影响，阶段的执行顺序可以通过 Builder 灵活调整。

- 新增引擎：新建 `XxxEngine` 类实现 `Engine` 接口，加 `@Component` 注解。`EngineSelector` 自动发现并在遍历时包含新引擎。已有的 `DefaultEngine` 代码完全不受影响。

- 替换存储实现：新建 `RedisMemoryManager` 实现 `MemoryManager` 接口。在 Spring 配置中通过 `@Primary` 注解切换注入。所有调用 `MemoryManager` 的代码（ContextBuilder、Pipeline、Engine）完全不需要修改，因为它们只依赖接口，不依赖具体实现。

- 替换事件总线：新建 `KafkaEventBus` 实现 `EventBus` 接口。切换注入。所有发布事件和订阅事件的代码完全不需要修改。

这种能力的基础是：所有组件都先定义接口（放在 lyclaw-core 中），再提供默认实现（放在 lyclaw-engine 中）。所有调用方只依赖接口，不依赖实现。具体实现通过 Spring 依赖注入在运行时绑定。

#### 原则三：依赖倒置原则

上层模块不依赖下层模块的具体实现，只依赖抽象接口。本架构严格遵守这一原则。

```
上层（Controller）    →  依赖 Engine 接口（lyclaw-core 中定义）
Engine 实现           →  依赖 PipelineStage 接口（lyclaw-core 中定义）
PipelineStage 实现     →  依赖 ContextBuilder / Interceptor / Tool 接口（lyclaw-core 中定义）
ContextBuilder 实现    →  依赖 ChatContext（纯数据对象，lyclaw-common 中定义）

关键设计：lyclaw-engine 不依赖 lyclaw-adapter 的任何具体类。
引擎通过 lyclaw-core 中的 ModelProvider 接口获取适配器，
ModelProvider 的实现由 lyclaw-adapter 模块提供，通过 Spring 注入。
```

这样设计的好处：

当需要替换某个实现时（如从文件存储切换到 Redis 存储），只需新建一个实现类，然后在 Spring 配置中切换注入。所有依赖该接口的代码无需任何修改。

当需要为测试 mock 某个组件时，只需提供一个接口的测试实现，不需要修改被测代码。这在单元测试和集成测试中极为有用。

当不同团队并行开发时，团队 A 负责 Engine 实现，团队 B 负责 MemoryManager 实现，团队 C 负责 EventBus 实现。他们只需要约定接口，就可以完全独立开发，互不干扰。

#### 原则四：接口隔离原则

接口小而精，不强迫使用者依赖它不需要的方法。本架构中的每个接口都只定义了最核心的 2-4 个方法，没有"胖接口"。

具体接口的方法数量：

- `Engine` 接口：4 个方法——getName、supports、execute、getMetadata
- `PipelineStage` 接口：3 个方法——getName、supports、execute
- `ContextBuilder` 接口：2 个方法——supports、build
- `Tool` 接口：4 个方法——getName、getDefinition、execute、getTimeout
- `Interceptor` 接口：3 个方法——getOrder、preHandle、postHandle
- `MemoryManager` 接口：4 个方法——remember、recall、forget、buildContext
- `EventBus` 接口：3 个方法——publish、subscribe、unsubscribe
- `ErrorPolicy` 接口：3 个方法——onModelError、onToolError、onTimeout
- `ToolCallPolicy` 接口：3 个方法——shouldContinue、getMaxRounds、onToolError

对比"胖接口"的设计：如果一个 `Engine` 接口定义了 15 个方法，那么每个 Engine 实现都需要提供这 15 个方法的实现，即使其中 10 个方法对某个特定的 Engine 毫无意义。这会导致大量空实现和 `throw new UnsupportedOperationException()`，不仅代码冗余，而且违反了里氏替换原则。

本架构的小接口设计彻底避免了这个问题。每个实现类只需要实现它真正需要的方法。如果某个 Engine 不需要工具调用功能，它完全可以不依赖 `ToolRegistry`。如果某个 Pipeline 不需要拦截器，它完全可以不包含 `InterceptorStage`。每个类只依赖它真正需要的接口，不被迫实现无意义的方法。

#### 原则五：里氏替换原则

任何子类或实现类都可以替换父类或接口使用，行为不发生变化。这个原则在本架构中通过 `supports()` 自描述机制得到增强。

具体体现：

- 任何 `Engine` 实现都可以被 `EngineSelector` 使用。选择器不知道也不关心具体是哪个实现类，它只调用 `supports()` 来判断是否匹配，只调用 `execute()` 来执行对话。替换引擎实现时，选择器的代码完全不需要修改。

- 任何 `ContextBuilder` 实现都可以被 `ContextBuildStage` 使用。Stage 遍历所有 ContextBuilder，通过 `supports()` 选择第一个匹配的。替换上下文策略时，Stage 的代码完全不需要修改。策略的行为完全由接口契约保证。

- 任何 `Tool` 实现都可以被 `ToolRegistry` 管理。注册表不关心工具的具体实现（是内置工具还是 MCP 工具），只调用 `getName()`、`getDefinition()`、`execute()`。替换工具实现时，注册表代码完全不需要修改。

- 任何 `Interceptor` 实现都可以被 `InterceptorChain` 按序执行。链管理器不关心拦截器的具体逻辑（是限流还是日志），只调用 `preHandle()` 和 `postHandle()`。替换拦截器时，链管理器代码完全不需要修改。

这个原则还确保了测试的便利性：任何接口都可以在测试中被 mock 实现替换，而不影响被测代码。例如，测试 DefaultEngine 时可以 mock ModelProvider 返回一个假的适配器，测试 ToolCallLoop 时可以 mock ToolRegistry 返回预设的工具结果。

#### 原则六：迪米特法则

一个对象应该对其他对象有最少的了解。也被称为"最少知道原则"或"不要和陌生人说话"。

具体体现：

- `Engine` 不需要知道 `ToolRegistry` 的内部实现——工具是如何注册的（HashMap 还是 Redis）、存储在哪里、如何管理生命周期。Engine 只需要调用 `execute()` 方法，传入工具名和参数，获取结果。ToolRegistry 的内部变化对 Engine 完全透明。

- `PipelineStage` 不需要知道其他 Stage 的存在。每个 Stage 只处理自己的逻辑，通过 `Chain.proceed()` 将控制权传递给下一个阶段。ContextBuildStage 不知道后面是 InterceptorStage 还是直接跳到 ToolCallLoopStage。这种隔离让阶段可以独立开发、独立测试、独立替换。

- `Interceptor` 不需要知道前后拦截器的逻辑。RateLimitInterceptor 不知道 SensitiveDataInterceptor 的存在，也不知道它在做什么。每个拦截器只处理自己的横切关注点，通过 InterceptorChain 串联。

- `EventBus` 的发布者不知道有哪些订阅者。当 `ToolCallLoopStage` 发布 `ToolCalledEvent` 时，它不知道有谁在监听这个事件——可能是 MetricsService 在记录指标，可能是 LogService 在记录日志，可能是 AlertService 在监控异常。新增订阅者时，发布者代码完全不需要修改。

- `MemoryManager` 的调用者不知道记忆存储在哪里。是文件系统的 Markdown 文件，还是 Redis 的 Hash 结构，还是数据库的表——对调用者完全透明。调用者只需要知道"我可以记住、可以回忆、可以忘记"。

模块之间通过接口通信，通过事件总线解耦，将耦合度降到最低，提高模块的独立性和可替换性。

### 2.2 核心设计哲学：一切皆可替换

本架构的核心设计哲学可以概括为一句话：**架构中没有任何一个组件是"写死"的。**

这意味着：

- 引擎逻辑可以替换：`Engine` 接口 + `EngineSelector` 自动选择。第一版使用 `DefaultEngine`，未来可以新增 `ReasoningEngine`、`PlanningEngine` 等。切换时只需要新 Engine 的 `supports()` 返回 true，选择器自动路由。

- 管道阶段可以替换：`PipelineStage` 接口 + `PipelineBuilder` 动态编排。阶段的新增、移除、顺序调整全部通过 Builder 配置，不修改核心流程代码。

- 上下文策略可以替换：`ContextBuilder` 接口 + `supports()` 自动遍历。策略的新增和切换不影响 ContextBuildStage 的代码。

- 工具执行可以替换：`Tool` 接口 + `ToolRegistry` 自动发现。新增工具只需加 `@Component`，注册表自动识别。

- 记忆管理可以替换：`MemoryManager` 接口 + 依赖注入。从文件存储切换到 Redis 只需新建实现类并切换注入。

- 事件总线可以替换：`EventBus` 接口 + 依赖注入。从内存事件总线切换到 Kafka 只需新建实现类并切换注入。

- 拦截器链可以替换：`Interceptor` 接口 + `@Order` 排序。拦截器的新增和移除不影响其他拦截器。

- 错误处理可以替换：`ErrorPolicy` 接口 + 依赖注入。从默认策略切换到重试策略或熔断策略只需切换注入。

- Agent 通信可以替换：`AgentChannel` 接口 + 依赖注入。从星型拓扑切换到树形拓扑只需切换注入。

- HTTP 客户端可以替换：`ModelProvider` 接口的内部实现。引擎层完全不感知 HTTP 客户端的实现细节。

这种设计哲学的具体落地方式是：**任何一个组件，先定义接口（放在 lyclaw-core 中），再提供默认实现（放在 lyclaw-engine 或 lyclaw-adapter 中）。所有调用方只依赖接口，不依赖实现。**

### 2.3 扩展方式：只加不减

未来任何需求变更都遵循一个原则：**新建一个类，实现一个接口，加一个 `@Component` 注解。**

这个原则的具体含义：

- 不需要修改已有类——已有代码保持稳定，不受新功能影响。每次变更都是增量式的，不会对已有功能造成回归风险。
- 不需要修改已有接口——接口保持稳定，向后兼容。接口定义后就成为"契约"，所有实现都必须遵守。
- 不需要修改已有配置——新类通过 `@Component` 自动注册到 Spring 容器，不需要手动配置。
- 不需要理解已有实现的细节——新类只需要关注自己的逻辑。开发者不需要阅读已有代码就能新增功能。

当需要替换某个实现时：
1. 新建一个实现类，提供新的逻辑
2. 在 Spring 配置中通过 `@Primary` 或配置文件切换注入
3. 旧实现可以保留，随时可以切回去（通过配置切换）

当需要移除某个功能时：
1. 移除对应的 `@Component` 注解或配置
2. 系统自动回退到默认行为（如果有兜底策略）
3. 或者通过 `@ConditionalOnProperty` 控制是否加载

这种"只加不减"的方式保证了代码的稳定性和可追溯性。每一次变更都是向前兼容的，不会破坏已有功能。

### 3.2 各包职责边界

每个包的职责边界必须清晰明确。一个类应该放在哪个包中，判断标准只有一个：**这个类唯一的变化原因是什么。**

| 包 | 职责 | 负责的事情 | 不负责的事情 |
|----|------|-----------|-------------|
| engine/ | 引擎顶层抽象和选择 | 定义 Engine 接口；提供 DefaultEngine 实现；EngineSelector 自动选择引擎 | 具体的对话流程（Pipeline 负责）；具体的策略选择（各策略的 supports() 自己负责） |
| pipeline/ | 管道编排和阶段管理 | 定义 Pipeline/PipelineStage 接口；PipelineBuilder 编排阶段；Chain 控制阶段流转 | 每个阶段的具体业务逻辑（各 Stage 负责）；策略选择（各策略的 supports() 自己负责） |
| context/ | 上下文构建策略 | 定义 ContextBuilder 接口；实现不同的窗口策略（全量/滑动/摘要）；ChatContext 数据传递 | 记忆存储（MemoryManager 负责）；模型调用（ToolCallLoop 负责）；消息持久化（SessionStorage 负责） |
| interceptor/ | 横切关注点处理 | 定义 Interceptor 接口；InterceptorChain 管理链；实现限流/日志/脱敏等拦截器 | 核心对话流程（Pipeline 负责）；业务规则（Tool/ContextBuilder 负责）；事件处理（EventBus 负责） |
| tool/ | 工具注册和执行 | 定义 Tool 接口；ToolRegistry 管理工具；ToolCallLoop 控制循环；ToolCallPolicy 控制终止条件 | 工具的具体业务实现（各 Tool 实现类负责）；判断是否需要工具（模型负责）；工具结果的持久化（调用方负责） |
| memory/ | 记忆的增删改查 | 定义 MemoryManager 接口；定义 MemoryStrategy 提取策略；实现文件存储 | 会话管理（SessionStorage 负责）；上下文构建（ContextBuilder 负责）；判断哪些信息重要（MemoryStrategy 或用户负责） |
| event/ | 事件的发布和订阅 | 定义 EventBus 接口；定义 Event 类型；实现内存/消息队列事件总线 | 事件的具体处理逻辑（各监听器负责）；事件的触发时机（各发布者负责）；事件的持久化（EventBus 实现负责） |
| agent/ | Agent 生命周期和通信 | 定义 AgentCoordinator；定义 AgentChannel 拓扑；管理 Agent 状态机（IDLE→RUNNING→COMPLETED/ERROR） | 具体的对话逻辑（Engine 负责）；工具执行（ToolRegistry 负责）；上下文构建（ContextBuilder 负责） |
| error/ | 错误处理策略 | 定义 ErrorPolicy 接口；实现重试/降级/熔断策略；处理模型错误、工具错误、超时 | 具体的错误恢复操作（由策略的具体实现负责）；错误的产生原因（由发生错误的组件负责） |
| config/ | 配置和自动装配 | EngineProperties 配置类；EngineAutoConfiguration 自动配置；Bean 的声明和注入 | 业务逻辑；核心流程；策略选择 |
| dto/ | 引擎内部数据对象 | ChatResult、AgentResult 等纯粹的数据传递对象 | 业务逻辑；任何行为方法 |

### 3.3 包之间的通信规则

包之间的依赖关系遵循严格的方向规则，确保不会出现循环依赖：

1. **engine 包**：定义顶层接口，被所有其他包依赖。Engine 接口是所有引擎实现的契约，是所有上层调用者的入口。

2. **pipeline 包**：被 engine 的 DefaultEngine 调用（通过 PipelineBuilder 构建管道）。pipeline 依赖 context、interceptor、tool 包来完成各阶段的具体逻辑。

3. **context 包**：被 pipeline 的 ContextBuildStage 调用。context 只依赖 ChatContext（数据对象）和 lyclaw-common 中的 DTO，不依赖其他业务包。

4. **interceptor 包**：被 pipeline 的 InterceptorStage 调用。interceptor 可以依赖 event 包来发布事件（如拦截到异常时发布 ErrorEvent），但不依赖其他业务包。

5. **tool 包**：被 pipeline 的 ToolCallLoopStage 调用。tool 可以依赖 event 包来发布事件（如工具执行完成时发布 ToolCalledEvent），也可以依赖 error 包来处理错误。

6. **memory 包**：被 engine 的 DefaultEngine 调用（对话结束后提取记忆）。memory 可以依赖 event 包来发布事件（如记忆提取完成时），也可以依赖 lyclaw-storage 来持久化。

7. **event 包**：被所有其他包调用。event 包不依赖任何业务包，它是纯粹的基础设施层。Event 基类和 EventBus 接口定义在这里，可以被任何包引用。

8. **agent 包**：被 engine 调用（需要 spawn 子 Agent 时）。agent 依赖 pipeline 来执行子任务，依赖 event 来发布状态变更事件。

9. **error 包**：被 tool 包和 pipeline 包调用。error 包只依赖基础类型和 lyclaw-common，不依赖其他业务包。它是横切关注点，为所有需要错误处理的组件提供统一策略。

10. **config 包**：被 Spring 容器调用，不依赖任何业务包。它只负责配置的读取和 Bean 的装配。

关键规则：**不允许循环依赖。**依赖方向始终是"业务包 → 基础设施包"。如果发现两个业务包互相依赖，说明它们的边界划分有问题，需要重新审视职责归属。

### 4.2 策略模式 — 4 处应用

策略模式是本架构中使用最多的模式。它解决的核心问题是：**同一种行为有多种实现方式，需要在运行时动态选择，而不是通过 if-else 写死。**

**应用位置 1：Engine 接口**

问题：不同对话场景需要完全不同的处理逻辑。标准对话、推理链对话、RAG 对话——它们的执行流程完全不同。如果在 DefaultEngine 中用 if-else 分支处理所有场景，代码会快速膨胀到数千行，且修改一种场景的逻辑可能影响其他场景。

方案：`Engine` 接口定义引擎的执行协议。每个引擎实现 `supports()` 方法自描述适用场景。`EngineSelector` 遍历所有引擎，通过 `supports()` 匹配。`DefaultEngine` 的 `supports()` 始终返回 true，作为兜底引擎（最后被检查）。

扩展方式：新增引擎只需新建类实现 `Engine` 接口，加 `@Component`。EngineSelector 自动发现并在遍历时包含新引擎。已有引擎代码完全不受影响。

**应用位置 2：ContextBuilder 接口**

问题：不同长度的对话需要不同的上下文构建策略。短对话用全量窗口（所有消息都放入上下文），长对话用滑动窗口（只保留最近 N 条），超长对话用摘要压缩（旧消息用 AI 做摘要）。如果在 ContextBuildStage 中用 if-else 判断对话长度来选择策略，新增策略必须修改 Stage 代码。

方案：`ContextBuilder` 接口 + `supports()`。每个策略自描述适用条件——SlidingWindowContextBuilder 在消息数超过 50 时返回 true，SummaryContextBuilder 在消息数超过 100 时返回 true。Stage 按 @Order 遍历所有策略，选择第一个 supports() 返回 true 的。FullWindowContextBuilder 不设 @Order，作为最低优先级的兜底策略。

扩展方式：新增策略只需新建类实现 `ContextBuilder` 接口，加 `@Component`。已有策略代码完全不受影响。

**应用位置 3：MemoryStrategy 接口**

问题：不同的场景需要不同的记忆提取策略。有时用户手动触发（说"记住这个"），有时系统需要自动检测关键事件（如用户分享偏好），有时需要 AI 自动判断哪些信息值得记住。

方案：`MemoryStrategy` 接口 + `shouldExtract()` + `extract()`。对话结束后，`MemoryManager.remember()` 调用当前策略的 `shouldExtract()` 判断是否需要提取记忆，如果需要则调用 `extract()` 提取内容。第一版使用 `ManualMemoryStrategy`（用户主动触发）。

扩展方式：新增策略只需新建类实现 `MemoryStrategy` 接口，加 `@Component`。

**应用位置 4：ToolCallPolicy 接口**

问题：工具调用循环的终止条件因场景而异。简单场景固定 10 轮上限，成本敏感场景根据 Token 预算动态决定，复杂场景让模型自己判断是否需要继续。

方案：`ToolCallPolicy` 接口 + `shouldContinue()` + `getMaxRounds()`。`ToolCallLoop` 在每轮循环后调用 `shouldContinue()` 判断是否继续。第一版使用 `DefaultToolCallPolicy`（固定 10 轮上限）。

扩展方式：新增策略只需新建类实现 `ToolCallPolicy` 接口，加 `@Component`。

### 4.3 模板方法模式 — 2 处应用

模板方法模式解决的核心问题是：**一个操作的流程骨架是固定的，但某些步骤的具体实现因场景而异。**骨架由基类控制，细节由子类填充。

**应用位置 1：ToolCallLoop**

流程骨架（由 ToolCallLoop 控制，子类不能改变顺序）：
1. 初始化轮次计数器
2. 调用模型获取响应（阻塞等待完整响应）
3. 检查响应中是否有工具调用请求
4. 如果没有 → 退出循环，返回回复内容
5. 执行工具（遍历所有工具调用请求）
6. 将工具结果注入上下文
7. 调用 ToolCallPolicy.shouldContinue() 判断是否继续
8. 如果继续 → 轮次+1，回到步骤 2
9. 如果不继续 → 退出循环

可变步骤（由策略接口决定，子类可以替换）：
- 步骤 7 的判断逻辑：由 `ToolCallPolicy.shouldContinue()` 的实现决定。默认策略检查轮次是否超过上限；未来可以实现基于 Token 预算的判断或基于模型反馈的判断。
- 工具执行失败的处理：由 `ToolCallPolicy.onToolError()` 的实现决定。默认策略记录错误日志并跳过该工具；未来可以实现重试或降级。
- 模型调用失败的处理：由 `ErrorPolicy.onModelError()` 的实现决定。默认策略根据状态码判断是否重试；未来可以实现熔断降级。

这种设计的优势：循环的核心逻辑（调用模型 → 检查工具 → 执行工具 → 注入结果 → 判断继续）是稳定的，但每个步骤的细节可以根据场景替换。替换策略时，ToolCallLoop 的代码完全不需要修改。

**应用位置 2：AbstractPipelineStage**

流程骨架（由 AbstractPipelineStage 控制）：
1. 检查 `supports(context)` 是否返回 true
2. 如果 false → 调用 `chain.proceed(context)` 跳过当前阶段
3. 如果 true → 执行阶段的核心逻辑（由 `doExecute()` 定义）
4. 调用 `chain.proceed(context)` 传递控制权给下一个阶段

可变步骤（由子类实现）：
- 步骤 1 的判断逻辑：由子类的 `supports()` 决定。例如 ToolCallLoopStage 在上下文中不需要工具时可以跳过。
- 步骤 3 的执行逻辑：由子类的 `doExecute()` 决定。这是每个阶段的核心业务逻辑。

### 4.4 管道模式 — Pipeline + PipelineStage + PipelineBuilder

管道模式解决的核心问题是：**一个请求需要经过多个处理阶段，每个阶段各司其职，阶段之间需要灵活编排。**这不同于传统的"一个方法按顺序调用多个步骤"的做法。

传统做法的致命问题：
```
execute() {
    step1();  // 构建上下文
    step2();  // 拦截器
    step3();  // 调用模型
    if (needTools) step4();  // 执行工具
    step5();  // 构建响应
}
```
如果需要在 step3 和 step5 之间加一个"安全审核"阶段，需要修改 execute() 方法。如果需要在 step2 之前加一个"认证"阶段，也需要修改 execute() 方法。随着业务增长，这个方法会变得难以维护。

管道模式的解决方案：
- `Pipeline` 不是一个拥有固定方法的类，而是一个包含 `List<PipelineStage>` 的容器
- 每个 `PipelineStage` 只负责一个明确的职责
- `PipelineBuilder` 负责编排阶段：通过 `.addStage()` 决定哪些阶段参与、以什么顺序参与
- `Chain` 负责在阶段之间传递控制权和数据

新增阶段时，只需要新建一个 Stage 类，在 Builder 中 `.addStage()` 加入。已有阶段代码完全不受影响。

### 4.5 责任链模式 — Interceptor + InterceptorChain

责任链模式解决的核心问题是：**一个请求需要经过多个处理器的处理，每个处理器可以决定是否继续传递给下一个。**

在传统的写法中，这些横切逻辑可能散布在 Controller 的各个方法中。当需要新增一个横切关注点（如审计日志）时，需要在每个方法中添加相应的代码。这种修改是侵入性的、容易遗漏的。

责任链模式将所有横切关注点集中到独立的拦截器中：
- `RateLimitInterceptor` 只关心限流
- `LoggingInterceptor` 只关心日志
- `SensitiveDataInterceptor` 只关心脱敏

每个拦截器独立开发、独立测试、独立部署。新增拦截器时，新建一个类实现 `Interceptor` 接口，加 `@Component`，设置合适的 `getOrder()` 返回值。`InterceptorChain` 自动发现并按 order 排序。已有拦截器代码完全不受影响。

拦截器链还支持**分支能力**：拦截器可以调用 `chain.skipToNext()` 跳过后续拦截器。例如，CacheInterceptor 在命中缓存时可以直接返回，跳过后续的认证、限流等拦截器。

### 4.6 观察者模式 — EventBus

观察者模式解决的核心问题是：**模块之间需要通信，但又不希望直接依赖，需要松耦合的事件通知机制。**

在没有事件总线的情况下，模块 A 需要通知模块 B 某个事件发生时，模块 A 必须直接调用模块 B 的方法。这意味着模块 A 必须知道模块 B 的存在，模块 B 的接口变化会影响模块 A，新增一个监听者 C 需要修改模块 A 的代码。

事件总线彻底解决了这些问题：
- 发布者只调用 `EventBus.publish(event)`，不需要知道有哪些订阅者
- 订阅者只调用 `EventBus.subscribe(type, handler)`，不需要知道事件是谁发布的
- 新增订阅者只需要调用 `subscribe()`，发布者代码完全不需要修改
- 新增事件类型只需要新建 Event 子类，已有事件类型不受影响

第一版使用 `InMemoryEventBus`，内部使用 `CopyOnWriteArrayList` 存储监听器列表。这种数据结构在遍历时不需要加锁（因为任何修改操作都会复制整个列表），适合"读多写少"的场景——监听器通常在启动时注册，运行时很少变化。

### 4.7 命令模式 — Tool 接口

命令模式解决的核心问题是：**每个工具是一个独立的可执行单元，需要统一的生命周期管理——执行、超时、重试、结果截断。**

每个工具封装为一个 `Tool` 对象：
- `getName()`：全局唯一标识，如 "web_search"、"calculator"
- `getDefinition()`：工具定义（名称、描述、参数 JSON Schema），会被发送给模型
- `execute(arguments)`：核心执行逻辑，返回 ToolResult
- `getTimeout()`：超时时间

`ToolRegistry` 管理所有工具，提供统一的执行接口。工具执行时通过 `CompletableFuture.orTimeout()` 控制超时，超时后抛出 `TimeoutException`，由 `ErrorPolicy.onToolError()` 处理。

新增工具时，新建一个类实现 `Tool` 接口，加 `@Component` 注解。`ToolRegistry` 通过 Spring 自动发现并注册。已有工具代码完全不受影响。

### 4.8 注册表模式

注册表模式解决的核心问题是：**系统中存在多个同类组件，需要一个中央注册表来发现和管理它们。**

本架构有三个注册表：

- `ToolRegistry`：管理所有 Tool 实现。启动时通过 Spring 注入所有 `Tool` 类型的 Bean，按 `getName()` 存入 Map。提供 `get(name)`、`getAll()`、`execute(name, args)` 等接口。

- `EngineSelector`：管理所有 Engine 实现。启动时通过 Spring 注入所有 `Engine` 类型的 Bean。按 `@Order` 排序。提供 `select(request)` 接口——遍历所有 Engine，调用 `supports()`，返回第一个匹配的。

- `InterceptorChain`：管理所有 Interceptor 实现。启动时通过 Spring 注入所有 `Interceptor` 类型的 Bean，按 `getOrder()` 排序。提供 `proceed(context)` 接口——依次调用每个拦截器的 `preHandle()`。

新增组件时，只需要实现对应接口并加 `@Component`，注册表自动发现，不需要修改注册表代码。

### 4.9 工厂模式 — ModelProvider

工厂模式解决的核心问题是：**对象的创建过程较复杂，需要根据条件创建不同类型的对象，同时需要解耦创建者和使用者。**

`ModelProvider` 是模型适配器的工厂接口。它定义了获取适配器的方法：`getAdapter(String provider)`——根据厂商标识返回对应的适配器实例。Engine 通过此接口获取适配器，完全不依赖 lyclaw-adapter 的具体类。

这种设计形成了 lyclaw-engine 和 lyclaw-adapter 之间的"防腐层"——Engine 不直接依赖 Adapter 的具体类，只依赖 ModelProvider 接口。未来如果 Adapter 模块的实现方式完全改变（如从 OkHttp 切换到 gRPC），Engine 层的代码完全不受影响。

### 4.10 建造者模式 — PipelineBuilder

建造者模式解决的核心问题是：**一个对象有很多配置选项，且大部分是可选的，直接使用构造函数会导致参数爆炸。**

`PipelineBuilder` 提供链式 API 编排管道阶段。每个 `addStage()` 返回 Builder 自身，支持链式调用。`build()` 方法执行最终的构建逻辑（包括验证阶段列表是否有效）。

高级编排方法：
- `addStage(stage)` — 在末尾添加
- `addStageBefore(existingClass, newStage)` — 在指定阶段之前插入
- `addStageAfter(existingClass, newStage)` — 在指定阶段之后插入
- `replaceStage(oldClass, newStage)` — 替换某个阶段
- `removeStage(stageClass)` — 移除某个阶段

这些方法使得阶段的编排完全灵活——不需要修改已有 Stage 的代码，只需通过 Builder 调整。

### 4.11 状态模式 — AgentState

状态模式解决的核心问题是：**对象在其生命周期中会经历多个状态，每个状态下可执行的操作不同。**

Agent 的状态转换规则：

```
IDLE ──spawn──► RUNNING
                  │
                  ├──► WAITING_TOOL ──result──► RUNNING
                  │       ↑                        │
                  │       └── 工具结果返回 ─────────┘
                  │
                  ├──► COMPLETED（正常完成）
                  │
                  ├──► ERROR（执行出错，不可恢复）
                  │
                  └──► TERMINATED（被手动终止）

任意状态 ──terminate──► TERMINATED
```

`AgentCoordinator` 在执行任何操作前都会检查当前状态是否允许该操作。例如：
- 只有 `IDLE` 状态的 Agent 可以被 spawn
- 只有 `RUNNING` 状态的 Agent 可以进入 `WAITING_TOOL`
- 只有 `RUNNING` 或 `WAITING_TOOL` 状态的 Agent 可以被 terminate
- `COMPLETED`、`ERROR`、`TERMINATED` 是终态，不能转换到其他状态

### 4.12 装饰器模式 — CacheDecorator、RetryDecorator（第二版预留）

装饰器模式解决的核心问题是：**在不修改原有类的情况下，动态地为对象添加额外的功能。**

第一版预留装饰器接口，第二版实现。装饰器实现与被装饰对象相同的接口，内部持有被装饰对象的引用，可以在调用前后添加逻辑。

```
ModelAdapter baseAdapter = modelProvider.getAdapter("minimax");

// 叠加缓存装饰器
ModelAdapter cachedAdapter = new CacheDecorator(baseAdapter);

// 再叠加重试装饰器
ModelAdapter robustAdapter = new RetryDecorator(cachedAdapter, 3);

// 再叠加指标装饰器
ModelAdapter monitoredAdapter = new MetricsDecorator(robustAdapter);
```

这种"层层包裹"的方式使得功能可以灵活组合，且每个装饰器只关注自己的逻辑。

### 4.13 中介者模式 — AgentCoordinator、AgentChannel

中介者模式解决的核心问题是：**多个 Agent 之间需要通信，但不希望它们直接依赖，需要一个中介者来协调。**

`AgentCoordinator` 作为中介者，管理主 Agent 和子 Agent 之间的通信。Agent 之间不直接通信，所有消息通过 `AgentChannel` 传递。`AgentChannel` 定义了通信拓扑——第一版使用 `StarAgentChannel`（星型拓扑），未来可以切换到 `TreeAgentChannel`（树形）、`MeshAgentChannel`（网状）或 `BroadcastAgentChannel`（广播）。

这种设计使得通信拓扑的变化不影响 AgentCoordinator 的核心逻辑——只需替换 AgentChannel 的实现即可。

## 第五章：核心接口设计

### 5.1 Engine 接口

**文件路径**：`lyclaw-core/src/main/java/lyjew/com/lyclaw/engine/Engine.java`

**设计模式**：策略模式

**接口职责**：

定义 AI 引擎的顶层执行协议。每一个引擎实现代表一种完全不同的对话处理逻辑。这个接口是整个引擎层的最高抽象——所有上层调用者（Controller、WebSocket Handler、CLI TUI 等）都通过这个接口与引擎层交互。

为什么需要这个接口？传统的 AI 应用中，对话引擎通常是一个具体的类（如 ChatService），所有对话逻辑都写在一个类中。当需要增加一种新的对话模式时（如从标准对话扩展到推理链对话），通常在原有类中加 if-else 分支。随着业务增长，这个类会快速膨胀到数千行，难以维护、难以测试、难以并行开发。

Engine 接口彻底解决了这个问题：每种对话模式对应一个 Engine 实现。它们共享底层组件（ToolRegistry、MemoryManager、EventBus），但执行逻辑完全独立。新增引擎时，现有引擎不受任何影响。

**方法说明**：

`getName()` — 返回引擎的唯一标识名称。用于日志记录（如 "[default] 开始处理请求"）、监控面板（如"当前活跃引擎：default"）和运维界面展示（如引擎列表）。典型值："default"、"reasoning"、"planning"、"rag"、"batch"。

`supports(ChatRequest request)` — 判断当前引擎是否支持处理这个请求。这是引擎选择的核心机制。EngineSelector 遍历所有注册的 Engine，返回第一个 `supports()` 返回 true 的引擎。设计要点：
- DefaultEngine 的 `supports()` 始终返回 true，作为兜底引擎。它必须放在引擎列表的最后（通过 @Order 控制）。
- 未来引擎的 `supports()` 根据请求特征判断——如 ReasoningEngine 检查 request.flags 是否包含 "chain_of_thought"，RagEngine 检查是否有检索需求。
- 引擎的匹配逻辑完全由引擎自己决定，不需要中心化的规则引擎。

`execute(ChatRequest request)` — 执行对话，返回流式响应（`Flux<String>`）。使用 Flux 而不是 String 的原因：模型调用本质上是流式的（逐 token 返回），引擎层应该保持这种流式特性，让上层可以实时消费。第一版中，ToolCallLoop 内部使用同步的 `chat()` 阻塞等待完整响应，但对外仍然通过 `Flux.just(content)` 返回 Flux。这为第二版实现真正的流式工具调用预留了空间。

`getMetadata()` — 返回引擎的元信息（EngineMetadata）。包含引擎名称、版本号、描述、支持的能力列表、当前配置状态。用于管理界面展示和运维监控。例如，运维面板可以展示"当前注册了 3 个引擎：default v1.0（活跃）、reasoning v0.5（实验性）、rag v1.2（活跃）"。

### 5.2 EngineSelector 类

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/engine/EngineSelector.java`

**设计模式**：策略模式 + 注册表模式

**职责说明**：

EngineSelector 是引擎层的入口门面。它的角色类似于"路由器"——收到请求后，找到最合适的引擎来处理。它是上层调用者唯一需要接触的引擎层入口。

工作流程：
1. 启动时，Spring 自动注入所有 `Engine` 实现（通过 `@Autowired List<Engine>`）
2. 引擎按 `@Order` 注解排序（数字越小优先级越高，DefaultEngine 的 @Order 设为最大值作为兜底）
3. 收到请求时，遍历引擎列表，调用每个引擎的 `supports(request)` 方法
4. 返回第一个 `supports()` 返回 true 的引擎
5. 如果没有匹配的引擎（理论上不会发生，因为 DefaultEngine 是兜底），抛出 `NoEngineFoundException`

这种设计的核心优势：
- **零修改扩展**：新增引擎不需要修改 EngineSelector 的代码。新引擎加 @Component 即可自动被发现。
- **自描述匹配**：引擎的匹配逻辑由引擎自己决定（通过 supports() 方法），而不是由中心化的规则引擎。这符合"信息专家"原则——引擎自己最清楚自己适合什么场景。
- **简单可控**：通过 @Order 控制优先级，行为可预测。

### 5.3 Pipeline 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/pipeline/Pipeline.java`

**设计模式**：管道模式

**职责说明**：

Pipeline 是一个由多个 PipelineStage 组成的处理管道。它本身不包含任何业务逻辑，只是一个容器和调度器。所有的业务逻辑都在各 PipelineStage 中实现。

Pipeline 的实现由 PipelineBuilder 构建。Builder 决定了哪些 Stage 参与、以什么顺序参与。Pipeline 接口只有一个核心方法：`execute(ChatContext context)`——按顺序执行所有 Stage。

### 5.4 PipelineBuilder 类

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/pipeline/PipelineBuilder.java`

**设计模式**：建造者模式

**职责说明**：

PipelineBuilder 负责构建 Pipeline 实例。它提供链式 API 让调用者自由编排管道阶段。

核心方法：
- `addStage(PipelineStage stage)` — 在管道末尾添加一个阶段。返回 Builder 自身，支持链式调用。
- `addStageBefore(Class<? extends PipelineStage> before, PipelineStage stage)` — 在指定阶段之前插入一个新阶段。用于在现有阶段之间插入新逻辑。
- `addStageAfter(Class<? extends PipelineStage> after, PipelineStage stage)` — 在指定阶段之后插入一个新阶段。
- `replaceStage(Class<? extends PipelineStage> old, PipelineStage newStage)` — 替换一个阶段，保持位置不变。
- `removeStage(Class<? extends PipelineStage> stage)` — 移除一个阶段。
- `build()` — 构建 Pipeline 实例。构建时验证阶段列表的有效性（如不允许空列表，不允许重复阶段类型）。

使用示例：
```java
Pipeline pipeline = Pipeline.builder()
        .addStage(new ContextBuildStage(contextBuilders, sessionStorage, memoryManager, toolRegistry))
        .addStage(new InterceptorStage(interceptorChain))
        .addStage(new ToolCallLoopStage(modelProvider, toolRegistry, toolCallPolicy, errorPolicy))
        .addStage(new MetricsStage(eventBus))
        .addStage(new ResponseBuildStage(interceptorChain))
        .build();
```

未来如果需要新增一个"安全审核"阶段，只需：
```java
.addStageBefore(ResponseBuildStage.class, new SafetyAuditStage(auditService))
```
已有代码零修改。

### 5.5 PipelineStage 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/pipeline/PipelineStage.java`

**设计模式**：管道模式 + 责任链模式

**职责说明**：

PipelineStage 是管道中的一个处理阶段。每个阶段负责一个明确的职责，阶段之间通过 Chain 传递控制权。

核心方法：
- `getName()` — 返回阶段名称，用于日志和调试。如 "ContextBuild"、"Interceptor"、"ToolCallLoop"。
- `supports(ChatContext context)` — 判断当前阶段是否适用于这个上下文。某些阶段可能只在特定条件下执行。例如，如果请求不需要工具调用，ToolCallLoopStage 的 `supports()` 可以返回 false，自动跳过该阶段。
- `execute(ChatContext context, Chain chain)` — 执行阶段逻辑。方法内部**必须**调用 `chain.proceed(context)` 将控制权传递给下一个阶段。如果阶段决定不继续（如缓存命中），可以不调用 `chain.proceed()`，从而中断管道。例如，CacheInterceptor 命中缓存时，可以跳过后续的模型调用和响应构建阶段。

**数据传递机制**：所有 Stage 共享同一个 ChatContext 对象（可变对象）。Stage 可以读取和修改 ChatContext 的任何字段。后面的 Stage 可以看到前面 Stage 的修改。这种设计避免了在每个阶段之间创建新对象的开销，也让数据流向更加清晰。

### 5.6 ContextBuilder 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/context/ContextBuilder.java`

**设计模式**：策略模式

**职责说明**：

ContextBuilder 是上下文构建策略接口。它的任务是将原始数据（会话历史、系统提示、记忆内容、工具列表）构建为发送给模型的最终消息列表。

核心方法：
- `supports(ChatContext context)` — 判断当前策略是否适用于这个上下文。策略选择不是由一个中心化的 if-else 决定，而是由每个策略自己决定。策略类自己最清楚自己适用于什么场景。例如：SlidingWindowContextBuilder 在消息数超过阈值（如 50）时返回 true；FullWindowContextBuilder 始终返回 true（作为兜底策略，但通过 @Order 设为最低优先级确保最后被检查）。
- `build(ChatContext context)` — 执行上下文构建。**注意：此方法直接修改传入的 ChatContext 对象（可变对象），不返回新对象。**该方法负责确定消息窗口范围、对超出窗口的消息执行压缩或丢弃、在消息列表开头注入 system prompt、在最前面注入记忆内容。构建完成后，ChatContext 中的消息列表已经是最终的、可直接发送给模型的格式。

**策略优先级机制**：多个 ContextBuilder 的 `supports()` 可能同时返回 true。为避免冲突，策略通过 `@Order` 注解控制检查顺序：
- SlidingWindowContextBuilder：@Order(10)，消息数 > 50 时触发
- SummaryContextBuilder：@Order(20)，消息数 > 100 时触发
- FullWindowContextBuilder：不设 @Order（默认最低优先级），作为兜底策略最后被检查

遍历时按 @Order 从小到大，兜底策略排在最后。这保证了优先策略有机会先匹配。

### 5.7 ChatContext 类

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/context/ChatContext.java`

**职责说明**：

ChatContext 是 Pipeline 各阶段之间传递数据的可变对象。它不是不可变的 DTO，而是一个在管道执行过程中不断被修改和增强的容器。选择可变对象的原因：避免在每个阶段之间创建新对象的开销，让数据流向更加直观。

核心字段及生命周期：
- 原始 ChatRequest（Pipeline 开始前设置，整个执行过程中不变）
- 当前构建的消息列表（ContextBuildStage 填充，后续阶段可能修改内容如脱敏）
- System prompt（ContextBuildStage 设置）
- 加载的记忆列表（ContextBuildStage 从 MemoryManager 加载）
- 可用工具列表（ContextBuildStage 从 ToolRegistry 获取）
- 工具调用历史（ToolCallLoopStage 追加，记录每轮调用了哪些工具、结果是什么）
- Token 用量累计（ToolCallLoopStage 和 MetricsStage 更新）
- 执行时间统计（MetricsStage 设置）
- 扩展属性 Map（任意 Stage 可用于传递自定义数据，避免 Stage 之间直接耦合）

ChatContext 的完整生命周期：
1. Pipeline 开始前创建——此时只有原始 ChatRequest
2. ContextBuildStage 填充——消息列表、记忆、工具列表
3. InterceptorStage 可能修改——消息内容脱敏、日志记录
4. ToolCallLoopStage 追加——工具调用历史、Token 用量
5. MetricsStage 追加——指标数据
6. ResponseBuildStage 读取——构建最终的 ChatResult

### 5.8 Interceptor 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/interceptor/Interceptor.java`

**设计模式**：责任链模式

**职责说明**：

Interceptor 是拦截器接口。拦截器在核心流程执行前后处理横切逻辑。每个拦截器只负责一个横切关注点（如限流、日志、脱敏、认证、缓存），不关心其他拦截器的存在。

核心方法：
- `getOrder()` — 返回拦截器的执行顺序。数字越小越先执行。预定义的 order 范围：认证类 0-9、限流类 10-19、缓存类 20-29、安全类 30-49（含脱敏）、日志类 100-199、审计类 200-299、指标类 300+。第一版实现的拦截器：RateLimitInterceptor(order=10)、SensitiveDataInterceptor(order=50)、LoggingInterceptor(order=100)。
- `preHandle(ChatContext context)` — 在核心流程执行前处理。可以修改上下文、中断请求（通过抛异常）、跳过后续拦截器（通过调用 chain.skipToNext()）。如果 preHandle 抛异常，后续拦截器和核心流程都不会执行，异常由 ErrorPolicy 处理。
- `postHandle(ChatResult result)` — 在核心流程执行后处理。可以修改响应、记录日志、发布事件。执行顺序与 preHandle 相反（后进先出）——preHandle 的顺序是 10→50→100，postHandle 的顺序是 100→50→10。

### 5.9 Tool 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/tool/Tool.java`

**设计模式**：命令模式

**职责说明**：

Tool 是所有工具的抽象接口。每个工具都是一个独立的可执行单元，封装了工具的所有信息——名称、描述、参数定义、执行逻辑、超时配置。

核心方法：
- `getName()` — 返回工具的唯一名称，全局不可重复。内置工具如 "web_search"、"calculator"、"current_time"。MCP 工具如 "mcp_filesystem_read_file"（带 server 前缀避免冲突）。
- `getDefinition()` — 返回工具定义（ToolDefinition 对象），包含名称、描述、参数 JSON Schema。这个定义会被序列化后发送给模型，让模型知道这个工具的功能和调用方式。模型根据这个定义决定什么时候调用工具、传入什么参数。
- `execute(Map<String, Object> arguments)` — 执行工具的核心逻辑。参数是从模型返回的工具调用请求中提取的。返回 ToolResult 对象，包含执行状态（SUCCESS/ERROR/TIMEOUT）、结果内容、错误信息、执行耗时。
- `getTimeout()` — 返回工具的超时时间（毫秒）。0 表示使用全局默认超时（30秒）。不同工具可以有不同的超时时间——网络搜索可能需要 30 秒，计算器可能只需要 5 秒。

### 5.10 ToolRegistry 类

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/tool/ToolRegistry.java`

**设计模式**：注册表模式

**职责说明**：

ToolRegistry 是所有工具的中心注册表。它负责管理所有已注册的工具，提供统一的发现和执行接口。

核心方法：
- `register(Tool tool)` — 手动注册一个工具。通常不需要手动调用，因为工具通过 `@Component` 自动注册。
- `unregister(String toolName)` — 移除一个工具。MCP Server 断开时，对应的工具会被移除。
- `get(String toolName)` — 根据名称获取工具，返回 Optional。
- `getAll()` — 获取所有已注册的工具实例。
- `getAllDefinitions()` — 获取所有工具的定义列表。用于发送给模型，让模型知道当前可用工具。
- `execute(String toolName, Map<String, Object> arguments)` — 执行指定工具。内部流程：根据名称查找工具 → 通过 CompletableFuture 异步执行 → 使用 orTimeout() 控制超时 → 返回 ToolResult。如果找不到工具，抛出 ToolNotFoundException。如果执行超时，抛出 TimeoutException 并由 ErrorPolicy 处理。

初始化流程：
1. 启动时，Spring 自动注入所有 `Tool` 类型的 Bean
2. 遍历所有 Tool，调用 `getName()` 获取名称
3. 检查是否有重名工具，有则抛出异常
4. 存入 `Map<String, Tool>` 中
5. 日志输出已注册的工具列表

### 5.11 ToolCallLoop 类

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/tool/ToolCallLoop.java`

**设计模式**：模板方法模式

**职责说明**：

ToolCallLoop 负责执行"模型调用 + 工具执行"的循环。这是整个引擎层最核心的组件之一——它决定了 AI 如何与外部工具交互。

工作流程（模板方法骨架，不可变）：
1. 初始化轮次计数器（rounds = 0）
2. 进入循环
3. 调用模型获取响应：`modelAdapter.chat(context)` — 第一版使用同步模式，阻塞等待完整响应
4. 检查响应中是否有工具调用请求：`resp.hasToolCalls()`
5. 如果没有 → 退出循环，将 `resp.getContent()` 包装为 `Flux.just()` 返回给上层
6. 执行工具：遍历 `resp.getToolCalls()`，对每个工具调用 `toolRegistry.execute()`
7. 将工具结果注入上下文：`context.addToolResult(callId, result)`
8. 调用 `toolCallPolicy.shouldContinue(context, rounds)` 判断是否继续
9. 如果继续 → rounds++，回到步骤 2
10. 如果不继续 → 退出循环，返回错误信息或最后已知的回复

第一版选择同步模式的原因：
- 实现简单，不需要处理流式响应中的工具调用判断（流式判断工具调用需要在流结束后才能确定）
- 与现有 ModelAdapter 的 `chat()` 方法完全兼容
- 避免复杂的异步状态管理
- 为第二版实现真正的流式工具调用预留接口空间（接口设计已考虑 Flux 的兼容性）

### 5.12 ToolCallPolicy 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/tool/ToolCallPolicy.java`

**设计模式**：策略模式

**职责说明**：

ToolCallPolicy 是工具调用循环的终止策略。它解决的核心问题是：**模型可能会不断地请求调用工具，循环需要有明确的终止条件。**

核心方法：
- `shouldContinue(ChatContext context, int currentRound)` — 判断是否应该继续下一轮循环。参数包括当前上下文（可以检查已使用的 Token 量、已调用的工具等）和已执行的轮次。
- `getMaxRounds()` — 返回最大允许轮次。用于在循环开始前设置硬性上限。
- `onToolError(ToolCall toolCall, Throwable error, int currentRound)` — 处理工具执行过程中发生的错误。返回一个 ToolResult（可能是错误信息）来决定如何处理——是跳过该工具继续执行其他工具，还是中断整个循环。

默认实现（DefaultToolCallPolicy）：
- 最大轮次：10 轮
- 工具错误处理：记录错误日志，返回包含错误信息的 ToolResult，跳过该工具继续执行其他工具
- 超过最大轮次：抛出 ToolCallLimitExceededException

未来可选实现：
- BudgetAwareToolCallPolicy：根据总 Token 预算决定是否继续。当已使用的 Token 接近预算上限时终止循环。
- ModelDrivenToolCallPolicy：让模型自己判断是否需要继续调用工具。每次循环后询问模型"还需要调用其他工具吗？"

### 5.13 MemoryManager 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/memory/MemoryManager.java`

**设计模式**：策略模式

**职责说明**：

MemoryManager 是记忆管理接口。它负责跨会话的记忆存储和读取。与"上下文"（单次会话的历史消息）不同，记忆是独立于会话的，可以在多个会话之间共享。

核心方法：
- `remember(Session session, MemoryStrategy strategy)` — 从会话中提取记忆并存储。提取逻辑由 MemoryStrategy 决定——第一版使用 ManualMemoryStrategy（用户说"记住"时才提取）。存储方式由 MemoryManager 的实现决定——第一版使用 FileMemoryManager（Markdown 文件），未来可以切换到 Redis 或数据库。
- `recall()` — 读取所有已启用的记忆。返回 Memory 列表。只返回 enabled=true 的记忆，disabled 的记忆不参与上下文构建。
- `forget(String memoryId)` — 删除指定记忆。第一版是物理删除（删除文件），未来可以实现软删除（设置 disabled=true）。
- `buildContext(List<Memory> memories)` — 将记忆列表格式化为可注入上下文的字符串。格式化后的内容会被放入 system prompt 或消息列表的首部，作为 AI 的"背景知识"。

### 5.14 EventBus 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/event/EventBus.java`

**设计模式**：观察者模式

**职责说明**：

EventBus 是事件总线接口。它是模块间解耦通信的核心机制——发布者不需要知道订阅者是谁，订阅者不需要知道事件是谁发布的。

核心方法：
- `publish(Event event)` — 发布一个事件。所有订阅了该事件类型的监听器都会收到通知。监听器的执行是异步的（通过线程池），不阻塞发布者。
- `subscribe(Class<T> eventType, Consumer<T> handler)` — 订阅指定类型的事件。当该类型的事件发布时，handler 会被调用。返回一个 Subscription 对象，可用于后续取消订阅。
- `unsubscribe(Subscription subscription)` — 取消订阅。释放相关资源，避免内存泄漏。

**线程安全设计**：InMemoryEventBus 使用 `CopyOnWriteArrayList` 存储每个事件类型的监听器列表。这种数据结构的特性：
- 遍历时不需要加锁（读操作安全）——因为任何修改操作都会创建新的副本
- 新增监听器时复制整个列表（写操作安全）
- 适合"读多写少"的场景——监听器通常在启动时注册，运行时很少变化
- 不适合频繁增删监听器的场景（如有此需求，可以切换到 ConcurrentHashMap + synchronized 块）

第一版的事件类型：
- TokenConsumedEvent：模型调用完成后发布，携带 sessionId、model、promptTokens、completionTokens、totalTokens
- ToolCalledEvent：工具执行完成后发布，携带 sessionId、toolName、arguments、result、duration
- AgentStateChangedEvent：Agent 状态变更时发布，携带 agentId、oldState、newState

### 5.15 AgentCoordinator 类

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/agent/AgentCoordinator.java`

**设计模式**：中介者模式

**职责说明**：

AgentCoordinator 负责管理 Agent 的生命周期和通信。

核心方法：
- `spawn(Session parentSession, AgentTask task)` — 创建一个子 Agent 执行指定任务。检查当前子 Agent 数量是否已达上限（第一版限制 1 个）。创建后子 Agent 进入 RUNNING 状态。
- `terminate(String agentId)` — 终止指定 Agent。Agent 状态变为 TERMINATED。
- `getStatus(String agentId)` — 获取 Agent 当前状态。返回 IDLE、RUNNING、WAITING_TOOL、COMPLETED、ERROR 或 TERMINATED。
- `cascadeTerminate(String sessionId)` — 级联终止一个会话下的所有 Agent。当主会话被关闭或删除时调用。

第一版约束：
- 同一会话最多 1 个子 Agent 并发执行
- 子 Agent 超时时间 5 分钟
- 子 Agent 不可再 spawn 孙 Agent（深度限制 1）

**子 Agent 结果汇总机制**：子 Agent 执行完成后，结果通过 AgentChannel 回传给主 Agent。主 Agent 将子 Agent 的执行结果汇总到 ChatContext 的扩展属性中。后续的 ContextBuilder 可以读取这些结果，将其注入到上下文中。

### 5.16 AgentChannel 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/agent/AgentChannel.java`

**设计模式**：中介者模式 + 策略模式

**职责说明**：

AgentChannel 定义了 Agent 之间的通信拓扑。不同的拓扑适用于不同的场景——简单的场景用星型，复杂的层级任务用树形，需要协同的用网状。

核心方法：
- `send(AgentMessage message)` — 发送消息到指定 Agent。消息包含 fromAgentId、toAgentId、消息类型和内容。
- `receive(String agentId)` — 接收发给指定 Agent 的消息流。返回 Flux<AgentMessage>，支持响应式消费。

默认实现（StarAgentChannel）：星型拓扑。主 Agent 可以直接与任何子 Agent 通信，子 Agent 之间不能直接通信，需要通过主 Agent 中转。

未来可选实现：
- TreeAgentChannel：树形拓扑，Agent 形成层级结构，适合目标分解场景
- MeshAgentChannel：网状拓扑，任意 Agent 之间可以通信，适合协同场景
- BroadcastAgentChannel：广播拓扑，消息发送给所有 Agent

### 5.17 ErrorPolicy 接口

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/error/ErrorPolicy.java`

**设计模式**：策略模式

**职责说明**：

ErrorPolicy 是错误处理策略接口。它决定在模型调用失败、工具执行失败、超时等异常情况下如何处理。

核心方法：
- `onModelError(ModelCallException e, ChatContext context)` — 模型调用失败时调用。参数包含异常信息和当前上下文。返回一个 ChatResult——可能是重试后成功的回复、降级后的回复或错误信息。实现可以根据异常类型（401、429、5xx 等）采取不同策略。
- `onToolError(ToolExecuteException e, ChatContext context)` — 工具执行失败时调用。返回一个 ToolResult——可能是错误信息或降级结果。实现可以决定是跳过该工具继续执行其他工具，还是中断整个循环。
- `onTimeout(ChatContext context, long elapsedMs)` — 超时时调用。返回一个 ChatResult。实现可以返回"请求超时，请稍后重试"之类的友好提示。

默认实现（DefaultErrorPolicy）：
- 模型调用失败：401/403 不重试（直接返回错误），429 等待 5 秒重试 1 次，5xx 重试 1 次
- 工具执行失败：记录错误日志，返回包含错误信息的 ToolResult，跳过该工具继续执行其他工具
- 超时：返回"请求超时，请稍后重试"的 ChatResult

未来可选实现：
- RetryErrorPolicy：失败重试 N 次，使用指数退避策略
- FallbackModelErrorPolicy：失败时切换到备用模型
- CircuitBreakerErrorPolicy：连续失败 N 次后熔断，一段时间后尝试恢复

### 5.18 ModelProvider 接口

**文件路径**：`lyclaw-core/src/main/java/lyjew/com/lyclaw/provider/ModelProvider.java`

（注意：接口定义在 lyclaw-core 中，实现类在 lyclaw-adapter 中。设计意图：形成防腐层，解耦引擎层和适配器层。）

**设计模式**：工厂模式 + 防腐层

**职责说明**：

ModelProvider 是模型适配器的提供者接口。Engine 通过此接口获取适配器，完全不依赖 lyclaw-adapter 模块的具体类。这是引擎层和适配器层之间的"防腐层"。

核心方法：
- `getAdapter(String provider)` — 根据厂商标识获取对应的适配器实例。如 getAdapter("minimax") 返回 MinimaxAdapter。
- `listProviders()` — 列出所有可用的厂商标识。用于管理界面展示和验证用户输入。
- `configure(String provider, ModelConfig config)` — 配置指定厂商的适配器。注入 apiKey、model、baseUrl 等参数。

这种设计使得引擎层与适配器实现完全解耦。未来如果适配器层的实现方式完全改变（如从 OkHttp HTTP 调用切换到 gRPC 调用），引擎层代码完全不受影响——只需要 ModelProvider 的实现类内部调整。

### 5.19 EngineProperties 配置类

**文件路径**：`lyclaw-engine/src/main/java/lyjew/com/lyclaw/config/EngineProperties.java`

**职责说明**：

EngineProperties 是引擎层的所有可配置参数。使用 Spring Boot 的 `@ConfigurationProperties` 注解，绑定配置文件中的 `lyclaw.engine` 前缀。

可配置参数及默认值：
- `max-tool-call-rounds`（默认 10）：工具调用最大轮次，超过后抛出异常

- `max-concurrent-agents`（默认 1）：同一会话最大并发 Agent 数

- `default-context-builder`（默认 "full-window"）：默认上下文构建策略
- `tool-timeout-millis`（默认 30000）：工具执行超时时间（毫秒）
- `model-timeout-millis`（默认 60000）：模型调用超时时间（毫秒）

## 第六章：Engine 顶层抽象设计

### 6.1 设计动机

在传统的 AI 应用架构中，对话引擎通常是一个具体的类（如 ChatService 或 AgentService），所有对话逻辑都写在这个类中。当需要增加一种新的对话模式时，比如从"标准对话"扩展到"推理链对话"，通常的做法是：

1. 在原有的 ChatService 中加一个 reasoningMode 标志
2. 在 execute() 方法中加一个 if-else 分支
3. 每个新功能都在同一个类中膨胀

这样做的问题：
- 类越来越庞大（可能超过 3000 行），难以理解和维护
- 修改一个模式的逻辑可能意外影响其他模式（共享状态、方法调用）
- 无法独立测试不同模式的逻辑（必须启动整个 ChatService）
- 无法独立部署或优化不同模式的性能（如推理模式需要更多内存、批处理模式需要更多 CPU）
- 多个开发者在同一个类上并行工作，频繁产生代码冲突

LLM 应用正在快速发展，未来可能出现各种不同的对话范式。每一种范式对应一个"引擎"。引擎之间共享底层组件（工具、记忆、事件总线），但执行逻辑完全不同。

### 6.2 Engine 接口的核心设计

Engine 接口是引擎层的最高抽象。它只定义四个方法，每个方法都有明确的语义：

`getName()` — 返回引擎的唯一标识名称。用于日志记录、监控面板和运维界面展示。

`supports(ChatRequest request)` — 引擎选择的核心。每个引擎自己判断是否支持处理当前请求。EngineSelector 遍历所有引擎，选择第一个 supports() 返回 true 的引擎。设计要点：DefaultEngine 的 supports() 始终返回 true，作为兜底引擎。它必须放在引擎列表的最后（通过 @Order 设为最大值），确保特殊引擎优先匹配。

`execute(ChatRequest request)` — 执行对话，返回流式响应。使用 Flux<String> 而不是 String，保持流式特性。第一版内部使用同步调用，通过 Flux.just() 包装；第二版可实现真正的流式处理。

`getMetadata()` — 返回引擎元信息。用于管理界面展示。

### 6.3 DefaultEngine 的实现设计

DefaultEngine 是第一版的核心引擎实现。它使用 Pipeline 模式组织对话流程。

DefaultEngine 的 execute() 流程：
1. 通过 PipelineBuilder 创建 Pipeline，编排 5 个处理阶段
2. 创建 ChatContext，装入 ChatRequest
3. 调用 Pipeline.execute(context)，按顺序执行所有 Stage
4. Pipeline 执行完毕后，更新会话（追加消息、持久化）
5. 根据 MemoryStrategy 判断是否需要提取记忆
6. 发布 ConversationCompletedEvent
7. 返回 ChatResult

DefaultEngine 通过依赖注入获取所有需要的组件：
- List<ContextBuilder>：上下文构建策略
- InterceptorChain：拦截器链
- ModelProvider：模型适配器提供者
- ToolRegistry：工具注册表
- ToolCallPolicy：循环终止策略
- ErrorPolicy：错误处理策略
- EventBus：事件总线
- MemoryManager：记忆管理器
- SessionStorage：会话存储

### 6.4 未来引擎的实现设想

**ReasoningEngine（推理引擎）**：执行 Chain-of-Thought 推理流程。与 DefaultEngine 的差异：多了一个"验证阶段"——模型先输出推理过程，然后对推理进行验证，可能调用工具辅助推理，最终输出结论。它共享 DefaultEngine 的 ToolRegistry 和 MemoryManager，但 Pipeline 编排完全不同。

**PlanningEngine（规划引擎）**：将复杂目标分解为子任务。流程：分析用户目标 → 制定执行计划 → 逐个执行子任务（每个子任务可能 spawn 子 Agent）→ 汇总结果 → 输出最终回答。它需要 AgentCoordinator 的更高级功能（并行 spawn）。

**RagEngine（RAG 引擎）**：检索增强生成。流程：从用户问题中提取检索关键词 → 调用检索工具查询知识库 → 将检索结果注入上下文 → 基于检索结果生成回答。它需要一个额外的"检索阶段"，可能需要向量数据库支持。

### 6.5 J 类场景（完全不同引擎）的支撑机制

所有 J 类场景（推理引擎、规划引擎、RAG 引擎、多模态引擎、实时引擎、批处理引擎、工具制造引擎）都通过同一个机制支撑：**实现 Engine 接口 + 共享底层组件。**

新增一个引擎只需要：
1. 新建类实现 Engine 接口
2. 实现 supports() 方法定义适用范围
3. 实现 execute() 方法定义执行逻辑
4. 通过依赖注入获取需要的共享组件
5. 加 @Component 注解自动注册

已有 Engine 的代码完全不受影响。EngineSelector 自动发现新引擎并在 supports() 匹配时使用。

## 第七章：Pipeline 可编排管道设计

### 7.1 设计动机

传统的对话处理流程通常写在一个方法中，所有步骤按顺序写死。这种写法的致命问题是：**流程是固定的，修改流程需要修改代码。**随着业务增长，这个方法会变成"上帝方法"——几十个步骤、数百行代码、深层的 if-else 嵌套。新增一个步骤需要在这堆代码中找到正确的位置插入，稍有不慎就会破坏已有逻辑。

### 7.2 Pipeline 的设计思路

Pipeline 模式将处理流程分解为多个独立的 Stage，每个 Stage 负责一个明确的职责。Pipeline 只是一个容器，负责按顺序调用 Stage。

**核心思想：流程与步骤分离。**
- 流程由 Pipeline 控制（按顺序调用 Stage）
- 步骤由 Stage 实现（每个 Stage 独立处理自己的逻辑）
- 编排由 PipelineBuilder 完成（决定哪些 Stage 参与、以什么顺序参与）

### 7.3 PipelineBuilder 的编排能力

PipelineBuilder 提供链式 API 编排管道阶段。每个 addStage() 返回 Builder 自身。高级编排方法允许在任意位置插入、替换、移除阶段。

### 7.4 Stage 之间的数据传递

Pipeline 中的 Stage 通过 ChatContext 对象传递数据。ChatContext 是一个可变对象，各 Stage 共享同一个实例，直接修改对象字段。这种设计避免了在每个 Stage 之间创建新对象的开销，也让数据流向更加直观——后面的 Stage 可以读取前面 Stage 的修改。

### 7.5 第一版的默认阶段编排

第一版 DefaultEngine 使用 5 个阶段：ContextBuildStage → InterceptorStage → ToolCallLoopStage → MetricsStage → ResponseBuildStage。每个阶段的职责明确，阶段之间通过 ChatContext 传递数据。

## 第八章：ContextBuilder 上下文构建设计

### 8.1 设计动机

AI 模型有上下文窗口限制（4K、8K、32K、128K tokens 等）。当对话历史过长时，无法将所有消息都发送给模型。此外，对话历史中并非所有消息同等重要——有些包含关键信息，有些只是过渡性的寒暄。不同场景需要不同的上下文构建策略。

### 8.2 ContextBuilder 的策略设计

ContextBuilder 是一个策略接口，不同实现代表不同策略。核心设计理念：**策略自描述 + 自动选择。**每个策略通过 supports() 方法自判断是否适用，ContextBuildStage 遍历所有策略，选择第一个匹配的。

### 8.3 第一版的三种策略

**FullWindowContextBuilder**：兜底策略，消息数较少时使用，将所有消息放入上下文。

**SlidingWindowContextBuilder**：消息数超过 50 时启用，只保留最近 N 条消息。

**SummaryContextBuilder**：消息数超过 100 时启用，旧消息用 AI 做摘要替换原文。

### 8.4 策略优先级和兜底机制

通过 @Order 注解控制检查顺序。SlidingWindowContextBuilder(@Order=10) 优先检查，SummaryContextBuilder(@Order=20) 次之，FullWindowContextBuilder(无@Order，最低优先级) 作为兜底最后检查。这保证了优先策略有机会先匹配，兜底策略只在没有其他策略匹配时才使用。

## 第九章：Interceptor 拦截器链设计

### 9.1 设计动机

在请求处理流程中，有许多横切关注点需要处理——限流、日志、脱敏、认证、缓存、审计、指标。如果将这些逻辑直接写在核心流程中，会导致核心流程代码膨胀，横切关注点的修改影响核心流程，不同关注点之间互相干扰。

拦截器链模式将这些横切关注点从核心流程中分离出来，形成独立的拦截器。每个拦截器只负责一个关注点，拦截器之间通过责任链模式串联。

### 9.2 拦截器链的设计

Interceptor 接口定义三个方法：getOrder()（执行顺序）、preHandle()（请求前处理）、postHandle()（请求后处理，逆序执行）。InterceptorChain 管理器启动时扫描所有 Interceptor 实现，按 getOrder() 排序，提供 proceed() 方法驱动链的执行。

### 9.3 第一版的拦截器

RateLimitInterceptor(order=10)：限流检查，超限则拒绝请求。
SensitiveDataInterceptor(order=50)：敏感信息脱敏。
LoggingInterceptor(order=100)：请求/响应日志记录。

### 9.4 未来扩展的拦截器

CacheInterceptor(order=20)：缓存检查和存储。
AuthInterceptor(order=5)：身份认证。
AuditInterceptor(order=300)：审计日志。
CostControlInterceptor(order=30)：成本控制。
FeatureFlagInterceptor(order=15)：功能开关。

### 9.5 拦截器的分支能力

拦截器可以调用 chain.skipToNext() 跳过后续拦截器。例如 CacheInterceptor 命中缓存时可直接返回，跳过后续所有拦截器和核心流程。

## 第十章：ToolExecutor 工具执行设计

### 10.1 设计动机

AI 模型可能需要调用外部工具来获取信息或执行操作。工具调用涉及多个问题：工具发现（模型需要知道可用工具列表）、工具执行（超时控制、错误处理、结果截断）、循环控制（防止死循环）、工具来源多样化（内置工具、MCP 工具、插件工具）。

### 10.2 Tool 接口设计

Tool 是所有工具的抽象接口，只定义四个方法：getName()、getDefinition()、execute()、getTimeout()。每个工具封装为一个独立命令对象。ToolResult 包含执行状态、结果内容、错误信息、执行耗时。

### 10.3 ToolRegistry 注册表设计

ToolRegistry 是所有工具的中心注册表。启动时通过 Spring 自动注入所有 Tool 实现，按名称存入 Map。提供注册、发现、执行、超时控制等功能。

### 10.4 第一版的内置工具

WebSearchTool：网络搜索，30 秒超时，结果截断 50KB。
CalculatorTool：数学计算，5 秒超时。
CurrentTimeTool：当前时间，1 秒超时。
McpToolAdapter：MCP 工具适配器，将外部 MCP Server 的工具适配为 Tool 接口。

### 10.5 ToolCallLoop 循环设计

ToolCallLoop 负责"调用模型 → 检查工具调用 → 执行工具 → 注入结果 → 再次调用模型"的循环。循环终止条件：模型不再请求工具、ToolCallPolicy 决定终止、达到最大轮次、发生不可恢复错误。

### 10.6 工具执行超时控制

通过 CompletableFuture 实现：supplyAsync 异步执行工具 → orTimeout 设置超时 → get 阻塞等待。超时时抛出 TimeoutException，由 ErrorPolicy.onToolError() 处理。第一版使用固定大小的线程池执行工具。

### 10.7 ToolCallPolicy 策略设计

ToolCallPolicy 定义循环终止策略。DefaultToolCallPolicy：最大 10 轮，工具错误时记录日志并跳过。未来可实现 BudgetAwareToolCallPolicy（基于 Token 预算）和 ModelDrivenToolCallPolicy（让模型自己决定）。

## 第十一章：MemoryManager 记忆管理设计

### 11.1 设计动机

AI 对话中的"记忆"是指跨会话的持久化信息。与"上下文"（单次会话的历史消息）不同，记忆独立于会话，可在多个会话之间共享。核心需求：记住重要信息、自动提取（未来）、存储灵活性（文件 → Redis → 数据库）、过期清理。

### 11.2 MemoryManager 接口设计

MemoryManager 定义记忆的 CRUD 操作：remember()（从会话提取并存储记忆）、recall()（读取所有已启用记忆）、forget()（删除记忆）、buildContext()（格式化为可注入上下文的字符串）。

### 11.3 MemoryStrategy 策略设计

MemoryStrategy 决定从会话中提取哪些信息作为记忆。ManualMemoryStrategy（第一版）：用户说"记住"时提取。KeyEventMemoryStrategy（未来）：检测关键事件自动提取。AiDrivenMemoryStrategy（未来）：AI 自动判断。

### 11.4 记忆的存储格式

第一版使用 Markdown 文件存储：memory/2026-04-27-001.md、memory/MEMORY.md。Memory 实体包含 id、title、content、enabled、tags、createdAt、updatedAt。

### 11.5 未来存储实现的可替换性

由于 MemoryManager 是接口，未来切换存储只需新建实现类并切换注入。所有调用 MemoryManager 的代码无需修改。

## 第十二章：EventBus 事件总线设计

### 12.1 设计动机

模块之间经常需要通信。如果直接调用，会导致紧密耦合——修改一个模块影响多个模块，新增监听者需要修改发布者代码，难以追踪事件流向。事件总线通过中央总线解耦发布者和订阅者。

### 12.2 EventBus 接口设计

publish(Event)：发布事件，异步执行监听器。subscribe(Class, Consumer)：订阅事件。unsubscribe(Subscription)：取消订阅。

### 12.3 第一版的事件类型

TokenConsumedEvent：模型调用完成后发布。ToolCalledEvent：工具执行完成后发布。AgentStateChangedEvent：Agent 状态变更时发布。ErrorEvent：发生错误时发布。

### 12.4 默认实现：InMemoryEventBus

使用 CopyOnWriteArrayList 存储监听器列表，保证线程安全。监听器的执行通过线程池异步进行，不阻塞发布者。

### 12.5 线程安全设计

CopyOnWriteArrayList 的特性：遍历时不需要加锁（读安全），新增监听器时复制整个列表（写安全）。适合"读多写少"的场景——监听器通常在启动时注册，运行时很少变化。

### 12.6 未来实现的可替换性

KafkaEventBus（分布式事件总线）、SpringEventBus（Spring 深度集成）。切换只需新建实现类并切换注入，所有发布者和订阅者代码无需修改。

## 第十三章：AgentCoordinator Agent 协调设计

### 13.1 设计动机

复杂 AI 对话中，一个任务可能需要分解为多个子任务并行或串行执行。每个子任务由一个"子 Agent"负责。主 Agent 与用户直接对话，子 Agent 执行具体任务。

### 13.2 Agent 生命周期

状态机：IDLE → RUNNING → WAITING_TOOL（可循环回 RUNNING）→ COMPLETED/ERROR/TERMINATED。AgentCoordinator 在操作前检查状态是否允许。

### 13.3 第一版的约束

同一会话最多 1 个子 Agent 并发。子 Agent 超时 5 分钟。子 Agent 不可再 spawn 孙 Agent（深度限制 1）。主会话终止时级联终止所有子 Agent。

### 13.4 AgentChannel 通信拓扑设计

AgentChannel 定义通信拓扑：StarAgentChannel（第一版，星型）、TreeAgentChannel（未来，树形）、MeshAgentChannel（未来，网状）、BroadcastAgentChannel（未来，广播）。切换拓扑只需替换 AgentChannel 实现。

### 13.5 子 Agent 结果汇总

子 Agent 执行完成后，结果通过 AgentChannel 回传给主 Agent。主 Agent 将结果汇总到 ChatContext 中，后续的 Pipeline 阶段可读取这些结果。

## 第十四章：ErrorPolicy 错误处理设计

### 14.1 设计动机

在 AI 对话流程中，可能发生多种类型的错误。模型 API 可能返回 401（Key 无效）、429（限流）、5xx（服务器错误）。模型调用可能超时。工具执行可能失败或超时。不同的错误需要不同的处理策略——有些需要重试，有些需要降级，有些需要熔断。

如果没有统一的错误处理策略，错误处理逻辑会散落在 Pipeline 的各个 Stage 中，导致：
- 错误处理逻辑重复（每个调用模型的地方都要写一遍重试逻辑）
- 错误处理策略不一致（有的地方重试 1 次，有的地方重试 3 次）
- 修改错误处理策略需要改动多处代码
- 无法灵活切换错误处理策略（如从"重试"切换到"熔断"）

### 14.2 ErrorPolicy 的核心设计理念

ErrorPolicy 将错误处理从核心流程中完全分离出来，形成一个独立的策略接口。所有需要错误处理的地方（模型调用、工具执行、超时控制）都通过 ErrorPolicy 来处理异常，而不是自己写 try-catch。

这种设计带来的好处：
- 错误处理逻辑集中管理，修改策略只需改一处
- 错误处理策略可以动态切换（通过依赖注入）
- 核心流程代码更简洁，只关注正常逻辑
- 可以独立测试错误处理策略（不需要启动整个 Pipeline）

### 14.3 ErrorPolicy 接口的方法详解

ErrorPolicy 接口定义了三个方法，分别处理三类不同的错误场景。这三个方法的设计遵循了一个原则：**错误处理的结果必须是对调用方可用的正常返回值，不能是异常。**

**方法一：onModelError(ModelCallException e, ChatContext context)**

触发时机：当 ModelAdapter.chat() 或 ModelAdapter.chatStream() 抛出异常时。ModelCallException 包含了 HTTP 状态码（如 401、429、503）、原始错误信息和请求上下文。

策略的决策空间：
- 401（Key 无效）：通常不重试——Key 无效重试多少次都没用。策略应该直接返回一个包含错误信息的 ChatResult，提示用户检查 API Key。
- 429（限流）：应该等待一段时间后重试。策略可以 sleep 几秒后再调用模型，或者返回一个 ChatResult 提示用户稍后再试。
- 503（服务器临时不可用）：可以重试 1-3 次。使用指数退避策略——第一次等 1 秒，第二次等 2 秒，第三次等 4 秒。
- 连接超时：可以重试 1 次。超时通常是网络抖动，重试一次很可能成功。

返回值：ChatResult。这是对调用方（ToolCallLoop 或 Pipeline）的最终结果。如果策略决定不重试，返回的 ChatResult 应该包含友好的错误提示（如"抱歉，服务暂时不可用，请稍后再试"），而不是原始异常信息。

**方法二：onToolError(ToolExecuteException e, ChatContext context)**

触发时机：当 ToolRegistry.execute() 抛出异常时。ToolExecuteException 包含了工具名称、调用参数、原始异常和工具调用上下文。

策略的决策空间：
- 工具不存在：不应该重试——工具名可能写错了。返回错误信息，让模型知道这个工具不可用。
- 工具执行超时：可以返回超时信息。模型会根据这个信息决定是换一种方式提问还是放弃。
- 工具返回结果过大：自动截断结果，井在结果中注明"结果过长已截断"。
- 工具内部业务错误（如文件不存在）：返回错误信息给模型，模型可能会调整参数再次调用。

返回值：ToolResult。这个结果会被注入到 ChatContext 中，作为工具调用的结果发送给模型。模型看到工具返回的错误信息后，可以决定如何处理（换参数重试、换工具、或告知用户）。

**方法三：onTimeout(ChatContext context, long elapsedMs)**

触发时机：当整个对话流程超过配置的超时时间时（如 60 秒）。elapsedMs 是已经过去的时间。

策略的决策空间：
- 对话总时长超过限制：返回一个友好的超时提示，如"抱歉，处理时间较长，请简化问题后重试"。
- 接近超时但未超过：可以返回当前已有的部分结果。
- 中间有工具调用导致的超时：可以返回工具调用前的部分结果。

返回值：ChatResult。这是给用户的最终回复。

### 14.4 DefaultErrorPolicy 的默认行为

DefaultErrorPolicy 是第一版的默认实现，采用了"保守重试"的策略——只在明确可能成功的情况下重试，避免浪费资源。

模型调用失败的处理逻辑：
- 401（Key 无效）：不重试。直接返回错误信息"API Key 无效或已过期，请检查配置"。
- 403（无权限）：不重试。返回错误信息"API Key 没有访问权限"。
- 429（限流）：等待 5 秒后重试 1 次。如果仍失败，返回错误信息"请求过于频繁，请稍后重试"。
- 5xx（服务器错误）：重试 1 次。两次请求之间等待 1 秒。如果仍失败，返回错误信息"模型服务暂时不可用，请稍后重试"。
- 其他错误（如网络超时）：不重试。返回错误信息"请求失败：{错误消息}"。

工具执行失败的处理逻辑：
- 所有工具错误：不重试。记录错误日志，返回包含错误信息的 ToolResult。ToolResult 的状态设为 ERROR，内容包含错误描述。模型收到这个 ToolResult 后可以看到工具执行失败了，可能会调整参数或换一种方式。

超时的处理逻辑：
- 对话超时：返回 ChatResult，内容是"抱歉，处理请求超时，请简化问题后重试或稍后再试"。ChatResult 中的 finishReason 设为 "timeout"。

### 14.5 ErrorPolicy 在架构中的调用链

ErrorPolicy 被以下组件调用：

ToolCallLoop 调用 onModelError()：
- 每次调用 modelAdapter.chat() 时，用 try-catch 包裹
- 捕获到异常后，调用 errorPolicy.onModelError()
- 根据返回的 ChatResult 决定是继续循环还是退出

ToolCallLoop 调用 onToolError()：
- 每次调用 toolRegistry.execute() 时，用 try-catch 包裹
- 捕获到异常后，调用 errorPolicy.onToolError()
- 根据返回的 ToolResult 决定是注入结果继续还是中断循环

Pipeline 调用 onTimeout()：
- Pipeline 执行过程中持续检查是否超时
- 超时时调用 errorPolicy.onTimeout()
- 根据返回的 ChatResult 结束 Pipeline 执行

### 14.6 ErrorPolicy 的可扩展性

ErrorPolicy 是一个策略接口，未来可以实现多种不同的策略，而不需要修改任何调用方代码（ToolCallLoop、Pipeline 等）。

**RetryErrorPolicy（重试策略）**：比 DefaultErrorPolicy 更激进的重试策略。模型调用失败时重试 3 次（而不是 1 次），使用指数退避（1 秒、2 秒、4 秒）。工具执行失败时也重试 1 次（DefaultErrorPolicy 不重试工具）。适合对可用性要求极高、成本不敏感的场景。

**FallbackModelErrorPolicy（降级策略）**：当主模型不可用时，自动切换到备用模型。例如，当 MiniMax 返回 5xx 时，自动切换到 DeepSeek 继续处理。需要配置备用模型列表和切换顺序。适合生产环境的高可用场景。

**CircuitBreakerErrorPolicy（熔断策略）**：使用熔断器模式，连续失败 N 次后熔断，一段时间后尝试恢复。熔断期间所有请求直接返回错误，不实际调用模型（快速失败）。适合防止雪崩效应的场景。

**CompositeErrorPolicy（组合策略）**：组合多个 ErrorPolicy，按顺序尝试。例如，先尝试 RetryErrorPolicy（重试 3 次），如果仍失败则使用 FallbackModelErrorPolicy（切换模型），如果仍失败则使用 CircuitBreakerErrorPolicy（熔断）。

切换方式：在 Spring 配置中通过 @Primary 或配置文件切换注入的 ErrorPolicy 实现类。所有调用方代码零修改。

### 14.7 错误处理的完整流程示例

以下是一个完整的错误处理流程示例，展示各个组件如何协同工作：

```
用户发送消息
  │
  ▼
Pipeline 开始执行
  │
  ├── Stage 1-2: 上下文构建和拦截器（正常执行）
  │
  ├── Stage 3: ToolCallLoopStage
  │   │
  │   ├── 第 1 轮调用模型
  │   │   │
  │   │   ├── ModelAdapter.chat() → 抛出 ModelCallException(status=503)
  │   │   │
  │   │   ├── ToolCallLoop 捕获异常
  │   │   │
  │   │   ├── 调用 ErrorPolicy.onModelError(exception, context)
  │   │   │   │
  │   │   │   ├── DefaultErrorPolicy 判断：503 是服务器错误
  │   │   │   ├── 等待 1 秒
  │   │   │   ├── 重新调用 ModelAdapter.chat()
  │   │   │   ├── 第 2 次成功，返回 ModelResponse
  │   │   │   └── 返回成功的 ChatResult
  │   │   │
  │   │   ├── 收到 ChatResult，检查是否有工具调用
  │   │   │
  │   │   ├── 有工具调用 → 执行工具
  │   │   │   │
  │   │   │   ├── ToolRegistry.execute() → 抛出 ToolExecuteException(timeout)
  │   │   │   │
  │   │   │   ├── ToolCallLoop 捕获异常
  │   │   │   │
  │   │   │   ├── 调用 ErrorPolicy.onToolError(exception, context)
  │   │   │   │   │
  │   │   │   │   ├── DefaultErrorPolicy 判断：超时
  │   │   │   │   ├── 不重试
  │   │   │   │   └── 返回包含错误信息的 ToolResult
  │   │   │   │
  │   │   │   └── 注入 ToolResult 到上下文
  │   │   │
  │   │   ├── ToolCallPolicy.shouldContinue() → true
  │   │   │
  │   │   └── 第 2 轮调用模型（上下文包含工具错误信息）
  │   │       │
  │   │       ├── 模型看到工具执行超时了
  │   │       ├── 模型决定不使用工具了，直接回复
  │   │       └── 返回正常的文本回复
  │   │
  │   └── 循环结束，返回最终回复
  │
  ├── Stage 4-5: 指标采集和响应构建（正常执行）
  │
  ▼
返回 ChatResult 给用户
```

这个流程展示了 ErrorPolicy 如何让核心流程在面对错误时保持简洁——ToolCallLoop 只需要用 try-catch 包裹调用，把异常交给 ErrorPolicy 处理，自己不需要写任何 if-else 判断 HTTP 状态码。

## 第十五章：流式响应处理机制

### 15.1 设计问题

ToolCallLoop 需要处理模型调用。模型调用有两种模式：

- 同步模式（chat()）：阻塞等待完整响应，返回 ModelResponse 对象。可以在拿到完整响应后检查是否有工具调用请求。
- 流式模式（chatStream()）：逐 token 返回，返回 Flux<String>。问题在于：工具调用请求（tool_calls）通常在流式响应的末尾才出现。如果使用流式模式，必须等待整个 Flux 完成才能知道模型是否请求了工具调用。

这导致了流式输出和工具调用判断之间的矛盾——用户期望看到实时的逐 token 输出，但 ToolCallLoop 需要完整响应才能判断是否需要调用工具。

### 15.2 第一版的选择：同步模式

第一版采用同步模式解决这个矛盾：

- Engine 对外接口保持流式（Flux<String>），为未来升级预留空间
- ToolCallLoop 内部使用同步的 chat() 方法阻塞等待完整响应
- chat() 返回完整的 ModelResponse 后，ToolCallLoop 判断是否有工具调用
- 如果没有工具调用，将 response.getContent() 通过 Flux.just() 返回给上层
- 如果有工具调用，执行工具后再次调用 chat()，循环直到没有工具调用

这种设计的优劣分析：

优势：
- 实现简单可靠——不需要处理流式响应中判断工具调用的复杂异步逻辑
- 工具调用循环的控制逻辑清晰——每轮都是完整的"请求-响应-判断"周期
- 与现有 ModelAdapter 的 chat() 方法完全兼容——不需要修改适配器
- 为第二版预留了接口空间——Engine 的 execute() 返回 Flux<String>，未来改为真正的流式时上层代码不需要修改

劣势：
- 用户看不到逐 token 的实时输出——必须等完整响应才能看到回复
- 对于不涉及工具调用的简单对话，用户感知的延迟较高——明明第一个 token 已经生成了，但必须等所有 token 生成完才能显示

第一版选择这个折中方案的理由：先保证功能正确性和代码简洁性，用户体验优化放在第二版。

### 15.3 第二版优化方向

第二版可以实现真正的流式工具调用：

1. 使用 chatStream() 获取流式响应
2. 将每个 token 实时通过 Flux 推送给用户
3. 同时将所有 token 收集到 StringBuilder 缓冲区
4. Flux 结束后（doOnComplete），解析缓冲区中的完整响应
5. 如果包含工具调用请求——静默执行工具（用户无感知），再次调用 chatStream()，继续实时推送 token
6. 如果不包含工具调用请求——流程自然结束

这样用户在第一轮就能看到实时输出，工具调用在后台静默执行。用户体验与直接调用聊天 API 一致，同时保留了工具调用的能力。

实现这个优化需要解决的技术问题：
- 如何判断流式响应中的 tool_calls 边界（不同厂商 SSE 格式不同）
- 如何在前端隐藏工具调用的中间过程（用户不需要看到"正在调用工具..."的技术细节）
- 如何处理嵌套的工具调用（工具调用结果又触发新的工具调用）

## 第十六章：Session 事务与数据一致性

### 16.1 设计原则

第一版采用**最终一致性**而非强一致性。这意味着不保证在 Pipeline 执行的每一刻 Session 都是最新的完整状态，但保证在流程结束后 Session 会达到一致的状态。

选择最终一致性的原因：
- 第一版是单用户应用，不存在并发修改同一 Session 的场景
- Pipeline 执行可能涉及多轮工具调用，耗时较长——如果使用强一致性（每次都持久化），会显著增加延迟
- 最终一致性简化了错误处理——不需要实现复杂的事务回滚机制

### 16.2 正常流程

```
用户发送消息
  │
  ├── 用户消息追加到 Session.messages[]
  ├── SessionStorage.save(session)
  │  用户消息已持久化——即使后续 Pipeline 失败，用户消息不会丢失
  │
  ▼
Pipeline 执行（可能耗时数秒到数十秒）
  │  在此期间 Session 文件中的状态是"已追加用户消息但还没有 AI 回复"
  │
  ├── 成功完成：
  │   ├── AI 回复追加到 Session.messages[]
  │   ├── 更新 Session.updatedAt
  │   ├── SessionStorage.save(session)
  │   │  此时 Session 文件中的状态是"用户消息 + AI 回复，完整"
  │   └── 可选：MemoryManager.remember(session, strategy)
  │
  └── 执行失败：
      ├── 追加一条 AI 错误消息到 Session.messages[]
      │   内容示例："抱歉，处理请求时遇到错误，请稍后重试。[错误码: MODEL_API_TIMEOUT]"
      ├── 更新 Session.updatedAt
      └── SessionStorage.save(session)
         此时 Session 文件中的状态是"用户消息 + AI 错误回复"
```

### 16.3 为什么不回滚

在设计讨论中，曾考虑过 Pipeline 失败时回滚 Session（删除用户消息，恢复执行前的状态）。经过分析后决定不采用回滚机制，原因如下：

第一，用户消息是用户确实执行过的操作。用户输入了消息、点击了发送——这个事实不应该因为后端处理失败而被抹去。保留用户消息是对用户操作记录的尊重。

第二，错误信息有助于排查问题。运维人员可以通过查看会话记录了解"这个用户遇到了什么错误、错误发生在什么时间、错误类型是什么"。如果回滚了，这些信息就丢失了。

第三，用户期望看到"已发送但回复失败"的状态。如果消息凭空消失（被回滚了），用户会困惑"我刚才发的消息去哪了？"保留用户消息和错误信息，用户至少能看到"消息发出去了，但回复是错误信息"。

第四，最终一致性模型简化了错误处理。不需要实现复杂的事务机制（如两阶段提交），不需要管理回滚日志，不需要处理回滚失败的情况。

### 16.4 异常场景下的数据状态

| 异常场景 | Session 状态 | 用户看到的内容 |
|----------|-------------|---------------|
| Pipeline 执行前崩溃 | 无变化（用户消息未追加） | 用户消息发送失败 |
| Pipeline 执行中崩溃 | 用户消息已存在，无 AI 回复 | 用户消息已发送但无回复 |
| 模型调用失败 | 用户消息 + AI 错误消息 | 用户消息 + 错误提示 |
| 工具执行失败 | 用户消息 + AI 回复（可能包含工具错误） | 用户消息 + AI 回复 |
| 超时 | 用户消息 + AI 超时消息 | 用户消息 + 超时提示 |

## 第十七章：模块依赖关系

### 17.1 依赖架构图

```
lyclaw-web（启动模块，Spring Boot 应用）
  │
  ├──► lyclaw-engine（引擎层）← 本文档设计的模块
  │       │
  │       ├──► lyclaw-core（引擎层的所有接口定义）
  │       │       │  Engine、PipelineStage、ContextBuilder、Interceptor、
  │       │       │  Tool、MemoryManager、EventBus、ErrorPolicy、ModelProvider
  │       │       │
  │       │       └──► lyclaw-common（公共 DTO：ChatRequest、ModelResponse、
  │       │               Session、Message、ModelConfig、Usage 等）
  │       │
  │       ├──► lyclaw-common（直接依赖公共 DTO）
  │       │
  │       └──► lyclaw-storage（SessionStorage、MemoryStorage、ConfigStorage）
  │               │
  │               └──► lyclaw-core → lyclaw-common
  │
  └──► lyclaw-adapter（模型适配器实现层）
          │
          ├──► lyclaw-core（实现 ModelAdapter 接口和 ModelProvider 接口）
          └──► lyclaw-common（直接依赖公共 DTO）

关键设计：
lyclaw-engine 不直接依赖 lyclaw-adapter 的任何具体类。
引擎通过 lyclaw-core 中的 ModelProvider 接口获取适配器。
ModelProvider 的实现由 lyclaw-adapter 提供，通过 Spring 在运行时注入。
```

### 17.2 依赖方向验证

- lyclaw-engine → lyclaw-core：✅ 正向依赖。引擎依赖接口（Engine、PipelineStage、ContextBuilder 等），接口定义在 core 中。这是符合依赖倒置原则的正确方向。
- lyclaw-engine → lyclaw-common：✅ 正向依赖。引擎依赖纯 DTO（ChatRequest、Session、Message 等），这些是无状态的纯数据对象，不包含任何业务逻辑。
- lyclaw-engine → lyclaw-storage：✅ 正向依赖。引擎依赖存储接口（SessionStorage、MemoryStorage），存储模块是基础设施层。
- lyclaw-engine → lyclaw-adapter：❌ 无直接依赖。通过 ModelProvider 接口解耦。引擎层与适配器层之间没有 import 关系，没有编译期依赖。

无循环依赖，单向依赖，符合 Clean Architecture 的分层原则。

### 17.3 防腐层设计

lyclaw-engine 不直接依赖 lyclaw-adapter 的具体类（如 ModelAdapterFactory、OkHttpModelApiClient）。所有对适配器的调用通过 lyclaw-core 中的 ModelProvider 接口进行。

为什么需要这个防腐层？

假设没有 ModelProvider 接口，Engine 直接依赖 lyclaw-adapter 的 ModelAdapterFactory。那么当 adapter 模块发生以下变化时，Engine 层代码必须修改：
- ModelAdapterFactory 改名或重构
- 新增适配器需要修改工厂的注册方式
- 切换 HTTP 客户端实现（从 OkHttp 切换到 WebClient）

有了 ModelProvider 接口后：
- Engine 只依赖接口，不依赖实现
- Adapter 模块的任何内部变化对 Engine 完全透明
- 可以在测试中轻松 mock ModelProvider
- 未来可以实现完全不同的适配器提供方式（如从配置文件读取、从服务发现获取）
