## 一、现状诊断：代码层面的具体问题

在讨论"应该做成什么样"之前，必须先搞清楚"现在是什么样，为什么不够好"。

### 1.1 工具参数解析：四份拷贝的同一种脆弱模式

LyClaw 目前有四个内置工具：`CalculatorTool`（数学计算）、`CurrentTimeTool`（时间查询）、`CommandTool`（Shell 命令执行）、`WebSearchTool`（网页搜索）。它们全部位于 `lyclaw-action/src/main/java/lyjew/com/lyclaw/action/tool/` 目录下。

每一个工具都实现了 `Tool` 接口。该接口的 `execute(ToolCall toolCall, ChatContext context)` 方法接收一个 `ToolCall` 对象，工具的参数以原始 JSON 字符串的形式放在 `toolCall.getArguments()` 中。问题就从这里开始——四个工具，每一个都自己手写了一套 JSON 字符串解析逻辑。

CalculatorTool 的解析方式是：用 `indexOf("\"expression\"")` 找到 key 的位置，然后用 `indexOf(":")` 找到冒号，再用 `indexOf("\"")` 找值的起止引号，最后用 `substring` 截出来。CurrentTimeTool 完全复制了这个模式，只是把 key 从 `"expression"` 换成了 `"timezone"`。CommandTool 换成了 `"command"`。WebSearchTool 换成了 `"searchQuery"`。

如果你把四个工具的 `extract*` 方法并排放在一起看，它们的结构几乎一模一样：null 检查 → indexOf 找 key → indexOf 找冒号 → indexOf 找起止引号 → substring 截取 → 返回。唯一的区别是 key 字符串和 fallback 处理。CalculatorTool 的 fallback 是 `replaceAll("\"", "").trim()`，CommandTool 的 fallback 是 `replaceAll("[\"{}\\s]", "").trim()`——连 fallback 策略都不统一。

**这种模式脆弱在哪里？**

这些方法假设 JSON 是单行的、没有多余空白的、值不包含转义引号的。以下任何一种情况都会让它返回错误的截取结果或者空字符串：

- LLM 返回了 pretty-printed JSON（带换行和缩进），因为 `indexOf` 在换行符之后会找不到期望的引号位置
- 参数值中包含转义引号（如 `"expression": "print(\"hello\")"` ），`indexOf("\"")` 会匹配到值内部的转义引号而非真正的字符串边界
- JSON 的 key 顺序不同（如 `{"sessionId":"x","expression":"2+2"}` ），因为 `indexOf("\"expression\"")` 只找第一个出现位置，如果 sessionId 恰好在前面包含 "expression" 这个子串就会误匹配
- 参数是一个嵌套对象或数组，因为字符串切割完全不理解 JSON 的嵌套结构

**最要命的是**：这些问题不会在测试中被发现（因为测试用的是"正常"格式的 JSON），但在生产环境中，不同的 LLM 返回的 JSON 格式变化无穷，随时可能触发。而且一旦出错，工具不会报"参数解析失败"，而是静默返回空字符串或错误结果，用户看到的是"计算结果是空"而非"参数解析出了 bug"。

**从框架的角度看**：参数解析是框架的职责，不是工具开发者的职责。一个好的框架应该在 `ToolCall` 传入 `execute` 之前就把 JSON 解析为类型安全的 Java 对象。工具开发者只需要声明"我期望一个 String 类型的 expression 参数"并接收一个 `String expression`，不需要知道 JSON 是什么格式。

### 1.2 元数据构建：样板代码的工业化复制

每个工具还有一个 `getDefinition()` 方法，返回一个 `ToolDefinition` 对象来描述工具的元数据——名称、描述、参数 schema。这个方法的实现在四个工具中也是结构完全相同。

典型的实现长这样（以 CalculatorTool 为例）：先 `ToolDefinition.builder()`，然后 `.name(TOOL_NAME)`、`.source("builtin")`、`.description("...")`，最后 `.parameters(Map.of(...))` 构建一个嵌套了三层的 `Map.of` 结构来描述 JSON Schema——最外层是 `"type":"object"`，中间是 `"properties"` 映射，每个 property 又是一个包含 `"type"`、`"description"` 的 Map，最后是 `"required"` 数组。

这段代码在 CalculatorTool 里占了约 15 行，在 CurrentTimeTool 里也约 15 行，在 CommandTool 里约 15 行，在 WebSearchTool 里约 15 行。四个工具加起来约 60 行纯样板代码。把工具总数按 4 个算，样板比例约 20-35%。如果未来有 20 个工具，就会有 300 行 `Map.of()` 链式调用。

**更深层的问题是**：这种样板代码不只是"行数多"的问题。它意味着元数据和业务逻辑的对应关系是靠"人工保持一致"来维护的。比如 `getDefinition()` 里声明参数名叫 `"expression"`，而 `extractExpression()` 方法里也用 `indexOf("\"expression\"")` 来解析——这两个 `"expression"` 字符串之间没有任何编译期关联。如果有人把 `getDefinition()` 里的参数名从 `"expression"` 改成 `"expr"` 但忘了改 `extractExpression()` 方法，代码照样编译通过，只是工具运行时永远解析不到参数。

在一个好的框架里，元数据应该从代码本身自动推导出来。参数名、类型、描述应该声明一次（比如在方法签名和参数注解上），然后框架同时用它们来做参数绑定（JSON → Java）和生成 `ToolDefinition`（发给 LLM）。一个真相来源，两个用途，零不一致风险。

### 1.3 两个 ToolResult：类型系统的分裂

LyClaw 项目中存在两个不同包下的 `ToolResult` 类：

- `lyjew.com.lyclaw.tool.ToolResult`——位于 `lyclaw-core` 模块，是 `Tool` 接口的 `execute()` 方法的返回类型。字段包括 `success`、`result`、`error`、`elapsedMs`、`tokenUsage`。使用构造函数和静态工厂方法创建。

- `lyjew.com.lyclaw.action.tool.ToolResult`——同样位于 `lyclaw-core` 模块但不同包，是 Action 服务的 REST API 的返回类型。字段包括 `toolName`、`success`、`output`、`errorMessage`、`durationMs`、`metadata`。使用 Lombok `@Builder` 模式创建。

两个类的字段名故意不同：一个是 `result` 另一个是 `output`，一个是 `error` 另一个是 `errorMessage`，一个是 `elapsedMs` 另一个是 `durationMs`。核心版没有 `toolName` 字段（因为工具本身知道自己的名字），Action 版却有。核心版有 `tokenUsage`，Action 版没有。

**这导致了什么？** 每次调用跨越模块边界，都需要手动写转换代码。`ToolSandboxImpl.convertResult()` 方法把核心版转为 Action 版。`ToolCallLoopStage` 里通过 OpenFeign 调用 Action 服务时，又把 Action 版的结果映射回核心版的语义。`ToolToSkillAdapter` 再把核心版映射为 `SkillResult`。这三个转换点散落在不同模块的不同类里，每个都自己写了一套字段映射逻辑。

**未来会怎样？** 如果给 `ToolResult` 加一个新字段（比如 `toolCallId` 来追踪是哪个工具调用产生的结果），你需要同时修改两个类定义、三个转换方法、以及所有直接构造 `ToolResult` 的地方。漏掉任何一个，那个路径上的新字段就是 null 或默认值，不会编译报错，只会静默丢数据。

**为什么会搞成这样？** 这不是某个开发者的失误，而是模块边界设计的问题。`Tool` 接口是核心抽象，它的返回类型应该是唯一的、权威的。如果需要 REST API 的返回格式不同，应该由 Controller 层做适配（比如用一个 DTO 包装），而不是在核心层定义两个同名不同类型。这说明 `lyclaw-core` 模块承担了太多职责，没有做到"核心只定义接口和基础类型"。

### 1.4 适配器选择：被架空的工厂模式

LyClaw 的适配器体系有一个有趣的矛盾：它同时实现了"完美的自动发现"和"完美的忽略自动发现"。

`ModelAdapterFactory` 类在 `lyclaw-adapter` 模块中，它通过 `ApplicationContext.getBeansOfType(ModelAdapter.class)` 自动发现所有实现了 `ModelAdapter` 接口的 Bean。它维护一个 `Map<String, ModelAdapter>`（key 是 provider 字符串，如 `"deepseek-openai"`、`"minimax"`），支持按名称查找、按配置对象装配。这个工厂本身设计得不错——支持多适配器共存、支持动态配置、支持列出所有可用 provider。

但是，`LlmConfiguration` 类在 `lyclaw-orchestration` 模块中，它**完全不使用** `ModelAdapterFactory`。它直接在 `@Bean` 方法的参数列表里声明 `DeepSeekOpenAIAdapter deepseekAdapter`——用具体的类名注入，编译期绑定。它创建的 `ModelProvider` Bean 带有 `@Primary` 注解，覆盖了其他所有候选。它生成的 `ConfiguredModelProvider` 内部类的 `getAdapter(String provider)` 方法对于任何非 deepseek 的 provider 都返回 null。

**结果**：MinimaxAdapter 虽然加了 `@Component`、实现了所有抽象方法、在 `ModelAdapterFactory` 的注册表里存在，但在运行时永远不会被调用。它是"活着的死代码"。

**更糟糕的是**：`LlmConfiguration` 是 `lyclaw-orchestration` 模块的一部分，这意味着 `orchestration` 模块对 `deepseek` 包有编译期依赖。如果未来有人想加一个 AnthropicClaudeAdapter，他不仅要写适配器类本身，还必须修改 `lyclaw-orchestration` 模块的 `LlmConfiguration.java`——改框架源码。这完全违背了框架的基本精神。

**理想状态**：框架发现所有适配器（通过 `ModelAdapterFactory` 的机制），配置决定用哪一个（通过 `application.yml` 的 `lyclaw.llm.provider` 属性）。加一个新适配器不需要改动任何框架代码，只需要加一个类、配一行配置。

### 1.5 管线排序：不可扩展的绝对数值

LyClaw 的管线阶段通过 `PipelineStage` 接口的 `getOrder()` 方法来决定执行顺序。目前的五个阶段分别返回 0、1、2、3、4——连续整数。

PipelineBuilder 的构造函数拿到所有 `PipelineStage` Bean 后，用 `Comparator.comparingInt(PipelineStage::getOrder)` 排序。这里有一个细节：构造函数直接在传入的 List 上调用 `sort()`——这会**修改调用者的列表**。如果同一个 List 被其他地方引用，这就成了一个隐蔽的副作用 bug。

**数字排序的问题在哪里？**

假设有一个第三方开发者想要在"安全检查（InterceptorStage，order=1）之后、工具调用循环（ToolCallLoopStage，order=2）之前"插入一个自定义阶段。他的选择是：

- 方案 A：把自己的阶段设为 order=1，期望排序稳定性能让它排在 InterceptorStage 之后。但这依赖 `List.sort` 的实现细节（Java 的 `TimSort` 是稳定的，但这不是 API 保证）。
- 方案 B：把自己的阶段设为 order=2，把 ToolCallLoopStage 挤到后面。但 ToolCallLoopStage 的 order 是 2，如果自己也是 2，两者的相对顺序是未定义的（取决于 Spring 注入 List 的顺序）。
- 方案 C：让所有后续阶段的 order 都 +1，但这意味着他要修改 MetricsStage、ResponseBuildStage 的源码——这些是框架内部的类，他不应该需要修改。

无论哪种方案，都是因为"绝对序号"这个设计决策导致的。当扩展的数量 N=5 时，绝对序号还能管理；当 N=50 时，维护这些序号本身就是一场噩梦。

**更好的设计**已经在很多框架中验证过：用**相对定位**代替**绝对定位**。一个阶段声明"我在 X 阶段之后"或"我在 Y 阶段之前"，框架在启动时做拓扑排序得出最终执行顺序。每个阶段只需要知道它和谁相邻，不需要知道全局有多少个阶段。

不过要注意**循环依赖**的问题——如果 A 声明"在 B 之后"而 B 声明"在 A 之后"，拓扑排序会检测到环并报错。框架应该给出清晰的错误信息："检测到阶段排序循环：A → B → A"。这比"两个阶段的 order 都是 5，没人知道谁先执行"要好得多。

### 1.6 沙箱白名单：硬编码的安全策略

`ToolSandboxImpl` 类负责控制工具的执行安全级别。它定义了一个沙箱等级枚举（NONE、READ_ONLY、RESTRICTED、CONTAINER、ISOLATED），不同等级对应不同的安全限制。

其中 `READ_ONLY` 等级的实现方式是：维护一个静态的 `READ_ONLY_TOOLS` 集合——`Set.of("calculator", "current_time", "web_search")`——执行前检查工具名是否在白名单中，不在就直接拒绝。

**问题一**：白名单是编译期硬编码的。新增一个"只读安全"的工具需要修改 `ToolSandboxImpl.java` 的源码。工具开发者可能根本不知道这个白名单的存在——他写了一个只读工具，加了 `@Component`，测试没问题，但到了 READ_ONLY 模式下突然被拒绝，没有任何编译期提示。

**问题二**：白名单用的是字符串（工具名），和工具类本身没有任何关联。如果 CalculatorTool 的作者把 `TOOL_NAME` 从 `"calculator"` 改成 `"math_calc"`，白名单里的字符串不会自动更新，工具就静默地从白名单中消失了。这又是一个"同一信息在两个地方维护，没有编译期关联"的例子。

**问题三**：`RESTRICTED` 级别的实现修改了 `System.getProperty("user.dir")`——这是一个 JVM 级别的全局可变状态。如果多个工具并发执行，一个工具修改了 `user.dir` 会影响另一个正在读文件的工具。这是典型的线程安全隐患。

**问题四**：`CONTAINER` 和 `ISOLATED` 级别的实现对于非 `command` 工具直接降级为 `RESTRICTED`。名称暗示了容器化隔离，但实际没有任何 Docker 或 cgroup 机制。这是"愿望式命名"——名字表达了期望的能力，但实现没有跟上。

**从框架的角度**：安全策略应该从工具的**元数据**中推导，而不是在一个集中的地方手工维护字符串白名单。工具应该在注册时声明自己的安全属性（如"我只读""我需要网络""我执行系统命令"），沙箱策略根据这些属性来决定允许还是拒绝。这样新增一个工具不需要修改安全策略代码，安全策略的含义也由工具的元数据自描述。

### 1.7 双体系并立：Tool 与 Skill 的分裂

LyClaw 同时维护着两套"可执行能力"的抽象：

**Tool 体系**：
- 接口：`Tool`（三个方法：`getName()`、`execute()`、`getDefinition()`）
- 注册器：`ToolRegistry`（通过 `List<Tool>` 构造器注入）
- 返回类型：`lyjew.com.lyclaw.tool.ToolResult`（同步，直接返回）
- 执行模式：同步方法调用

**Skill 体系**：
- 接口：`Skill`（四个方法：`getSkillId()`、`getName()`、`getDescription()`、`execute()`）
- 注册器：`SkillRegistry`（同样通过 `List<Skill>` 构造器注入，但有依赖图管理）
- 返回类型：`SkillResult`（异步，`CompletableFuture` 包装）
- 执行模式：异步，支持依赖关系排序

两套体系之间的桥梁是 `ToolToSkillAdapter`——一个把 `Tool` 包装成 `Skill` 的适配器类。注意方向：Tool 可以伪装成 Skill，但 Skill 不能伪装成 Tool。这意味着如果你写了一个 Skill，它是无法在 Tool 的上下文中被调用的。

**为什么会这样？** 推测是历史原因——最初可能只有 Tool 体系，后来因为需要支持异步执行和依赖管理引入了 Skill 体系，但为了兼容已有的 Tool 实现，写了 `ToolToSkillAdapter` 做桥接。这是典型的"加一层而不是重构"导致的架构债务。

**应该怎样？** Tool 和 Skill 在概念上极其相似——都是"框架可以调用的能力单元"，都有名字、描述、参数、执行逻辑。它们的差异（同步/异步、有无依赖管理）是**实现层面的差异**，不应该导致**两套完全不同的接口和注册体系**。一个好的设计是用一个统一的能力抽象（就叫 `Capability` 或保持 `Tool` 这个名字），在这个统一抽象上支持同步和异步两种执行模式，依赖管理作为一个可选特性而不是强制另一个接口。

### 1.8 缺乏框架自描述能力

最后一个问题是"元层次"的：LyClaw 没有办法告诉使用者"我有哪些扩展点、你可以在哪里插入自己的逻辑"。

当前，如果你想了解 LyClaw 有哪些可以扩展的接口，你需要：搜索所有 `implements` 关键字的用法、搜索所有接收 `List<SomeInterface>` 的构造函数、阅读 `DefaultToolRegistry` 的源码来理解它怎样收集扩展、阅读 `PipelineBuilder` 的源码来理解阶段排序机制。没有任何一个地方——不管是文档、注解、还是配置——总结了"这里是所有的扩展点"。

一个成熟的框架应该**自描述**。Spring Boot 的 Actuator 有 `/beans`、`/conditions`、`/configprops` 端点。LyClaw 也应该有一个类似的机制，让开发者能查询：当前注册了哪些工具、哪些管线阶段、哪些适配器、它们的顺序是什么、哪些是启用的哪些被条件排除了。这不只是方便调试——它本身就是框架的"用户界面"。

## 二、框架化的定义与目标

在讨论具体怎么做之前，必须先对齐一个根本问题：**什么叫做"像框架"**？

### 2.1 什么叫做"像框架"

一个"框架"和一个"应用"的区别不在于代码量、不在于有没有用 Spring、也不在于有没有接口。区别在于**控制权的归属**。

在应用架构中，你的代码调用库的代码。你写 `main` 方法，你决定什么时候调用什么函数。控制流在你手里。库是被动的——你叫它它才动。

在框架架构中，框架调用你的代码。你实现框架定义的接口、你在类上标注框架定义的注解，然后框架在适当的时机找到你的实现并调用它。控制流在框架手里。你的代码是被动的——框架叫它它才动。

这就是著名的**好莱坞原则**："Don't call us, we'll call you."

LyClaw 目前处在一个**中间状态**。它有一些框架的特征（比如 `Tool` 接口——你实现接口，框架在需要时调用），但它的实现方式让使用者意识不到"我被框架管理了"——因为扩展的发现机制（Spring 组件扫描）是隐式的，注解是 Spring 的通用注解（`@Component`）而非 LyClaw 的领域注解，注册逻辑藏在构造函数的参数注入里。使用者感知到的不是"我为一个框架写了一个插件"，而是"我写了一个 Spring Bean"。

**框架化就是把这种隐式的契约显式化**。让开发者明确知道：这个类是被 LyClaw 管理的，它遵循 LyClaw 的约定，它在 LyClaw 的生命周期中有明确的位置。

### 2.2 四个核心目标

**目标一：降低扩展成本**

当前添加一个新工具需要：写一个类 → 实现三个方法 → 手动解析 JSON 参数（手写字符串切割）→ 手动构建 ToolDefinition（手写嵌套 Map.of()）→ 加 `@Component` → 可能需要修改沙箱白名单。其中真正有业务价值的只有"写业务逻辑"那部分，其余全是仪式性代码。

框架化后，添加一个工具应该是：写一个类 → 加注解声明元数据 → 写业务逻辑方法。框架自动完成参数绑定、schema 生成、注册、安全策略判断。

**目标二：配置驱动的行为切换**

替换 LLM 提供商不应该需要改 Java 代码。启用或禁用一个工具不应该需要改 Java 代码。调整管线阶段的顺序不应该需要改 Java 代码。这些应该在配置文件（`application.yml`）中完成。

这不是说所有行为都要可配置（过度配置本身就是一种复杂度），而是说**策略选择点**（"用哪个"）应该和**策略实现**（"怎么做"）分离。

**目标三：独立演进**

框架自身升级（修 bug、加特性）不应该破坏使用者已写的工具和管线。使用者增加自定义工具不应该需要 fork 框架代码。两者的代码库、版本号、发布周期完全解耦。

**目标四：渐进式可达**

从当前的"应用"状态到理想的"框架"状态，中间必须有一条每一步都能让系统正常工作的路径。不允许"先全部重写，三个月不能用，最后一次性切过去"。

### 2.3 什么不是目标

同样重要的是明确**什么不是目标**，避免过度设计：

- **不是要做成 Spring 那样的通用框架**：LyClaw 的领域是 AI Agent，不需要通用的 DI 容器或 AOP 框架（这些 Spring 已经做了）。LyClaw 只需要在 Spring 的基础上提供 AI Agent 领域的扩展机制。
- **不是要支持非 Spring 环境**：至少在当前阶段。LyClaw 深度依赖 Spring Boot（WebFlux、Cloud Gateway、Nacos、OpenFeign），脱离 Spring 的成本远超收益。设计上保持"如果有一天需要脱离"的可能性（比如注解不硬编码 Spring 类型），但不为此牺牲当前阶段的开发效率。
- **不是要把所有东西都变成可插拔的**：核心流程（如 5 阶段管线）保持合理的默认行为。可插拔性集中在"用户最可能需要定制的点"——工具、适配器、管线阶段、拦截器。

## 三、六个核心设计思路

### 3.1 领域注解：让代码自描述

这是框架化最基础的改造。目前所有扩展都靠 `@Component` 标记，然后靠"实现了哪个接口"来区分角色。

**为什么 `@Component` 不够好？**

`@Component` 告诉 Spring："这是一个 Bean，请管理它的生命周期。"但它不告诉读代码的人："这是一个工具"还是"这是一个管线阶段"还是"这是一个拦截器"。看一个类比如 `CalculatorTool`，你能知道它是 Spring Bean（因为有 `@Component`），但你需要看它 `implements Tool` 才知道它是工具。而 `implements Tool` 这个信息藏在类声明的第 20 个字符之后——不是一眼可见的。

领域注解解决的是**代码的可读性和意图表达**。`@Tool` 注解在类上，扫一眼就知道这个类的角色。它和 `@Component` 的关系是通过元注解（在 `@Tool` 的定义上标注 `@Component`）实现的——所以加了 `@Tool` 的类自动成为 Spring Bean，开发者不需要写两个注解。

**领域注解可以携带什么？**

- **身份信息**：名称、描述、版本。这些是扩展的"身份证"，框架可以用它们做日志、做监控、做审计。
- **行为声明**：是否只读、是否需要网络、是否有副作用。框架可以用这些做安全策略（替代硬编码白名单）。
- **依赖声明**：需要哪些配置项、依赖哪些其他扩展。框架可以用这些做条件注册（配置不满足就跳过）。
- **排序声明**：相对排序（在谁之后、在谁之前）。框架可以用这些做拓扑排序。

**一个关键的克制**：注解属性的数量要极其克制。每增加一个属性，所有使用者就多填一个（或者依赖默认值），注解处理器就多一个判断分支。一个简单的判断标准是：**这个属性是否在 80% 的使用场景下都需要？** 如果不是，它不应该在注解上，而应该作为一个可选的高级配置项存在。

### 3.2 声明式元数据：从方法返回变为注解承载

目前工具的元数据（名称、描述、参数 schema）是通过 `getDefinition()` 方法运行时返回的。这个设计的问题是：
- 每个工具都要写 15 行完全同构的样板代码
- 元数据和实际参数（`execute` 方法的参数）之间没有编译期关联
- 每次调用 `getDefinition()` 都要重新构建对象（虽然影响很小，但不够优雅）

声明式元数据的意思是：元数据**声明**在类和方法上，框架在**启动时一次性读取并缓存**，运行时直接使用缓存。

具体来说：
- 工具名称、描述、版本：在类注解上声明
- 参数名称、类型、描述、是否必填：在参数声明处声明。可以是方法参数上的注解，也可以是独立的参数定义（取决于选用的参数模型）
- 框架在启动时做一次扫描，从注解中提取元数据，构建 `ToolDefinition` 对象，放入缓存

**为什么启动时做而不是运行时做？**

因为元数据是不变的（编译时确定），启动时做一次就够了。这样做有几个好处：
- 运行时不需要反射或方法调用来获取元数据，直接从缓存读取
- 如果元数据有错误（如参数类型不合法），可以在启动时报错，而不是等到第一次工具调用时才报
- 缓存可以被多个消费者使用（LLM 的工具选择、API 文档生成、健康检查端点）

**元数据和参数绑定的关系**：声明在注解上的参数信息（名称、类型、是否必填）应该**同时**用于两个用途——生成发给 LLM 的 JSON Schema（让 LLM 知道这个工具接受什么参数），以及运行时把 LLM 返回的 JSON 参数反序列化为 Java 对象（让框架知道怎样把 JSON 字段映射到 Java 参数）。一个真相来源，两个用途，零不一致。

### 3.3 自动参数绑定：框架接管协议转换

这是对开发者体验改进最大的一步。当前每个工具都在 `execute` 方法内部自己解析 JSON 参数，用 `indexOf` + `substring` 做字符串切割。这是完全不应该由工具开发者关心的**协议转换**问题——JSON 是 LLM 和框架之间的协议，不是框架和工具之间的协议。

自动参数绑定的理想状态是：工具方法接收的是类型安全的 Java 参数（如 `String expression`、`int timeout`），框架在调用工具之前，自动把 `ToolCall` 中的 JSON 参数字符串反序列化为对应的 Java 对象，然后传给工具方法。

这里有几种实现路径，选择取决于对接口兼容性的要求：

**路径 A：不改变 `Tool` 接口，在调用链上游做绑定**

在 `ToolRegistry.execute()` 或 `ToolExecutor` 中，调用 `tool.execute()` 之前，先用 Jackson 把 `toolCall.getArguments()` 反序列化为一个 `Map<String, Object>` 或参数对象，然后通过某种机制（比如 `ToolCall` 上增加一个 `getParsedArguments()` 方法）让工具直接获取已解析的参数。工具接口本身不变——已有的工具可以继续用旧的 `toolCall.getArguments()` 字符串解析方式，新的工具可以用 `toolCall.getParsedArguments()` 获取 pre-parsed 的参数。

- 优点：零破坏性，旧代码不需要任何修改。参数绑定的逻辑从工具移到框架，但接口兼容。
- 缺点：工具仍然需要自己从 Map 中取值，类型转换还是手动进行。本质上只是把 JSON 解析从"手写字符串切割"升级为"Jackson 解析 + Map 取值"。

**路径 B：引入新的工具模型，让方法参数直接绑定**

工具不再是"一个实现了 `Tool` 接口的类"，而是"一个带有方法注解的 POJO"。框架通过反射找到工具的执行方法，把 JSON 参数反序列化为方法参数的类型，调用方法，取返回值包装为 `ToolResult`。

- 优点：工具开发者只需要写一个普通方法，参数是强类型的，框架自动完成所有转换。开发体验最好。
- 缺点：这是一个全新的编程模型，和现有的 `Tool` 接口完全不兼容。需要同时维护两套工具模型，直到旧工具全部迁移完毕。

**推荐的分阶段策略**：先实施路径 A（低风险、立刻改善现状），在路径 A 稳定运行一个版本后，再引入路径 B 作为可选的高级模式。路径 B 的实现可以在内部委托给路径 A 的机制，减少重复代码。

**参数绑定的错误处理**：这是一个容易忽略但很重要的设计点。如果 LLM 返回的 JSON 参数不合法——缺少必填参数、类型不对（传了字符串但工具期望整数）、包含未定义的额外参数——框架应该怎样处理？

建议分两层处理：
- 第一层（框架层）：做基本的 JSON 解析和类型校验。如果 JSON 格式本身非法（不是合法 JSON），返回一个框架级别的错误"参数格式错误"，并附上原始 JSON 和 Jackson 的错误信息——这有助于调试 LLM 的输出问题。
- 第二层（工具层）：做业务级别的参数校验（如"timeout 必须大于 0 且小于 300"）。工具可以在方法内部做校验并返回 `ToolResult.failure("timeout 必须在 1-300 之间")`。

框架层不应该尝试理解业务含义的参数约束——那是工具开发者的事。框架只负责"JSON 到 Java 的转换是否正确"。

### 3.4 注册门面：在发现和注册之间加一层

当前的扩展注册是"发现即注册"模式：Spring 扫描到所有 `Tool` 类型的 Bean → 注入到 `DefaultToolRegistry` 构造函数 → 构造函数里 for 循环全部注册。没有中间环节。

"发现即注册"的问题在于：**没有任何机会在注册前做决策**。不能根据配置排除某个工具，不能根据环境决定启用或禁用，不能给工具排序，不能注入额外的元数据。所有扩展都是全量、无条件的。

**注册门面的设计**：在"发现"和"注册"之间插入一个门面层。发现阶段产出"候选扩展"列表，门面层对候选列表做过滤、排序、初始化、元数据注入，然后才注册到最终的注册器中。

```
发现（Spring扫描/@Component/@Tool注解）
    ↓
候选列表
    ↓
门面层 → 条件过滤（配置控制哪些启用）→ 排序（相对定位解析）→ 初始化（@PostConstruct回调）→ 元数据注入
    ↓
最终注册列表（注册器中的实际数据）
```

门面层不需要是一个很大的类。它甚至可以只是一个 `List<Tool>` 到 `ToolRegistry` 之间的一个处理管道。关键是**把"决策"从"执行"中分离出来**。

**条件过滤的一个例子**：假设 `WebSearchTool` 需要 Brave Search API key。当前它总是注册，但如果 API key 没配置，调用时返回"search failed"。更好的设计是：`WebSearchTool` 声明"我需要配置项 `lyclaw.tools.brave.api-key`"，框架在注册门面中检查这个配置项是否存在，如果不存在就跳过注册，并且生成一条 INFO 日志："WebSearchTool 因缺少配置 lyclaw.tools.brave.api-key 而跳过注册"。用户既不会看到一个"可用但永远失败"的工具，也能从日志中知道为什么这个工具没有加载。

**门面的另一个作用：健康检查**。门面层记录了哪些扩展被过滤掉了以及原因。这些信息可以通过 Actuator 端点暴露出来，让运维能快速诊断"为什么我的 XXX 工具没有加载"。

### 3.5 相对排序：用拓扑而非绝对值

当前管线阶段的顺序由 `getOrder()` 返回的整数决定，这个设计在[1.5 节](#15-管线排序不可扩展的绝对数值)中已经讨论了其问题。

**相对排序的模型**：一个阶段不声明"我是第 3 个"，而是声明"我在 X 阶段之后"或"我在 Y 阶段之前"。框架启动时收集所有阶段的相对声明，做一次拓扑排序，得出全局执行顺序。

具体来说，每个阶段可以提供以下信息之一或组合：
- `after = XxxStage.class`：我必须在 X 阶段之后
- `before = YyyStage.class`：我必须在 Y 阶段之前
- `group = "preprocessing"`：我属于预处理组

框架预设几个组的顺序（如：预处理 → 核心逻辑 → 后处理），组内阶段用 `after`/`before` 排序。如果某个阶段没有提供任何排序信息，给它一个默认位置（如放在最后）。

**循环依赖检测**：拓扑排序天然能检测循环依赖（A after B，B after A）。相比于"两个阶段都是 order=3"的静默未定义行为，拓扑排序会给出明确的错误信息。

**向后兼容**：保留 `getOrder()` 方法，但这个值从"绝对顺序"降级为"组内排序偏好"。当相对声明冲突时，`getOrder()` 作为 tiebreaker。已有的阶段不需要改动，新阶段可以用 `after`/`before` 声明。

**配置覆盖**：允许在 `application.yml` 中覆盖排序，用于运维调整而不需要重新编译：

```yaml
lyclaw:
  pipeline:
    order:
      - ContextBuildStage
      - MyCustomStage
      - InterceptorStage
      - ToolCallLoopStage
```

如果配置文件和注解同时指定了排序，配置优先（因为配置是运维可控的，不需要重新编译）。

### 3.6 配置驱动选择：策略的声明式绑定

适配器选择的硬编码问题在[1.4 节](#14-适配器选择被架空的工厂模式)中讨论了。解决思路是：让 `application.yml` 来决定使用哪个适配器。

这不仅仅适用于适配器选择，相同的模式可以用于记忆后端选择、安全策略选择、嵌入模型选择等。

**设计原则**：
- 框架负责**发现**：通过接口 + 扫描（或注解）找到所有可用的策略实现
- 配置负责**选择**：通过配置项指定要使用哪一个
- 默认值**覆盖 80% 场景**：不给配置项就用默认策略，新用户零配置启动

**错误反馈**：如果用户配置了 `lyclaw.llm.provider: anthropic` 但 classpath 上没有 Anthropic 适配器，框架应该在启动时报错，并且**列出所有可用的 provider**。这比返回 null 然后在第一次调用时 NPE 要好得多——启动时报错是立即反馈，运行时 NPE 可能要排查几个小时。

**动态切换**：阶段一不需要支持运行时动态切换（实现复杂度太高），但设计上要为未来留空间——不要在代码里把"配置值"缓存到一个 static final 字段里。至少保持每次调用时从配置读取（Spring 的 `@ConfigurationProperties` 天然支持刷新）。

## 四、扩展性深度设计

这是本方案最核心的部分——如何保证框架在 1 年、3 年、5 年后仍然"容易迭代"。

### 4.1 SPI 接口的稳定性契约

SPI（Service Provider Interface）是框架对外暴露的接口——框架使用者通过实现这些接口来扩展框架。`Tool`、`PipelineStage`、`ModelAdapter` 都是 SPI。

SPI 的稳定性是框架信誉的基础。一旦发布，就不应该做不兼容的修改。

**什么构成"不兼容修改"？**

- 在接口中增加一个**没有 default 实现**的抽象方法——所有已有的实现类会编译失败
- 修改已有方法的**签名**（参数类型、返回值类型、抛出的 checked exception）——所有调用方和实现方都需要修改
- 修改方法的**语义**（不改变签名但改变行为）——已有实现可能依赖旧语义。这种修改最隐蔽，因为编译器不会报错
- 删除接口——所有实现类失去编译基础

**什么不是不兼容修改？**

- 增加一个有 `default` 实现的方法——已有实现类不需要改动
- 增加一个新的 SPI 接口——已有代码不受影响
- 在已有的类（非接口）中增加方法——不影响接口实现

**接口设计的"窄原则"**：一个接口暴露的方法越少，越容易保持稳定。每增加一个方法，就增加了一个未来可能不兼容的风险点。`Tool` 接口的三个方法（`getName`、`execute`、`getDefinition`）已经足够窄。不要因为"方便"在接口上加辅助方法——辅助方法应该放在抽象类或工具类里。

**接口的扩展机制**：如果确实需要给 Tool 增加新的能力（比如"支持取消"），不要给 `Tool` 接口加 `cancel()` 方法。更好的方式是定义一个新接口 `CancellableTool extends Tool`，让需要取消能力的工具额外实现它。调用方用 `instanceof CancellableTool` 来判断是否支持取消。这比让所有工具都实现一个空 `cancel()` 方法要好。

**版本化接口**：如果接口的不兼容变更无法避免，用新的接口名（如 `ToolV2`），保持旧接口一段时间的兼容期（至少一个次版本）。新代码用 `ToolV2`，旧代码继续用 `Tool`。框架内部同时支持两种接口。

### 4.2 注解的演化策略

注解的演化比接口更难——接口可以加 `default` 方法，注解属性没有类似机制。每增加一个属性，所有使用该注解的类都必须提供值（或依赖默认值）。

**注解属性的添加原则**：
- 新增属性**必须**有默认值。没有默认值的属性是 breaking change。
- 默认值应该是**最保守、最安全**的选择。比如 `boolean readOnly() default false`——如果工具作者忘了声明只读，默认按"不是只读"处理，比默认按"是只读"更安全。
- 在加属性之前问自己：**不添加这个属性，用户能不能通过其他方式达到目的？** 如果可以（比如通过配置文件而非注解），那就不加。

**注解属性的删除原则**：
- 不要删除。用 `@Deprecated` 标记并在文档中说明替代方式。
- 如果语义变了（比如 `timeout()` 以前单位是毫秒，现在要改成秒），不要改——加一个新属性 `timeoutSeconds()`，保留旧属性但标记废弃。
- 框架内部处理废弃属性时，如果新旧属性同时存在，新属性优先。

**注解属性的类型选择**：
- 对于可能扩展的取值（如工具的 `source` 可能从 `"builtin"`、`"mcp"` 扩展到 `"plugin"`、`"external"`），**用 String 而非 Enum**。Enum 的值一旦发布就不能增删（二进制兼容性），String 没有这个限制。
- 但 String 的问题是：拼写错误只能在运行时发现。折中方案是：用 String 作为注解属性类型，但在框架内部做校验（启动时检查值是否在已知集合中，未知值打印 warning）。

### 4.3 扩展点的三级分层

不要让所有扩展点平铺在同一层次。分层让每一层可以独立演进。

**L1：核心 SPI 层（`lyclaw-framework` 模块）**

这是框架的"宪法"。定义最基础的契约：
- `Tool` 接口——工具是什么，怎样执行
- `ToolRegistry` 接口——怎样注册和查找工具
- `ModelAdapter` 接口——怎样调用 AI 模型
- `PipelineStage` 接口——怎样参与处理管线
- `ToolResult`——统一的返回类型

变更频率：极低（可能一年一次）。每次变更需要跨版本的兼容性评估。所有实现这些接口的代码都不应该因为 L1 的变更而编译失败。

**L2：注解层（`lyclaw-framework` 模块）**

这是 SPI 的"便利包装"。提供更友好的声明式编程体验：
- `@Tool` 注解——声明一个类是工具，携带元数据
- `@Param` 注解——声明工具的参数
- `@PipelineStage` 注解——声明管线阶段和排序偏好
- `@Interceptor` 注解——声明拦截器和其执行顺序

变更频率：低（可能半年一次）。新增注解不影响已有的 SPI 实现。注解属性可以加（带默认值），不能删。

**L3：自动配置层（`lyclaw-autoconfigure` 模块）**

这是框架的"自动化装配"。利用 Spring Boot 的机制自动发现和注册扩展：
- 注解处理器——读 L2 的注解，注册到 L1 的 SPI
- `AutoConfiguration` 类——条件装配、Bean 创建
- `AutoConfiguration.imports`——Spring Boot 自动配置入口

变更频率：中等（随 Spring Boot 版本升级可能需要调整）。L3 的变更不影响 L1 和 L2 的稳定性。

**分层的核心价值**：每一层都可以被绕过。用户可以直接实现 SPI 接口（跳过注解层），也可以手动装配 Bean（跳过自动配置层）。层次越高越方便，越低的层次越灵活、越稳定。这种设计让不同类型的用户各取所需：初学者用 L2+L3（开箱即用），高级用户直接操作 L1（完全控制）。

### 4.4 隔离性：一只燕子的死亡不该终结整个夏天

框架的一个关键质量属性是**隔离性**：一个扩展的失败不影响其他扩展和框架核心。

**加载隔离**：框架在加载每个扩展时，应该用独立的 try-catch 包裹。如果一个工具因为依赖缺失或配置错误加载失败：
- 日志记录 ERROR 级别，包含失败原因和堆栈
- **不阻止应用启动**——其他工具和框架核心功能正常工作
- 提供一个健康检查端点（如 `/actuator/health`），其中包含"哪些扩展加载失败了"的信息

**执行隔离**：框架在调用每个工具的 `execute` 方法时，同样应该捕获未处理的异常：
- 异常被转为 `ToolResult.failure("工具执行异常: " + e.getMessage())`
- 异常信息记录到日志（WARN 级别，不是 ERROR，因为已经被处理了）
- 异常不传播到上层调用方（如 LLM 调用循环），循环可以继续处理下一个工具调用
- 如果工具频繁失败（如连续 3 次），框架可以自动禁用它并通知运维

**资源隔离**：工具执行应该有自己的超时控制。如果一个工具因为外部 API 响应慢而卡住，框架应该在超时后中断执行并返回失败，而不是让整个请求链一直等待。

**这和"快速失败"原则的关系**：快速失败（fail-fast）说的是**框架自己的错误**应该尽早暴露——比如配置错误、注解使用错误——这些是开发者能立即修复的问题。隔离性说的是**运行时错误**——工具调用的外部服务挂了、LLM 返回了非法 JSON——这些不是开发者的错，框架不应该因为这些外部因素而崩溃。

### 4.5 语义化版本与废弃流程

语义化版本（SemVer）是框架演化最基本的契约语言。

**版本号规则**：

- **主版本号**（X.0.0）：包含 SPI 的不兼容变更或废弃 API 的删除。这是唯一允许 breaking change 的版本。主版本升级意味着使用者需要修改代码才能编译通过。
- **次版本号**（0.X.0）：新增 SPI 方法（带 default 实现）、新增注解属性（带默认值）、新增扩展点、新增自动配置。次版本**不包含**任何 breaking change——使用者的代码不需要修改就能升级。
- **修订号**（0.0.X）：Bug 修复、性能优化、日志改进、内部重构。对外 API 和行为完全不变。

**废弃流程**：当需要删除或替换一个 API 时，不能一次性完成。标准流程是三步走：
1. 在当前版本标记 `@Deprecated`，Javadoc 中写明替代方案和计划删除的版本（如"计划于 2.0 版本移除，请迁移至 ToolV2 接口"）
2. 下一个次版本中，废弃的 API 仍然存在且功能正常，但日志中增加 WARNING 提示
3. 再下一个主版本中，真正删除

这意味着：一个 API 从被标记废弃到真正删除，至少跨越一个次版本和一次主版本升级。给使用者充足的迁移时间。

**配置兼容**：配置项（`application.yml` 中的 key）的向后兼容比代码更重要，因为配置项通常不由编译器检查。如果必须重命名一个配置项：
1. 新 key 和旧 key 在一个次版本中同时有效
2. 使用旧 key 时打印 WARNING 日志提示迁移
3. 下一个主版本中旧 key 不再有效，启动时打印 ERROR 提示需要修改配置

### 4.6 测试基础设施

框架化后，测试的便捷程度直接影响迭代速度。如果测试一个自定义工具需要启动整个 Spring 容器 + Nacos + Redis，没有人会愿意写测试。

**框架应该提供的测试支持**：

- **独立的单元测试支持**：工具开发者应该能在不启动 Spring 容器的前提下测试自己的工具逻辑。框架提供 `MockToolCall`（模拟 LLM 传入的参数）和 `MockChatContext`（模拟上下文信息），工具类可以直接 new 出来然后调 `execute`。
- **注解处理器的独立测试**：注解处理器本身是纯逻辑——"读注解 → 生成元数据"。它应该可以在不依赖 `ApplicationContext` 的情况下测试。框架提供 `AnnotationTestHelper`——给定一个 Class 对象，返回提取的元数据。
- **注册器的内存实现**：`ToolRegistry` 有一个基于 `ConcurrentHashMap` 的实现，它本身已经适合测试。确保这个实现可以独立使用（不依赖 Spring Bean 生命周期）。
- **集成测试的测试夹具**：对于确实需要 Spring 容器的测试（如测试管线执行），框架提供 `@LyClawTest` 注解——一个组合了 `@SpringBootTest` 和相关自动配置的元注解。使用者只需要标注这个注解就能获得一个最小的、可用的框架测试环境。

**测试工具包**：建议创建一个独立的 `lyclaw-test` 模块，包含上述所有测试支持。这个模块只在 test scope 下使用，不会打入生产包。

### 4.7 配置设计原则

框架的配置项（`application.yml` 中 `lyclaw.*` 下的内容）是框架的使用界面之一。配置设计的好不好，直接影响使用者的第一印象。

**命名空间**：所有框架配置统一在 `lyclaw` 前缀下。子模块用子前缀：`lyclaw.llm.*`（LLM 相关）、`lyclaw.memory.*`（记忆系统）、`lyclaw.pipeline.*`（管线）、`lyclaw.tools.*`（工具）。

**默认值原则**：每个配置项都应有合理的默认值，让新用户零配置启动。默认值覆盖最常见的使用场景。比如 LLM provider 默认 `deepseek`，因为这是目前唯一在生产中验证过的适配器。

**配置项的粒度**：不要为一个配置项设计得太细。`lyclaw.llm.deepseek.connect-timeout` 和 `lyclaw.llm.deepseek.read-timeout` 是两个配置项还是合并为一个 `lyclaw.llm.deepseek.timeout`？答案是后者——大多数用户不需要区分连接超时和读取超时。只有在确实有用户反馈需要区分时，才拆分。

**配置校验**：框架应该在启动时校验配置的合法性。比如 `lyclaw.llm.provider: anthropic` 但 classpath 上没有 AnthropicAdapter，启动时直接报错（清晰的错误信息 + 可用的 provider 列表），而不是等到第一次 LLM 调用时才抛异常。

**配置文档自动生成**：使用 `@ConfigurationProperties` 注解时，配合 `spring-boot-configuration-processor` 可以自动生成配置元数据（`additional-spring-configuration-metadata.json`）。IDE 能利用这些元数据提供自动补全和文档提示。

### 4.8 错误处理的分层策略

框架中的错误处理不应该一刀切，不同层次的错误应该有不同的处理方式。

**配置错误（启动时）**：配置项语法错误、provider 不存在、必填配置缺失。**策略：启动时校验，错误直接阻止启动，给出清晰的错误信息和修复建议。** 这是 "fail-fast" 原则——配置错误不应该被隐藏，应该让开发者在第一时间发现并修复。

**扩展加载错误（启动时）**：某个工具因为依赖缺失或配置不完整加载失败。**策略：记录 ERROR 日志，跳过该扩展，继续启动。** 一个工具的失败不应该阻止整个应用启动。健康检查端点暴露失败信息。

**参数绑定错误（运行时）**：LLM 返回的 JSON 参数格式不正确。**策略：返回 `ToolResult.failure` 附带具体的错误信息（如"参数 expression 是必填的"或"timeout 期望整数但收到了字符串"），让 LLM 看到错误后可以重试。** 不要抛出异常终止流程——这会让 LLM 的 tool-calling 循环中断。

**工具执行错误（运行时）**：工具内部抛出未捕获异常。**策略：框架层 try-catch，转为 `ToolResult.failure`。** 工具开发者不需要自己写 try-catch 样板代码。如果一个工具频繁失败，记录 WARN 日志，运维可以据此排查。

**基础设施错误（运行时）**：Nacos 不可达、Feign 调用超时、内存系统故障。**策略：根据错误的严重程度决定。** 暂时性故障（如网络闪断）可以重试；持久性故障（如配置错误导致的服务不可达）应该返回明确的错误信息给用户。永远不要让框架内部异常（如 NullPointerException）传播到用户界面。

## 五、模块架构重新设计

### 5.1 当前模块结构的问题

当前 LyClaw 有 13 个 Maven 模块。从功能角度看覆盖得很全，但从框架化角度看有几个问题：

**问题一：没有独立的 API 模块。** SPI 接口（`Tool`、`ToolRegistry`、`ModelAdapter` 等）分散在 `lyclaw-core` 和其他模块中。框架使用者只需要依赖接口来写扩展，但目前没有这样一个"只包含接口"的轻量模块。使用者被迫依赖包含大量实现代码的 `lyclaw-core`。

**问题二：`lyclaw-core` 承担了太多职责。** 它既包含 SPI 接口（`Tool`、`ModelAdapter`），又包含抽象实现（`AbstractModelAdapter`），又包含数据模型（`ToolDefinition`、`ChatRequest`），又包含 OpenFeign 客户端定义。这个模块是"什么都往里面放"的结果——没有清晰的职责边界。

**问题三：没有自动配置模块。** 没有 `spring.factories` 或 `AutoConfiguration.imports`，框架无法作为 starter 被其他项目引用。使用者必须 `@ComponentScan("lyjew.com.lyclaw")` 扫描整个包才能使用框架——这既低效（扫描大量不需要的类），也脆弱（包名一改就坏）。

**问题四：适配器模块和编排模块之间的不健康依赖。** `lyclaw-orchestration` 模块（编排服务）直接依赖 `lyclaw-adapter` 模块中的具体实现类（`DeepSeekOpenAIAdapter`）。这违反了依赖倒置原则——高层模块（编排）依赖低层模块（具体适配器），而不是两者都依赖抽象。

### 5.2 新增模块的职责边界

**新增模块一：`lyclaw-framework`**

定位：框架的公共 API。这是框架使用者唯一**必须**依赖的模块。也是最稳定的模块。

应该包含的内容：
- 所有 SPI 接口：`Tool`、`ToolRegistry`、`ToolExecutor`、`ModelAdapter`、`ModelProvider`、`PipelineStage`、`Interceptor`、`ContentFilter`、`SecurityManager`
- 所有自定义注解：`@Tool`、`@Param`、`@PipelineStage`、`@Interceptor`、`@Adapter`
- 核心数据模型：`ToolDefinition`、`ToolResult`（统一后的唯一版本）、`ToolCall`、`ChatContext`、`Message`
- 框架级别的配置属性：`LyClawProperties`（承载 `lyclaw.*` 配置）
- 框架级别的异常类型：`ToolExecutionException`、`AdapterNotFoundException`、`ParameterBindingException`
- 框架级别的常量和枚举：`SandboxLevel`、`ToolSource`

不应该包含的内容：
- 任何具体实现类（如 CalculatorTool、DeepSeekOpenAIAdapter）
- 任何 Spring 特定机制（如 BeanPostProcessor、自动配置）
- 任何外部库的适配器

依赖：尽可能少。理想情况下只依赖 `slf4j-api`（日志抽象）和 `jackson-annotations`（JSON 注解）。不依赖 Spring Context、不依赖 Spring Boot。

**新增模块二：`lyclaw-autoconfigure`**

定位：Spring Boot 自动配置层。包含所有"魔法"——注解处理器、条件装配、默认 Bean 创建。

应该包含的内容：
- 注解处理器：`ToolAnnotationProcessor`、`PipelineStageProcessor`、`InterceptorProcessor`、`AdapterAnnotationProcessor`
- `AutoConfiguration` 类：`ToolAutoConfiguration`、`PipelineAutoConfiguration`、`AdapterAutoConfiguration`、`MemoryAutoConfiguration`
- `AutoConfiguration.imports` 文件（Spring Boot 3.x 自动配置入口）
- 条件装配逻辑：`@ConditionalOnProperty`、`@ConditionalOnClass`、`@ConditionalOnMissingBean`
- 注册门面实现：集中处理扩展的发现、过滤、排序、注册

不应该包含的内容：
- 具体工具实现（工具属于业务模块）
- 具体适配器实现（适配器属于适配器模块）

依赖：`lyclaw-framework`、Spring Boot、Spring Context。不依赖具体的业务模块。

**新增模块三：`lyclaw-test`**

定位：测试支持工具包。只在 test scope 下使用。

应该包含的内容：
- Mock 实现：`MockToolRegistry`、`MockModelAdapter`、`MockChatContext`
- 测试注解：`@LyClawTest`（组合了 Spring Boot Test 和框架自动配置）
- 测试辅助类：`ToolTestHelper`（快速测试单个工具）、`AnnotationTestHelper`（测试注解处理）

### 5.3 依赖关系与包结构

**理想依赖图**（箭头表示"依赖"）：

```
lyclaw-framework          （零 Spring 依赖，纯接口 + 注解 + 模型）
    ↑
lyclaw-autoconfigure      （依赖 Spring Boot，负责"魔法"）
    ↑
lyclaw-core               （现有抽象实现，如 AbstractModelAdapter）
    ↑
┌───┴──────────┬──────────┬──────────┬──────────┐
lyclaw-adapter  lyclaw-action  lyclaw-memory  lyclaw-plan  ...
    ↑
lyclaw-orchestration       （编排服务，依赖所有下层）
    ↑
lyclaw-gateway             （网关，入口）
```

**外部项目使用时的依赖选择**：

- 仅编写工具扩展：只需要 `lyclaw-framework`（最轻，不引入 Spring Boot）
- 完整使用框架：依赖 `lyclaw-autoconfigure`（自动拉取 `lyclaw-framework`，框架自动装配）
- 自定义全部：排除 `lyclaw-autoconfigure`，手动装配所有 Bean（最大灵活性）

**包结构约定**：

```
lyjew.com.lyclaw.framework         —— SPI 接口和注解（lyclaw-framework 模块）
lyjew.com.lyclaw.framework.tool    —— Tool、ToolRegistry、ToolDefinition
lyjew.com.lyclaw.framework.annotation —— @Tool、@Param、@PipelineStage
lyjew.com.lyclaw.framework.model   —— 核心数据模型
lyjew.com.lyclaw.framework.config  —— LyClawProperties
lyjew.com.lyclaw.framework.exception —— 框架异常

lyjew.com.lyclaw.autoconfigure     —— 自动配置（lyclaw-autoconfigure 模块）
lyjew.com.lyclaw.autoconfigure.tool —— ToolAutoConfiguration、ToolAnnotationProcessor
lyjew.com.lyclaw.autoconfigure.pipeline —— PipelineAutoConfiguration
```

**关键约束**：
- `lyclaw-framework` 的包不能被任何其他 lyclaw 模块**反向依赖**——这是单向的。如果有循环依赖，说明某个类型应该移到 framework 中，或者某个依赖不应该存在。
- `lyclaw-autoconfigure` 不能包含任何会被外部直接 import 的类型——它的内容都是框架内部的"魔法"，外部不应感知。

### 5.4 各模块迁移计划

**`lyclaw-framework` 的迁移**：

这是最关键的一步。需要从现有模块中**移动**（不是复制）以下内容到新模块：

从 `lyclaw-core` 移出：
- `lyjew.com.lyclaw.tool.Tool` → `lyjew.com.lyclaw.framework.tool.Tool`
- `lyjew.com.lyclaw.tool.ToolRegistry` → `lyjew.com.lyclaw.framework.tool.ToolRegistry`
- `lyjew.com.lyclaw.tool.ToolResult` → `lyjew.com.lyclaw.framework.tool.ToolResult`
- `lyjew.com.lyclaw.model.ToolDefinition` → `lyjew.com.lyclaw.framework.model.ToolDefinition`
- `lyjew.com.lyclaw.pipeline.PipelineStage` → `lyjew.com.lyclaw.framework.pipeline.PipelineStage`
- `lyjew.com.lyclaw.adapter.ModelAdapter` → `lyjew.com.lyclaw.framework.adapter.ModelAdapter`

**注意**：移动后旧包下保留一个 `@Deprecated` 的子类或类型别名，指向新包的位置。比如旧 `lyjew.com.lyclaw.tool.Tool` 变为一个空接口 `extends lyjew.com.lyclaw.framework.tool.Tool`。这保证了所有现有代码不需要立即修改 import 语句。

**`lyclaw-autoconfigure` 的迁移**：

从 `lyclaw-adapter` 中的 `AdapterAutoConfiguration` 和 `ModelAdapterFactory` 移出自动配置相关的代码。业务代码（适配器实现）留在 `lyclaw-adapter`。

从 `lyclaw-action` 中的 `DefaultToolRegistry` 移出注解处理相关的代码（如果有的话）。注册器实现本身留在 `lyclaw-action`。

**不需要迁移的内容**：

- 具体工具实现（CalculatorTool 等）——这是业务代码，不是框架代码
- 具体适配器实现（DeepSeekOpenAIAdapter 等）——留在 lyclaw-adapter
- Feign 客户端接口——这是微服务通信机制，不属于框架公共 API
- Controller 层——这是 REST API，属于服务模块

## 六、分阶段实施路线图

按"收益 / 风险"以及"依赖关系"排序，分为五个阶段。每个阶段产出可运行的中间版本。

### 6.1 阶段零：基础清理（1 周）

**目标**：消除最明显的技术债务，为后续框架化扫清障碍。这一阶段的改动对开发者几乎透明。

**任务**：

**统一 ToolResult**：选择 `lyjew.com.lyclaw.tool.ToolResult` 作为权威版本（因为它是 `Tool` 接口的返回类型，地位更核心）。把 `action.tool.ToolResult` 标记为 `@Deprecated`，保留一个 `toToolResult()` 方法做类型转换。所有使用 `action.tool.ToolResult` 的地方（ToolSandboxImpl、ActionController、ActionFeignClient）逐步迁移到核心版。

**提取参数绑定工具类**：在 `lyclaw-core` 中创建一个 `ParameterBinder` 工具类，封装 Jackson `ObjectMapper` 的 JSON → `Map<String, Object>` 反序列化逻辑。这是一个纯工具类，不依赖 Spring 容器。每个工具可以可选地使用它来替代手写的 `indexOf` 解析，但这不是强制的——所以不破坏现有代码。

**清理双重管线**：确认 PipelineBuilder 构建的组件管线是否真的被使用。如果 OrchestratorImpl 完全使用自己的硬编码管线而 PipelineBuilder 的管线只是存在但未被调用，则把 PipelineBuilder 和其关联的 PipelineStage 实现标记为"实验性"并在文档中说明，但不删除（给用户时间迁移）。同时修复 PipelineBuilder 构造函数中 `allStages.sort()` 的副作用 bug（改为先拷贝再排序）。

**为什么阶段零放在最前面**：这些改动是最低风险的（不改变对外接口、不改变用户代码），但直接消除了后续框架化工作的障碍。如果阶段零都做不好，后面的注解体系更不可能做好。

### 6.2 阶段一：框架骨架（2 周）

**目标**：建立 `lyclaw-framework` 模块，定义框架的公共 API。

**任务**：

**创建 `lyclaw-framework` 模块**：新建 Maven 子模块，定义其 `pom.xml`（最小依赖），移动 SPI 接口、核心数据模型、配置属性类到新模块。旧包下保留 `@Deprecated` 的类型别名，指向新位置。

**定义统一配置属性**：创建 `LyClawProperties` 类，使用 `@ConfigurationProperties(prefix = "lyclaw")`。包含以下子配置：
- `LlmProperties`：provider 选择、timeout、base-url
- `MemoryProperties`：后端选择（inmemory/redis）、缓存配置
- `PipelineProperties`：管线阶段排序覆盖
- `ToolsProperties`：工具级别的配置（如 API key）

**实现配置驱动的适配器选择**：修改 `LlmConfiguration`，改为委托给 `ModelAdapterFactory` 做适配器发现，用 `LyClawProperties.llm.provider` 做适配器选择。DeepSeek 作为默认值。MinimaxAdapter 立即复活——只要配置 `lyclaw.llm.provider: minimax` 就能切换到它。

**创建 `lyclaw-autoconfigure` 模块**：创建模块骨架，包含空的 `AutoConfiguration.imports` 文件（暂时只有一个占位 AutoConfiguration 类）。这个模块在阶段一中不包含实质内容——它是为后续阶段准备容器。

**编写模块迁移指南**：文档记录哪些类型从哪个旧包移到了哪个新包，提供 import 迁移参考。

**阶段一的交付物**：
- `lyclaw-framework` 模块（包含 SPI 接口、数据模型、配置类）
- `lyclaw-autoconfigure` 模块（空壳，为后续阶段准备）
- 适配器选择由配置驱动（`lyclaw.llm.provider`）
- 旧代码通过 `@Deprecated` 类型别名继续工作

### 6.3 阶段二：注解体系（2 周）

**目标**：引入自定义注解，让工具的元数据可以从注解声明而非方法返回中获取。

**任务**：

**定义注解**：在 `lyclaw-framework` 模块中定义 `@Tool`、`@Param`、`@PipelineStage`、`@Interceptor`、`@Adapter` 注解。每个注解用 `@Component` 元注解标记，确保标注了自定义注解的类自动成为 Spring Bean。

**实现注解处理器**：在 `lyclaw-autoconfigure` 模块中实现：
- `ToolAnnotationProcessor`（BeanPostProcessor）：发现标注了 `@Tool` 的类，从注解读取元数据，注册到 `ToolRegistry`
- `PipelineStageProcessor`：发现标注了 `@PipelineStage` 的类，读取 `after`/`before` 属性，做拓扑排序，构建最终执行顺序
- `InterceptorProcessor`：发现标注了 `@Interceptor` 的类，自动注册到 `InterceptorChain`

**注解处理器的一个关键设计细节**：注解处理器必须同时支持"新方式"（注解声明元数据）和"旧方式"（接口方法返回元数据）。如果一个类标注了 `@Tool` 但没实现 `getName()` 方法——不对，`getName()` 是 `Tool` 接口的方法，类必须实现。关键兼容性是：注解处理器检查类上是否有 `@Tool` 注解，如果有，从注解读取元数据；如果没有但实现了 `Tool` 接口，调用 `getName()` 和 `getDefinition()` 方法获取元数据。两种方式在同一个注册器中共存。

**创建 AutoConfiguration 类**：在 `lyclaw-autoconfigure` 中创建 `ToolAutoConfiguration`、`PipelineAutoConfiguration` 等自动配置类。每个都用 `@ConditionalOnBean` 或 `@ConditionalOnProperty` 保护，让使用者可以排除不需要的自动配置。写入 `AutoConfiguration.imports` 文件。

**阶段二的交付物**：
- 完整的自定义注解体系
- 注解处理器（兼容新旧两种模式）
- 自动配置类（条件装配，可被排除）
- 已有的工具不需要任何修改仍然正常工作

### 6.4 阶段三：自动配置与门面（2 周）

**目标**：建立注册门面，支持扩展的过滤、排序、生命周期管理。提供测试工具包。

**任务**：

**实现注册门面**：在 `lyclaw-autoconfigure` 中实现 `ExtensionFacade` 类（或等价的机制），在 Spring 的自动发现和最终的注册器之间做：
- 条件过滤：读取工具的配置项，决定是否注册
- 顺序解析：读取 `@PipelineStage` 的 `after`/`before`，做拓扑排序
- 生命周期回调：在工具注册后调用 `@PostConstruct` 标记的初始化方法

**扩展注册的日志与健康检查**：门面记录每个扩展的注册状态（成功/失败/跳过/被过滤），这些信息暴露在 Actuator 端点中。

**将 AnnotationProcessor 接入门面**：阶段二的处理器产生的候选列表，经过阶段三的门面处理后，才真正注册到注册器中。

**创建 `lyclaw-test` 模块**：包含 `MockToolRegistry`、`MockModelAdapter`、`@LyClawTest` 注解、`ToolTestHelper` 等测试支持。

**迁移第一个工具到新模型**：选择 CalculatorTool 作为试点，用 `@Tool` 注解声明元数据，用 `ParameterBinder` 做参数解析。验证整个链路（注解处理器 → 门面 → 注册 → 执行）都正常工作。其他三个工具保持不变，证明新旧模式可以共存。

**阶段三的交付物**：
- 注册门面（过滤、排序、生命周期）
- Actuator 端点（扩展注册状态）
- `lyclaw-test` 测试工具包
- 一个用新模式的试点工具

### 6.5 阶段四：高级特性与文档（2 周）

**目标**：完善高级特性，编写完整的框架文档。

**任务**：

**管线相对排序**：实现 `@PipelineStage` 注解的 `after`/`before` 属性的拓扑排序。保持 `getOrder()` 作为 tiebreaker 和向后兼容。

**条件注册**：让 `@Tool` 注解支持"需要配置项 X 才启用"的声明，门面在注册前检查。

**插件打包支持**：验证外部 JAR 包中的 `@Tool` 类能否被框架发现和注册（利用 Spring Boot 的组件扫描或 `AutoConfiguration.imports` 机制）。

**编写框架文档**：
- 《快速开始》：5 分钟写出第一个工具
- 《工具开发指南》：参数声明、元数据、错误处理、测试
- 《适配器开发指南》：如何接入新的 AI 模型提供商
- 《管线扩展指南》：如何插入自定义处理阶段
- 《配置参考》：所有 `lyclaw.*` 配置项的完整文档

**迁移剩余工具**：把 CurrentTimeTool、CommandTool、WebSearchTool 迁移到新注解模型。这一步验证了迁移流程的可行性——逐个迁移，每次迁移后测试通过。

**阶段四的交付物**：
- 管线相对排序功能
- 条件注册功能
- 插件打包验证
- 完整框架文档
- 所有内置工具迁移到新模型

### 6.6 什么不要做——在每个阶段

- **阶段零**：不要删除任何东西——只移动和标记废弃。即使确认某个类没被使用，也只标记废弃不删除，等下一个主版本再清理。
- **阶段一**：不要在 `lyclaw-framework` 中引入 Spring 依赖。保持这个模块的轻量和独立性。如果发现需要 Spring 类型，说明那个类型不应该放在 framework 中。
- **阶段二**：不要强制旧代码迁移到注解。注解处理器必须同时支持两种模式。不要删除 `getName()` 和 `getDefinition()` 方法，它们在无注解的情况下仍然是唯一的元数据来源。
- **阶段三**：不要为了门面的纯粹性而牺牲简单性。如果某个扩展点只需要简单的发现→注册，不需要过滤和排序，就不要为它强行套用门面。门面是工具，不是教条。
- **阶段四**：不要追求文档完美。框架文档应该在后续使用中持续完善。发布一个"够用"的初版比反复打磨但不发布要好。

## 七、迁移策略：保持系统永远可运行

### 7.1 双轨制兼容

整个迁移过程的核心策略是**双轨制**：新旧两种机制同时有效，任何扩展都可以选择使用旧方式或新方式。框架不强制迁移。

在框架内部的实现上，这意味着每个处理流程有两个分支：

- **工具注册**：先检查 `@Tool` 注解（新方式），如果有，从注解读取元数据；如果没有，调用 `getName()` 和 `getDefinition()` 方法（旧方式）。两种方式产出的都是 `ToolDefinition` 对象，注册到同一个注册器。
- **管线排序**：先检查 `@PipelineStage` 注解的 `after`/`before` 属性（新方式），如果有，参与拓扑排序；如果没有，用 `getOrder()` 的绝对数值（旧方式）。两种方式的产出最终合并为一个有序列表。
- **适配器选择**：先检查 `application.yml` 中的 `lyclaw.llm.provider` 配置（新方式），如果有，用配置值查找适配器；如果没有，像现在一样用硬编码的默认值（旧方式——已废弃但还在）。

双轨制运行的周期：至少一个次版本。在这期间，新功能用新方式实现，旧功能的迁移逐步推进但不强制。框架文档中清晰标注新旧方式的对应关系。

### 7.2 迁移的五个步骤

对于每个需要迁移的组件（如一个工具），迁移流程是：

1. **理解现状**：阅读工具的当前实现，理解它的参数、行为、错误处理
2. **编写新实现**：用新注解模型重写，保持业务逻辑完全不变。业务逻辑的代码直接复制——不要在这个步骤重构业务逻辑，否则出了问题不知道是"迁移引入的 bug"还是"重构引入的 bug"
3. **并行测试**：新旧两个实现同时存在（旧的有 `@Component`，新的也有），写一个对比测试——相同的输入 → 相同的输出
4. **切换**：删除旧实现的 `@Component` 注解（但保留类文件），让框架只使用新实现
5. **清理**：下一个次版本中删除旧的类文件

**步骤 3 是关键**：并行测试保证了新实现的行为和旧实现完全一致。如果有差异，要么是迁移出错（需要修复），要么是旧实现有 bug（新实现修复了，需要记录）。

### 7.3 回滚策略

每一批改造都应该有明确的回滚路径。如果新机制出了问题：

- **阶段一改动的回滚**：`lyclaw-framework` 中的新类型和旧包下的 `@Deprecated` 别名同时存在。如果 framework 模块有问题，使用者可以批量将 import 从 `lyjew.com.lyclaw.framework.tool.Tool` 改回 `lyjew.com.lyclaw.tool.Tool`（旧路径仍然有效）。
- **阶段二改动的回滚**：注解处理器如果出问题，可以通过配置项 `lyclaw.annotation.processing.enabled: false` 关闭整个注解处理，框架回退到纯接口模式。
- **阶段三改动的回滚**：门面可以通过配置排除。门面的过滤逻辑如果错误排除了重要工具，配置 `lyclaw.extension.filtering.enabled: false` 关闭过滤，所有候选扩展全量注册（同旧行为）。

这些开关不需要在每个阶段都保留——它们是临时的安全网。一个次版本后，如果新机制被验证稳定，开关就可以移除。

### 7.4 已有代码的改造示例

以 CalculatorTool 为例，展示迁移前后代码结构的变化（仅展示结构，不展示具体代码）。

**迁移前**（当前状态）：
- 类注解：`@Slf4j` + `@Component`
- 实现接口：`implements Tool`
- `getName()`：返回常量字符串 `"calculator"`
- `getDefinition()`：15 行的 `ToolDefinition.builder()` + 嵌套 `Map.of()` 构造
- `execute()`：手写 try-catch + `startTime` 计时 + 调用 `extractExpression()` 手写字符串切割 + 业务逻辑（递归下降解析器）

**迁移后**（理想状态）：
- 类注解：`@Slf4j` + `@Tool(name="calculator", description="执行数学计算", readonly=true)`（`@Tool` 包含 `@Component`，不需要两个都写）
- 实现接口：`implements Tool`（或者实现新的 `AnnotatedTool` 接口）
- **不再需要** `getName()`：框架从 `@Tool` 注解读取
- **不再需要** `getDefinition()`：框架从 `@Tool` + `@Param` 注解自动生成
- **不再需要** `extractExpression()`：框架在调用前自动把 JSON 参数绑定到类型安全的参数对象
- **不再需要** try-catch + 计时：框架自动计时，异常自动转为 `ToolResult.failure`
- **保留的**：业务逻辑（递归下降解析器）——完全不变

工具类从 170 行缩减到约 130 行（仅保留业务逻辑），删除了约 40 行纯样板代码。

## 八、长期愿景

### 8.1 LyClaw 作为 AI Agent 开发平台

完成框架化后，LyClaw 的定位从"一个 AI 对话助手应用"升级为"AI Agent 开发平台"。

对开发者而言，使用 LyClaw 和直接使用 LLM API（如 DeepSeek API、OpenAI API）的区别在于：
- 直接使用 LLM API：你需要自己管理对话历史、工具调用循环、记忆系统、管线编排、安全策略
- 使用 LyClaw：你只需要写工具类（描述能力、实现逻辑），框架提供所有基础设施

这和"Spring 之于 Java EE"的关系类似——Spring 不是替代了 Servlet API，而是在 Servlet API 之上提供了更方便的开发体验和更强大的基础设施。LyClaw 不是替代 LLM API，而是在 LLM API 之上提供了 Agent 的基础设施。

### 8.2 生态系统的可能性

框架最强大的力量不在于框架本身，而在于它的生态系统。Spring 之所以成功，不只是因为 IoC 容器设计得好，更是因为 Spring Security、Spring Data、Spring Cloud 等庞大的生态系统。

LyClaw 的生态可以包括：
- **工具市场**：社区贡献的工具包（如"天气查询工具包"、"数据库查询工具包"、"代码分析工具包"）。用户只需要加 Maven 依赖，工具自动注册。
- **适配器生态**：支持更多 AI 模型提供商（OpenAI、Anthropic、Google Gemini、国产模型等）。
- **管线模板**：不同场景的预配置管线（如"代码审查管线"、"数据分析管线"、"客户支持管线"）。
- **记忆后端**：Redis、PostgreSQL（pgvector）、Milvus、Pinecone 等不同的记忆存储实现。

框架的注解体系和自动配置机制天然支持这种生态——第三方开发者发布一个 JAR，JAR 里包含 `@Tool` 注解的类和 `AutoConfiguration.imports` 文件，使用者在 `pom.xml` 里加一个依赖，工具自动出现在工具的注册表中。

### 8.3 五年后的 LyClaw

五年后，理想中的 LyClaw 应该具备以下特征：

- **工具丰富**：数百个社区贡献的工具，覆盖常见 AI Agent 能力需求
- **模型无关**：支持数十种 AI 模型提供商，切换只需改配置
- **多语言支持**：不仅是 Java 框架，还有 Python SDK、TypeScript SDK（共享相同的能力抽象和注解风格）
- **生产验证**：在多个企业的生产环境中运行，有丰富的运维经验和最佳实践
- **标准化**：LyClaw 的工具描述格式（基于注解的声明式元数据）成为 AI Agent 工具的标准之一

最重要的：**保持简单**。五年后的 LyClaw 不应该变成一个"什么都能做但什么都很难做"的庞然大物。好的框架是"让你只关心你要做的事情，剩下的框架帮你搞定"。

### B. 术语对照表

| 术语 | 含义 |
|------|------|
| SPI (Service Provider Interface) | 框架定义、使用者实现的接口。如 `Tool`、`ModelAdapter`、`PipelineStage` |
| API (Application Programming Interface) | 框架提供、使用者调用的接口。如 `ToolRegistry.register()`、`ModelAdapter.chatStream()` |
| 扩展点 (Extension Point) | 框架中允许插入自定义逻辑的位置。如工具注册、管线阶段、拦截器 |
| 注册门面 (Registry Facade) | 在扩展的"发现"和"注册"之间的处理层，负责过滤、排序、生命周期管理 |
| 注解处理器 (Annotation Processor) | 在 Spring 容器中读取自定义注解并执行注册逻辑的 BeanPostProcessor |
| 拓扑排序 (Topological Sort) | 根据"在 X 之后"的相对声明，计算出全局执行顺序的算法 |
| 双轨制 (Dual-track) | 新旧两种机制同时有效，旧的逐步迁移，新的从一开始就可用 |
| 约定优于配置 (Convention over Configuration) | 框架提供合理的默认行为，只在需要定制时才需要配置 |
| 渐进式迁移 (Incremental Migration) | 每一步迁移后系统都完整可运行，不搞"大爆炸式"切换 |
| 好莱坞原则 (Hollywood Principle) | "Don't call us, we'll call you."——框架调用你的代码，不是你的代码调用框架 |

```
- 负面影响：[这个决策带来的代价或限制]

## 相关

```
